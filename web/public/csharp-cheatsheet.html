Reference vs Value Types (class vs struct)

Big shift: class = reference type (heap; variable holds a reference; assign/pass copies the reference). struct = value type (copied by value on assign/pass/return). ! Java has no user-defined value types — every new object is a reference.

JavaC#
All objects ref typesclass = ref type (heap)
Primitives only (int, long…)struct = value type, incl. your own
boxed Integer, autoboxint,double,bool ARE structs
—DateTime,Guid,decimal,TimeSpan structs
null for any objectstruct can't be null; int?/T? for nullable

Copy semantics

struct Point { public int X, Y; }
var a = new Point { X=1 };
var b = a;        // whole struct copied
b.X = 9;          // a.X still 1

class Box { public int X; }
var p = new Box { X=1 };
var q = p; q.X = 9;  // p.X == 9 (same ref)
  • Passing a struct to a method copies it; mutations don't escape (unless ref).
  • default(T): struct = all-zero fields (never null); class = null.

When to use struct

  • Small (~≤16 bytes), immutable, value-like: a Point, Money, Color.
  • Else use class (identity, large, mutable, polymorphism).
  • Prefer readonly struct — fields immutable, avoids hidden defensive copies. ! mutable structs are a classic trap.

Records

record class Person(string Name);  // ref, value-equality
record struct Coord(int X, int Y); // value type + value-equality
readonly record struct Money(decimal Amt, string Ccy);
  • record (C#9) = value-based Equals/GetHashCode + with copies; record class still a ref type.

Boxing

object o = 42;     // boxes: heap alloc + copy
int n = (int)o;    // unbox
  • Storing a struct in object or a non-generic interface boxes it. ! Avoid in hot paths/loops — use generics (List<int> doesn't box).

Nullable Reference Types & Null Handling

NRT (C#8+) — opt-in

<Nullable>enable</Nullable> in .csproj. Compiler tracks nullability of reference types and warns on possible null deref. Closest C# gets to "explicit null" — but it's static analysis, not a wrapper type.

JavaC#
String s (any may be null)string s = non-null intent; warns if assigned null
@Nullable String sstring? s = may be null
NPE at runtimecompiler ! warning at build (no enforcement)
! NRT warnings don't fail the build by default and erase at runtime — a non-null string can still be null from un-annotated/legacy code.

Null operators

—x! null-forgiving: suppress warning !

! ! only silences the compiler — it does NOT null-check. Wrong use = surprise NRE. Use sparingly.

Nullable VALUE types — int?

int? = Nullable<int> (a struct, pre-NRT, always existed). Applies to int bool DateTime structs etc.

int? age = null;
if (age.HasValue) Use(age.Value);   // .Value throws if null
int a = age.GetValueOrDefault();    // 0 if null
int b = age ?? -1;                  // also works

No idiomatic Optional

! C# has no Optional<T>. Don't port Java Optional<T> fields/returns — use T? + NRT instead. (Nullable<T> is values only; not a monad — no .map.)

LINQ vs Streams

Both lazy pipelines over sequences. LINQ on IEnumerable<T> (no .stream() needed) via using System.Linq;

.map(f).Select(f)
.flatMap(f).SelectMany(f)
.collect(toList()).ToList()

Two syntaxes (same result)

// method chain
xs.Where(x => x > 0).Select(x => x * 2);
// query syntax (SQL-like)
from x in xs where x > 0 select x * 2;

Deferred execution (key!)

  • Query is lazy — built, not run. Executes only on enumeration: foreach, .ToList(), .Count(), .First().
  • Re-enumerating re-runs the whole pipeline against the current source (no caching).

! Multiple enumeration of an IEnumerable re-executes the source (DB/IO → N+1, or captured-variable surprises). Materialize once with .ToList() if reused.

var adults = people
    .Where(p => p.Age >= 18)
    .Select(p => p.Name)
    .ToList();

Generics (vs Java — reified!)

Big difference: reified vs erased

  • Java erases generics; C# keeps them at runtime (reified). !
  • typeof(T) works; Java can't do T.class.
  • new T() allowed with new() constraint.
  • T[] arrays work directly; no unchecked-cast hacks.
  • is/as work with generic types.
  • List<int> != List<string> at runtime — distinct types.

No primitive specialization

  • List<int> stores ints inline — no boxing, no Integer wrapper.
  • No need for IntStream/int[] escape hatches.

Generic methods & default(T)

  => a.CompareTo(b) >= 0 ? a : b;

  • default(T) = type's zero value (0 / null / empty struct).
  • Type args usually inferred: Max(3, 9).

Events

public event EventHandler Clicked;   // EventHandler(object?,EventArgs)

Clicked += OnClicked;   // subscribe
Clicked -= OnClicked;   // unsubscribe
Clicked?.Invoke(this, EventArgs.Empty); // raise (null-safe)
  • event = multicast delegate restricted to +=/-= outside the class (no direct invoke/assign). Java: listener-list boilerplate.
  • Standard pattern: EventHandler or EventHandler<TArgs>; handler sig (object? sender, TArgs e).
  • ! += never reassigns — it adds a handler. Forgetting -= leaks the subscriber.

async / await (vs CompletableFuture/threads)

JavaC#
CompletableFuture<T>Task<T>
CompletableFuture<Void>Task (no result)

Shape

async Task<int> GetAsync(string url) {
    var resp = await httpClient.GetAsync(url);   // Task<T> -> T
    var body = await resp.Content.ReadAsStringAsync();
    return body.Length;
}
  • await unwraps Task<T> → T, suspends method, frees the thread until done.
  • Async all the way: callers await too — don't block at any layer.

Traps !

  • NEVER .Result / .Wait() / .GetAwaiter().GetResult() on a Task — blocks a thread & can deadlock (context capture).
  • async void ONLY for event handlers. Else async Task — exceptions in async void are unobservable & crash the process.

Cancellation & library code

async Task DoAsync(CancellationToken ct) {
    await Task.Delay(1000, ct);   // cooperative cancel
    ct.ThrowIfCancellationRequested();
}
var all = await Task.WhenAll(t1, t2);  // ~ allOf
  • Thread CancellationToken through calls (cooperative, like checking a flag).
  • In libraries: await x.ConfigureAwait(false) — don't capture/resume on caller's context (perf, avoids deadlock).

async / await flow

flowchart LR A["async Task<T> M()"] --> B["await ioCall()"] B -->|"not done"| Y["thread RETURNS to caller (no block)"] Y --> C["I/O completes → resume after await"] C --> D["return T → Task<T> completes"]

Never .Result/.Wait() — that blocks (and can deadlock). 'async all the way'. ~ Java CompletableFuture but language-level.

Exceptions (NO checked exceptions)

Biggest surprise

  • C# has no checked exceptions — no throws clause, compiler never forces a catch. ! Any method can throw anything; freedom + risk — read docs/source to know what throws.
  • No equivalent of Java's checked/unchecked split — all exceptions are like Java's RuntimeException.

Mechanics — mostly identical

JavaC#
try/catch/finallytry/catch/finally (same)
throw new X()throw new X()
throws IOException— (no signature decl)
e.getMessage()e.Message
e.printStackTrace()e.StackTrace / e.ToString()
e.getCause()e.InnerException

Rethrow — STACK TRACE TRAP !

catch (Exception ex)
{
    Log(ex);
    throw;        // ✓ rethrow, PRESERVES stack
    // throw ex;  // ✗ RESETS stack to here
}
  • throw; = bare rethrow (no Java equivalent — Java's throw e; keeps the stack; C#'s throw ex; loses it).

Exception filters (no Java equiv)

catch (HttpRequestException e)
      when (e.StatusCode == 404)
{ ... }
  • Filter runs before stack unwinds; falls through to next catch if false.

No multi-catch !

  • No catch (A | B e) syntax. Instead:
  • Catch a common base + switch on type, or use when filters.
catch (Exception e) when (e is IOException or TimeoutException)
{ ... }

Implementing

class Cache : IDisposable
{
    private readonly Stream _s;
    public void Dispose() => _s.Dispose();
}
  • Managed-only? Just dispose your fields. No finalizer needed.
  • Owns unmanaged handle? Use full dispose pattern: Dispose(bool) + GC.SuppressFinalize(this) + finalizer. Rare — prefer SafeHandle.

Java-dev traps

  • ! IDisposable created but not in using = leak. C# has no try-with-resources enforcement — analyzer warns (CA2000), not the compiler.
  • ! new HttpClient() per request = socket exhaustion. Reuse one instance or use IHttpClientFactory.
  • ! Multiple resources: stack declarations using var a=..; using var b=..; — disposed reverse order. No need to nest.

Reviewing C# Code — What to Flag

async

  • ☐ async void — only for event handlers; else async Task (else exceptions can't be caught) !
  • ☐ Blocking on async: .Result / .Wait() / .GetAwaiter().GetResult() — deadlock + thread-block !
  • ☐ Fire-and-forget Task not awaited (swallows exceptions)
  • ☐ Library code missing .ConfigureAwait(false)
  • ☐ CancellationToken not threaded through async calls
  • ☐ throw ex; resets stack trace — use bare throw; !

LINQ / IEnumerable

  • ☐ Multiple enumeration of a deferred query (re-runs / N+1 to DB) !
  • ☐ Returning IEnumerable<T> then enumerating repeatedly — materialize once
  • ☐ Missing/premature .ToList()
  • ☐ LINQ allocations (closures, delegates) in hot paths

Disposal

  • ☐ IDisposable not in using → leak
  • ☐ new HttpClient() per request → socket exhaustion; reuse / IHttpClientFactory !
  • ☐ Streams / DB connections not disposed

Nullability / Equality

  • ☐ Overuse of null-forgiving ! / suppressed NRT warnings
  • ☐ == vs .Equals() on reference types (ref vs value compare)
  • ☐ DateTime.Now vs .UtcNow for instants !
  • ☐ DateTime vs DateTimeOffset for points in time

Idioms

  • ☐ Public mutable fields instead of { get; set; } properties
  • ☐ Mutable struct (copy-by-value surprises) !
  • ☐ catch {} / catch (Exception) too broad
  • ☐ Mutable static state — thread-safety
  • ☐ String concat in loops → use StringBuilder
  • ☐ Non-PascalCase public members; magic (MyEnum)intValue casts
