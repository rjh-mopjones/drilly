  • Cache line = 64 B everywhere — the unit of transfer/coherence/false-sharing.
  • The cliff: L3 (~40 cyc) → DRAM (~250 cyc). One DRAM miss ≈ ~200–1000 retired-instruction slots lost !
  • Reduce misses before reducing instructions: one avoided miss ≈ 100 saved ALU ops.

The Memory Hierarchy

Each level ~10× bigger, ~10× cheaper/byte, ~10× slower than the one above. No single technology is fast + dense + cheap, so you tier it.

LevelSize~Lat
Registers16–32 × 64b<1 cyc
L1i / L1d32–64 KB each/core~4 cyc
L2 (private)256 KB–2 MB/core~12 cyc
L3 / LLC (shared)8–64 MB~40 cyc
DRAMGBs–TBs~80 ns
SSD (flash)100s GB–TBs~10–100 µs
Disk / network∞ms+
  • SRAM (6T/bit, no refresh) → registers/caches; DRAM (1T1C, refreshed) → main memory. SRAM ~10× faster but far less dense/pricier.
  • Locality is why it works: temporal (reuse same addr — loop vars) + spatial (neighbours — array walk, whole 64 B line fetched).
  • AMAT = hit-time + miss-rate × miss-penalty — the summary metric; locality collapses it toward L1 latency at DRAM capacity.
  • Why not one giant fast cache? Bigger = slower (longer wires/decode), SRAM is low-density + power-hungry, area-bound !

ISA & the Abstraction Stack

  • ISA = HW/SW contract: registers, instructions, addressing modes, memory model, exceptions. The stable interface compilers target.
  • Architecture (what the programmer sees) vs microarchitecture (how a chip implements it: pipeline depth, caches, OoO). Same ISA, many µarches — Zen vs Golden Cove both run x86-64.
ISAStyle · notes
x86-64CISC, var-len 1–15 B, 16 GPR, decodes to µops. Density + legacy.
AArch64RISC-ish, fixed 32-bit, 31 GPR. Easy parallel decode, mobile→server.
RISC-VOpen, fixed 32-bit (+C ext), modular. Clean, extensible.
  • RISC vs CISC blurred: x86 cracks CISC into RISC-like µops; ARM added rich ops. Real distinction is decode complexity, not "few vs many" instructions.
  • ISA ≠ ABI: ISA lets HW run bytes; ABI (calling convention, struct layout, syscall nums) lets separately-compiled binaries interoperate !
  • von Neumann (unified mem) vs Harvard (split I/D): real CPUs are "modified Harvard" — split L1I/L1D, unified beyond.

Number Representation

  • Two's complement: one zero, add/sub identical to unsigned HW, top bit = sign. Range [-2^(n-1), 2^(n-1)-1]. Negate = invert + 1. Won over sign-mag/1's-comp (no −0, no end-around carry).
  • Signed overflow = UB in C/C++ ! HW sets OF flag; language may assume it never happens. Unsigned wraps (mod 2^n) — defined.
  • Sign-extend signed widening, zero-extend unsigned. Mixing signed/unsigned compares is a classic bug !
  • Endianness: x86/ARM little-endian; network byte order big-endian. Bites on raw byte serialization / casts.

IEEE 754 single (32b)

[ sign 1 | exponent 8 | mantissa 23 ]
value = (-1)^s × 1.m × 2^(e-127)   // bias 127
  • double = 1/11/52, bias 1023. exp=all-1s: mantissa 0 → ±Inf; ≠0 → NaN. exp=0 → subnormal/±0.
  • NaN != NaN (always false) ! 0.1 not exact in binary → 0.1+0.2 != 0.3 ! Never == floats — compare |a-b| < ε (abs+rel).
  • Catastrophic cancellation: subtracting near-equal values exposes pre-existing rounding error (Sterbenz: the subtract itself is exact). Reformulate — e.g. 1−cos θ = 2 sin²(θ/2).

Rounding modes

  • RNE (round-to-nearest, ties-to-even) — default; unbiased, avoids drift over many ops. Every basic op (+ − × ÷ √) is correctly rounded (as if infinite-precision then rounded once).
  • Toward-zero (trunc, float→int in C), toward +∞ (ceil), toward −∞ (floor). Directed rounding → interval arithmetic / provable bounds.

Fixed-point (Qm.n)

  • Integer with an implied binary scale. Q16.16: store x × 2^16. Add/sub = plain int; multiply needs a shift ((a*b)>>16, promote to int64 to avoid overflow) !
  • Use for determinism/exactness: money (cents/micro-units, DECIMAL/BigDecimal), FPU-less embedded/DSP, lockstep sim (bit-identical across machines). Cost: limited range, manual scale bookkeeping.

Pipeline & the Perf Equation

Classic 5-stage (RISC)

IFfetch instr from I-cache, PC+4
IDdecode, read regs, sign-extend
EXALU op / addr calc / branch resolve
MEMdata-cache load/store
WBwrite result to register file
  • Pipelining improves throughput (1 instr/cycle ideal), not single-instruction latency. Clock set by the slowest stage, so shorter stages → higher freq.
  • Deeper (superpipeline) = higher clock but bigger mispredict/hazard penalty and diminishing returns (latch overhead, clock skew).
  • Register file: write in first half of WB, read in second half of ID — same-cycle so a WB feeds a dependent ID.

CPU performance equation

Time = Instructions × CPI × Clock_period
     = I × CPI / frequency

Three knobs, and they fight: fewer instrs (ISA/compiler), lower CPI (µarch), faster clock (process/pipeline). Never quote one in isolation !

Hazards & Forwarding

ClassCause · fix
Structuraltwo stages want one resource → duplicate (split I/D cache), pipeline the unit
Datainstr needs a not-yet-written result → forwarding + stall
Controlbranch outcome unknown → predict + speculate

Data-hazard taxonomy

  • RAW (true dependency) — the only real data hazard; forwarding hides most.
  • WAR / WAW — false/name deps; vanish with register renaming in OoO.
  • Forwarding/bypass: route EX/MEM result straight to a later EX input, skipping WB. Kills most RAW stalls.
  • Load-use hazard: data isn't ready until MEM, so a dependent next instr must stall 1 cycle — forwarding can't go back in time ! Compiler schedules an independent instr into the slot.
  • Branch delay slot: old MIPS trick, dropped — exposes µarch, useless once pipelines deepened.

Branch Prediction & Speculation

  • A mispredict flushes the pipeline: ~15–20 cycle penalty on a deep OoO core ! At 95% accuracy in a hot loop that's a big chunk of runtime.
  • 1-bit predictor mispredicts twice per loop (entry+exit). 2-bit saturating counter (Strong/Weak Taken/NotTaken) needs two wrong in a row to flip — tolerates the loop-exit blip.
StructureAnswers
BHTtaken / not-taken (direction)
BTBtarget address (where to)
RASreturn-address stack for ret
  • Global history (GHR) captures correlation between branches; tournament/TAGE pick the best predictor per branch — modern accuracy >95–99%.
  • Indirect branches (vtables, switch) are hard — need target prediction, not just direction.
  • Speculation: predicted-path instrs execute but retire only if correct; on mispredict they're squashed. Leaked microarchitectural state → Spectre !

Superscalar & Out-of-Order

  • ILP = independent instrs runnable at once; limited by true deps, branches, memory. Superscalar = issue/retire several instrs/cycle (width 4–6 on big cores).
  • OoO executes ready instrs regardless of program order to hide latency (esp. cache misses) — but retires in order for precise exceptions.

Tomasulo / modern OoO parts

Renamearch→physical regs; kills WAR/WAW
RS / schedulerhold instrs till operands ready, wake on broadcast
ROBtrack in-flight instrs, retire in order
LSQload/store queue, memory disambiguation
  • Frontend (fetch/decode/rename, in-order) → backend (OoO issue/execute) → in-order retire.
  • Real sustained IPC is well below issue width (~1–3) — deps, misses, mispredicts. Wider ≠ proportionally faster !
  • Mispredict: squash all ROB entries after the branch, restore rename map, refetch.

The 3 C's

  • Compulsory (cold) — first touch; fix w/ prefetch, bigger lines.
  • Capacity — working set > cache; fix w/ blocking/tiling.
  • Conflict — too many hot addrs map to one set; fix w/ associativity. Power-of-2 stride maps everything to few sets → thrash !
  • Write-back (dirty bit, write on evict) beats write-through for bandwidth; write-allocate fetches line on write miss. True LRU rare → pseudo-LRU.

Inclusion policy (L1 vs LLC)

PolicyNote
InclusiveL1 lines ⊆ LLC. LLC = snoop filter (simple coherence) but wastes capacity; evict forces back-invalidate. (older Intel client)
Exclusiveline in exactly one level → max capacity (Σ levels). Complex fills; probe every level. (AMD victim L3)
NINEno guarantee; needs a separate snoop filter. (Intel server mesh, Skylake-SP+)
  • VIPT L1 works only if index bits stay within the page offset: 4 KB page (12b) + 64 B line (6b) → 6 index bits → 8-way × 64 sets = exactly 32 KB. That's why L1 stuck near 32 KB; bigger → synonym/aliasing (fix: assoc, page colouring, or 16 KB pages like Apple M).

Coherence & False Sharing

MESI states (per line, per cache)

Modifieddirty, exclusive — only valid copy
Exclusiveclean, only copy — can write silently
Sharedclean, other caches may hold it
Invalidnot present / stale
  • A write to a Shared line must invalidate all other copies (RFO — read-for-ownership) before proceeding.
  • Snoop (broadcast on bus) is simple but doesn't scale; directory-based tracks sharers per line for many-core/NUMA.
  • Invalidation beat update protocols (avoids useless update traffic).

False sharing !

  • Two threads write different variables in the same 64 B line → line ping-pongs between cores' caches (RFO each write). No logical sharing, huge slowdown.
  • Symptom: parallel code slower than serial; perf shows high coherence/HITM.
  • Fix: pad/align hot per-thread data to 64 B — alignas(64), cache-line padding, or per-thread local accumulation merged at the end.
  • MOESI adds Owned (dirty-shared): serve dirty data to others without writing back to memory first. MESIF (Intel) adds Forward: one sharer designated responder so only it replies to a read — cuts redundant snoop responses.
  • Cache-to-cache transfer of a Modified line (HITM) costs the inter-core / cross-socket latency (~40–100+ ns) — an atomic counter or mutex line bouncing between cores is a hardware scalability wall, not a code bug !

Memory Consistency & Fences

  • Coherence = one address, all cores agree on its value order. Consistency = ordering across different addresses. Different problems !
ModelReorders
SC (sequential)none — intuitive, expensive
x86-TSOonly store→load (store buffer); loads not reordered w/ loads
ARM/POWER (weak)almost anything — need explicit barriers
  • Store buffer lets a core's store retire before it's globally visible → later loads can pass earlier stores. Root of TSO's one relaxation.
  • x86 fences: mfence (full), sfence, lfence. lock-prefixed RMW is a full barrier.
  • C++/language model: acquire (loads after stay after), release (stores before stay before), seq_cst default. Pair release-store with acquire-load to publish data safely.
  • Compiler reorders too — a lock/atomic/fence, not volatile, gives ordering !

Store-buffer litmus (SB)

init x=y=0
T0: x=1; r0=y    T1: y=1; r1=x
// SC: r0=r1=0 impossible. TSO: possible!
  • Both stores sit in each core's store buffer while both loads read the old value → r0=r1=0. Fix: mfence (or seq_cst store) between store and load to drain the buffer. A full fence costs ~tens of cycles — it stalls the pipeline until the store buffer flushes !

Virtual Memory & TLB

  • Page table maps virtual→physical pages (typ. 4 KB). x86-64 uses a 4-level radix tree (PML4→PDPT→PD→PT); a miss = 4 dependent memory loads (the page walk) !
  • TLB caches recent translations (small, fully/highly-assoc). Hit → translate in ~1 cyc; miss → HW page walker.

TLB reach

reach = entries × page_size
64 entries × 4 KB = 256 KB
64 entries × 2 MB = 128 MB   // huge pages
  • Working set > TLB reach → TLB thrash; huge/large pages (2 MB/1 GB) multiply reach and cut walk depth.
  • ASID/PCID tags entries by address space → avoid full TLB flush on context switch.
  • L1 is usually VIPT (virtually-indexed, physically-tagged): index the set from the untranslated offset bits while the TLB translates the tag — overlap for speed.
  • Page fault (not present) traps to OS; distinct from a TLB miss (HW-handled on x86/ARM).

DRAM & Main Memory

  • Cell = 1T1C (1 transistor + 1 capacitor) — dense but leaky → refresh every ~64 ms (~32 ms hot). "Dynamic." SRAM (6T) needs no refresh, ~10× faster/bigger per bit → caches.
  • Hierarchy: channel → DIMM → rank → bank → row × column. Bank = independent grid w/ its own row buffer = unit of parallelism.

Row buffer = the whole game

  • ACTIVATE a row → sense amps (row buffer). Row hit: read/write open row, cheap. Row conflict: PRECHARGE old + ACTIVATE new, expensive !
  • Timings: tRCD (ACT→CAS), tCAS/CL (CAS→data), tRP (precharge). Row-miss ≈ tRP+tRCD+CL.
  • Latency ~50–90 ns for years — barely improves. DDR5 / more channels raise bandwidth (tens–100s GB/s), not single-access latency !
  • DDR = double data rate (both clock edges) + prefetch, not a faster array.
  • Little's Law: outstanding requests to saturate BW = BW × latency. Can't keep that many in flight → latency-bound.

Memory controller (on-die)

  • Decodes phys addr → (channel, rank, bank, row, col) with interleaving that spreads consecutive lines across channels/banks. Obeys tRCD tRP tRAS tFAW (≤4 ACTs/window), read/write turnaround.
  • FR-FCFS scheduling: serve row-buffer hits first (ready, cheap) over older row-conflicting requests → max throughput, needs anti-starvation/QoS. Batches writes (drain in bursts, avoid bus turnaround) !

Bank-level parallelism (BLP)

  • One bank is ~serial (mid-ACT/PRE blocks it); a rank has 16–32 independent banks — ACT bank 3 while bank 1 streams while bank 5 precharges. This is how DRAM reaches rated BW despite slow cycle time.
  • Only materialises if requests hit different banks/channels — a stride aliasing the bank-map bits hammers one bank → sudden throughput cliff !

ECC

  • Server SECDED: 8 extra bits / 64b word (72-bit DIMM) — corrects 1-bit flip, detects 2-bit (machine-check). ~12.5% more chips + cost; mandatory at fleet scale (soft errors from cosmic rays).
  • DDR5 on-die ECC ≠ end-to-end link ECC — it just props up yield at tiny cells; the data path is still unprotected without a real ECC stick ! Chipkill/SDDC survive a whole chip failing.

SIMD & Data Parallelism

  • One instruction, many lanes. Same op across a vector register in parallel — throughput multiplier for regular data.
ISAWidth · f32 lanes
SSE128-bit · 4
AVX/AVX2256-bit · 8
AVX-512512-bit · 16 (+ mask regs)
ARM NEON128-bit · 4 (SVE = scalable)
  • Auto-vectorization: compiler does it if the loop is countable, no aliasing, unit stride, no cross-iter deps. Check with -fopt-info-vec / disassembly !
  • Otherwise intrinsics (_mm256_add_ps) or libraries. SoA beats AoS for vectorization (contiguous lanes).
  • Alignment matters: unaligned loads slower / faulting on some ops; align to vector width. Reductions need horizontal ops (extra cost).
  • AVX-512 can cause frequency throttling on some parts — measure before assuming a win !

Multicore, SMP & NUMA

  • SMT/Hyper-Threading: 2 logical threads share one core's execution resources — hides latency, ~1.2–1.3× not 2×. Contends for L1/L2 and ports.
  • SMP: symmetric cores, shared coherent LLC + memory, uniform latency (small systems).

NUMA

  • Each socket owns local DRAM; remote memory reached over interconnect (UPI/Infinity Fabric). Remote access ~1.5–2× local latency + lower BW !
  • First-touch: a page is placed in the node of the thread that first writes it — init data in the thread that will use it, not a single setup thread !
  • Pin threads (numactl --cpunodebind --membind, affinity) so hot data stays local. Cross-node coherence traffic is expensive.
  • LLC often shared per socket; false sharing across sockets is the worst case.

GPUs & Accelerators

  • SIMT: threads grouped into warps/wavefronts (32/64) run in lockstep. Massive thread count hides memory latency instead of caching it — swap warps on a stall.
  • Throughput, not latency: thousands of ALUs, high BW (HBM), weak single-thread. Right for data-parallel, regular work.

Footguns

  • Warp divergence: if that splits a warp serializes both paths — keep branches uniform within a warp !
  • Uncoalesced access: threads in a warp should touch contiguous addresses so one memory transaction serves all. Strided/random = many transactions, tanks BW !
  • Occupancy = enough resident warps to hide latency; limited by registers/shared memory.
  • Accelerators: TPU / systolic arrays for matmul (MACs stream data), NPUs, FPGAs. Trade generality for perf/watt on one domain (matrix, ML, crypto).

Storage, I/O, DMA & Interrupts

  • MMIO: device registers mapped into physical address space — CPU reads/writes them like memory (uncached).
  • DMA: device transfers to/from RAM without the CPU copying byte-by-byte; CPU sets up descriptors, device signals completion. Frees the core for real work.
  • PCIe: serial, point-to-point lanes (x1..x16); NVMe SSDs and GPUs hang off it.

Interrupts vs polling

ModeWhen
Interruptlow rate / latency — sleep till event; context-switch cost
Pollinghigh rate — busy-check; burns CPU but no IRQ overhead
  • MSI/MSI-X: message-signaled interrupts (a memory write) replace legacy INTx lines — steer to a specific core, more vectors.
  • NVMe: many deep parallel submission/completion queues in RAM — exploits SSD parallelism, minimal per-IO CPU. NIC drivers poll (DPDK/NAPI) under load.
  • Cache coherence for DMA: modern IOMMU/DMA is coherent, but on some systems drivers must flush/invalidate !

PCIe (point-to-point serial, tree of switches)

  • Gen4 x4 NVMe ≈ 8 GB/s (why consumer SSDs top ~7). A read is a split transaction (~100s ns RTT) → you write doorbells + let the device DMA, never CPU-read device mem in a loop !
  • Coalescing (ethtool -C rx-usecs/rx-frames): 1 IRQ per N completions or T µs — throughput↑ latency↑. Trading box sets 0 or bypasses (DPDK/busy-poll).

Performance Analysis

  • Golden equation: Time = I × CPI × clock_period. To go faster, cut the dominant term — measure which first.

Amdahl vs Gustafson

  • Amdahl (fixed problem): speedup = 1 / (s + p/N); the serial fraction s caps you — 5% serial ⇒ ≤20× ever !
  • Gustafson (scale problem with N): near-linear speedup — grow the workload, serial part stays fixed.

Roofline

  • Plot GFLOP/s vs arithmetic intensity (FLOP/byte). Left of the ridge = memory-bound (raise intensity / reuse); right = compute-bound (vectorize, more FLOPs).
  • Perf counters (PMU): IPC, cache-miss rate, branch-mispredict, stalled cycles. perf stat, perf record/report, top-down analysis (frontend/backend/retiring/bad-spec bound).
  • Profile before optimizing — intuition about hotspots is usually wrong !

Power, Thermals & Scaling

  • Dynamic power: P = α·C·V²·f — voltage dominates (squared). Static power = leakage (grows as transistors shrink).
  • Dennard scaling (power/area constant as transistors shrink) ended ~2005 — couldn't keep dropping V. → the power wall.

The chain of consequences

  • Can't raise clock without melting → clocks stalled ~3–5 GHz.
  • Moore's Law still gave transistors → spend them on more cores (multicore era), not faster ones.
  • Dark silicon: can't power all transistors at once → specialized accelerators, aggressive power gating.
  • DVFS: dynamically scale V/f to workload (turbo up when thermal headroom, throttle when hot). Race-to-idle vs steady-state tradeoffs.
  • TDP is a sustained thermal budget (cooler sizing), not peak. Boost exploits thermal headroom: short-term PL2 > sustained PL1≈TDP for a window (tau), then settle. Throttle = safety valve at ~90–100 °C Tj,max !

Two cores > one fast core (same power)

  • Push +40% freq: V↑ ~1.2× → 1.2²×1.4 ≈ 2.0× power for 1.4× work — efficiency backwards. Two cores @0.8× freq, ~0.85× V → ~0.58× power each, ~1.16× total, 1.6× throughput. That gap is the whole multicore case (if it parallelizes — Amdahl).

Heterogeneous & chiplets

  • big.LITTLE / P+E: mix perf + efficiency cores (Apple M, Intel Alder Lake+, Arm DynamIQ). Background threads on little cores at a fraction of power; OS scheduler places them.
  • Fixed-function accel: GPU, NPU, ISP, video codec, crypto — each 10–100× more efficient/watt than a general core. Where dark-silicon transistors earn their keep.
  • Chiplets (AMD CCD+IO die, Intel tiles, Apple UltraFusion): small dies co-packaged → better yield (defects scrap one small die not a huge one), mix process nodes (compute on newest, IO on mature), modular core scaling. Cost: die-to-die links burn energy/latency vs on-die wires.

Interview Playbooks — Worked Estimates

Answer arc, every time: (1) classify compute- vs memory-bound + access pattern → (2) locate stall → (3) estimate (events × latency table) → (4) fix with a reason. Assume memory until proven otherwise.

Sum 1 GB int32 array

  • Sequential, prefetchable → bandwidth-bound (adds hide under loads). 1 GB ÷ ~15 GB/s single-thread ≈ ~65 ms. Unhidden it'd be 16M lines × 100 ns = 1.6 s — the 20–25× gap is prefetch + MLP. Claim of 5 ms ⇒ ~200 GB/s (HBM/Apple only).

Traverse 1M scattered linked-list nodes

  • node=node->next is a dependent load → OoO has nothing to overlap → serialize on latency. ~100 ns/hop × 1M ≈ ~100 ms. Same count as an array sum (~1 ms) → ~100× slower. The case for vector over list, SoA, arena alloc.

Loop 10× slower than expected

  • Classic: column-major walk of a row-major matrix — stride-N → miss on nearly every load + TLB thrash + prefetch defeated. Fix = loop interchange. Same big-O, 10× from layout !

Counter won't scale past 1–2 threads

  • A: one shared atomic — line ping-pongs Modified between cores, serialized → often below single-thread. Fix: per-thread shards.
  • B: false sharing — separate counters, same 64 B line. Fix: alignas(64). Tell apart: padding fixes B, not A. perf HITM.

Adding threads made it slower

  • Name the wall with a number: BW saturation (2 threads already hit ~30 GB/s), coherence/false sharing, NUMA remote, or oversubscription — not just Amdahl.

★ Mechanical-Sympathy Checklist

Data layout

  • ☐ SoA over AoS when you scan one field — 8× fewer lines touched, vectorizable.
  • ☐ Hot fields packed together; cold/rare fields split out so a line carries only useful bytes.
  • ☐ Structs sized/padded to fit lines; avoid straddling a 64 B boundary on hot data.

Access pattern

  • ☐ Sequential, unit-stride access (prefetcher-friendly) over pointer-chasing / random.
  • ☐ Working set fits the target cache level (block/tile large loops).
  • ☐ Avoid power-of-2 strides that alias into one set (conflict thrash) !

Concurrency

  • ☐ No false sharing: per-thread hot data padded/aligned to 64 B; NUMA first-touch + affinity.
  • ☐ Right memory ordering (acquire/release), not volatile; minimize contended atomics.

Control flow

  • ☐ Predictable branches in hot loops; branchless / sort data so predictor learns.
  • ☐ Confirm the compiler vectorized the loop (check disasm), didn't spill.

Before optimizing

  • ☐ Classified the loop: compute- / memory- / latency-bound? (roofline + perf) — fixes differ.
  • ☐ Measured with perf counters, not guessed. One avoided DRAM miss > 100 saved ALU ops.
