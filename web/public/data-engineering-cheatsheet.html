ETL vs ELT

  • ETL: transform before load (legacy, fixed schema, external compute).
  • ELT: load raw, transform in the warehouse (SQL/dbt). Won because cloud-warehouse compute is cheap + elastic, raw data is kept for replay, and transforms are versioned SQL. Default to ELT.

Pipeline stages

ingest → store (raw/bronze) → transform (silver/gold) → serve (BI/ML/reverse-ETL). Reverse ETL = push warehouse data back into SaaS tools (CRM, ads).

Batch vs Streaming — choosing

BatchStreaming
Latencyminutes–hoursms–seconds
Modelbounded, reprocess whole windowunbounded, per-event/micro-batch
Cost/opscheap, simple, replayableexpensive, always-on, harder
  • Default to batch. Reach for streaming only when the business needs sub-minute freshness: fraud, alerting, real-time inventory, live dashboards.
  • ! "We want it real-time" usually means "faster than daily." Micro-batch every 5–15 min often beats true streaming at a fraction of the complexity.
  • Lambda (batch + speed layers, reconcile) vs Kappa (one stream path, replay from log). Kappa is simpler; Lambda tolerates a mature batch estate.

Dimensional Modeling

  • Fact = measurements at a grain (numeric, additive), FKs to dims. Dimension = descriptive context (who/what/where/when), wide + textual.
  • Grain = what one fact row means (e.g. "one order line"). Declare grain first — every other decision follows ! Mixed grain = wrong sums.
StarSnowflake
Dimsdenormalized, flatnormalized into sub-dims
Queryfewer joins, fast, simplemore joins, less redundancy

Prefer star. Storage is cheap; join simplicity and scan speed matter more. Snowflake only for huge, volatile dims.

Fact types

  • Transaction — one row per event (most common).
  • Periodic snapshot — state at intervals (daily balance).
  • Accumulating snapshot — one row per process, updated as it moves (order → ship → deliver).
  • Additive / semi-additive / non-additive: sum over all dims / some (balances not over time) / none (ratios) !

SCD2 columns

surrogate_key  (PK, meaningless int)
business_key   (natural id)
valid_from, valid_to  (or NULL / 9999-12-31)
is_current     (bool)
  • Surrogate key = warehouse-generated int PK; decouples from source PKs, enables SCD2 (many rows / one business key), speeds joins, survives source re-keying ! Never join facts on the natural key.
  • MERGE on business key: if changed → close current (set valid_to, is_current=false) + insert new version. Needs upsert → table-format or warehouse.
  • Late-arriving dim: fact refers to a dim row not yet loaded → insert a placeholder ("inferred member"), backfill attributes later.

Batch Processing & Idempotency

Idempotent = running a task N times = running it once. The single most important batch property — retries, backfills, manual re-runs all re-execute !

Anti-patternIdempotent fix
INSERT INTO (blind append)delete-partition + insert or MERGE
auto-increment key on reloaddeterministic / hash keys
"process today" (wall clock)process the data interval
  • Incremental load via a high-water mark: WHERE updated_at > last_max. Store the mark; advance only on success. Cheap but misses hard deletes (use CDC).
  • Full load: simple, self-healing, expensive — small / slowly-changing tables only.
  • Backfill: partition by date, overwrite each partition idempotently so a 2-year replay never double-counts.
  • Medallion: bronze (raw, immutable) → silver (cleaned, conformed) → gold (aggregated, serving). Immutable raw = replayable pipeline.
  • DLQ / quarantine: route bad records aside; don't drop (silent loss) or fail the whole batch !

Spark Fundamentals

APIUse
DataFramedefault — Catalyst-optimized, columnar
Datasettyped (Scala/Java only)
RDDescape hatch — custom partitioning, no optimizer
  • Lazy: transformations (select, filter, join) build a DAG; nothing runs until an action (count, write, collect) triggers it — lets Catalyst optimize the whole plan.
  • Narrow (map, filter) = no shuffle, pipelined. Wide (join, groupBy, distinct) = shuffle → stage boundary.
  • Job → stages (split at shuffles) → tasks (one per partition). Partitions = unit of parallelism.
  • ! collect() pulls all data to the driver — OOMs on big frames. Use write / take(n).
  • ! Python UDFs break Catalyst + serialize row-by-row (slow). Prefer built-in SQL functions; use pandas/Arrow UDFs if you must.
  • Fault tolerance = lineage: a lost partition is recomputed from the DAG, not replicated.

Spark Internals & Tuning

  • Catalyst = query optimizer (predicate pushdown, column pruning, join reorder). Tungsten = off-heap memory + whole-stage codegen.
  • Shuffle = the expensive op: writes partitioned files to disk, network-transfers by key. Minimize wide ops; every join/groupBy is a shuffle !

Data skew !

  • Symptom: 1 task runs 10× longer (one key = huge partition). Fix: salt the key, enable AQE skew join, or broadcast.
  • AQE (on by default): re-plans at runtime — coalesces shuffle partitions, converts to broadcast, splits skewed partitions.
  • Spill = shuffle/agg exceeds memory → disk (slow). Raise partitions or memory.
  • cache() / persist(): only if reused ≥2× and it fits; else it evicts + hurts. persist picks the storage level (MEMORY_AND_DISK).
  • Tune spark.sql.shuffle.partitions (default 200) to data size; aim ~128MB / partition.

Spark Structured Streaming

  • Micro-batch: unbounded input processed as small batches; same DataFrame API as batch.
  • Output modes: append (new rows only), update (changed keys), complete (whole result — small aggs only).
  • Checkpoint = offsets + state on durable storage → exactly-once recovery. ! Never delete/reuse a checkpoint dir across incompatible query changes.
spark.readStream.format("kafka")…
  .withWatermark("ts", "10 minutes")
  .groupBy(window("ts","5 minutes"), $"key")
  .count()
  .writeStream.outputMode("update")
  .option("checkpointLocation", path).start()
  • Watermark = "drop events later than X behind the max seen" — bounds state so windows close and memory doesn't grow forever !
  • Stream-static join OK; stream-stream join needs watermarks on both sides.
  • End-to-end exactly-once = replayable source (Kafka offsets) + checkpoint + idempotent sink.

Kafka Fundamentals

  • Topic → partitions (ordering + parallelism unit). Order is guaranteed only within a partition ! Key → same partition → per-key order.
  • Offset = per-partition monotonic message id. Consumers track their own offset; Kafka doesn't delete on read (retention by time/size).
  • Replication factor = copies across brokers. Leader serves reads/writes; followers replicate. ISR = in-sync replicas caught up to the leader.
  • Log-structured: append-only, sequential disk I/O + zero-copy = very high throughput. It's a durable, replayable log, not a queue.

Producer durability

acksGuarantee
0fire-and-forget — may lose
1leader ack — loses on failover
allfull ISR ack — durable, slower

! acks=all means all of the ISR, gated by min.insync.replicas — not all RF copies. Set min.insync.replicas=2 with RF=3 for real durability.

Kafka Delivery & Consumers

  • Consumer group: partitions split across members, one member per partition. More consumers than partitions ⇒ idle ones ! Partitions cap parallelism.
  • Rebalance = reassignment on membership/subscription change; pauses consumption. Use cooperative/sticky assignor to avoid stop-the-world thrash.

Semantics = where you commit the offset

CommitSemantic
before processingat-most-once (may lose)
after processingat-least-once (may dup) — default
txn / dedupexactly-once
  • ! True cross-system exactly-once is almost always at-least-once + idempotent write on a business key. Ask "can my sink absorb a duplicate?" — if yes, don't chase EOS.
  • Idempotent producer dedups retries only. Kafka transactions give read-process-write EOS within Kafka.
  • ! Auto-commit fires on a timer regardless of processing — subtle loss/dup on crash. Prefer manual commit after work.
  • Lag = log-end-offset − committed. Almost always a slow/stuck consumer, not the broker — add partitions + consumers or speed up processing.

Kafka Ecosystem

  • Kafka Connect = declarative, scalable ingest/egress via connectors (JDBC, Debezium, S3). Source (into Kafka) / Sink (out). No custom code for common systems.
  • Schema Registry = central store of Avro/Protobuf/JSON schemas; messages carry a schema id. Enforces compatibility so a bad schema change is rejected at produce time, not discovered downstream !
  • Backward-compatible = new schema reads old data (add optional/defaulted field, drop field). Forward = old schema reads new data. Choose per how producers/consumers deploy.
  • Kafka Streams / ksqlDB = stream processing on Kafka: joins, windows, aggregations; state in RocksDB + changelog topics. Streams = library (embed in app); ksqlDB = SQL over it.
  • Compacted topic: keeps the latest value per key (not time-based) — a changelog / materialized-state store (e.g. CDC current state).

Stream Processing Concepts

  • Event time (when it happened) vs processing time (when seen). Correctness uses event time; late and out-of-order events are the norm !

  • Watermark = heuristic "event time has advanced to T; expect nothing older" → triggers window close + evicts state. Trades latency vs completeness ! too tight drops late data, too loose grows state.
  • State: keyed, checkpointed to durable store; the reason streaming is hard. Bound it with watermarks + TTL.
  • Late data: allowed-lateness grace period, side-output, or reprocess in batch (the batch reconcile of Lambda).

Data Warehousing

  • Columnar + MPP: store by column (prune + compress), spread work across nodes. Separated storage/compute (Snowflake, BigQuery) = scale each independently, pay per query.
  • ! Billing ≈ bytes scanned (BigQuery) or compute-seconds (Snowflake warehouse). Optimize by scanning less: partition/cluster, select only needed columns, filter on partition keys.

Lakehouse & Table Formats

Three generations: warehouse (fast, closed, pricey) → lake (cheap object-store files, schema-on-read, no ACID → swamp) → lakehouse (lake files + a transaction/metadata log ⇒ warehouse semantics on lake economics).

  • Key idea: the table is "the files the metadata log points to," not "the files in this directory." Readers see a consistent snapshot; writers commit a new log entry atomically.
  • Adds ACID, time travel, schema evolution, MERGE/upsert, compaction onto plain Parquet.
DeltaIcebergHudi
MetadataJSON logmanifest treetimeline
StrengthSpark/Databricksengine-neutralCDC upserts
  • COW (copy-on-write) = rewrite files on update, fast reads / slow writes. MOR (merge-on-read) = write deltas, fast writes / merge on read — for high-frequency upserts.
  • ! Time travel pins old files; you pay storage until VACUUM/expire — which then breaks older reads. Object storage gives durable blobs, not multi-file transactions.

File Formats & Physical Storage

Columnar = read less + compress more = cheaper scans. OLAP touches few columns of many rows.

FormatLayoutBest for
Parquetcolumnaranalytics / lake tables
ORCcolumnarHive/Hadoop
AvrorowKafka / streaming, schema evo
JSON/CSVrow textedges only — no stats/typing !
  • Parquet hierarchy: file → row groups → column chunks → pages, with min/max/null stats at each level → the engine skips row groups that can't match.
  • Projection pushdown (read only referenced cols) + predicate pushdown (filter via stats) + partition pruning (skip dirs by path value) = the three savings.
  • Compression: snappy/zstd (fast decode) beat gzip for scan-heavy work — ratio isn't the goal, total query time is. Encoding (dictionary/RLE) often wins more than the codec.
  • ! Small-files problem: millions of tiny files wreck planning/throughput. Fix with compaction; over-partitioning creates it.

Ingestion & CDC

  • CDC = capture row-level inserts/updates/deletes from an OLTP DB and stream them to the warehouse. Preferred over batch SELECT: low-latency, low source load, and captures deletes a high-water-mark query misses !
CDC methodNote
Log-basedread WAL/binlog (Debezium) — best: no source load, all changes, deletes
Query-basedupdated_at poll — simple, misses deletes + intermediate states
Trigger-basedDB triggers — heavy on the source
  • Pattern: Debezium → Kafka (compacted topic) → sink → MERGE into a lakehouse/warehouse table (needs upsert support).
  • Schema drift: source adds/renames/retypes a column. Enforce via Schema Registry (reject) or auto-evolve + alert. ! Silent drift = the classic "dashboard wrong all week, nothing failed."
  • Land raw/immutable first (bronze), transform after — so you can always replay.

Orchestration (Airflow)

Orchestrator = reliable, observable cron that understands dependencies + failure. Holds orchestration logic only — heavy transforms go to Spark/SQL/dbt, not a PythonOperator !

  • DAG = acyclic task graph; the scheduler topologically runs tasks whose upstreams succeeded, retries failures, records per-run state.
  • ! execution_date / logical date = the data interval the run represents, not when it fires. The run "for" Jul-01 fires after that day closes and processes that day's data. Get this and backfill/catchup click.
  • Idempotent tasks are the prerequisite for retries + backfills. Retrying a non-idempotent INSERT doubles the data.
  • Sensor = wait for a condition; use reschedule/deferrable mode or it holds a worker slot ! XCom = small metadata (a path, a count), never DataFrames.
  • Executor: Local / Celery (worker pool) / Kubernetes (pod per task).
  • Dagster/Prefect = asset-aware: schedule on data freshness, not just tasks.

Check dimensions

  • Freshness (arrived on time), volume (row count in band), schema (types/columns), distribution (nulls, ranges, cardinality), uniqueness/PK, referential (FKs resolve).
  • Place checks at ingest (reject/quarantine) and post-transform (gate before serving). Fail loud, fail early !

  • PII/governance: classify, mask/tokenize, enforce retention + GDPR delete (needs upsert/MERGE on the lakehouse).

Serving & Distributed Internals

  • Real-time OLAP (Druid, ClickHouse, Pinot): pre-aggregated, columnar, sub-second scans for high-QPS dashboards — the serving layer after streaming.
  • Shuffle / partitioning is the universal distributed cost: hash-partition by key so all rows of a key meet on one node for join/aggregate. Skew = one key too big !
  • Broadcast the small side to kill a shuffle; co-partition tables on the join key to avoid repeated reshuffles.
  • Exactly-once end-to-end = replayable source offsets + checkpointed state + idempotent sink. No free lunch; it's engineered per boundary.
  • Fault tolerance: lineage recompute (Spark) or checkpoint + replay (streaming) — not full replication of intermediate data.
  • Backpressure: a slow consumer signals upstream to slow down (or buffer to a durable log) rather than drop or OOM.

★ Design Review Checklist

Idempotency & correctness

  • ☐ Every task safe to re-run: delete-partition+insert or MERGE, not blind INSERT !
  • ☐ Keyed on the data interval, not wall-clock "now"; backfillable per partition.
  • ☐ Fact grain declared; additive vs semi/non-additive handled correctly.
  • ☐ SCD strategy chosen per dimension (2 = surrogate key + valid_from/to + is_current).

Storage & cost

  • ☐ Columnar (Parquet) + partitioned on a real filter column; not over-partitioned (small files).
  • ☐ Queries select needed columns only; filters hit partition/cluster keys (no fn(col) defeating pushdown).
  • ☐ Compaction/OPTIMIZE scheduled; VACUUM retention set vs time-travel needs.

Spark

  • ☐ No collect() on large frames; shuffle partitions sized to data; skew handled (salt/AQE/broadcast).
  • ☐ Broadcast the small join side; cache only if reused and it fits.

Streaming / Kafka

  • ☐ Delivery semantic explicit; sink idempotent on a business key (don't chase EOS blindly).
  • ☐ acks=all + min.insync.replicas=2 (RF3) where durability matters; offset committed after processing.
  • ☐ Watermark bounds state; checkpoint location stable; partitions ≥ consumers.

Reliability & quality

  • ☐ Raw/bronze immutable → replayable; DLQ/quarantine for bad records (no silent drop).
  • ☐ Freshness/volume/schema/uniqueness checks gate serving; alerts + lineage in place.
  • ☐ CDC (log-based) where deletes matter; schema drift caught at source (contract/registry).
  • ☐ Orchestrator only orchestrates; heavy transform in Spark/SQL/dbt; retries + SLAs configured.
