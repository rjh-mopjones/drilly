Return shape → pattern

  • single scalar → aggregate, no GROUP BY
  • row-per-input + computed col → window fn (never GROUP BY)
  • row-per-group → GROUP BY
  • one representative row per group → DISTINCT ON
  • matrix (rows × categories) → FILTER pivot
  • tree → recursive CTE

JOIN types & ON vs WHERE

JoinMeaning
INNERboth sides match (default)
LEFTevery left row, NULLs if no right
FULL OUTERevery row either side; set XOR
CROSScartesian; pair with generate_series

! The ON vs WHERE trap: a right-side filter in WHERE silently turns a LEFT join into an INNER one — unmatched left rows have NULL there and fail the predicate.

-- WRONG: drops customers with no 2024 orders
LEFT JOIN orders o ON o.cust_id = c.id
WHERE o.created_at >= '2024-01-01';
-- RIGHT: filter inside the join
LEFT JOIN orders o ON o.cust_id = c.id
     AND o.created_at >= '2024-01-01';
  • Rule: right-side predicate + you want non-matches to survive → put it in ON, never WHERE.
  • Rewrite RIGHT as LEFT with sides flipped for readability.
  • USING(col) = ON a.col=b.col and folds the column to one output col.
  • Anti-join = LEFT JOIN ... WHERE r.key IS NULL. Semi-join = EXISTS (no row duplication).

LATERAL & Self-Joins

LATERAL — top-N per group, cleanly

SELECT c.name, o.*
FROM customers c
CROSS JOIN LATERAL (
  SELECT * FROM orders o
  WHERE o.cust_id = c.id
  ORDER BY o.created_at DESC
  LIMIT 3            -- 3 latest per customer
) o;
  • Right side is correlated — evaluated per left row, may return a set.
  • Beats a window fn when there's an index on (cust_id, created_at DESC) and N is small vs group size: each per-group query is an early-stopping index scan. Window fn sorts the whole table once — steadier without the index. Check EXPLAIN ANALYZE.
  • Use LEFT JOIN LATERAL ... ON true to keep left rows with an empty right set.

Self-join — pairs & one-level hierarchy

-- unordered pairs, each once
FROM logins a JOIN logins b
  ON a.day = b.day AND a.user_id < b.user_id;
-- earns more than manager
FROM emp e JOIN emp m ON m.id = e.mgr_id
WHERE e.salary > m.salary;
  • a.id < b.id dedupes (alice,bob)/(bob,alice). ! alias both sides or the planner picks the wrong reference.

GROUP BY · HAVING · FILTER

  • Eval order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. So aggregate aliases are invisible to WHERE, visible to ORDER BY !
  • WHERE filters rows (before grouping, cheaper); HAVING filters groups (needs an aggregate). Predicate on a row → WHERE; on a group → HAVING.
  • Every SELECT col must be in GROUP BY or wrapped in an aggregate.

Conditional aggregation — many counts, one scan

SELECT region,
  COUNT(*) FILTER (WHERE status='paid')    AS paid,
  COUNT(*) FILTER (WHERE status='pending') AS pending,
  SUM(amount) FILTER (WHERE status='paid') AS rev
FROM orders GROUP BY region;
  • FILTER (WHERE ...) STD = same plan as SUM(CASE WHEN..THEN 1 END), cleaner. Also the pivot template.
  • ! COUNT(*) counts NULL rows; COUNT(col) skips NULLs; COUNT(*) FILTER (WHERE x IS NULL) counts them — opposite of COUNT(x).
  • COUNT(DISTINCT col) needs a hash/sort — pricier. On a LEFT JOIN, COUNT(*) overcounts NULL-padded rows; use COUNT(r.id).
  • STRING_AGG(name, ', ' ORDER BY name) STD replaces MySQL GROUP_CONCAT.

GROUPING SETS · ROLLUP · CUBE

-- per (region,cat), per region, grand total: 1 scan
SELECT region, category, SUM(revenue) AS total
FROM sales
GROUP BY ROLLUP(region, category);
FormProduces
ROLLUP(a,b)(a,b),(a),() — hierarchy subtotals
CUBE(a,b)(a,b),(a),(b),() — every combo
GROUPING SETS(...)exactly the groupings you list
  • Subtotal rows carry NULL in the rolled-up column. GROUPING(category)=1 flags a subtotal row so you can label it (distinguishes real NULLs from subtotal NULLs) !
  • Recognition: "with subtotals" → ROLLUP; "every combination" → CUBE; "these specific groupings" → GROUPING SETS. Beats 4 queries UNION'd that re-scan the data.

Window Functions — Ranking & Ties

<fn> OVER (PARTITION BY k ORDER BY x [frame])
FnTies (1,1,?)
ROW_NUMBER()1,2,3 — arbitrary tiebreak !
RANK()1,1,3 — gaps after ties
DENSE_RANK()1,1,2 — no gaps
NTILE(4)quartile bucket per row
  • Windows keep the row count and add a per-row column — not GROUP BY.
  • Can't filter a window in the same SELECT (runs after WHERE) — wrap in a CTE/subquery and filter there !
-- 2nd-highest salary per dept (distinct value)
WITH r AS (
  SELECT *, DENSE_RANK() OVER (
    PARTITION BY dept ORDER BY salary DESC) rk
  FROM emp)
SELECT * FROM r WHERE rk = 2;
  • DENSE_RANK=2 = 2nd distinct salary; ROW_NUMBER=2 = literally the 2nd row (wrong if tie semantics matter). The prompt's tie rule decides.

Window Functions — Analytics

FnReturns
LAG(x[,n[,dflt]])value n rows back in partition
LEAD(x)value from following row
FIRST_VALUE / LAST_VALUEframe endpoints !
NTH_VALUE(x,n)nth in frame
-- day-over-day delta per customer
SELECT ts, amount - LAG(amount) OVER (
  PARTITION BY cust_id ORDER BY ts) AS delta
FROM txns;
  • "previous/next by group" → LAG/LEAD reflexively. O(N log N) sort vs O(N²) self-join.
  • ! LAST_VALUE with the default frame returns the current row, not the partition end — default frame is RANGE UNBOUNDED PRECEDING → CURRENT ROW. Fix: add ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING.
  • COUNT(DISTINCT ...) OVER (...) is not supported ! — reformulate via first-appearance (see Gaps & Islands neighbours).

Window Frames — ROWS / RANGE / GROUPS

-- 7-day rolling avg (row-based): 6 PRECEDING = 7 rows
AVG(rev) OVER (ORDER BY day
  ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)
-- 7 calendar days regardless of row count
AVG(rev) OVER (ORDER BY day
  RANGE BETWEEN INTERVAL '6 days' PRECEDING
            AND CURRENT ROW)
Mode"N preceding" =
ROWSN physical rows back
RANGErows within N of the ORDER BY value
GROUPSN peer-groups (ties) back
  • ! Off-by-one: 6 PRECEDING AND CURRENT ROW = 7 rows. Writing 7 PRECEDING gives 8.
  • ! Default frame is RANGE, not ROWS — differs when ties exist on the ORDER BY key. Pick explicitly.
  • ROWS is integer-count only; interval windows need RANGE BETWEEN INTERVAL PG. Missing days don't shrink a RANGE window (right for "rolling N calendar days"); ROWS would.
  • Ranking fns (ROW_NUMBER/RANK) ignore the frame — always whole partition.

Subqueries vs CTEs vs Windows

  • Scalar subquery in SELECT/WHERE: returns one value. Correlated subquery re-evaluates per outer row — usually a perf smell !
  • Derived table: subquery in FROM. CTE: WITH x AS (...), named, referenceable multiple times, reads top-down.
  • ! Pre-PG12 a CTE was an optimisation fence (always materialised). PG12+ inlines CTEs used once — add AS MATERIALIZED to force the old fence, NOT MATERIALIZED to force inlining.
WITH recent AS MATERIALIZED (   -- force one eval
  SELECT * FROM big WHERE ts > now() - '1d'::interval
)
SELECT ... FROM recent a JOIN recent b ON ...;
  • Reach for a window fn when you need a per-row aggregate without collapsing rows; a CTE to name/reuse an intermediate; a correlated subquery only when small and index-backed.
  • EXISTS vs IN: modern planner treats both as semi-joins — pick by readability. But never NOT IN over a nullable column ! (one NULL → zero rows).

Recursive CTEs (graph / hierarchy)

WITH RECURSIVE descent AS (
  SELECT id, parent_id, 1 AS lvl       -- base/anchor
  FROM categories WHERE id = :root
  UNION ALL
  SELECT c.id, c.parent_id, d.lvl + 1  -- recursive
  FROM categories c
  JOIN descent d ON c.parent_id = d.id
)
SELECT * FROM descent;
  • Anchor runs once; recursive member joins the CTE's own prior output; stops when it yields 0 rows. This is BFS — each iteration is a level.
  • Ascent (ancestors): flip to JOIN a ON c.id = a.parent_id.
  • ! UNION ALL not UNION — UNION dedupes each iteration, compounding cost.
  • ! Cycles loop forever on dirty data. PG14+: ... CYCLE id SET is_cycle USING path then WHERE NOT is_cycle. Pre-14: carry a path array, WHERE NOT id = ANY(path).
  • Bound runaways with WHERE lvl < 100; deep recursion hits max_stack_depth.
  • Wrong tool for weighted shortest path (Dijkstra), TSP, heavy per-node work — no heap, repeats work. Use app code.

Gaps & Islands

Detect consecutive runs. The trick: for qualifying rows, value - ROW_NUMBER() is constant within a run (rows 1,2,3 on dates d,d+1,d+2 → all d-1). Group by that difference.

WITH q AS (                       -- FILTER FIRST !
  SELECT day FROM daily_rev WHERE rev > 100000
), g AS (
  SELECT day,
    day - (ROW_NUMBER() OVER (ORDER BY day))::int AS grp
  FROM q
)
SELECT MIN(day) start, MAX(day) fin, COUNT(*) len
FROM g GROUP BY grp
HAVING COUNT(*) >= 3;             -- streaks of 3+
  • ! Filter to qualifying rows before numbering — numbering the full table breaks the alignment.
  • Per-group streaks: PARTITION BY user_id in the ROW_NUMBER.
  • Generalises to any length K (self-join only does fixed K). LAG-variant: flag boundaries, SUM(flag) OVER (ORDER BY ts) = island id — more flexible for "new island when X changes".

Sessionization & Event Sequences

Gaps & islands on time with an inactivity boundary (e.g. 30-min gap = new session).

WITH marked AS (
  SELECT user_id, ts,
    CASE WHEN ts - LAG(ts) OVER (PARTITION BY user_id
         ORDER BY ts) > INTERVAL '30 min'
         OR LAG(ts) OVER (PARTITION BY user_id
         ORDER BY ts) IS NULL
    THEN 1 ELSE 0 END AS new_sess
  FROM events
)
SELECT user_id, ts,
  SUM(new_sess) OVER (PARTITION BY user_id ORDER BY ts)
    AS session_id
FROM marked;
  • Boundary flag + running sum = stable session id. First row of a partition is always a boundary (LAG is NULL) !
  • Then GROUP BY user_id, session_id for session length / event count / duration.

Top-N per Group

-- most recent order per customer (PG, shortest)
SELECT DISTINCT ON (cust_id) *
FROM orders
ORDER BY cust_id, created_at DESC;
PatternUse when
DISTINCT ON PGN=1, shortest, index-friendly
ROW_NUMBER()<=Nany N, portable
LATERAL ... LIMIT NN small + good index
  • ! DISTINCT ON's leading ORDER BY cols must match the ON list, then the tiebreak (created_at DESC) picks the kept row.
  • Portable form for N>1:
WITH r AS (SELECT *, ROW_NUMBER() OVER (
  PARTITION BY cust_id ORDER BY created_at DESC) rn
  FROM orders)
SELECT * FROM r WHERE rn <= 3;
  • Avoid WHERE created_at = (SELECT MAX(...) WHERE cust_id=o.cust_id) — correlated, re-evaluates per row.

Pivot & Unpivot

Pivot — rows → columns (FILTER)

SELECT cust_id,
  SUM(rev) FILTER (WHERE month=1) AS jan,
  SUM(rev) FILTER (WHERE month=2) AS feb
FROM revenue GROUP BY cust_id;
  • Column list must be known at query time ! — SQL can't return a variable-shape result. Truly dynamic pivot → generate the SQL in app code.
  • tablefunc.crosstab PG (CREATE EXTENSION tablefunc) is shorter but has the same static-column constraint — usually not worth the dependency.

Unpivot — columns → rows

SELECT id, k, v
FROM wide,
LATERAL (VALUES ('jan',jan),('feb',feb),('mar',mar))
  AS u(k, v);
  • LATERAL (VALUES ...) or UNNEST turns N columns into N rows per input row.

Set ops need matching column count & compatible types; ORDER BY goes once, at the end.

"in A not in B" — three forms

-- 1. NOT EXISTS  (planner favourite, NULL-safe)
WHERE NOT EXISTS (SELECT 1 FROM b WHERE b.uid = a.uid);
-- 2. LEFT JOIN ... IS NULL
LEFT JOIN b ON b.uid = a.uid WHERE b.uid IS NULL;
-- 3. EXCEPT  (returns DISTINCT rows)
  • ! Never NOT IN (subquery) over a nullable column — a single NULL makes the whole predicate UNKNOWN and you get zero rows. NOT EXISTS is immune.
  • Semi-join (EXISTS/IN) = "has ≥1 match", no duplication. Anti-join = the negation.

NULL & Three-Valued Logic

  • NULL = absence of value → comparisons yield UNKNOWN, treated as FALSE in WHERE. So = NULL, != NULL are always wrong — use IS NULL / IS NOT NULL !
  • NULL = NULL → UNKNOWN. NULL-safe equality: a IS NOT DISTINCT FROM b (both-NULL = TRUE). Inequality: IS DISTINCT FROM.
  • Aggregates skip NULLs: SUM/AVG/MIN/MAX/COUNT(col) ignore them; COUNT(*) counts the rows.
  • ! SUM over zero rows is NULL, not 0 → COALESCE(SUM(x),0) when no-rows means zero.
  • ! AVG(x) ignores NULLs (mean of non-NULLs); if NULL should count as 0 use AVG(COALESCE(x,0)) — different answer.
-- sentinel → real NULL
NULLIF(qty_text, 'N/A')
-- NULLs last regardless of engine default
ORDER BY signup_date ASC NULLS LAST;
  • COALESCE(a,b,c) = first non-NULL. NULLIF(a,b) = NULL if a=b.

Dedup & Messy Data

Order is the whole game: normalise → coerce types → null-out sentinels → dedup → key. Stage as a CTE chain, one transform each, so you can reconcile counts.

WITH norm AS (           -- 1. normalise text keys
  SELECT *, lower(btrim(ticker)) AS tk FROM raw
), typed AS (            -- 2. safe cast + 3. sentinel→NULL
  SELECT *, NULLIF(amt_text,'N/A')::numeric AS amt
  FROM norm
), deduped AS (          -- 4. keep one per business key
  SELECT DISTINCT ON (tk, trade_date) *
  FROM typed ORDER BY tk, trade_date, ctid
)
SELECT md5(tk||trade_date::text) AS id, *  -- 5. stable key
FROM deduped;
  • ! SELECT DISTINCT only kills byte-identical rows — " AAPL " ≠ AAPL until normalised.
  • ! '' is a real value in Postgres, not NULL — NULLIF(x,'') it.
  • ! A blanket ::date aborts the whole query on one bad row — guard with pg_input_is_valid(v,'date') (PG16+) or a regex CASE.
  • ROW_NUMBER() needs a stable tiebreaker (ctid, load ts) or reruns key differently. Prefer a content hash over gen_random_uuid(). Quarantine bad rows — don't silently drop.

UPSERT · ON CONFLICT · MERGE

-- idempotent insert (retry-safe)
INSERT INTO events (external_id, payload)
VALUES (:x, :p)
ON CONFLICT (external_id) DO NOTHING;

-- upsert; EXCLUDED = would-be-inserted row
INSERT INTO customers (email, name, last_seen)
VALUES (:e, :n, now())
ON CONFLICT (email) DO UPDATE
  SET name = EXCLUDED.name,
      last_seen = EXCLUDED.last_seen
  WHERE customers.last_seen < EXCLUDED.last_seen  -- LWW
RETURNING id, (xmax = 0) AS was_inserted;
  • ! Idempotency needs a UNIQUE constraint on the conflict target — without it there's nothing to detect and concurrent inserts both succeed.
  • EXCLUDED is a pseudo-table, only in DO UPDATE. xmax=0 ⇒ row was inserted (not updated). WHERE on DO UPDATE gates the update (last-write-wins).
  • RETURNING PG avoids the insert-then-select round-trip (SQL Server: OUTPUT).
MERGE INTO customers c USING staging s ON c.email=s.email
WHEN MATCHED AND s.is_deleted THEN DELETE
WHEN MATCHED THEN UPDATE SET name=s.name
WHEN NOT MATCHED THEN INSERT (email,name) VALUES (s.email,s.name);
  • MERGE STD (PG15+): multi-action bulk ETL with a DELETE branch. Use ON CONFLICT for simple single-row upserts.

  • Seq Scan on a big filtered table → missing index. Nested Loop with high row count → bad estimate (ANALYZE stale stats). Big gap estimated vs actual rows → re-stat.

Running Distinct — the unsupported case

COUNT(DISTINCT x) OVER (ORDER BY …) is rejected by Postgres ! — the classic "cumulative distinct users up to each day" trap. Two reformulations:

First-appearance trick — O(N log N)

WITH firsts AS (          -- each user's first day
  SELECT DISTINCT ON (user_id) user_id, day
  FROM logins ORDER BY user_id, day
)
SELECT day,
  COUNT(*) OVER (ORDER BY day) AS distinct_so_far
FROM firsts;
  • Collapsing each user to their first day turns a running-distinct into a plain running COUNT(*) — every user is counted exactly once, on the day they first appear.
  • Brute-force alt: for each day, COUNT(DISTINCT user_id) WHERE d <= day — a self-join, O(N²). Only viable on tiny tables.
  • Same limitation bites 30-day rolling distinct (DAU/MAU) — no window form; pre-aggregate a daily distinct-user list, then window the trailing 30 days.

Temporal & As-Of Joins

Time as a first-class dimension. Core op: for each A row, the most recent B row at or before A's timestamp.

As-of join — LATERAL … LIMIT 1

-- most recent quote at/before each trade
SELECT t.*, q.bid, q.ask
FROM trades t
CROSS JOIN LATERAL (
  SELECT * FROM quotes q
  WHERE q.symbol = t.symbol
    AND q.ts <= t.ts
  ORDER BY q.ts DESC LIMIT 1
) q;
  • Index (symbol, ts DESC) → each LATERAL is one index seek. This is Postgres's answer to KDB's aj.
  • ! Ties on ts → LIMIT 1 picks one arbitrarily. Add a deterministic tiebreak: ORDER BY q.ts DESC, q.id DESC. Non-deterministic as-of joins break downstream reconciliation.

SCD type-2 point-in-time lookup

WHERE valid_from <= :ts
  AND (valid_to > :ts OR valid_to IS NULL);
  • ! The valid_to IS NULL arm catches the currently-valid (open-ended) row — drop it and you miss the present tier.
  • Range form: tstzrange(valid_from, valid_to, '[)') @> :ts PG. Half-open [) avoids boundary double-counting.

Range overlap

  • tstzrange(a.lo,a.hi,'[)') && tstzrange(b.lo,b.hi,'[)') PG — GiST-indexable. Portable form: a.lo < b.hi AND a.hi > b.lo.
  • ! timestamptz stores UTC; timestamp is naive. Mixing them is a silent-bug source — store timestamptz.

Cohort, Funnel & Retention

Cohort analysis = pivot of distinct-user counts on (cohort, week-offset). Frame it that way and it's mechanical.

WITH cohorts AS (
  SELECT user_id,
    date_trunc('week',signup)::date AS cw
  FROM users
), acts AS (
  SELECT c.cw,
    (date_trunc('week',l.day)::date - c.cw)/7 AS off,
    l.user_id
  FROM cohorts c JOIN logins l USING(user_id)
)
SELECT cw,
  COUNT(DISTINCT user_id) FILTER (WHERE off=0) w0,
  COUNT(DISTINCT user_id) FILTER (WHERE off=1) w1,
  COUNT(DISTINCT user_id) FILTER (WHERE off=2) w2
FROM acts GROUP BY cw ORDER BY cw;
  • Divide each cell by w0 per cohort for retention %.
  • ! Naive GROUP BY (cohort,off) drops zero-retention cells — CROSS JOIN generate_series the offsets, LEFT JOIN … COALESCE(…,0) to fill.

Funnel — ordered steps

MIN(ts) FILTER (WHERE event='signup')   AS s1,
MIN(ts) FILTER (WHERE event='checkout') AS s2
-- then COUNT(s2) FILTER (WHERE s2 > s1)
  • ! "N-day" is ambiguous: N-th day = day-signup = N; by N-day = BETWEEN 1 AND N. Ask which.
  • Stickiness = DAU/MAU. No COUNT(DISTINCT) OVER → MAU needs a 30-day rolling distinct subquery or first-appearance trick.

Statistical SQL

Most "stats in SQL" prompts want the right built-in, not a hand-rolled formula.

SELECT customer_id,
  PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY val) med,
  PERCENTILE_CONT(ARRAY[0.5,0.95,0.99])
    WITHIN GROUP (ORDER BY val) AS pcts
FROM orders GROUP BY customer_id;

  • ! Bare stddev() = stddev_samp (÷N-1), not population.
  • ! No PERCENTILE_CONT … OVER window form — rolling p95 must pre-aggregate per day, then window the dailies. width_bucket returns 0 below range, n+1 above.

generate_series & Zero-Fills

The dead-on tool whenever the prompt says "every day / hour", "all values in range", or "including empty buckets".

-- one row per day, zero-filled signups
SELECT d::date, COUNT(s.id) AS signups
FROM generate_series(
  CURRENT_DATE-29, CURRENT_DATE, '1 day'::interval) d
LEFT JOIN signups s ON s.created_at::date = d::date
GROUP BY d::date ORDER BY d::date;
  • ! Without the series + LEFT JOIN, days with no events vanish — nothing anchors them. The LEFT JOIN + COUNT(s.id) (not COUNT(*)) gives the zero.
  • Numeric: generate_series(1,100); stepped: generate_series(1,100,5).
  • Cohort grid = cohorts CROSS JOIN generate_series(0,12) AS off, then LEFT JOIN the measured cells.
  • Time-bucket join: date_trunc('hour',ts) both sides, join on the bucket; add a functional index ON (date_trunc('hour',ts)) to keep it fast.

For every prompt ask: "is there a PG feature that does this in one line?"

CREATE INDEX ON users (email) WHERE active;

Anti-patterns & Smells

  • ! NOT IN (subquery) on nullable col → zero rows. Use NOT EXISTS.
  • ! SELECT * in production / views — breaks on schema change, defeats index-only scans, ships extra bytes.
  • ! Right-side filter in WHERE on a LEFT JOIN → accidental inner join.
  • ! Correlated subquery in SELECT where a window fn or join does it in one pass (N+1 in SQL).
  • ! Function on an indexed column in WHERE → full scan.
  • ! GROUP BY 1 (ordinal) in stored SQL — breaks silently when columns reorder.
  • ! OFFSET pagination on deep pages — O(offset). Use keyset/seek: WHERE (ts,id) < (:ts,:id) ORDER BY ts DESC,id DESC LIMIT n.
  • ! Implicit cross join from FROM a, b with the join predicate forgotten.
  • ! DISTINCT sprinkled to hide a fan-out from a bad join — fix the join.
  • ! COUNT(*) after LEFT JOIN overcounts NULL-padded rows.

★ SQL Review Checklist

Correctness

  • ☐ No NOT IN over a nullable subquery; anti-joins use NOT EXISTS !
  • ☐ LEFT JOIN right-side filters live in ON, not WHERE.
  • ☐ NULL checks use IS [NOT] NULL; no = NULL.
  • ☐ Aggregates over nullable cols have an explicit "NULL means what?" decision (COALESCE).

Windows & grouping

  • ☐ Window frame explicit where ties/time matter; off-by-one on N PRECEDING checked.
  • ☐ Row-per-input output uses a window fn, not GROUP BY; row-per-group uses GROUP BY.
  • ☐ Ranking fn matches tie semantics (RANK/DENSE_RANK/ROW_NUMBER).
  • ☐ WHERE vs HAVING: row predicates in WHERE.

Recursion & cleaning

  • ☐ Recursive CTE has a cycle guard (CYCLE / visited array) and depth bound.
  • ☐ Cleaning pipeline: normalise → type → sentinel-null → dedup → key; stable tiebreaker on ROW_NUMBER.

Writes & performance

  • ☐ ON CONFLICT backed by a matching UNIQUE constraint.
  • ☐ Predicate columns are SARGable (no function/cast on the indexed side); composite index respects leftmost-prefix.
  • ☐ EXPLAIN ANALYZE checked for seq scans / estimate-vs-actual gaps on hot queries.
