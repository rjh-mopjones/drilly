Instruments & Basics

Core instrument types

InstrumentWhat it is
EquityOwnership share in a company
BondLoan to issuer; pays coupons, repays par
FutureExchange-traded contract to buy/sell at a future date/price
OptionRight (not obligation) to buy (call) / sell (put) at a strike

  • Derivative = value derived from an underlying (future/option/swap qualify). Sensitivities (the "Greeks") exist but are pricing-desk concerns, not yours.

Direction & jargon

TermMeans
longOwn it / bet price up
shortSold-borrowed / bet price down
the bookA portfolio / set of positions
notionalContract face amount — what exposure is calculated on
parA bond's face / redemption value
  • ! long/short is direction, not time horizon. A "short" can be held for months.
  • ! "the book" is a portfolio, not a ledger or a DB table.
  • ! notional ≠ market value — a $10m notional swap may have near-zero present value.

Engineer angle

  • These are the entity types your security master (instrument reference data) + position system model.
  • Instrument is the dimension; position/trade rows reference it by id. Symbol conventions differ per vendor (e.g. Bloomberg vs Reuters tickers) — normalise to an internal id. See SQL sheet for modelling, System Design sheet for reference-data distribution.

Why a Security Master exists

  • One instrument carries MANY ids across vendors/venues & asset classes — none is universal.
  • The security master holds one internal canonical id + a mapping table to every external id (ISIN, CUSIP, ticker, FIGI...).
  • Raw ticker feeds are messy: reused symbols, corporate actions, renames, exchange suffixes.

Engineer angle

  • Instrument lookups join through the master; never key business data (trades, positions) on a raw ticker.
  • Canonical id is the FK everywhere — see SQL sheet for the mapping-table join pattern.
  • ! Vendor symbol conventions differ (e.g. Bloomberg vs Reuters suffix styles). NEVER string-strip/regex two symbols to decide they're the same instrument — map via the master. (-> SQL sheet: messy-identifier cleaning.)
  • Mapping is many-to-many over time — model effective dates, not a single static row.

OfficeDoes

Data model

! False-friend: Order (intent) vs Execution (match event) vs Trade/Fill (done deal) are different entities.
  • One order → many executions/fills → aggregated into a trade. Model as parent/child rows, never one flat table (see SQL sheet for 1:N keys).
  • Every stage is an append-only state change — never overwrite; audit trail is regulatory.

Positions, PnL & NAV

The core distinction !

ConceptNatureEngineer's view
tradeEVENTImmutable fact; append-only
positionDERIVED stateFold/reduce over trade events
balancepoint-in-time AGGREGATESnapshot at instant t
  • Engineers conflate these constantly. A position is computed, not stored as truth.

Position = fold over trades

  • Running aggregate of all trades for one (instrument, portfolio): net qty, avg cost.
  • Classic event-sourcing problem → see System Design sheet (Event Sourcing / CQRS): events = source of truth, position = materialised read-model fold.
  • Snapshots speed replay; the SQL aggregation is a GROUP BY → SQL sheet.

PnL

TermMeaning
Realised PnLLocked in by closing a position
Unrealised PnLPaper gain/loss on open position at current price
  • Unrealised PnL changes every tick even with zero trades → it depends on price feed, not just your data.

Marks & NAV

TermOne-liner
Mark-to-market (MtM)Revalue open positions at current market price
The close / closing priceOfficial end-of-day price used for marks
NAV (Net Asset Value)assets − liabilities, per fund/portfolio
  • NAV is typically struck daily after the close → a scheduled end-of-day batch job, not real-time.
  • ! Same position yields different PnL/NAV depending on which mark price you used — store the price source & timestamp, not just the number.

Counterparties, Custody & Reconciliation

Who's who

TermOne line

Reconciliation

  • Recon = match your internal records vs an external source (custodian / counterparty / exchange) to prove they agree.
  • Break = an unmatched or mismatched item to investigate & resolve.
  • Runs daily / intraday; ops chase breaks until cleared (T+0, aged-break reports).

How matching works

StepDetail
Match keytrade_id, else instrument+date+qty
ToleranceAllow small price/qty rounding diffs
Classifymatched / unmatched / broken

Why an engineer cares

  • Core ops engineering: the bread-and-butter of an ops dev team — ingest two feeds, match, surface & route breaks.
  • System: idempotent loaders, audit trail per break, dashboards, replay.

! Recon is fundamentally a JOIN + DIFF on imperfect data from two systems with different conventions (symbology, date/tz, sign, rounding, dupes). It's the messy-data problem in business form — see SQL sheet (cleaning / dedup / fuzzy keys) and System Design sheet (idempotent ingestion); data-quality work, not arithmetic.

Treasury, Cash & FX

Core concepts

TermOne-liner
Cash managementRight cash, right place, right currency, right time
FundingSourcing cash to meet obligations as they fall due
Margin / CollateralAssets posted to cover potential loss / counterparty exposure
Nostro / Vostro"Our"/"your" account held at another bank per currency

FX & multi-currency

  • Trade ccy = currency a deal is priced in; settlement ccy = what you actually pay/receive. They can differ.
  • Quote EUR/USD = 1.10 means 1 EUR = 1.10 USD. ! Inverting the quote, or applying it in the wrong direction, is a common bug class — silent, off by the square of the rate.
  • A rate has a timestamp + source; store both. Same pair differs by venue/snapshot.

Minor-unit traps !

CodeTrap
GBP vs GBpPounds vs pence — factor of 100 (vendor symbol convention; Bloomberg/Reuters differ)
USD2 dp — cents, not dollars
JPY0 dp — NO minor unit; ÷100 corrupts the amount
  • Minor-unit count varies per currency (ISO 4217 exponent) — never hard-code 2. Off-by-100 / wrong-scale errors result.

Engineer angle

  • Always store currency beside every amount — a bare number is meaningless.
  • Use an exact decimal type, never float (see Java/C# exact-money card; SQL currency-unit gotcha).
  • Define rounding rule + scale per currency explicitly; persist the FX rate used on conversion for audit.

MarketPrice / rate / FX moves against you

Why audit trail & immutability are non-negotiable

  • Regulators (and your own auditors) must reconstruct who did what, when, from what input data — sometimes years later.
  • ! Never silently correct a number. Don't UPDATE a booked trade. Post a new compensating / reversing entry so the original and the fix both survive.
  • This is the accept-and-reconcile / never-silently-correct pattern — see the System Design sheet. For ML-driven decisions, the AI-governance sheet covers model explainability.

How regulation constrains HOW you build

TermMeans for you
Change controlProd changes are reviewed, approved, logged — no ad-hoc hotfixes
Segregation of dutiesThe dev who writes a fix can't also approve the prod data change
Data retentionRecords kept N years; deletes are policy-driven, not casual
LineageTrace every figure back to its source inputs

Engineer angle

  • Design for append-only history + full lineage from day one — retrofitting it is brutal.
  • Prefer event logs / bitemporal tables over in-place mutation (-> SQL sheet for temporal modelling). Treat audit fields (who, when, source) as mandatory, not optional.

Financial-Systems Patterns I

Event sourcing for trades/positions

  • Trades are immutable events (append-only log); never updated in place.
  • A position is a fold (reduce) over a portfolio's trade events.
  • As-of / point-in-time queries replay events up to a timestamp.
  • Periodic snapshots: snapshot + delta = O(delta), not O(full history).
  • Corrections = new compensating events, not mutation -> full audit trail. (-> System Design: Event Sourcing & CQRS)

Idempotency in trade processing

  • Same trade event may be redelivered; dedupe on a business idempotency key (e.g. source trade id), not a transport id.
  • Persist seen keys; on replay, no-op — never double-book.
  • ! at-least-once delivery is the norm => the consumer must be idempotent; "exactly-once" is usually idempotent + dedup, not magic. (-> System Design: messaging delivery semantics)

Ordering per portfolio/account

ScopeRule
Within one portfolioapply in order (a buy then sell must not reorder)
Across portfoliosprocess in parallel — independent
  • Partition / key the stream by portfolioId so order is preserved per key, throughput scales across keys.
  • ! Global ordering kills throughput — only order where it matters. (-> System Design partitioning; Java/C# keyed-executor)

Financial-Systems Patterns II

Exact money handling

  • ! NEVER float/double for money — binary FP can't represent 0.10; rounding errors compound & break reconciliation.
  • Use exact decimal (BigDecimal/C# decimal) or store minor units as integers (cents/pence). See Java/C# cheat sheets.
  • Define rounding explicitly (e.g. HALF_EVEN) — never rely on a default.
  • Always persist the currency alongside the amount; an amount without a currency is meaningless. Money = (amount, currency, scale).

Reconciliation pipeline

StageDoes
IngestRead external file/feed (CSV, fixed-width)
NormaliseMap to internal shape; fix dates/symbols (SQL cheat sheet: cleaning)
MatchJoin on keys (trade id, date, amount) with tolerances
Classifymatched / unmatched / broken (amount or date mismatch)
ReportBreaks list for ops investigation
  • Slow batch → parallelise: chunk by date or counterparty. See System Design cheat sheet (scaling a slow batch).

Accept-and-reconcile vs reject-and-reprocess

Behaviour
Accept & reconcileStamp rate + timestamp used, proceed; fix breaks downstream
Reject & reprocessBlock until correct; unpredictable latency, can loop
  • High-throughput pricing/PnL favours accept-and-reconcile — don't block the hot path.
  • ! Audit trail is mandatory: what value, which source, when. See System Design cheat sheet (Consistency & CAP).

Scenario Prompts (drill)

Drive each like the System Design sheet's method: restate → assumptions → diagnose → simple-first → flag tradeoffs. Lead with the data model and invariants, not the framework.

Prompts (don't answer — reason aloud)

  • Design a real-time position-keeping service from a trade event stream. (per-portfolio ordering, idempotency on retries, fold/event-sourcing the stream, periodic snapshots to bound replay)
  • Design an end-of-day NAV/PnL calc that's also queryable intraday. (batch close vs streaming, as-of / point-in-time semantics, CQRS read model, what "the close" actually means)
  • Design a reconciliation system matching internal trades to a custodian feed. (fuzzy join + diff on messy keys, amount/date tolerances, classify breaks, chunk-by-counterparty to scale)
  • Design a multi-currency cash/treasury ledger with point-in-time balances. (exact money + currency unit, FX rate direction & pair, append-only history, balance = aggregate-as-of, no mutating rows)

Speaking the Language (false-friends)

Same English word, different meaning to the business. Get these wrong and your schema/API lies to stakeholders.

Lifecycle terms (don't conflate)

TermMeans
orderIntent to trade (not yet done)
executionA match event (order met liquidity)
fillQuantity executed (partial or full)
tradeThe done deal (one or more fills)
positionNet holding — derived, not stored raw
balancePoint-in-time aggregate (cash/qty)
  • ! One order → many fills → one trade. Model them as separate entities; position/balance are computed, never a writable column.

Words that aren't what they sound like

TermMeans (not...)

longOwn it (direction) — NOT duration
shortSold-borrowed (direction) — NOT brief

  • ! notional ≠ market value — a $1M-notional swap can be worth ~$0. Store both; never reuse one column.
  • Use bp for rates/fees to dodge float rounding (see SQL / Java/C# sheets on DECIMAL vs float for money).

Post-trade (often used interchangeably — they aren't)

StageWhat happens
executionThe match (trade is born)
clearingNetting + guarantee before money moves
settlementCash/securities actually change hands
T+2Settles 2 business days after trade date
  • ! Trade done ≠ settled. Status is a state machine (executed→cleared→settled), not a boolean — model failed/pending settlements explicitly (see System Design sheet on saga/state-machine patterns).
  • T+2 uses business days — needs a holiday calendar, not + INTERVAL '2 days'.
