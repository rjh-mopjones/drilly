Instruments & Basics

Core instrument types

InstrumentWhat it is
EquityOwnership share in a company
BondLoan to issuer; pays coupons, repays par
FutureExchange-traded contract to buy/sell at a future date/price
OptionRight (not obligation) to buy (call) / sell (put) at a strike

  • Derivative = value derived from an underlying (future/option/swap qualify). Sensitivities (the "Greeks") exist but are pricing-desk concerns, not yours.

Direction & jargon

TermMeans
longOwn it / bet price up
shortSold-borrowed / bet price down
the bookA portfolio / set of positions
notionalContract face amount — what exposure is calculated on
parA bond's face / redemption value
  • ! long/short is direction, not time horizon. A "short" can be held for months.
  • ! "the book" is a portfolio, not a ledger or a DB table.
  • ! notional ≠ market value — a $10m notional swap may have near-zero present value.

Engineer angle

  • These are the entity types your security master (instrument reference data) + position system model.
  • Instrument is the dimension; position/trade rows reference it by id. Symbol conventions differ per vendor (e.g. Bloomberg vs Reuters tickers) — normalise to an internal id. See SQL sheet for modelling, System Design sheet for reference-data distribution.

Why a Security Master exists

  • One instrument carries MANY ids across vendors/venues & asset classes — none is universal.
  • The security master holds one internal canonical id + a mapping table to every external id (ISIN, CUSIP, ticker, FIGI...).
  • Raw ticker feeds are messy: reused symbols, corporate actions, renames, exchange suffixes.

Engineer angle

  • Instrument lookups join through the master; never key business data (trades, positions) on a raw ticker.
  • Canonical id is the FK everywhere — see SQL sheet for the mapping-table join pattern.
  • ! Vendor symbol conventions differ (e.g. Bloomberg vs Reuters suffix styles). NEVER string-strip/regex two symbols to decide they're the same instrument — map via the master. (-> SQL sheet: messy-identifier cleaning.)
  • Mapping is many-to-many over time — model effective dates, not a single static row.

Data model

! False-friend: Order (intent) vs Execution (match event) vs Trade/Fill (done deal) are different entities.
  • One order → many executions/fills → aggregated into a trade. Model as parent/child rows, never one flat table (see SQL sheet for 1:N keys).

Positions, PnL & NAV

The core distinction !

ConceptNatureEngineer's view
tradeEVENTImmutable fact; append-only
positionDERIVED stateFold/reduce over trade events
balancepoint-in-time AGGREGATESnapshot at instant t
  • Engineers conflate these constantly. A position is computed, not stored as truth.

Position = fold over trades

  • Running aggregate of all trades for one (instrument, portfolio): net qty, avg cost.
  • Classic event-sourcing problem → see System Design sheet (Event Sourcing / CQRS): events = source of truth, position = materialised read-model fold.
  • Snapshots speed replay; the SQL aggregation is a GROUP BY → SQL sheet.

PnL

TermMeaning
Realised PnLLocked in by closing a position
Unrealised PnLPaper gain/loss on open position at current price
  • Unrealised PnL changes every tick even with zero trades → it depends on price feed, not just your data.

Reconciliation

  • Recon = match your internal records vs an external source (custodian / counterparty / exchange) to prove they agree.
  • Break = an unmatched or mismatched item to investigate & resolve.
  • Runs daily / intraday; ops chase breaks until cleared (T+0, aged-break reports).

How matching works

StepDetail
Match keytrade_id, else instrument+date+qty
ToleranceAllow small price/qty rounding diffs
Classifymatched / unmatched / broken

Why an engineer cares

  • Core ops engineering: the bread-and-butter of an ops dev team — ingest two feeds, match, surface & route breaks.
  • System: idempotent loaders, audit trail per break, dashboards, replay.

! Recon is fundamentally a JOIN + DIFF on imperfect data from two systems with different conventions (symbology, date/tz, sign, rounding, dupes). It's the messy-data problem in business form — see SQL sheet (cleaning / dedup / fuzzy keys) and System Design sheet (idempotent ingestion); data-quality work, not arithmetic.

Treasury, Cash & FX

Core concepts

TermOne-liner
Cash managementRight cash, right place, right currency, right time
FundingSourcing cash to meet obligations as they fall due
Margin / CollateralAssets posted to cover potential loss / counterparty exposure
Nostro / Vostro"Our"/"your" account held at another bank per currency

FX & multi-currency

  • Trade ccy = currency a deal is priced in; settlement ccy = what you actually pay/receive. They can differ.
  • Quote EUR/USD = 1.10 means 1 EUR = 1.10 USD. ! Inverting the quote, or applying it in the wrong direction, is a common bug class — silent, off by the square of the rate.
  • A rate has a timestamp + source; store both. Same pair differs by venue/snapshot.

Minor-unit traps !

CodeTrap
GBP vs GBpPounds vs pence — factor of 100 (vendor symbol convention; Bloomberg/Reuters differ)
USD2 dp — cents, not dollars
JPY0 dp — NO minor unit; ÷100 corrupts the amount
  • Minor-unit count varies per currency (ISO 4217 exponent) — never hard-code 2. Off-by-100 / wrong-scale errors result.

Engineer angle

  • Always store currency beside every amount — a bare number is meaningless.
  • Use an exact decimal type, never float (see Java/C# exact-money card; SQL currency-unit gotcha).
  • Define rounding rule + scale per currency explicitly; persist the FX rate used on conversion for audit.

Risk & Regulation (vocabulary)

Risk types (one line each)

TypeLoss from
MarketPrice / rate / FX moves against you
CreditA counterparty defaults / fails to pay

  • You'll surface these as columns/limits, not compute them — risk engines own the maths. Greeks (price sensitivities) are a quant concern; for you they're just more numbers to store and serve.

Why audit trail & immutability are non-negotiable

  • Regulators (and your own auditors) must reconstruct who did what, when, from what input data — sometimes years later.
  • ! Never silently correct a number. Don't UPDATE a booked trade. Post a new compensating / reversing entry so the original and the fix both survive.
  • This is the accept-and-reconcile / never-silently-correct pattern — see the System Design sheet. For ML-driven decisions, the AI-governance sheet covers model explainability.

How regulation constrains HOW you build

TermMeans for you
Change controlProd changes are reviewed, approved, logged — no ad-hoc hotfixes
Segregation of dutiesThe dev who writes a fix can't also approve the prod data change
Data retentionRecords kept N years; deletes are policy-driven, not casual
LineageTrace every figure back to its source inputs

Engineer angle

  • Design for append-only history + full lineage from day one — retrofitting it is brutal.
  • Prefer event logs / bitemporal tables over in-place mutation (-> SQL sheet for temporal modelling). Treat audit fields (who, when, source) as mandatory, not optional.

Financial-Systems Patterns I

Event sourcing for trades/positions

  • Trades are immutable events (append-only log); never updated in place.
  • A position is a fold (reduce) over a portfolio's trade events.
  • As-of / point-in-time queries replay events up to a timestamp.
  • Periodic snapshots: snapshot + delta = O(delta), not O(full history).
  • Corrections = new compensating events, not mutation -> full audit trail. (-> System Design: Event Sourcing & CQRS)

Idempotency in trade processing

  • Same trade event may be redelivered; dedupe on a business idempotency key (e.g. source trade id), not a transport id.
  • Persist seen keys; on replay, no-op — never double-book.
  • ! at-least-once delivery is the norm => the consumer must be idempotent; "exactly-once" is usually idempotent + dedup, not magic. (-> System Design: messaging delivery semantics)

Ordering per portfolio/account

ScopeRule
Within one portfolioapply in order (a buy then sell must not reorder)
Across portfoliosprocess in parallel — independent
  • Partition / key the stream by portfolioId so order is preserved per key, throughput scales across keys.
  • ! Global ordering kills throughput — only order where it matters. (-> System Design partitioning; Java/C# keyed-executor)

Financial-Systems Patterns II

Exact money handling

  • ! NEVER float/double for money — binary FP can't represent 0.10; rounding errors compound & break reconciliation.
  • Use exact decimal (BigDecimal/C# decimal) or store minor units as integers (cents/pence). See Java/C# cheat sheets.
  • Define rounding explicitly (e.g. HALF_EVEN) — never rely on a default.
  • Always persist the currency alongside the amount; an amount without a currency is meaningless. Money = (amount, currency, scale).

Reconciliation pipeline

StageDoes
IngestRead external file/feed (CSV, fixed-width)
NormaliseMap to internal shape; fix dates/symbols (SQL cheat sheet: cleaning)
MatchJoin on keys (trade id, date, amount) with tolerances
Classifymatched / unmatched / broken (amount or date mismatch)
ReportBreaks list for ops investigation
  • Slow batch → parallelise: chunk by date or counterparty. See System Design cheat sheet (scaling a slow batch).

Accept-and-reconcile vs reject-and-reprocess

Behaviour
Accept & reconcileStamp rate + timestamp used, proceed; fix breaks downstream
Reject & reprocessBlock until correct; unpredictable latency, can loop
  • High-throughput pricing/PnL favours accept-and-reconcile — don't block the hot path.
  • ! Audit trail is mandatory: what value, which source, when. See System Design cheat sheet (Consistency & CAP).

Reference vs market data

ReferenceMarket
Slow-changing (instruments, counterparties, calendars)High-volume, fast (prices, quotes)

  • Vendor symbol conventions differ (e.g. Bloomberg vs Reuters tickers) — normalise to an internal id at ingest.

Equities & Corporate Actions

Basics

TermOne line
shareOne unit of ownership; a holding is a signed count
share classA/B differ in votes/economics — distinct instruments
dividendCash (or stock) distribution out of profits
corporate actionIssuer event that rewrites holdings/reference data
  • ! Class A and Class B are separate instruments in the security master, not one company. Model issuer ⟶ many share-class instruments; a position is always in a specific class.

The three dates !

DateGoverns
ex-dateEntitlement cutoff + price/position adjusts here
record dateMust be holder-of-record to qualify
pay dateCash/shares actually move (ledger settle)
  • Dividend = accrue a receivable at ex-date, settle it at pay-date. The ex-date price drop is expected — don't flag it as a PnL loss.

Splits & the cardinal sin

before: 100 sh @ 50, price 50  = 5,000
apply 2-for-1 (ratio 2)
after:  200 sh @ 25, price 25  = 5,000  (unchanged)
  • Split re-denominates: qty ×N, cost basis ÷N, total value unchanged — not a gain. Reverse split is the inverse (N⟶1, price ×N).
  • ! UPDATE positions SET qty = qty*2 destroys history: breaks recon, corrupts the return series, no audit, and double-adjusts on feed re-send. Apply as a dated, idempotent event; keep as-reported and adjusted price series both.
  • A symbol change is not a string rename — canonical id persists, identifier is effective-dated, so trade/position history isn't orphaned (⟶ security master).

Fixed Income & Money Markets

A bond = a schedule generator, not a row

TermFixed at issue?
issuer / par / coupon / maturityYes — reference data
price / yieldNo — float (market data)
  • From 5 terms (issuer, par, coupon rate, frequency, maturity) you derive every cash flow: a coupon per date + par at maturity. Don't hand-key coupons.
  • Price & yield are inverse views of one instrument — store one authoritative number, derive the other. A 5% coupon bond can yield 6%.

Clean vs dirty !

settlement amount = clean + accrued = dirty
  • Screen shows clean; the buyer pays dirty. Accrued interest = coupon earned-but-unpaid since the last coupon date, paid by buyer to seller.
  • ! Settling on the clean price underpays the seller by the accrued amount. Keep clean / accrued / dirty as distinct auditable fields.

Day-count conventions (silent-bug factory)

ConvDays / year basis
30/360Every month = 30 / 360 (lies about the calendar)
ACT/360Actual days / 360 (money markets)
ACT/ACTActual / actual (many govt bonds)
  • ! Never days/365. The convention is a property of the instrument — store it, thread it into every accrual, use a library, exact decimal. A wrong convention doesn't crash; it pays the wrong amount and surfaces at recon weeks later.
  • Repo = sell-now-buy-back-later; economically a collateralised loan, not a change of ownership. Money markets = short-dated (<1yr) T-bills/CP/deposits; a T-bill is a discount instrument (issued below par, no coupon).

Derivatives: Margin, CCP & Legs

Future vs forward vs option

TermEvents it generates
futureExchange-traded; daily margin variation calls
forwardOTC equivalent; bilateral, no daily margin
optionPremium up front; exercise/expiry event; asymmetric payoff
swapTwo legs of cash flows; periodic resets on floating
  • Model an option's 4 states: call/put × holder(long, right)/writer(short, obligation). Store strike, expiry, exercise style, underlying id.
  • A floating-leg reset fixes the next period's rate — model it as a dated event, not a mutated field. A swap = two legs, each its own schedule.

Margin & collateral

TermMeans
initial marginUpfront good-faith deposit
variation marginDaily mark-to-market top-up/return
collateralAssets posted to cover exposure
  • Your system tracks required vs posted margin and generates margin calls — a daily flow, exact money, per counterparty/CCP.
  • ! Summing swap notionals and labelling it "portfolio value" is a classic bug — a $10m notional swap can be worth ~$0. Notional drives exposure calc, not value.
  • A CCP (central counterparty) novates the trade: it becomes buyer to every seller and vice versa, multilaterally nets, and guarantees — so you now store the CCP as counterparty and its margin schedule (⟶ Clearing).

Orders, Order Types & FIX

Order types

TypeBehaviour
marketExecute now at best available price
limitOnly at price X or better; may rest unfilled
stopBecomes a market/limit order when price crosses a trigger
IOC / FOKImmediate-or-cancel / fill-or-kill (no resting)
  • A limit order can rest on the book unfilled — so an order is never "one row that flips to FILLED"; it has a life of partial fills.

One order ⟶ many fills ⟶ one trade

  • Model orders / executions / fills as separate parent/child rows. Avg exec price = Σ(qty×price)÷Σqty over the fills — computed, not stored raw.
  • ! Storing an order as one row whose status flips PENDING⟶FILLED loses the partial-fill history and the audit trail. Model state as an event stream; amend/cancel are new events, not overwrites.

FIX protocol

  • FIX = the standard messaging protocol for order entry & execution reports (tag=value fields). Execution reports stream back as an order progresses.
  • Ingest execution reports idempotently — dedupe on the exec id (a business key), because the feed is at-least-once and will redeliver.

Clearing, Settlement & DVP

Post-trade stages (distinct, ordered)

StageMoves money?
confirmationNo — both agree the economics
clearingNo — CCP nets & guarantees
settlementYes — cash vs securities (DVP)
  • Agree ⟶ de-risk & net ⟶ exchange. Each is an append-only state transition on the immutable trade; a stuck trade's exact stage must be queryable.

DVP & netting

  • DVP (delivery-versus-payment): the cash leg and securities leg commit together or neither — distributed atomicity in business form. Eliminates principal / Herstatt risk (you pay and don't receive). Not two fire-and-forget writes.
  • Netting: collapse many gross obligations to one net per counterparty (owe 100, owed 70 ⟶ settle 30). Net is a derived fold over gross — keep gross for audit, net for what settles.

FAIL vs BREAK !

TermIs a...Goes to
FAILReal-world settlement event (a leg didn't move)Settlements/ops
BREAKData disagreement between two systems' recordsRecon/data
  • ! Different entities, different desks. A fail is a status on a trade (settlement state machine); a break is an output of reconciliation. Conflating them misroutes alerts.
  • ! T+2 uses business days — needs a holiday calendar, never + INTERVAL '2 days'.

Ledgers & Double-Entry

Double-entry as a checksum

pay 100 to Broker X:
  cash account     -100
  broker payable   +100    (debits == credits)
  • Every movement posts a debit + an equal credit; whole-ledger sum is always zero. Money never appears/vanishes — it moves between accounts.
  • Gives you a built-in consistency check (debits ≠ credits ⟶ bug), no money leaks, and a natural audit trail with append-only entries.
  • ! A single-sided UPDATE accounts SET balance = balance - :amt is exactly the anti-pattern double-entry prevents — no counter-entry, no trail, races on concurrent writes. Balance = sum of an account's entries, not a mutable field.

Money = (amount, currency, scale)

{"amount":1050,"currency":"GBP","scale":2}  // £10.50
{"amount":1050,"currency":"JPY","scale":0}  // ¥1050 — /100 corrupts it
  • ! Never float/double: 0.10 has no exact binary form; errors compound and break nostro recon — and you can't tell a real break from FP drift. Use exact decimal (BigDecimal/decimal/NUMERIC) or integer minor units.
  • Currency is a mandatory non-null companion of every amount. Derive scale from ISO 4217 exponent (USD 2, JPY 0, some 3) — never hard-code 2. Define rounding explicitly (e.g. HALF_EVEN).

Payment Rails & Fintech

Rails compared

RailWhat / speed
SWIFTInterbank messaging — instructions, not money; cross-border
ACHDomestic batched bulk transfer; slow (1+ day), cheap
wireHigh-value, individually processed; (near-)real-time, final
  • ! SWIFT moves messages, not money — cash actually moves via correspondent/nostro relationships. A payment isn't "done" on message send: instructed ⟶ in-transit ⟶ settled/failed. Confirm settlement, reconcile via nostro recon.

Idempotent payments

  • Delivery is at-least-once ⟶ processing the same instruction twice = a duplicate payment (real money out, hard to claw back). Dedupe on an originator-controlled business key, not a transport id.
  • Persist seen keys (unique constraint); check-and-execute must be atomic so concurrent retries can't both slip through; on repeat, no-op & return the original result.

Nostro / vostro

  • Nostro = "our" account held at another bank (per currency); vostro = "your" account we hold for you. Nostro recon matches expected movements vs the bank statement — the recon JOIN+DIFF pattern applied to cash.
