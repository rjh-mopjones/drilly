Architecture — masterless ring

flowchart LR C["client"] --> CO["coordinator (any node)"] CO --> R1["replica 1"] CO --> R2["replica 2"] CO --> R3["replica 3"] R1 -. gossip .- R2 R2 -. gossip .- R3

Peer-to-peer ring — every node equal, no leader / no SPOF. Nodes exchange membership + state via gossip (1×/s, ~3 peers). Any node can coordinate a request and forward to the RF replicas that own the token.

  • AP in CAP with tunable consistency — favours availability + partition tolerance; you dial correctness per query via CL.
  • Write-optimized LSM tree; linear horizontal scale — add nodes for more throughput/storage, no re-sharding downtime.
  • Built for multi-DC, always-on, huge write volume. No joins, no ad-hoc queries, eventual consistency by default.

Partitioning & the Token Ring

  • Data placed by consistent hashing: Murmur3(partition key) → 64-bit token → owning node (first replica) + next RF−1 clockwise.
  • Vnodes (default num_tokens 16): each node owns many small ranges → even balance + parallel, fast streaming on rebuild/bootstrap.
  • Partition key choice = load balance. Low-cardinality or "celebrity" key (e.g. country, a viral user) → hot partition, one node saturated !
  • Consistent hashing means adding/removing a node reshuffles only neighbouring ranges, not the whole dataset. Run nodetool cleanup on old owners after.
  • The token is derived from the partition key only — clustering columns never affect placement.
  • Murmur3 token space is the signed 64-bit range (−2^63 … 2^63−1) arranged as a ring; each vnode owns a contiguous arc, ownership wraps past the top back to the bottom.
  • Fewer vnodes (16) + allocate_tokens_for_keyspace beats the old random-256 default: random token selection with few vnodes skews ownership; the allocation algorithm minimizes imbalance for the RF.

Replication & Snitches

  • RF = copies per partition (3 typical). Replicas = token owner + next nodes clockwise, skipping to satisfy topology rules.
  • NetworkTopologyStrategy (production): RF per DC, places replicas on distinct racks to survive a rack failure. SimpleStrategy = single-DC dev only !
  • A snitch (GossipingPropertyFileSnitch standard) tells the cluster each node's DC/rack so replicas + routing are topology-aware.
  • RF is a keyspace property; changing it requires a full repair to stream the new copies.
CREATE KEYSPACE app WITH replication =
 {'class':'NetworkTopologyStrategy','dc1':3,'dc2':3}
 AND durable_writes = true;

Tunable Consistency (CL)

CLmeaning
ANYwrite only; a hint counts (weakest, may be unreadable) !
ONE / LOCAL_ONE1 replica / 1 in local DC — fast, may be stale
QUORUMmajority of all replicas across DCs = ⌊RF/2⌋+1
LOCAL_QUORUMmajority in local DC — multi-DC workhorse, no cross-DC latency
EACH_QUORUMquorum in every DC (write only)
ALLevery replica — zero availability slack !
SERIAL / LOCAL_SERIALPaxos read for LWT (linearizable)
  • Strong / read-your-writes ⇔ R + W > RF. RF3, W=QUORUM(2), R=QUORUM(2): 2+2>3 ✓ !
  • RF3 + QUORUM tolerates 1 node down and still reads/writes. RF3 + ALL tolerates 0.
  • Conflicts resolved by last-write-wins on the cell timestamp → clock skew across nodes can silently drop a "newer" write ! Keep NTP tight.
  • CL is per request (set in the driver), not a schema property — different queries can use different CLs.
  • Availability math (RF3): QUORUM=2 → survives 1 replica down; ONE → survives 2 down but risks stale; ALL → survives 0. RF5 + QUORUM(3) survives 2 down — raise RF, not CL, for more slack.
  • A CL is a threshold, not a target: at CL=ONE the write still propagates to all RF replicas asynchronously; ONE just means the coordinator ACKs after the first success.

CQL & the Primary Key

CREATE TABLE users_by_id (
  id uuid PRIMARY KEY, email text, name text);

CREATE TABLE msgs_by_conv (
  conv_id uuid, bucket date, ts timeuuid,
  sender text, body text,
  PRIMARY KEY ((conv_id, bucket), ts)
) WITH CLUSTERING ORDER BY (ts DESC);

SELECT * FROM msgs_by_conv
 WHERE conv_id=? AND bucket=? LIMIT 50;   -- fast
  • PK = partition key + clustering columns. First paren group = partition key (WHICH node); the rest = clustering (ORDER + uniqueness within the partition). ((a,b),c) = composite partition key.
  • Query must supply the whole partition key (equality), then clustering columns left-to-right in order; range allowed only on the last one used.
  • INSERT is an UPSERT — no existence check, no error on overwrite ! Same PK = last-write-wins.
  • ALLOW FILTERING = red flag: coordinator scans + filters rows it read, unpredictable + O(cluster). Remodel instead !

Query-First Data Modeling

  • Start from access patterns, never from entities/ER diagrams. List every query first, then design a table per query.
  • Denormalize aggressively; one table per query. Disk is cheap, a slow read at scale is not.
  • No joins, no ad-hoc queries, no GROUP BY at scale. Duplicate data across tables and keep them in sync on write (app logic or a single-partition logged batch).
  • Pick the partition key for even distribution; pick clustering columns for the order the query needs (and to make rows unique).
  • Need another lookup (by email)? → build users_by_email, not a secondary index !
  • Estimate partition size before shipping: rows-per-partition × row size. Bound it.

  • Target: partitions ≲ 100 MB and ≲ 100k rows (hard limit 2 billion cells/partition, but pain starts far earlier).
  • Bucketing = composite partition key with a time/hash component, e.g. ((sensor_id, day), ts) — bounds size + spreads load, at the cost of the client iterating buckets.
  • Check with nodetool tablehistograms (partition-size percentiles) + compaction warnings in logs.

Write Path — why writes are fast

flowchart LR W["write"] --> CL["commit log (disk, durable)"] W --> MT["memtable (RAM, sorted)"] MT -->|flush| SS["immutable SSTable"]
  • Per replica, two cheap ops: sequential append to commit log (durability) + in-memory memtable update. ACK once CL replicas confirm. No random IO.
  • No read-before-write, no in-place update, no locks — that is the whole speed story. An update/delete is just a new timestamped cell.
  • Memtable fills → flush to a new immutable SSTable → commit-log segment recycled.
  • Down replica → coordinator stores a hinted handoff and replays it when the node returns (up to max_hint_window, default 3h).
  • commitlog_sync: periodic (batched fsync, default, small data-loss window) vs batch (fsync before ACK, safer, slower) !

Read Path — reconstruction

A read is a merge, not a lookup: the row's cells may be smeared across the memtable + many SSTables, with tombstones masking deletes. Newest cell (by timestamp) wins.

  • Bloom filter per SSTable: "might this key be here?" — no false negatives; lets a replica skip SSTables that definitely lack the key.
  • Key cache → offset for hot keys; partition summary/index → byte offset in the SSTable; row cache = whole rows (great for tiny hot rows, deadly on wide partitions !).
  • Coordinator does 1 full data read + digest reads from others (per CL); mismatch → read repair writes newest back to stale replicas.
  • Speculative retry sends an extra read to another replica if the first is slow — protects p99.
  • read_repair table option: BLOCKING (default — coordinator waits for the repair write before returning, so CL is honored) vs NONE (skip). Digest mismatch → full data reads from the disagreeing replicas to reconcile.
  • SSTables-per-read is the #1 read-latency lever; tombstones + too many SSTables turn a cheap read into a timeout !

Storage Engine: SSTables & Compaction

LSM tree: memtable flushes → immutable, sorted SSTables; never edited in place. Compaction merges them (keep newest cell, drop shadowed/expired data), cutting SSTables-per-read + reclaiming disk.

StrategyUse / trade
STCS (default)write-heavy; merges similar-size SSTables. Read + space amp; needs ~2× table size headroom !
LCSread/update-heavy; ~1 SSTable per level → bounded reads. High write amp
TWCStime-series + TTL — buckets by time window, drops whole expired windows cheaply. No deletes/updates of old data !
UCS (5.0)unified, tunable STCS↔LCS via scaling params
  • Amplification trade — pick 2 of 3: write / read / space. STCS optimizes writes; LCS optimizes reads; TWCS optimizes TTL data.
  • Don't run manual major compaction on STCS: one giant SSTable that then won't compact and hoards tombstones !
  • Watch pending compactions (nodetool compactionstats) — a climbing backlog degrades reads.
  • Read amp = SSTables touched per read; write amp = times a byte is rewritten by compaction; space amp = on-disk size ÷ live size. STCS: low write / high read+space amp. LCS: low read+space / high write amp.
  • Compaction runs in the background on concurrent_compactors threads, throttled by compaction_throughput_mb_per_sec; each SSTable ships a partition index + bloom filter alongside Data.db.

Tombstones · Deletes · TTL

  • A delete is a write — it writes a tombstone that masks older cells until compaction physically removes it. Reads must still read past tombstones.
  • gc_grace_seconds (default 10 days) keeps tombstones so a repair can propagate the delete to every replica before it's purged !
  • Repair within gc_grace or deletes resurrect ("zombie" data): a replica that missed the delete + never got repaired re-propagates the old value !
  • Too many tombstones scanned per read → slow reads, then TombstoneOverwhelmingException (aborts at 100k). The queue / delete-then-read pattern is an anti-pattern !
  • TTL auto-expires cells (→ becomes a tombstone → compacted away). Prefer TTL + TWCS over explicit deletes for anything time-bounded.
  • Range/partition/row/cell tombstones exist; a range delete is cheaper than deleting many cells.
  • Hidden tombstone sources: inserting null writes a tombstone; a TTL expiry becomes one; overwriting a collection wholesale tombstones the old collection then rewrites it !
  • Warn threshold tombstone_warn_threshold (1000) logs; tombstone_failure_threshold (100k) aborts the query — tune the query/model, not just the threshold.

Repair & Anti-Entropy

  • Replicas drift; 3 mechanisms reconcile: hinted handoff (brief outages), read repair (only data actually read), nodetool repair (everything — the real backstop).
  • nodetool repair builds Merkle trees per range, compares them across replicas, and streams only the differing ranges.
  • Must repair every node within gc_grace_seconds or risk zombies. Use Cassandra Reaper to schedule + throttle so it doesn't crush the cluster !
  • Full vs incremental (marks repaired SSTables so they're skipped next time); -pr (primary range) run on every node avoids redundant work.
  • Hints alone are not a substitute for repair — they expire and can be lost.
  • Repair cadence < gc_grace_seconds, always — that's the operational contract. A node down longer than gc_grace must be repaired before it serves, or it resurrects deletes.

Types · Collections · Indexing

  • Collections (set / map / list) — keep small (whole collection read at once); list append/prepend can need read-before-write ! Frozen = stored as one blob, immutable.
  • UDTs group related fields; static columns = one value shared by all rows in a partition.
  • Counters = special column, distributed increment — approximate, not safe for exact accounting (retries can double-count) !
  • Secondary index (2i) = local per-node index; a query scatter-gathers all nodes → only for low-cardinality, already-restricted queries; a separate table is usually better !
  • SAI (Storage-Attached Index, 5.0) = the modern index — multiple columns, range/text, lower overhead; still not a substitute for good partition design. Adds vector/ANN search.
  • Old materialized views exist but are flagged experimental — hand-roll a second table + keep it in sync.
  • timeuuid = time-ordered UUID (v1): unique + sortable, ideal clustering key for feeds; now(), minTimeuuid()/maxTimeuuid() for range bounds.
  • Frozen vs non-frozen: a frozen collection/UDT is one opaque blob (rewrite whole to change); non-frozen allows per-element updates but each element is its own cell (more overhead, tombstones on overwrite).

LWT & Batches

Cassandra has no general multi-row ACID by default — writes are last-write-wins, no locks. Two narrow bolt-ons:

-- LWT: linearizable compare-and-set (Paxos)
INSERT INTO users_by_name (username, id)
VALUES ('alice', ?) IF NOT EXISTS;      -- ~4x latency !

UPDATE accounts SET status='closed'
WHERE id=? IF status='active';          -- [applied]=true/false
  • LWT = conditional write via Paxos (SERIAL/LOCAL_SERIAL): ~4× latency, low throughput. Ration it — uniqueness, optimistic concurrency; never as a general lock !
  • Logged batch = atomicity (all-or-nothing via batchlog), not isolation, not speed. Good use: keep a few same-partition denormalized tables in sync.
  • Multi-partition batch for bulk = anti-pattern: overloads one coordinator, slower than parallel async token-aware writes !
  • Accord (5.0) = general leaderless multi-partition transactions — the real "transaction" answer.

Time-Series & Modeling Patterns

  • Time-series: partition by (entity, time_bucket), cluster by ts DESC, set a TTL, use TWCS. Newest-first reads are a cheap key-order prefix scan.
  • Bucketing keeps partitions bounded; client walks buckets (today, yesterday…) for a time range.
  • Latest-N / feed: cluster DESC + LIMIT N — data is pre-sorted on disk, no sort at read.
  • Lookup by two keys (id and email) → two tables (x_by_id, x_by_email), written together.
  • Leaderboard / top-N is hard — Cassandra can't sort across partitions; bucket + merge client-side, or use a different store.
  • Model the write to be a single-partition upsert whenever possible.

Multi-DC · Availability · Failure

  • Multi-DC is a headline feature: NetworkTopologyStrategy with RF per DC gives geo-locality + DR. Apps read/write LOCAL_QUORUM to stay in-region (no cross-DC latency).
  • Cross-DC replication is async — a write ACKed at LOCAL_QUORUM propagates to the other DC in the background.
  • Node states via nodetool status: UN up/normal, DN down/normal, UJ joining, UL leaving. A DN replica is covered by hints then repair.
  • Survives node/rack/whole-DC loss if RF + CL leave a quorum reachable. RF3 per DC + LOCAL_QUORUM survives 1 node/DC down.
  • Failure detection is gossip + phi-accrual — a node flapping (long GC pause) gets marked down, dropping mutations !

Cluster Ops — nodetool

nodetool status              # UN/DN, ownership, load

nodetool tablestats ks.tbl   # SSTables, reads, tombstones
nodetool tablehistograms     # partition-size / latency %iles
nodetool compactionstats     # pending compactions

nodetool decommission        # stream data off, remove node
  • Add node → auto-bootstrap streams its ranges in → run cleanup on old owners. Backup = snapshot + copy SSTables off-node.
  • Replace a dead node with -Dcassandra.replace_address; never just re-add with the same tokens.

Performance & Monitoring

  • Watch p99 / p999 read+write latency, SSTables-per-read, tombstones-per-read, pending compactions, dropped mutations, hint counts.
  • JVM heap ~8–16 GB with G1GC; a long stop-the-world GC pause makes a node flap → dropped writes + read timeouts !
  • Key cache = generally safe win; row cache = dangerous on wide partitions (caches whole partitions) !
  • Throttle compaction/streaming so background work doesn't starve live queries; keep <70% disk (STCS needs headroom).
  • Use TRACING ON in cqlsh to see exactly which replicas + SSTables a slow query touched.
  • Token-aware, DC-aware driver policy so clients hit a replica directly (1 hop, not 2).
  • Slow-reads triage order: (1) GC pauses (gc.log, promotion failures) → (2) wide partition (tablehistograms max partition bytes) → (3) tombstones/read (tablestats) → (4) SSTables/read + compaction backlog → (5) cold caches. Usually one of the first four.
  • Expose metrics via JMX → Prometheus + Grafana; alert on p99 latency, dropped mutations, pending compactions, and hint accumulation, not just node up/down.

Node Lifecycle & Streaming

Masterless ⇒ ops are node-by-node. Add/remove/replace/repair all reduce to nodes streaming SSTables to each other; watch nodetool netstats and let each finish before the next.

ActionHow
add nodeauto_bootstrap: joins UJ, streams its ranges, → UN. Then cleanup old owners !
remove livedecommission on that node — re-streams its data out first (preferred)
remove deadremovenode <id> from a healthy node — rebuilds its ranges elsewhere
stuck/deadassassinate = force out, no streaming → under-replicated, repair after !
replace dead-Dcassandra.replace_address_first_boot=<ip> — assumes the dead tokens
  • Add one node at a time; never bootstrap two at once — token allocation + streaming stay sane.
  • Forgetting cleanup after an add = old nodes keep ranges they no longer own, disks stay full, "the add didn't help" !
  • Replace a dead node via replace_address, not a fresh join — a fresh join leaves the dead ranges under-replicated.

Gossip · Seeds · Failure Detection

  • Gossip: every node picks ~3 peers each second and exchanges heartbeat + state (membership, load, schema version, tokens) — epidemic spread, converges in O(log n) rounds. No central registry.
  • Seed = a well-known bootstrap contact point a joining node gossips with to learn the ring. Not a master, not a data role.
  • Never add a new node as a seed — seeds skip auto-bootstrap streaming, so it would serve incomplete data. Bootstrap as non-seed, then optionally promote !
  • Keep a small fixed set (2–3/DC, across racks). "All nodes are seeds for resilience" actively breaks adding capacity !
  • Phi-accrual failure detector: not a hard timeout — computes a probability (φ) that a node is down from the recent heartbeat-arrival distribution, adapting to network jitter. A long GC pause spikes φ → node marked down → coordinators drop its mutations !
  • States in nodetool status: UN up/normal, DN down, UJ joining, UL leaving, UM moving.

Backup · Restore · PITR

nodetool snapshot -t nightly my_ks   # instant, hard-links SSTables
nodetool clearsnapshot               # drop old snaps (unpin SSTables)
sstableloader -d host ./sstables     # bulk restore / stream in
  • Snapshot = hard-links to the immutable SSTables → instant, near-zero space at creation. Per-node: snapshot all nodes together for a cluster-consistent image.
  • Hard-links sit on the same disk — copy them off-node or a disk loss takes the "backup" too !
  • Incremental backups hard-link every new SSTable as it flushes → capture deltas between snapshots.
  • PITR = snapshot (base image at T) + commitlog archiving (every mutation after T); restore snapshot, replay archived commitlogs to the target timestamp.
  • Snapshots pin SSTables even after compaction would delete them — clearsnapshot to reclaim. A backup you've never restored is a hypothesis, not a backup.

Rolling Restart & Upgrade

  • Masterless + RF>1 ⇒ take one node at a time offline, cluster keeps serving. Per node: drain → stop → change → start → wait for UN + gossip settle → next.
  • Always drain first (flush memtables + stop writes) so restart is clean — no long commitlog replay !
  • Restarting too fast (next before the previous rejoins) can drop below the CL's required replicas → errors/unavailability !
  • Major upgrade: mixed-version cluster is OK briefly — do not repair, add/remove nodes, or change schema during the window. After all nodes upgraded, run nodetool upgradesstables to rewrite to the new format.

Worked Example — message feed

Access patterns first: (1) a conversation's messages newest-first, paged; (2) a message by id; (3) a user's conversations. One table per pattern:

CREATE TABLE messages_by_conv (
  conv_id uuid, bucket text,        -- '2026-07' bounds partition
  msg_id timeuuid,                  -- time-order + uniqueness
  sender_id uuid, sender_name text, -- denormalized, no user join
  body text,
  PRIMARY KEY ((conv_id, bucket), msg_id)
) WITH CLUSTERING ORDER BY (msg_id DESC);
  • Partition (conv_id, bucket): groups the chat, month bucket caps a busy conversation's partition growth.
  • Clustering msg_id DESC (timeuuid): newest-first read is a cheap key-order prefix scan; also breaks ties.
  • sender_name denormalized so rendering needs no lookup — the "join" happened at write time.
  • On send, fan out a write to messages_by_conv, messages_by_id, conversations_by_user. Every read = single-partition, pre-sorted.
  • Change to a key value (e.g. email in users_by_email) ⇒ INSERT new + DELETE old, not an in-place UPDATE !

Driver & Client Tuning

  • Token-aware + DC-aware load balancing: the driver hashes the partition key and sends the request straight to a replica in the local DC → 1 hop, not 2. The single biggest client win.
  • Prepared statements: parse once, bind many — saves coordinator CPU, avoids CQL-injection, and carries routing info for token-awareness. Prepare at startup, reuse.
  • Paging (fetch_size, default 5000): large result sets stream in pages via an opaque paging state — never pull an unbounded partition into memory at once !
  • Async + bounded concurrency for bulk: fire many single-partition writes in parallel (token-aware) — far faster than a multi-partition batch on one coordinator.
  • Retry & speculative execution: idempotent-only retries; speculative retry issues a second read to another replica if the first is slow → guards p99. Mark statements setIdempotent(true) deliberately.
  • Set CL per statement in the driver (LOCAL_QUORUM default), plus connect/read timeouts sized above your compaction-worst-case.

CAP · PACELC · Where Cassandra Sits

  • CAP: during a partition Cassandra chooses availability — an AP store. Replicas keep taking reads/writes and reconcile later (LWW + repair), rather than refusing to serve.
  • PACELC: Partition → Availability; Else (normal ops) → favors Latency over Consistency (PA/EL). Contrast a CP store (e.g. HBase/Spanner-style) that sacrifices availability to stay consistent.
  • "AP" is the default, not a ceiling — you dial correctness per query with CL. QUORUM read + QUORUM write with R+W>RF gives linearizable-ish read-your-writes on a per-key basis; LWT (Paxos) gives true linearizable compare-and-set when you need it.
  • The cost of availability: no cross-partition transactions by default, eventual convergence, and clock-dependent conflict resolution (LWW) — keep NTP tight !
  • Accord (5.0) adds genuine leaderless strict-serializable multi-partition transactions without giving up the masterless model.

★ Data-Model Review Checklist

  • ☐ Each table designed for a specific query (query-first, denormalized, one table per pattern).
  • ☐ Partition key gives even distribution — no hot / celebrity / low-cardinality key.
  • ☐ Partition size bounded via bucketing — ≲ 100 MB / ≲ 100k rows.
  • ☐ Queries supply the whole partition key + clustering columns in order; clustering gives the needed sort.
  • ☐ No ALLOW FILTERING; extra lookups = extra tables (or SAI), not 2i.
  • ☐ Right consistency: LOCAL_QUORUM default; R + W > RF where strong reads are needed.
  • ☐ Tombstone hygiene — TTL + TWCS; no delete-heavy / queue patterns.
  • ☐ No multi-partition batch for bulk; LWT only where truly needed.
  • ☐ Repair scheduled within gc_grace (Reaper); NTP tight (LWW depends on clocks).
  • ☐ Counters not used for exact accounting; collections kept small.

☐ Troubleshooting Playbook

One node overloaded

  • ☐ Hot partition → higher-cardinality / composite partition key, or add a hash bucket.

Reads timing out (tombstones)

  • ☐ TombstoneOverwhelmingException / delete-heavy → TTL + TWCS, remodel to avoid deletes; check tablestats tombstones/read.

High p99 read latency

  • ☐ Too many SSTables / compaction backlog / wide partition / GC pause → fix compaction strategy, partition design, heap; use TRACING.

Deleted data came back

  • ☐ Zombie: didn't repair within gc_grace → run repair; ensure Reaper schedule; raise CL (R+W>RF) for stale reads.

Query needs ALLOW FILTERING

  • ☐ Redesign a table around that exact query (or add SAI) — don't ship the filter.

Bulk-load batch slow

  • ☐ Multi-partition batch → parallel async, token-aware writes; batches only for same-partition atomicity.

Node flapping / dropped mutations

  • ☐ Long GC pause or overload → tune heap/G1GC, throttle compaction, check for wide partitions.
