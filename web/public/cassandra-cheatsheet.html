Architecture

flowchart LR C["client"] --> CO["coordinator (any node)"] CO --> R1["replica 1"] CO --> R2["replica 2"] CO --> R3["replica 3"] R1 -. gossip .- R2 R2 -. gossip .- R3

Masterless peer-to-peer ring — every node equal, no leader/SPOF. Nodes gossip membership. Any node coordinates a request & forwards to the RF replicas. AP in CAP with tunable consistency; write-optimized (LSM).

Partitioning & the Ring

  • Data placed by consistent hashing on a token ring: hash(partition key) → token → owning node(s) (Murmur3).
  • Vnodes: each node owns many small token ranges → balance + fast rebuild/streaming.
  • The partition key choice = load balance. Low-cardinality / celebrity key → hot partition !
  • Adding a node reshuffles only neighbouring ranges (run nodetool cleanup after).

Replication

  • RF = copies per partition (3 typical); replicas = the token owner + next nodes clockwise.
  • NetworkTopologyStrategy (production): RF per DC, replicas on distinct racks. SimpleStrategy = dev only !
  • A snitch tells nodes the DC/rack topology.
CREATE KEYSPACE app WITH replication =
 {'class':'NetworkTopologyStrategy','dc1':3,'dc2':3};

Tunable Consistency

CLmeaning
ONE / LOCAL_ONE1 replica (fast, may be stale)
QUORUMmajority of ALL replicas
LOCAL_QUORUMmajority in local DC (multi-DC workhorse)
ALLevery replica (no availability slack)
  • Strong (read-your-writes) ⇔ R + W > RF — e.g. RF3, W=QUORUM(2), R=QUORUM(2): 2+2>3 ✓ !
  • RF3 + QUORUM tolerates 1 node down. Conflicts = last-write-wins by timestamp (clock skew risk).

CQL & Primary Key

CREATE TABLE users_by_id (
  id uuid PRIMARY KEY, email text, name text);

CREATE TABLE messages_by_conv (
  conv_id uuid, bucket date, ts timeuuid,
  sender text, body text,
  PRIMARY KEY ((conv_id, bucket), ts)
) WITH CLUSTERING ORDER BY (ts DESC);
SELECT * FROM messages_by_conv
 WHERE conv_id=? AND bucket=? LIMIT 50;
  • PK = partition key + clustering columns. Partition key = WHICH node; clustering = ORDER within the partition. ((a,b),c) = composite partition key.
  • Query by the WHOLE partition key + clustering columns in order; INSERT is an UPSERT (no existence check) !
  • ALLOW FILTERING = red flag (full scan) — remodel instead !

Query-First Modeling

  • Start from access patterns, not entities. Denormalize; one table per query.
  • No joins, no ad-hoc queries. Duplicate data across tables; keep in sync on write (batch/app).
  • Choose partition key for even distribution, clustering for order/uniqueness.
  • Need another lookup (by email)? → a second table users_by_email, not a secondary index !
  • Validate partition size BEFORE shipping.

Target: partitions ≲100MB / ≲100k rows (2B-cell hard limit). Even spread across the ring.

Write & Read Paths

flowchart LR W["write"] --> CL["commit log (durable)"] W --> MT["memtable (RAM)"] MT -->|flush| SS["immutable SSTable"]
  • Write = append to commit log + memtable → ACK at CL → later flush to SSTable. Very fast, no read-before-write. Down replica → hinted handoff.
  • Read merges the memtable + many SSTables (newest cell wins), using bloom filters + partition index + caches; read repair fixes stale replicas. Many SSTables/tombstones → slow reads !

SSTables & Compaction

LSM tree: immutable SSTables merged in the background to discard overwrites/expired data & cut read count.

StrategyUse
STCS (default)write-heavy; read/space amp; needs 2× disk
LCSread/update-heavy; ~1 SSTable/level; high write amp
TWCStime-series + TTL — drop whole windows cheaply
UCS (5.0)unified, tunable STCS↔LCS

Throttle compaction so it doesn't starve queries; watch pending compactions.

Tombstones · Deletes · TTL

  • A delete is a write — it writes a tombstone masking old data until compaction removes it.
  • gc_grace_seconds (default 10d) keeps tombstones so a repair can propagate the delete to all replicas !
  • Run repair within gc_grace or deleted data can resurrect (zombies) !
  • Too many tombstones → slow reads / TombstoneOverwhelmingException (100k abort). The queue pattern is an anti-pattern !
  • TTL auto-expires (→ tombstone → compacted). Prefer TTL+TWCS over explicit deletes.

Repair & Anti-Entropy

  • Replicas drift → 3 mechanisms fix them: hinted handoff (brief outages), read repair (only read data), nodetool repair (everything).
  • nodetool repair uses Merkle trees to compare ranges & stream only differences.
  • Must repair every node within gc_grace_seconds — use Cassandra Reaper to schedule/throttle !
  • Full vs incremental; -pr primary-range to avoid redundant work.

Types · Indexing · LWT · Batch

  • Collections (set/map/list — keep small; list has read-before-write) · UDTs · counters (approximate, not exact accounting) · static columns.
  • Secondary index (2i) = local, scatter-gather across nodes — only for restricted/low-card queries; often a separate table is better ! SAI (5.0) is the modern index (+ vector/ANN).
  • LWT (IF NOT EXISTS / CAS) = linearizable via Paxos → ~4× latency; use rarely (uniqueness) !
  • Batch ≠ performance. Logged batch = atomicity across a FEW related tables; a multi-partition batch for bulk load overloads the coordinator & is SLOWER than parallel async writes !

Ops & Tuning

nodetool status          # UN/DN, ownership, load
nodetool tablestats ks.tbl   tablehistograms
nodetool compactionstats     tpstats   # dropped/pending
nodetool repair -pr          nodetool cleanup
nodetool snapshot            nodetool decommission
  • Add node → bootstraps & streams → cleanup old nodes. Backups = snapshot (SSTable hard-links) + off-node copy.
  • JVM heap ~8–16GB, G1GC; long GC pause → node flaps & dropped mutations !
  • Watch p99/p999 latency, SSTables/read, tombstones/read, pending compactions, hints. Key cache good; row cache dangerous.

☐ Data-Model Review Checklist

  • ☐ Table designed for a specific query (query-first, denormalized).
  • ☐ Partition key gives even distribution (no hot/celebrity key).
  • ☐ Partition size bounded (bucketing) — ≲100MB / ≲100k rows.
  • ☐ Clustering columns give the needed order; queries hit the WHOLE partition key + key-order prefix.
  • ☐ No ALLOW FILTERING; extra lookups = extra tables (or SAI), not 2i.
  • ☐ Right consistency (LOCAL_QUORUM default; R+W>RF where you need strong).
  • ☐ Tombstone hygiene (TTL+TWCS, avoid delete-heavy/queue patterns).
  • ☐ No multi-partition batch for bulk; LWT only where truly needed.
  • ☐ Repair scheduled within gc_grace (Reaper).

★ Troubleshooting Playbook

One node overloaded

  • ☐ Hot partition → higher-cardinality/composite partition key or bucket.

Reads timing out (tombstones)

  • ☐ TombstoneOverwhelmingException / delete-heavy → TTL+TWCS, remodel to avoid deletes.

High p99 read latency

  • ☐ Too many SSTables / compaction backlog / wide partition / GC → compaction strategy, partition design, heap.

Deleted data came back

  • ☐ Zombie: didn't repair within gc_grace → run repair; raise CLs (R+W>RF) for stale reads.

Query needs ALLOW FILTERING

  • ☐ Redesign a table around that query (or SAI).

Bulk-load batch slow

  • ☐ Multi-partition batch → parallel async token-aware writes.
