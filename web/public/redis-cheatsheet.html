Architecture

  • Redis = in-memory key–value data-structure server (rich types, not a dumb blob cache).
  • Single-threaded command execution → each command is atomic; but one slow O(N) command blocks everyone !
  • Fast: all in RAM, mostly O(1), no locks, RESP protocol, epoll. (6+ adds I/O threads for networking only.)
  • Memory-bound (data must fit in RAM). Use for cache / sessions / rate-limit / leaderboard / queue / pub-sub — NOT a primary store for data > RAM or complex queries.

Keys · TTL · Eviction

SET user:1 alice EX 3600     # value + TTL
EXPIRE k 60    TTL k    PERSIST k
  • Namespaced keys type:id:field. Expiry = lazy (on access) + active (sampling).
  • maxmemory + eviction policy: noeviction (default — errors on write!) · allkeys-lru/lfu · volatile-* (only keys with a TTL) !
  • Eviction (memory pressure) ≠ expiry (TTL elapsed). For a cache: allkeys-lru/lfu + TTLs; noeviction + no TTLs → OOM !

  • In-memory ≠ non-durable. Hybrid RDB+AOF is the recommended default.
  • BGSAVE/AOF-rewrite fork → latency spike + COW memory on write-heavy loads ! Back up the RDB off-box.

Single-Thread Footguns

  • Never KEYS * in prod — O(N), freezes the server → use SCAN (cursor) !
  • Beware big-key O(N): SMEMBERS/HGETALL/LRANGE 0 -1/SORT on huge keys; DEL big key → UNLINK (async).
  • Pipelining: batch commands to amortize RTT (throughput, not atomicity).
  • Spot slow commands with SLOWLOG GET; latency from fork/swap/big-keys.

Pub/Sub vs Streams · Txn · Lua

  • Pub/Sub = fire-and-forget, at-most-once, no persistence (no subscriber → lost) ! Streams = durable log + consumer groups + ack + replay.
  • MULTI/EXEC = queued + atomic, but NO rollback on a runtime error ! WATCH = optimistic CAS (EXEC aborts if a watched key changed → retry).
  • Lua (EVAL/EVALSHA) runs atomically (blocks the server) — the way to do multi-step read-modify-write. Keep scripts short. Redis 7 Functions persist & replicate.

Caching Patterns

  • Cache-aside (lazy): miss → load DB → SET key val EX ttl → return; hit → return. The default.
  • Write-through (write cache+DB together) · write-behind (async flush). Always set a TTL.
  • Invalidation: TTL vs delete-on-write vs event-driven. "Two hard problems…"
  • Stampede/thundering herd (hot key expires → all miss → hammer DB): single-flight lock, early recompute, TTL jitter !
  • Penetration (cache the null / Bloom filter); avalanche (spread TTLs). Client-side caching (RESP3) for hot keys.

Distributed Lock

SET lock:res <token> NX PX 30000     # acquire
# release ONLY if it's still my token (atomic):
EVAL "if redis.call('get',KEYS[1])==ARGV[1]
      then return redis.call('del',KEYS[1]) else return 0 end"
      1 lock:res <token>
  • NX = mutual exclusion; PX = auto-release so a crash can't deadlock.
  • Never bare DEL — you may delete someone else's re-acquired lock !
  • Work > TTL → lock expires mid-work → 2 holders (watchdog renew).
  • Redlock for multi-node; Kleppmann: fine for efficiency, NOT correctness without fencing tokens !

Rate Limit & Patterns

  • Fixed window: INCR k + EXPIRE k 60 (allows 2× boundary bursts).
  • Sliding window: a ZSET of timestamps — ZADD, ZREMRANGEBYSCORE (drop old), ZCARD.
  • Token bucket: atomic Lua (tokens + last-refill) — the robust one.
  • Sessions: SET session:id data EX ttl, sliding TTL, shared across app servers.
  • Queues: list + BRPOP → reliable via LMOVE to a processing list → Streams groups → a real broker.
  • Leaderboard (ZSET) · uniques (HLL) · DAU (bitmap) · dedup (set/Bloom).

Replication

  • Primary → replicas, asynchronous (read scaling + HA). Initial full sync (RDB) then a command stream; PSYNC = partial resync.
  • Async ⇒ a crash can lose the last unreplicated writes; failover promotes a replica that may miss them !
  • WAIT n timeout for stronger acks; min-replicas-to-write to refuse writes if too few healthy.
  • Replicas read-only; watch replication lag (INFO replication). A no-persistence replica restart can wipe the primary !

  • Sentinel: monitors, quorum SDOWN→ODOWN, promotes a replica, tells clients the new primary.
  • Cluster: key→slot via CRC16; smart clients follow MOVED/ASK; multi-key ops need one slot → hash tags user:{123}:x ! Built-in gossip failover.

Memory

  • Small aggregates use compact encodings (listpack/ziplist, intset, embstr) → convert to hashtable/skiplist past thresholds. Keeping collections small saves lots of memory.
  • Find hogs: INFO memory, MEMORY USAGE k, redis-cli --bigkeys.
  • Big keys (multi-MB / millions of elements) → slow O(N) ops block the loop; split/cap them !
  • Hot keys bottleneck one node (even in Cluster) → client-side cache / split.
  • Fragmentation (mem_fragmentation_ratio, jemalloc, activedefrag); prefer hashes over millions of tiny keys.

Ops · Monitoring · Security

INFO   INFO memory   INFO replication
SLOWLOG GET   LATENCY DOCTOR   redis-cli --bigkeys
  • Watch: hit rate (keyspace_hits/misses), used_memory, evicted_keys, clients, replication lag, persistence status.
  • MONITOR = every command — great for debug, NEVER leave on in prod !
  • Never expose Redis to the internet — bind private, protected-mode, requirepass/ACLs/TLS, rename dangerous commands (FLUSHALL/CONFIG/KEYS) !
  • Pool client connections (don't open one per request). Disable THP; never let Redis swap.

Ecosystem & Alternatives

  • Redis 7: Functions, ACLs, RESP3 + client-side caching, sharded pub/sub.
  • Redis Stack modules: RedisJSON, RediSearch (index/full-text/vector search), RedisTimeSeries, RedisBloom.
  • Valkey = the Linux-Foundation BSD fork after the 2024 licence change (AWS/Google/Oracle) — near drop-in.
  • Memcached = simpler, multi-threaded, pure LRU cache, no persistence/rich types. MemoryDB = durable Redis-as-a-DB. KeyDB/Dragonfly = multi-threaded rewrites.

☐ Cache / Design Review Checklist

  • ☐ Right data structure for the access pattern (ZSET for ranked/window, hash for objects).
  • ☐ Every cache key has a TTL; an eviction policy set (allkeys-lru/lfu), not noeviction-with-no-TTLs.
  • ☐ No KEYS/unbounded O(N) in hot paths (use SCAN); no giant/big keys or hot keys.
  • ☐ Stampede protection (lock/early-recompute/jitter) on hot keys; a defined invalidation strategy.
  • ☐ Compound read-modify-write done atomically (Lua/WATCH), not check-then-act races.
  • ☐ Locks: NX+PX + safe Lua release (+ watchdog); know the correctness caveats.
  • ☐ Persistence & replication data-loss window understood & acceptable (WAIT if needed).
  • ☐ Secured (no public bind, auth/ACL/TLS); connections pooled; memory sized with headroom.

★ Troubleshooting Playbook

Server froze

  • ☐ Someone ran KEYS * / a big-key O(N) → SCAN, split keys; check SLOWLOG.

p99 latency spike

  • ☐ Fork (BGSAVE/AOF-rewrite), swap/THP, big DEL (→UNLINK), hot key → LATENCY DOCTOR.

OOM / evicting / write errors

  • ☐ maxmemory + noeviction + no TTLs, or a big key → set policy, add TTLs, split keys.

Low hit rate

  • ☐ TTLs too short, wrong keys cached, eviction thrashing, cold cache.

Lost data on failover

  • ☐ Async replication window → WAIT / min-replicas; accept the tradeoff.

Lock let two run

  • ☐ Work > TTL or unsafe DEL → safe Lua unlock + watchdog + fencing token.
