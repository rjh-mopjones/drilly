Architecture & Model

  • In-memory key-value store; data structures as first-class values. Optional durability to disk.
  • Single-threaded command execution (one command at a time, atomic) — I/O is multiplexed; Redis 6+ has multi-threaded I/O only, not command exec.
  • Sub-ms latency because everything is RAM + no lock contention. The event loop is the whole model.
  • Use cases: cache, session store, rate limiter, queue, leaderboard, pub/sub, real-time counters.
  • Rule of thumb: reach for Redis when you need sub-millisecond access to hot, mostly-ephemeral data — and keep the durable copy in a real database behind it !
  • Everything is a string under the hood at the key level; values have specialised encodings (ziplist/listpack/intset/skiplist/hashtable) chosen by size !

Keys · TTL · Eviction

SET k v EX 3600 NX   # set + 1h TTL, only if absent
EXPIRE k 60          # add/replace TTL
TTL k                # -1 no TTL, -2 gone
SCAN 0 MATCH u:* COUNT 100
  • Expiry = lazy (on access) + active (sampled background). A never-accessed expired key lingers in RAM until sampled !
  • Never use KEYS in prod — O(n), blocks the single thread. Use SCAN (cursor, non-blocking) !
  • Writing to a key removes its TTL unless you use KEEPTTL !

  • Prod default: both — AOF for durability, RDB for fast restart/backups.
  • Fork for snapshot uses copy-on-write; under heavy writes the child doubles memory briefly !

Single-Thread Footguns

  • One slow O(n) command blocks every other client (head-of-line). Cul­prits: KEYS, big SMEMBERS/HGETALL/ZRANGE 0 -1, SORT, Lua that loops !
  • Find them: SLOWLOG GET, LATENCY DOSTOR, redis-cli --latency.
  • Big-key deletion blocks — use UNLINK (async free) not DEL for large values !
  • Prefer O(1)/O(log n) ops; paginate with SCAN/ZSCAN; keep values small.
  • Pipelining batches N commands in one RTT (throughput, not atomicity). MULTI adds atomicity.

  • Cap growth with XADD MAXLEN ~ 10000.
  • Keyspace notifications (config notify-keyspace-events) publish on key events — but delivery is best-effort pub/sub !

Transactions & Lua

WATCH bal
val = GET bal          # optimistic
MULTI
DECRBY bal 10
EXEC        # nil if bal changed → retry (CAS)
  • MULTI/EXEC = queued commands run atomically, no rollback — a command erroring mid-batch still runs the rest ! (not like SQL txns).
  • WATCH = optimistic lock; EXEC aborts if a watched key changed.
  • Lua scripts (EVAL/EVALSHA) run atomically on the server — best for read-modify-write in one round trip. Keep them fast (they block!) !
  • Redis 7 Functions = persisted, named server-side logic (successor to cached scripts).

Caching Patterns

  • Cache-aside (lazy): app reads cache → miss → load DB → SET. Most common; stale until TTL/invalidate.
  • Write-through: write cache+DB together (consistent, slower writes). Write-behind: write cache, async to DB (fast, risk loss).
  • Always set a TTL; invalidate on write.

The 3 stampede failure modes !

Distributed Lock

SET lock:job  NX PX 30000   # acquire
# ...do work (must finish < TTL)...
# release ONLY if still mine (atomic):
EVAL "if redis.call('get',KEYS[1])==ARGV[1]
  then return redis.call('del',KEYS[1]) else return 0 end"
  1 lock:job
  • SET NX PX + unique token; release via Lua compare-and-del so you never delete someone else's lock !
  • TTL bounds a dead holder; but if work > TTL two holders overlap ! — add a fence token or watchdog.
  • Redlock (N independent masters, majority) is contested (Kleppmann): single Redis lock is fine for efficiency, not for correctness-critical mutual exclusion.

  • Fixed window = simple but bursts at edges; sliding window / token bucket (Lua for atomicity) smooth it !
  • Sessions: HSET session:{id} + TTL; sliding expiry on each request.
  • Leaderboards: sorted set, ZADD score, ZREVRANK for position, ZREVRANGE 0 9 top-10.

Replication

  • Async primary→replica by default: acked writes can be lost on failover ! (not strongly consistent).
  • Replicas serve reads (scale reads), are read-only. Initial sync = RDB snapshot + backlog buffer; partial resync after brief disconnects.
  • WAIT n ms blocks until n replicas ack (tunable durability, not a guarantee).
  • One primary per shard; chained replication possible.
  • repl-backlog-size buffers writes during a replica disconnect so it can partial resync (PSYNC) instead of a full RDB transfer — size it for your write rate × expected blip !
  • Read-from-replica scales reads but serves stale data (async lag); never route read-your-write flows there.
  • Monitor master_repl_offset vs replica offset for lag; a growing gap means the replica can't keep up (network or slow disk).

HA: Sentinel vs Cluster

SentinelCluster
HA + auto-failoverHA + horizontal sharding
single dataset, replicas16384 hash slots across masters
quorum monitors + promoteseach master owns slot range
  • Sentinel: ≥3 sentinels, quorum detects primary down → promotes a replica, updates clients.
  • Cluster: slot = CRC16(key) mod 16384. Multi-key ops must share a slot → use hash tags {user1}:... !
  • Cluster tolerates minority master loss; needs replicas to survive a master failure.

Memory & Optimization

  • INFO memory, MEMORY USAGE key, --bigkeys to profile.
  • Small hashes/lists/sets use compact listpack encoding until a threshold, then convert to hashtable/skiplist (much bigger) ! — keep them under the limit.
  • Prefer hashes over many top-level keys (less per-key overhead). Shorten key names at scale.
  • Fragmentation: mem_fragmentation_ratio ≫1 → activedefrag or restart.
  • Set maxmemory + eviction policy so Redis never OOM-kills the box.
  • LRU is approximate (samples a few keys, evicts oldest of the sample) — cheaper than true LRU; raise maxmemory-samples for accuracy at CPU cost. LFU tracks frequency, better for skewed access !
  • Overhead per key (dict entry + object header + expire entry) dominates for millions of tiny keys — batching fields into a hash slashes it.

Ops · Monitoring · Security

  • Watch: hit rate (keyspace_hits/misses), evictions, connected_clients, instantaneous_ops_per_sec, replication lag, SLOWLOG.
  • Security: ACLs (Redis 6) per-user command/key perms; requirepass; TLS; bind/protected-mode; rename/disable FLUSHALL/CONFIG/KEYS !
  • Never expose Redis to the internet unauthenticated ! (classic crypto-mining pwn).
  • Backups: RDB snapshots off-box; test restores.

Bitmaps · HLL · Geo

  • Bitmaps (on a string): SETBIT/GETBIT/BITCOUNT/BITOP. Daily-active-users = one bit per user id; 1M users ≈ 125KB. BITCOUNT for totals, BITOP AND across days for retention ! only works if ids are dense integers.
  • HyperLogLog: PFADD/PFCOUNT/PFMERGE — count uniques in ~12KB with 0.81% error regardless of cardinality. Use for "unique visitors" where exactness doesn't matter.
  • Geo (sorted-set backed): GEOADD, GEOSEARCH ... BYRADIUS for "shops within 5km". Score encodes a geohash.
  • These trade exactness/generality for tiny memory — pick them when an exact set would be gigabytes.

Redis Cluster Deep-dive

  • 16384 hash slots spread across masters; slot = CRC16(key) mod 16384. Each master owns a contiguous-ish slot range + has replicas.
  • Client caches the slot→node map. Wrong node → MOVED (permanent, update map) or ASK (transient, mid-migration) !
  • Resharding migrates slots live; a smart client follows ASK redirects during the move.
  • Multi-key ops (MGET, SINTER, txns, Lua) require all keys in one slot → force it with a hash tag: {user1}:profile, {user1}:cart hash on user1 only !
  • No cross-slot transactions. Cluster ≠ a bigger single DB — model for locality.

  • Reach for Lua when you must decide based on a value you just read (check-then-set) without a race !
  • Keep scripts short — they block the single thread like any command.
  • Pipeline for bulk loads/warmups (10–100× fewer round trips).

Redis 7.x & Alternatives

  • Functions (7.0): persisted, named server-side logic (replaces relying on cached EVALSHA scripts).
  • ACLv2, multi-part AOF, client-side caching (tracking: server invalidates client caches), sharded pub/sub in cluster.
  • Licence shift (2024) → Valkey (Linux Foundation fork, drop-in) is the OSS successor many adopt.
  • Performance forks: KeyDB (multi-threaded), Dragonfly (multi-threaded, higher throughput per node).
  • When Redis is the wrong tool: durable source-of-truth (use a DB), huge datasets ≫ RAM, complex queries — Redis is a fast supplement, not a primary store !

★ Design / Review Checklist

Type & access

  • ☐ Right type for the access pattern; no huge single keys; O(n) commands paginated with SCAN not KEYS !
  • ☐ Every cache key has a TTL; large deletes use UNLINK.

Correctness

  • ☐ Read-modify-write is atomic (Lua / WATCH-CAS), not GET-then-SET race !
  • ☐ Locks use SET NX PX + token + Lua release; TTL > max work time (or watchdog).
  • ☐ Aware async replication can lose acked writes; not used as source of truth for money.

Ops

  • ☐ maxmemory + eviction policy set; persistence (AOF everysec + RDB) matches durability need.
  • ☐ TTL jitter / stampede protection on hot keys; auth + ACL + no public exposure.
