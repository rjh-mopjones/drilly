Architecture & Model

  • In-memory key-value store; data structures as first-class values. Optional durability to disk.
  • Single-threaded command execution (one command at a time, atomic) — I/O is multiplexed; Redis 6+ has multi-threaded I/O only, not command exec.
  • Sub-ms latency because everything is RAM + no lock contention + optimised C data structures. The event loop is the whole model.
  • Use cases: cache, session store, rate limiter, queue, leaderboard, pub/sub, real-time counters, geo.
  • Rule of thumb: reach for Redis for sub-millisecond access to hot, mostly-ephemeral data — and keep the durable copy in a real database behind it !
  • Everything is a string at the key level; values have specialised encodings (listpack/intset/skiplist/hashtable) chosen by size !
  • RESP wire protocol: RESP2 (arrays/bulk strings); RESP3 adds native maps, sets, doubles, big numbers, and push messages (enables client-side-cache invalidations on the same connection).
  • 16 logical DBs (SELECT n) share one process/memory — namespacing only, not isolation; Cluster only allows DB 0 !

Strings · Counters · Bitmaps

SET k v EX 3600 NX GET   # set+TTL, only if absent, return old
INCR views      # O(1) atomic counter; INCRBY / DECR
APPEND log "..."  # amortised O(1) build; watch big key !
GETRANGE / SETRANGE k 0 5
  • INCR works because integer strings use the int encoding (stored as a long) — atomic read-modify-return in one op, no GET-then-SET race !
  • Bitmaps on a string: SETBIT/GETBIT/BITCOUNT/BITOP. DAU = one bit per user id; 1M users ≈ 125KB. BITOP AND across day keys for retention ! only if ids are dense integers.
  • BITFIELD packs many small counters (e.g. 8-bit tallies) into one string with atomic INCRBY/overflow control.
  • 512MB max string; store JSON as a string only if you read/write it whole — else use a hash or RedisJSON (JSON.SET/GET path access) !

Hashes & Lists

HSET user:1 name alice age 30    # object with fields
HGET user:1 name   HGETALL user:1 # O(n) — small only !
LPUSH q job   BRPOP q 0           # queue: FIFO, block-pop
LRANGE q 0 9   LTRIM q 0 999      # keep newest 1000
  • Hash = the object type: one key, many fields, one lot of per-key overhead. Small hashes are listpack-encoded (cheap). Field-level TTLs arrived in Redis 7.4 (HEXPIRE).
  • List ends are O(1) (LPUSH/RPUSH/LPOP/RPOP); the middle is O(n) — LINDEX/LINSERT on a big list is slow !
  • Stack = LPUSH+LPOP (LIFO); queue = LPUSH+BRPOP (FIFO).
  • LTRIM caps a list to the latest N (capped activity feed) so it never becomes a big key.

Sets & Sorted Sets

SADD tags:1 red blue   SISMEMBER tags:1 red   # O(1)
SINTER a b   SUNION a b   SDIFF a b            # set algebra
ZADD board 1500 alice   ZINCRBY board 50 alice
ZREVRANGE board 0 9 WITHSCORES  # top-10
ZREVRANK board alice            # 0-based rank
  • Set: uniqueness + algebra (intersection for "users in A and B", union, diff). All-integer sets use compact intset; SMEMBERS on a big set is O(n) — use SSCAN/SISMEMBER !
  • ZSET: score-ordered, ZADD/ZSCORE O(log n), range O(log n + m). The purpose-built leaderboard, priority queue, time-index and sliding-window structure.
  • ZADD flags: NX/XX (only-add/only-update), GT/LT (only if greater/less — great for high-score), CH (count changed), INCR.
  • ZRANGEBYLEX does prefix/autocomplete when all scores are equal.

Keys · TTL · Eviction

SET k v EX 3600 NX   # set + 1h TTL, only if absent
EXPIRE k 60          # add/replace TTL; KEEPTTL to preserve
TTL k                # -1 no TTL, -2 gone
SCAN 0 MATCH u:* COUNT 100
  • Expiry = lazy (on access) + active (sampled background, ~10Hz). A never-accessed expired key lingers in RAM until sampled !
  • Never use KEYS in prod — O(n), blocks the single thread. Use SCAN (cursor, non-blocking, may return dupes, won't miss keys present throughout) !
  • Writing to a key removes its TTL unless you use KEEPTTL !
  • Replicas don't expire keys themselves — they wait for the primary's DEL so reads stay consistent.

Persistence: RDB vs AOF

RDBAOF
Whatpoint-in-time snapshot (fork+COW)append every write command
Restartfast loadslower (replay)
Durabilitylose since last snapshot !everysec ≈ ≤1s loss
Sizecompactlarger; needs rewrite/compaction
  • appendfsync: always (safe, slow) · everysec (default, ~1s risk) · no (OS decides).
  • Prod default: both — AOF for durability, RDB for fast restart/backups. Hybrid AOF (RDB preamble) writes an RDB header then AOF tail: fast load + fine-grained durability.
  • AOF rewrite (BGREWRITEAOF) compacts the log to the shortest command set that rebuilds current state, so it doesn't grow forever.
  • Fork for snapshot uses copy-on-write; under heavy writes the child can double memory briefly ! and the fork itself pauses the main thread on big datasets.

Single-Thread Footguns

  • One slow O(n) command blocks every other client (head-of-line). Culprits: KEYS, big SMEMBERS/HGETALL/LRANGE 0 -1/ZRANGE 0 -1, SORT, Lua that loops !
  • Find them: SLOWLOG GET, LATENCY LATEST/DOCTOR, redis-cli --latency.
  • Big-key deletion blocks — use UNLINK (async free in a bg thread) not DEL for large values !
  • Prefer O(1)/O(log n) ops; paginate with SCAN/HSCAN/SSCAN/ZSCAN; keep values small.
  • Pipelining batches N commands in one RTT (throughput, not atomicity). MULTI adds atomicity.
  • Single-thread limit is real only when you saturate one core or have big keys — then shard (Cluster) or split hot keys.

Pipelining vs MULTI vs Lua

  • Keep scripts short — they block the single thread like any command.
  • Pipeline for bulk loads/warmups (10–100× fewer round trips).

Transactions & Optimistic Lock

WATCH bal              # optimistic lock on bal
val = GET bal
MULTI
DECRBY bal 10
EXEC        # nil if bal changed since WATCH → retry (CAS)
  • MULTI/EXEC = queued commands run atomically, no rollback — a command erroring mid-batch still runs the rest ! (not like SQL txns).
  • No rollback because Redis command errors are programming bugs, not business conditions — omitting rollback keeps it simple and fast.
  • WATCH = optimistic lock; EXEC aborts (returns nil) if a watched key changed. Retry loop = CAS. UNWATCH/DISCARD to abandon.
  • ACID-ish: Atomic (all-or-nothing queue) & Isolated (single-threaded) yes; Consistency app's job; Durability depends on AOF fsync.
  • Cluster: all keys in a txn must share one slot (hash tag) !

Lua Scripting & Functions

EVAL "return redis.call('INCR', KEYS[1])" 1 counter
SCRIPT LOAD "..."          # → sha; then EVALSHA  ...
  • Runs atomically on the server (single-threaded) — the whole script is one indivisible step; ideal for read-modify-write in one round trip.
  • KEYS vs ARGV: pass every key you touch as a KEYS[] arg (not hard-coded) so Cluster can route and validate the slot !
  • redis.call raises on error (aborts script); redis.pcall returns the error to handle it.
  • Long scripts block everyone; SCRIPT KILL only works if no write has happened yet, else SHUTDOWN NOSAVE !
  • Redis 7 Functions (FUNCTION LOAD) = persisted, named, replicated server-side libraries — successor to relying on cached EVALSHA.

Pub/Sub vs Streams

  • Pub/Sub: SUBSCRIBE/PUBLISH, PSUBSCRIBE patterns. Good for ephemeral fan-out (live notifications, cache-invalidation broadcasts) where a missed message is fine.
  • Cluster: normal pub/sub floods all nodes — use sharded pub/sub (SPUBLISH/SSUBSCRIBE, keyed to a slot).
  • Keyspace notifications (notify-keyspace-events) publish on key events (e.g. expired) — but it's best-effort pub/sub, so an offline listener misses them ! The expired event fires when the key is actually removed (lazy/active), not exactly at TTL.

Streams Deep-dive

XADD events * type click user 42   # * = auto ms-seq id
XLEN events   XRANGE events - +
XGROUP CREATE events g1 $           # group, from now
XREADGROUP GROUP g1 c1 COUNT 10 BLOCK 0 STREAMS events >
XACK events g1 <id>                 # ack processed
XPENDING events g1                  # unacked (PEL)
XAUTOCLAIM events g1 c2 60000 0     # steal dead consumer's msgs
  • Consumer groups: each group has a cursor + a Pending Entries List (delivered-but-unacked). Crash before XACK → msg stays pending → XCLAIM/XAUTOCLAIM reassigns it. This is at-least-once ⇒ consumers must be idempotent.
  • IDs are <ms>-<seq>, monotonic → time-ordered and range-queryable.
  • Cap growth: XADD events MAXLEN ~ 10000 * ... (approximate trim is cheaper) or XTRIM ... MINID.
  • Streams vs Kafka: Streams are simpler and in-RAM; graduate to Kafka for huge throughput, long retention, and true partitioned replay.

Caching Patterns

  • Cache-aside (lazy): app reads cache → miss → load DB → SET ... EX. Most common; degrades to "slower" if cache is down, not "broken".
  • Read-through: cache library loads on miss (app never sees DB). Write-through: write cache+DB together (fresh, slower writes). Write-behind: write cache, async to DB (fast, risk loss).
  • Always set a TTL (safety net vs missed invalidation + memory leak); invalidate on write.

Invalidate: order matters !

db.update(id)          # 1. write source of truth FIRST
redis.DEL("user:"+id)  # 2. then invalidate

Delete (not update) on write is the safer default — you never cache a wrong value, just force a reload. Reverse order lets a reader re-cache the stale value. Residual race → short TTL / double-delete.

The 3 stampede failure modes !

Penetrationmiss for keys that don't exist → cache the null (short TTL) / Bloom filter
Avalanchemany keys expire together → jitter the TTLs (the #1 fix)
Stampedehot key expires, N rebuilds → single-flight lock / serve-stale / early recompute

Single-flight & Hit-rate

read(key):
  v = GET key
  if v: return v                    # hit
  if SET lock:key tok NX PX 5000:   # I recompute
     v = db.load(key)
     SET key v EX ttl+jitter
     lua_release(lock:key, tok)
     return v
  else: sleep(short); return GET key # wait & re-read
  • Only one request rebuilds a hot key; the rest wait or serve stale. Prevents the thundering herd from hitting the DB.
  • Serve-stale-while-revalidate: store logical-expiry inside the value with a longer physical TTL, so waiters get stale-but-fast data.
  • Hit rate = keyspace_hits/(hits+misses) from INFO stats (cumulative — sample twice & diff). Healthy read cache > ~90%. Falling rate → short TTLs, wrong keys cached, cold cache, or eviction thrashing.
  • Client-side caching (RESP3 tracking): app keeps a local copy; Redis pushes an invalidation when the key changes — cuts the round trip entirely for the hottest, rarely-changing keys.

Distributed Lock

SET lock:job <token> NX PX 30000   # acquire (atomic)
# ...do work (must finish < TTL)...
# release ONLY if still mine (atomic):
EVAL "if redis.call('get',KEYS[1])==ARGV[1]
  then return redis.call('del',KEYS[1]) else return 0 end"
  1 lock:job <token>
  • SET NX PX + unique token; release via Lua compare-and-del so you never delete someone else's lock ! A bare DEL can free a lock re-acquired by another client after yours expired.
  • One atomic SET — the old SETNX+EXPIRE had a crash window with no TTL = permanent deadlock !
  • TTL bounds a dead holder; but if work > TTL two holders overlap ! There is no TTL that is both deadlock-safe and overlap-safe — you trade one risk for the other.
  • Watchdog: bg timer renews the TTL (Lua compare-and-PEXPIRE, e.g. every TTL/3) while work runs; stops on crash. Redisson's default.

Locks: Redlock & Fencing

  • Redlock: acquire the same key+token on a majority of N independent masters (typ. 5, no replication) within a time bound; validity = TTL − elapsed. Survives a minority of node failures.
  • Kleppmann critique: GC pauses, network delay, and clock skew break Redlock's timing assumptions — a paused client can wake believing it still holds an expired lock. No node count fixes this.
  • Fencing token = monotonic int (INCR fence) handed out per acquire; the protected resource rejects any write with a token ≤ the highest it's seen. Makes a stale holder's write harmless — real correctness !
  • Single-instance lock loses safety on failover: async replication means the acquire write can be lost when a replica is promoted → two holders !
  • Bottom line: Redis locks are fine for efficiency (avoid duplicate work); for correctness (must-be-at-most-one) use fencing tokens or a consensus system (ZooKeeper/etcd).

Rate Limiting

# fixed window — cheap, O(1)
INCR rl:u:123:<minute>
EXPIRE rl:u:123:<minute> 60   # only on first hit
# > limit → reject 429

! Fixed window allows ~2× the limit across a boundary (100 at 12:00:59 + 100 at 12:01:00). Smooth it with:

  • Sliding-window log (ZSET of timestamps): ZREMRANGEBYSCORE old → ZADD now → ZCARD. Exact, but one member per request = memory + O(log n).
  • Sliding-window counter: current + previous·(1−elapsed_fraction) — two counters, tiny memory, smooths the burst. What Cloudflare-style limiters use.
  • Token bucket (Lua): tokens refill at rate up to cap, each request spends one; smooths bursts up to cap while bounding long-run rate.

All are read-modify-write ⇒ do them atomically (INCR-then-check or Lua) or two requests race past the limit ! Return 429 + X-RateLimit-Remaining/Retry-After.

Token Bucket (Lua)

local st = redis.call('hmget', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(st[1]) or cap
local ts     = tonumber(st[2]) or now
tokens = math.min(cap, tokens + (now-ts)*rate)  -- refill
local ok = tokens >= 1
if ok then tokens = tokens - 1 end
redis.call('hmset', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('expire', KEYS[1], math.ceil(cap/rate)*2)
return ok and 1 or 0
  • Lua is required: the refill-check-decrement is a multi-field read-modify-write — split across client commands two requests both read the same count and both "allow" !
  • Token vs leaky bucket: token bucket allows bursts up to cap (banked allowance); leaky bucket smooths to a constant drip (traffic-shaping a fragile downstream).

Sessions & Queues

# session: hash + sliding TTL
HSET session:abc user 123 role admin
EXPIRE session:abc 1800     # refresh each request
DEL session:abc             # logout = instant revoke
  • Redis suits sessions: fast (every request), native TTL (the whole lifecycle), and shared across app servers → stateless app tier. Instant revoke beats stateless JWTs (a valid JWT is accepted until expiry unless you keep a Redis denylist).

Reliable queue (no lost jobs)

LMOVE q processing:w7 RIGHT LEFT   # atomic claim (not RPOP)
# ...work... then ack:
LREM processing:w7 1 <job>
  • Plain LPUSH+BRPOP is a good simple queue but a crash between pop and finish loses the job ! The processing-list pattern keeps the job in Redis until acked; a reaper re-queues stale ones ⇒ at-least-once ⇒ idempotent consumers. Streams give the same with XACK.
  • Delayed jobs: ZSET scored by due-time; poll ZRANGEBYSCORE 0 now and ZREM claimed jobs atomically in Lua.

Replication

  • Async primary→replica by default: primary acks the client before replicas confirm, so acked writes can be lost on failover ! (eventual, not strong, consistency).
  • Replicas serve reads (scale reads), are read-only. Initial full sync = BGSAVE RDB + buffered writes; then a continuous command stream.
  • PSYNC / partial resync: replica tracks (replication-id, offset); on a brief disconnect it resumes from the primary's in-memory backlog (repl-backlog-size) instead of a full RDB transfer — size it for write-rate × expected blip !
  • WAIT n ms blocks until n replicas ack (durability dial, not linearizable, not a full guarantee).
  • min-replicas-to-write / min-replicas-max-lag: refuse writes unless N replicas are within S seconds — shrinks the loss window, trades availability (CAP made explicit).
  • Read-from-replica serves stale data (lag); never route read-your-writes there. Monitor master_repl_offset vs replica offset for lag.
  • Footgun: a persistence-less replica that restarts comes back empty and can propagate emptiness upstream and wipe the dataset ! Keep at least RDB on replicas.

HA: Sentinel

  • Sentinel = external supervisor processes for a non-sharded primary+replicas: monitor, notify, auto-failover, and act as a config provider (clients ask it for the current primary). Not a proxy — data never flows through it.
  • Failover state machine: SDOWN (one sentinel's opinion after down-after-milliseconds) → ODOWN (a quorum agree) → elect a leader (needs a majority of all sentinels) → promote best replica (REPLICAOF NO ONE) → repoint the rest.
  • Quorum ≠ majority: quorum triggers ODOWN; a majority authorises the promotion. With 5 sentinels, quorum 2, a leader still needs 3 votes !
  • Run an odd number ≥ 3 across failure domains so a partition can't split evenly and can still form a majority.
  • Best replica = filter unhealthy → lowest replica-priority (0 = never) → highest offset → smallest run-id.
  • Failover restores availability, not the un-replicated writes (async). TILT mode: a sentinel that detects clock jumps sits out to avoid spurious failovers.

Redis Cluster Deep-dive

  • 16384 hash slots across masters; slot = CRC16(key) mod 16384. Each master owns a slot range + has replicas. (16384 slots, not nodes — the bitmap gossiped between nodes stays ~2KB.)
  • Client caches the slot→node map (CLUSTER SLOTS/SHARDS) and routes directly. Wrong node → MOVED (permanent, update map) or ASK (transient, mid-migration, send ASKING first, don't update map) !
  • Resharding moves slots live; keys already moved → ASK, not yet → served by source; then MOVED.
  • Multi-key ops (MGET, SINTER, txns, Lua) require all keys in one slot or CROSSSLOT error → force it with a hash tag: only the substring in {...} is hashed, so user:{123}:profile & user:{123}:cart co-locate ! Over-coarse tags create a hot slot.
  • Built-in HA: gossip on the cluster bus (port +10000) → PFAIL→FAIL → a replica gets a master majority vote → promoted. No Sentinel.
  • Availability is per-slot: lose a master + all its replicas and that slot range is down; cluster-require-full-coverage no keeps the rest serving. Min viable = 3 masters (majority voting) + a replica each.
  • Still async ⇒ same failover loss window; a minority-side master keeps taking writes until cluster-node-timeout then stops.

Memory & Optimization

  • Profile: INFO memory, MEMORY USAGE key, MEMORY DOCTOR, redis-cli --bigkeys/--memkeys/--hotkeys (all SCAN-based, non-blocking).
  • Per-key overhead (dict entry + robj header + optional expire entry) ≈ 50–100B per key. Millions of tiny keys waste huge memory — pack fields into a hash (one key, listpack): Instagram cut ~5× this way !
  • Big key = one huge value/collection → O(n) commands block the loop (a latency bug, not just space) + slow migration + blocking DEL. Split/shard it, cap it (LTRIM/TTL), read with SCAN-family, delete with UNLINK.
  • Hot key = one key with skewed traffic. Cluster does NOT fix it — it hashes to one slot on one node ! Fix via client-side cache, read replicas, or split into counter:{shard0..N}.
  • Cheaper types: bitmap (~1.2MB for 10M flags) vs a set of ids; HLL (~12KB) for approx uniques vs a growing set.
  • Fragmentation: mem_fragmentation_ratio = RSS/used_memory. >1.5 → enable activedefrag (jemalloc, online); <1 → swapping (bad, add RAM) !
  • Set maxmemory below box RAM (leave room for fork COW) + an eviction policy so Redis never OOM-kills the box.

Ops · Monitoring

SLOWLOG GET 10        # exec time > slowlog-log-slower-than (µs)
LATENCY DOCTOR        # triage spike sources
redis-cli --stat      # live ops/mem/clients
redis-cli --latency   # PING RTT sampling
  • Alert on: used_memory/maxmemory %, rising evicted_keys, hit-rate drop, rejected_connections, persistence status ≠ ok, replica master_link_status/lag, blocked_clients, single-core CPU. Alert on leading indicators, not lagging ones.
  • Latency spikes: fork (BGSAVE/BGREWRITEAOF/sync), swap, Transparent Huge Pages (disable THP), big-key O(n), large DEL, expiry bursts.
  • MONITOR streams every command — invaluable but can halve throughput; never leave running in prod !
  • Pool connections — never one per request (marches toward maxclients 10000 → rejected_connections). Give blocking cmds their own pool.
  • CONFIG SET is live but in-memory only — CONFIG REWRITE to persist. Backups: RDB off-box, snapshot on a replica, test restores.

Security

  • An internet-exposed, unauthenticated Redis is remote code execution: attacker does CONFIG SET dir + SET + SAVE to write a cron/SSH key/webshell as the Redis user. Mass crypto-mining pwn !
  • Network: bind private interfaces, firewall the port, protected-mode yes. Never bind 0.0.0.0 on a public IP.
  • Auth: requirepass = one all-powerful default user. ACLs (6+) = named users, per-command + per-key scope: ACL SETUSER app on >pw ~cache:* +get +set; disable default. Least privilege = smaller blast radius.
  • TLS for client + replication on untrusted networks. Run as non-root.
  • Neuter dangerous commands: rename-command FLUSHALL ""/CONFIG/KEYS/DEBUG, or deny via ACL (-@dangerous) — preferred, scoped.

Advanced: Bitmaps · HLL · Geo

  • Bitmaps: SETBIT/BITCOUNT/BITOP. DAU = 1 bit/user; BITOP OR daily keys → WAU; BITOP AND → retention ! dense integer ids only.
  • HyperLogLog: PFADD/PFCOUNT/PFMERGE — uniques in ~12KB, 0.81% error at any cardinality. PFMERGE combines periods (mergeability is the power).
  • Geo (zset-backed, score = geohash): GEOADD, GEOSEARCH ... BYRADIUS for "drivers within 5km", GEODIST.
  • These trade exactness/generality for tiny memory — pick them when an exact set would be gigabytes. Ask: do I need the ids, or just membership (bitmap) / a count (HLL)?

Redis 7.x & Alternatives

  • Functions (7.0): persisted, named, replicated server-side logic (replaces relying on cached EVALSHA).
  • ACLv2, multi-part AOF, client-side caching (tracking: server invalidates client caches), sharded pub/sub in cluster, HEXPIRE (7.4) hash-field TTLs.
  • Licence shift (2024) → Valkey (Linux Foundation fork, drop-in) is the OSS successor many adopt.
  • Performance forks: KeyDB (multi-threaded), Dragonfly (multi-threaded, higher throughput/node).
  • Modules: RediSearch (secondary index/query), RedisJSON (path access), RedisBloom (Bloom/Cuckoo/top-k), RedisTimeSeries.
  • Wrong tool for: durable source-of-truth (use a DB), datasets ≫ RAM, rich queries/joins, correctness-critical locks — Redis is a fast supplement, not a primary store !

Consistency & Data-Loss Windows

  • Cache vs DB: a cache is an eventually-consistent replica — there is always a window where they disagree. Bound it with TTL + delete-on-write; the must-be-fresh field bypasses the cache.
  • Async replication: acked writes not yet on a replica are lost if the primary dies before replicating (Sentinel and Cluster). Narrow with WAIT / min-replicas-to-write; can't eliminate.
  • Persistence gaps: RDB loses since last snapshot; AOF everysec ≤1s. Only appendfsync always is per-write durable (slow).
  • Locks: expiry-vs-work overlap + GC pause + failover loss ⇒ efficiency yes, correctness needs fencing tokens.
  • Pub/Sub: at-most-once, offline subscriber loses messages — use Streams for anything you can't lose.
  • Zero-loss requirement ⇒ Redis is not the system of record (or use MemoryDB, which adds a durable multi-AZ log).

★ Design / Review Checklist

Type & access

  • ☐ Right type for the access pattern; no huge single keys; O(n) commands paginated with SCAN not KEYS !
  • ☐ Every cache key has a TTL (with jitter); large deletes use UNLINK; collections kept under listpack thresholds.

Correctness

  • ☐ Read-modify-write is atomic (Lua / WATCH-CAS / INCR), not a GET-then-SET race !
  • ☐ Locks use SET NX PX + token + Lua release; TTL > max work time (or watchdog); fencing token if correctness-critical.
  • ☐ Aware async replication can lose acked writes; Redis not used as source of truth for money.

Ops

  • ☐ maxmemory + eviction policy set; persistence (AOF everysec + RDB) matches durability need.
  • ☐ TTL jitter / stampede protection on hot keys; auth + ACL + no public exposure; connections pooled.
