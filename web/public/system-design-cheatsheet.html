Orders of Magnitude

  • ns cache/RAM → us SSD/intra-DC → ms disk/cross-DC → 100ms+ cross-continent
  • Each tier is roughly ~1000× the last. ! An intercontinental RTT ≈ ~1.5M RAM reads.

Rules of Thumb

  • Memory fast > disk slow > network slower > cross-region very slow.
  • SSD » HDD (no seek; random read ~100× faster).
  • Sequential » random for both SSD & disk.
  • Avoid disk on hot path; cache in RAM. Batch/pipeline network calls; one cross-region hop dwarfs all local work.
  • Speed of light floor: ~5 ms per 1000 km RTT — geography caps latency. ! Can't optimize below physics; replicate closer to users.

Health & stickiness

  • Active: LB probes /health on interval; eject on N fails, re-add on M passes.
  • Passive: infer from live traffic errors/timeouts; eject outliers.
  • Sticky: cookie or src-IP pins client to one node (in-mem session/cache hit). ! breaks statelessness, uneven load, lost on node death — prefer shared session store + stateless nodes.

HA & global

  • LB is a SPOF — run a pair: active-passive w/ floating/virtual IP (VRRP failover), or active-active behind anycast.
  • Global (GeoDNS/anycast): route user to nearest healthy region; per-region LB handles local spread.
  • DNS LB: cheap, coarse; ! client TTL caching delays failover.

Where used

  • Edge → web/app tier (internet-facing, L7+TLS).
  • Service → service (internal/east-west, mesh sidecar).
  • Front of DB read replicas (spread read load; writes → primary).

SQL vs NoSQL — Database Selection

Pick SQL when

  • Relationships & multi-table JOINs
  • Transactions / ACID (money, orders, inventory)
  • Strong consistency required
  • Ad-hoc / unpredictable queries, reporting
  • Structured, stable schema
  • ! Default choice for most apps — start here unless a constraint forces otherwise

Pick NoSQL when

  • Massive scale, horizontal sharding
  • Flexible / rapidly evolving schema
  • Very high write throughput
  • Simple, known access patterns (key lookups)
  • Denormalized, self-contained records
  • ! Schema is "flexible" not "free" — model around query patterns up front; cross-entity queries hurt

Partitioning / sharding

Scheme+−
Rangerange scans, orderedhot spots (sequential keys)
Hasheven spreadno range scans

  • Key choice drives parallelism: partition by a natural business boundary (e.g. portfolio), not a high-skew/hot dimension (one hot instrument) — one key dominates & serialises load.

Consistent hashing

  • Nodes + keys on a ring; key → next node clockwise.
  • Add/remove node remaps only ~1/N keys (vs hash-mod-N = all keys move).
  • Virtual nodes: many points per physical node → even spread + smooth rebalance on heterogeneous hardware.

Pitfalls & rebalancing

  • ! Hot/celebrity shard → salt/sub-shard the key, dedicated replica or cache — but can't salt an ordering key (salt breaks per-key order): give the hot entity a dedicated partition, or use async/non-blocking IO inside the worker.
  • ! Cross-shard joins & txns expensive (scatter-gather, 2PC) → co-locate related data via shared shard key.
  • Rebalance w/o downtime: consistent hashing OR fixed partition count (>>nodes), move whole partitions; never hash-mod-N.

Consistency & CAP

  • CAP: in a network Partition you must pick — C (reject/err to stay correct) or A (serve possibly-stale). ! Not "pick 2 of 3": P is unavoidable in a distributed system, so the real choice is CP vs AP.
  • PACELC: if Partition → C-vs-A; Else (normal ops) → Latency-vs-Consistency. Strong reads cost round-trips even with no partition.

Quorum (R + W > N)

  • Read R + write W replicas of N; R+W>N ⇒ read set overlaps latest write ⇒ strong-ish reads.
  • Read-heavy: small R, large W (e.g. R=1,W=N). Write-heavy: large R, small W (W=1).
  • Balanced quorum: R=W=⌊N/2⌋+1. ! R+W>N alone gives overlap, not full linearizability (needs read-repair / sync writes).

Conflict on stale data: accept vs reject

  • Accept & reconcile (preferred at high throughput): take the write, fix later. Reject & reprocess adds unpredictable latency and can loop under load.
  • Stamp each event with its value + fetch-timestamp so a downstream can reconcile / pick the latest deterministically.
  • ! In finance, an audit trail is mandatory — correct via a new compensating entry, never silently overwrite a number.

Event Sourcing, CQRS & As-Of Queries

Event sourcing

  • Store the append-only log of events as the source of truth; current state = fold/replay of events. Full audit trail for free (finance ✓).
  • As-of / point-in-time: replay events up to time T. Naive = O(history) ! → keep periodic snapshots; answer = nearest snapshot + delta replay = O(delta).
  • Cache (e.g. Redis) snapshots in front of the durable store; on cache loss, fall back to the durable snapshot + replay.

CQRS (split read / write)

Write storeRead projection
Append + lookup by known keyDenormalised for complex queries
Source of truthDerived, eventually consistent
  • ! Need a real-time, zero-staleness point lookup? Hit the write store by key directly, not the lagging projection.

Messaging & Streaming

Why async

  • Decouple producer/consumer (independent scale, deploy, fail)
  • Buffer/absorb spikes, smooth bursty load to steady consumer rate
  • Built-in retry on failure; fan-out one event to many consumers

Shapes

TypeDeliveryTraits
Queue (SQS, RabbitMQ)Point-to-point; 1 consumer per msgCompeting consumers, work distribution, msg gone on ack
Pub/Sub (SNS, topics)Every subscriber gets a copyFan-out, broadcast; no replay
Log/stream (Kafka)Ordered partitions, consumer groupsReplayable, retention, offset-based, high throughput

Delivery semantics

ModeRiskUse
At-most-onceMay lose msgsMetrics, fire-and-forget
At-least-onceMay dup !Default; needs idempotent consumer
Exactly-onceHard/costlyUsually = at-least-once + dedup key
  • Ordering guaranteed only within a partition/key. Ask: global or per-entity ordering? Usually per-entity → that entity is the partition key. ! Global ordering = one partition = no parallelism.
  • Keyed/striped executor = the in-process version: hash(key) % N routes a key to a fixed worker → ordered per entity, parallel across entities (→ Java/C# concurrency cards).
  • Idempotency keys to dedup on consumer (e.g. messageId in a seen-set)
  • DLQ routes poison messages after N retries — alert & inspect, don't drop !
  • Backpressure when consumers lag: monitor lag/queue depth, autoscale or throttle producers

API Gateway & Rate Limiting

Gateway responsibilities

  • Single entry point; routing + service discovery
  • Auth/authz (validate JWT/API key, propagate identity)
  • TLS termination; mTLS to backends
  • Rate limiting + quotas; throttling
  • Request aggregation / fan-out (BFF per client type)
  • Response caching; protocol translation (REST↔gRPC, HTTP/2)
  • Logging, metrics, tracing, request IDs
  • ! Keep it thin — no business logic; gateway is a chokepoint & SPOF, scale it horizontally

Distributed limiting (Redis)

  • Fixed window: INCR key; set EXPIRE on first hit; reject if > limit
  • Token bucket: store tokens + last-refill ts; refill on read via Lua (atomic, race-free)
  • Key by user_id / IP / api_key / route; e.g. rl:{key}:{window}
  • ! Multi-step check-then-set must be atomic — use Lua/MULTI to avoid TOCTOU overcount
  • Local in-memory pre-check + async sync trades accuracy for latency

Where to enforce

  • Edge/gateway: coarse global + per-client abuse protection

Resilience Patterns

  • Timeouts ! ALWAYS set connect + read; never wait forever. Budget across chain: child timeout < parent remaining. Default < one user-perceptible unit (e.g. 1-2s), not 60s.
  • Retries: only idempotent ops. Exponential backoff + jitter (avoid synchronized retry storms). Cap attempts (~3). Use a retry budget (e.g. ≤10% of req rate) so retries can't amplify a failing dependency.

DNS resolution

  • Path: client → recursive resolver → root → TLD (.com) → authoritative NS.
  • Cached at each hop by record TTL (short TTL = fast failover, more queries).
  • Records: A (IPv4), AAAA (IPv6), CNAME (alias), NS, MX.
  • GeoDNS / latency routing returns nearest IP → steers users to closest region/CDN edge.

TLS (HTTPS = HTTP over TLS)

  • Handshake: asymmetric (cert/key exchange) to agree a symmetric session key; bulk data uses fast symmetric cipher.
  • Cost in RTTs: TLS 1.2 ≈ 2-RTT; TLS 1.3 = 1-RTT (0-RTT on resume).
  • Cert validates server identity via CA chain; SNI selects vhost.

Connection reuse & ports

  • keep-alive + pooling: reuse TCP/TLS conns → skip per-request handshake (saves RTTs + CPU).
  • Ports: 80 HTTP, 443 HTTPS/QUIC.
  • L4 LB = routes by IP/port (TCP/UDP, fast, opaque); L7 LB = routes by HTTP path/host/header (smart, TLS-terminating). See LB card.

Each RTT adds latency — TLS 1.3 is 1-RTT, HTTP/3 (QUIC) folds transport+TLS together. Reuse connections (keep-alive/pooling).

Throughput vs Latency Tradeoffs

TermMeaning
Latencytime for ONE op (ms)
Throughputops/sec (QPS)
  • Different axes: optimizing one often hurts the other (e.g. batching raises QPS but adds wait).

Little's Law

L = λ × W
concurrency = arrival_rate × latency
  • 1000 QPS × 0.2s = 200 in-flight.
  • Sizes thread pools, conn pools, queue depth.

Tail latency

  • Track p50/p95/p99/p99.9, not avg ! avg hides the tail.
  • Fan-out amplifies: req hitting 100 services waits on slowest → p99 of one ≈ typical of whole.
  • Fixes: hedged/backup requests, tail-tolerant design, copy-the-fastest.

Queueing

  • M/M/1: wait ≈ 1/(1-ρ) → as utilization →100%, latency → ∞.
  • Keep ρ ≈ 60-70%; add capacity BEFORE saturation ! last 10% util is exponential.

Scaling a slow batch / report

  • Diagnose first !: is it the query or the processing? (EXPLAIN ANALYZE → SQL sheet.)
  • Fix the query layer first: indexes, type-mismatch on the join/filter, push work into SQL (aggregate in DB, fetch less).
  • Can the DB parallelise natively (partition scans, parallel query) before you add app complexity?
  • Then chunk by natural key & parallelise: thread pool sized to the DB connection pool, bulk-write results.

Overload protection

  • Backpressure: signal upstream to slow (bounded queues, reject when full).
  • Load shedding: drop low-priority reqs to protect p99 of the rest ! failing fast beats queue collapse.

Behaviour (the reflex)

  • Restate the problem → state assumptions out loud → ask 1-2 scoping questions (labs under-specify on purpose).
  • Diagnose before fixing !: logs / metrics / EXPLAIN ANALYZE / git log — never optimise blind.
  • Propose the simplest correct solution first, then optimise; narrate reasoning and drive the conversation.
  • Flag what any fix or data-clean costs — never silently drop a row or lose data.

Common Mistakes !

  • Jumping to a solution w/o gathering requirements.
  • Skipping capacity estimation.
  • Naming a choice but not stating its tradeoff.
  • Over-engineering for scale you'll never hit.
  • Ignoring failure modes (node death, network partition, hot key).
  • Staying too high-level — no deep-dive on any component.
