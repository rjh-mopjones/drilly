How to read & print

  • ! footgun / gotcha   ☐ review checklist item
  • Mental model: an ADT (contract — ops + guarantees) vs an implementation (memory layout). "Which structure" = which implementation of which ADT, given the access pattern. Complexities are for the ops you actually run.
  • Big-O = asymptotic upper bound, not average, not wall-clock. Amortized = averaged over a sequence (worst-case robust); average = over random inputs (adversary-defeatable). Cache locality (~1ns hit vs ~100ns miss) breaks ties Big-O ignores !
  • Senior focus: the trade-off tables, the footguns, and the "what would you use for X" decision drill. Last 2 cards = bug table + review checklist.
  • Print: Ctrl/⌘-P → A4, margins None, scale 100%, background graphics on (keeps colour bars). 4 columns built-in.

Complexity Recall & Foundations

  • Combine phases: add sequential, multiply nested, max dominates. Build map O(n) then n heap ops O(n log n) = O(n log n).
  • Hidden O(n) space: recursion stack (O(depth)), slice/substring copies, output collection, boxing, dedup set !
  • In-place = O(1) aux space (some defs allow O(log n) stack). Recursion stack counts — a "no extra memory" recursion isn't O(1) space.
  • Comparison sort lower bound is Ω(n log n). An O(n) array scan often beats an O(log n) pointer-tree at real n (locality).

Arrays & Dynamic Arrays

OpCost
index a[i]O(1) = base+i*sz
appendO(1) amortized (resize O(n))
insert/delete middleO(n) (shift tail)
search (unsorted)O(n); sorted O(log n)

Invariant: 0 ≤ size ≤ capacity; [0,size) valid, [size,cap) slack. Grow geometrically (2x / 1.5x) — additive growth breaks amortized O(1). Doubling copies ~2n total across all resizes.

Use when

  • Index-heavy, append-heavy, iteration-heavy — the default. Random access + cache locality win decisively.

Gotchas

  • Append is amortized, not worst-case O(1) — one append can be O(n) !
  • Resize holds old+new = up to 3x peak memory ! Pre-size (reserve/ensureCapacity) when target known → n true O(1) writes.
  • Never auto-shrinks — a grown-then-shrunk list pins the big backing array (leak) !
  • Slices share backing memory (Go slice, NumPy view) — mutating one mutates the other; append may alias or copy by cap !
  • Unordered O(1) delete: swap-with-last then pop (destroys order).

Strings

Length + contiguous array of fixed-size code units → indexing a code unit is O(1). Usually immutable (Java/C#/Python/JS): edits allocate a new string.

OpCost
index / lengthO(1)
concatO(n+m) (copies both)
substringO(k) copy; O(1) view (Rust/Go/C++)
search naiveO(nm); KMP O(n+m)

Gotchas

  • s += x in a loop is O(n^2) ! — each += copies the whole string. Fix: StringBuilder/strings.Builder/"".join → O(n) (char dynamic array, amortized append).
  • length ≠ user-visible chars. Levels: byte < code unit < code point < grapheme cluster. "😀".length==2 in JS/Java (UTF-16 surrogate pair) !
  • Reverse by code units shatters emoji/combining marks — reverse grapheme clusters !
  • UTF-8: 1–4 bytes/code point, ASCII-compatible, self-syncing; k-th code point is O(n) (byte-indexed).
  • Immutability → cacheable hash (compute once, O(1) thereafter — Java String), safe sharing, interning, ideal map key.
  • Substring O(1) view (Rust &str, C++ string_view, Go slice) aliases parent's lifetime; old Java shared arrays → tiny substring pinned a huge parent (leak) → now copies !
  • == vs .equals() (Java): == is reference identity — literals intern so "a"=="a", but a runtime-built string fails ! Use .equals() for content.

Memory Layout & Semantics

Constants Big-O hides. Two knobs decide real cost: how a value is stored and how it's passed.

SemanticsAssign/pass = / mutation
valuecopies whole value / original untouched (C#/Go/Rust structs, C++ objects, primitives)
referencecopies a handle / both see the change (Java/Py/JS objects)

2-D layout

  • Row-major (C, NumPy): [i][j] at base+(i*ncols+j)*sz — iterate inner index innermost or you stride & thrash cache ! Column-major = Fortran/MATLAB/R.
  • True 2-D = one contiguous block, perfect locality. Jagged (Java int[][]) = array of row pointers, extra indirection, ragged rows, cheap row-swap.

Gotchas / adjacent

  • Value copies can be O(n); reference passing is O(1) but invites aliasing bugs ! Know which your type is.
  • Interning: one canonical copy per distinct immutable value → O(1) ref-equality + memory savings (Java literals, Py identifiers). Rope = tree of string fragments → O(log n) concat/insert, O(log n) index (text editors) vs flat string's O(1) index / O(n) edit.

Linked Lists

OpCost
index / searchO(n) — walk from head
insert/delete at held nodeO(1) splice
insert/delete after searchO(n) (find dominates)
delete tail (singly)O(n) (need predecessor)

Singly=next only; doubly=+prev (O(1) delete any held node); circular=tail→head. Sentinel/dummy node kills head/null edge-cases: dummy.next=head; return dummy.next.

Use when

  • Frequent O(1) splice at held positions, no random access: LRU recency list, run queue, intrusive kernel lists. Else default to array.

Gotchas

  • "insert is O(1)" only at the node — finding it is O(n) ! Pointer overhead + scattered nodes make it 10–100x slower than an array to iterate.
  • Reversal: save curr.next before rewiring or you sever the list !
  • Floyd cycle detect: slow+1, fast+2; meet ⇒ cycle (O(1) space vs hash-set O(n)). Fast gains +1/step in the cycle so the gap must close. Entry: reset one to head, advance both by 1. Middle: fast/slow one pass.
  • Merge sort > quicksort for lists: needs only sequential access + O(1) splice, no random access or aux array, and it's stable. Merge two sorted lists = dummy head + tail, attach smaller, O(n+m) / O(1) space.
  • Intrusive list = next/prev live inside the data object (Linux list_head) — no wrapper alloc, one object in many lists. Delete given only a mid-node: copy successor's value in, unlink successor (fails on tail) !

Stacks (LIFO)

ADT: push/pop/peek/isEmpty — all O(1), all touch only the top. Removal order = reverse of insertion.

BackingNote
dynamic arraypush=append, pop=truncate; O(1) amortized, cache-friendly (default)
linked listpush/pop at head; true worst-case O(1), no resize, pointer overhead

Monotonic stack

  • Keep increasing/decreasing by popping violators → "next greater/smaller", daily temps, largest rectangle, stock span in O(n) (each elem push+pop once) vs naive O(n²).
  • Store indices, not values — gives position for distances/widths !

Gotchas

  • Data-structure stack ≠ call stack (frames region); deep recursion overflows the latter !
  • Guard underflow (pop empty). Min-stack: aux stack of running min → O(1) getMin. Iterative DFS = explicit stack (avoids recursion-depth crash).

Queues & Deques (FIFO)

enqueue back / dequeue front — O(1). Deque = both ends O(1) (subsumes stack+queue).

Circular (ring) buffer

  • Fixed array + head/tail advanced mod cap — nothing shifts. Naive array queue that shifts on dequeue is O(n) !
  • Full-vs-empty both show head==tail ! Fix: explicit count, or leave one slot empty.
ImplTrade
ring buffercache-friendly, zero alloc, fixed cap → back-pressure
linked listunbounded, no resize pause, pointer overhead

Gotchas & uses

  • BFS uses a queue (level-by-level); swap for a stack → DFS. Level-order: record queue size, dequeue exactly that many per level.
  • Priority queue is NOT FIFO — it's a heap ordered by key !
  • Sliding-window-max: monotonic decreasing deque of indices → O(n) vs naive O(nk). Bounded queue = back-pressure; unbounded risks OOM.

Hash Tables

OpCost
insert / lookup / deleteO(1) average, O(n) worst
ordered / range / min-maxunsupported (unordered)

index = hash(key) mod m. Good hash = deterministic, uniform, fast (uniformity matters most). Load factor α=n/m is the master dial. Keep α<~0.75 (open) / ~1.0 (chained). Resize doubles m + rehashes all n (indices depend on m — can't memcpy) → O(1) amortized insert.

Collision resolution

StrategyNote
separate chaininglist/tree per slot; tolerates high α, simple delete, pointer chase
linear probing(h+i); primary clustering, best locality
quadratic / double-hashspreads probes; double-hash kills clustering, 2nd hash cost
Robin Hoodevict "richer" resident; equalizes probe distance

Gotchas

  • O(1) average, not guaranteed — all-collide ⇒ O(n). Hash-flooding DoS: seeded/SipHash, or tree-ify buckets (Java >8 → red-black, O(log n)) !
  • Open-addr delete needs tombstones — clearing a slot breaks probe chains !
  • Must verify key equality after hashing (lossy). equal ⇒ equal hash contract; mutating a key's hash-fields strands the entry !
  • Resize is rehash-all (indices depend on m — can't memcpy) → a single insert can spike O(n); pre-size if final count known. Load factor is the master dial: too high ⇒ long chains/probe runs, too low ⇒ wasted memory + poorer locality.

Sets & Maps (ADT choice)

A set = map whose values don't matter (key→present). Same ADT, two dominant impls:

FlavorImpl / gets you
unorderedhash — O(1) avg, no order (default)
sortedbalanced BST — O(log n), range/floor/ceil/min-max
insertion-orderedhash + linked list (LinkedHashMap, Py dict)
multiset / bagkey→count (Counter) — "how many times"
multimapkey→collection — one-to-many

Set ops

  • union/intersection/diff = O(|A|+|B|); intersect: iterate smaller, probe larger → O(min).

Gotchas

  • Hash iteration order is unspecified and changes on resize/version — relying on it is a portability bug !
  • sorted order (tree) ≠ insertion order (linked-hash) — different guarantees.
  • Tell: "seen / unique / duplicate" → set; "count of / most frequent" → multiset; "in sorted order / range" → tree map. Any O(n²) that repeatedly searches → replace inner scan with O(1) membership.

Trees & Traversals

Connected, acyclic, one root; n nodes = n−1 edges, one path between any two. Depth counts down from root; height counts up from leaves (state edges vs nodes). Balanced ⇒ height O(log n); degenerate ⇒ O(n).

ShapeDef
fullevery node has 0 or 2 children
completelevels filled L→R, last may be partial (heap shape)
perfectall levels full: 2^(h+1)−1 nodes

Traversals — all O(n) time

OrderUse / space
pre (N,L,R)serialize / copy top-down
in (L,N,R)sorted output on a BST; k-th smallest
post (L,R,N)height, free/delete, postfix eval
level (BFS)shortest-by-depth, per-level; queue
  • DFS space O(h); BFS space O(w) (balanced last level ~n/2 ⇒ O(n)).
  • Array layout: child 2i+1/2i+2, parent (i−1)/2 — compact, but only for complete trees ! Deep skewed tree overflows recursion → go iterative !
  • In-order sorts only a search tree, not any binary tree !

Binary Search Trees

Invariant: for every node, entire left subtree < node < entire right subtree (recursive, not just children). In-order ⇒ sorted. All ops O(h).

OpBalanced / degenerate
search / insert / deleteO(log n) / O(n)
min/maxleftmost / rightmost, O(h)
k-th smallestin-order to k; augment subtree size → O(h)

Delete — 3 cases

  • Leaf → unlink. One child → splice child up. Two children → copy in-order successor's key (leftmost of right subtree, ≤1 child), then delete successor !

Gotchas

  • Not inherently O(log n) — sorted/sequential insert (timestamps, auto-IDs) degenerates to an O(n) chain ! → use a balanced tree.
  • Validate by carrying (min,max) range down, NOT comparing only to immediate children !
  • BST invariant (horizontal, sorted) ≠ heap invariant (vertical, parent-child only) !

Balanced BSTs (AVL / Red-Black)

Enforce height O(log n) via rotations (local O(1) re-link, always preserves in-order order). Turns BST's "avg O(log n)" into "worst-case O(log n)".

AVLRed-Black
balancebf∈{−1,0,+1}, h≤1.44 log ncolor rules, h≤2 log n
readsfaster (tighter)slightly slower
writesmore rotationsfewer (O(1) amort.)
best forread-heavy indexwrite/mixed (lib default)

RB properties

  • Root black; NIL black; no red-red edge; every root→null path has equal black-height. Together: longest path ≤ 2× shortest ⇒ O(log n).
  • AVL fixes: LL/RR single rotate, LR/RL double — ≤2 rotations.

Gotchas / uses

  • Rotations never break sort order ! RB is not "perfectly balanced" (up to 2× min height) !
  • Deletion is much harder than insertion (fix-ups cascade) — why interviewers rarely ask you to code it !
  • Java TreeMap/TreeSet, C++ std::map/set, Linux kernel = RB trees. Pointer-scattered → less cache-friendly than a sorted array.

Heaps & Priority Queues

Complete binary tree in a flat array (parent (i−1)/2, children 2i+1/2i+2). Heap property: parent ≤/≥ children (parent-child only — NOT sorted).

OpCost
peek min/maxO(1)
insert (sift-up)O(log n)
extract (sift-down)O(log n)
build-heapO(n) bottom-up heapify
find arbitrary elemO(n)

Gotchas

  • A heap is NOT sorted — in-order is meaningless, only root is extreme !
  • Build-heap is O(n), not O(n log n) — sift-down cost ∝ node height, most nodes shallow ! (n one-by-one inserts is O(n log n)).
  • decrease-key needs elem→index map, or use lazy deletion (push new, skip stale on pop) — Dijkstra.
  • Binary heap = default; d-ary shallower (faster decrease-key, slower extract); Fibonacci O(1) amortized insert/decrease-key but huge constants — rarely worth it !

Patterns

  • k largest in stream: size-k min-heap, pop when >k → O(n log k). Running median: two heaps (max-heap low / min-heap high), O(log n) insert, O(1) query.
  • Heapsort: O(n log n) in-place, not stable. Dijkstra/Prim/Huffman/k-way merge/schedulers.

Tries (Prefix Trees)

Tree keyed on characters: each node = a prefix, each edge = a char, word = root→node path with isEnd flag. Key distributed across the path — shared prefixes stored once.

OpCost
insert / search / startsWithO(L) (key length, indep. of N)
autocomplete prefix PO(P + matches)
count words with prefixO(P) if nodes cache subtree count
  • search checks isEnd; startsWith just checks path exists. Children: fixed array[R] (O(1), wastes null slots) vs hash map (sparse-friendly).
  • Radix/Patricia trie: collapse single-child chains → edge holds a substring; cuts memory on long non-branching runs.

Gotchas

  • Not faster than a hash set for exact lookup (both O(L)) — the win is prefix ops hash can't do !
  • Forgetting isEnd ⇒ "ca" wrongly a word when only "cat" inserted ! Ops are O(L), not O(1) !
  • Alphabet = any symbol set (bytes, Unicode via map, DNA, bits for XOR/IP-prefix). Longest-prefix match (routing): record last isEnd while descending. Memory-heavy on sparse fan-out (null child slots) — radix/Patricia collapses chains to fix it.

Graphs — Representations

Vertices + edges; may have cycles, be disconnected, directed, weighted. Representation fixes the two hot questions: "who are u's neighbours?" and "is u–v an edge?".

RepSpace / edge? / neighbours
adjacency listO(V+E) / O(deg) / O(deg) — sparse default
adjacency matrixO(V²) / O(1) / O(V) — dense only
edge listO(E) / O(E) / O(E) — edge-centric (Kruskal, Bellman-Ford)
  • Sparse (E≈V): list. Dense (E≈V²) or O(1) edge-check or matrix-algebra: matrix. Need O(1) edge-check on sparse: list with hash-set neighbours.
  • V=10^6, E=2·10^6: list ≈ tens of MB; matrix = 10^12 cells (infeasible) !

Gotchas

  • Undirected edge stored twice in a list; matrix symmetric ! total in-deg = total out-deg = E; deg sum (undirected) = 2E.
  • Matrix neighbour iteration O(V) even for degree 1 ! Traverse all components (loop over unvisited starts) or you miss nodes ! DAG ⇒ topological order (scheduling / prereqs).

Graph Traversal & Algorithms

Both BFS and DFS visit every vertex+edge once ⇒ O(V+E) on an adjacency list. A visited set is mandatory (cycles ⇒ infinite loop) and you must launch from every unvisited vertex to cover all components.

AlgoStruct / gets you
BFSqueue — shortest path in unweighted graph, level order
DFSstack/recursion — cycle detect, topo, path exists, SCC
Dijkstramin-heap — shortest path, non-negative weights, O((V+E)log V)
Bellman-Fordedge list — handles negative edges, detects neg cycles, O(VE)
topo sortKahn (BFS on in-degree) / DFS post-order — DAG only

Gotchas

  • BFS gives shortest path only when edges are unit-weight — weighted needs Dijkstra !
  • Dijkstra breaks on negative edges (a settled node may still improve) — use Bellman-Ford ! Lazy-delete stale heap entries (push new dist, skip if > recorded).
  • Directed-cycle detect = DFS 3-colour (white/grey/black); a back-edge to a grey node ⇒ cycle. Undirected cycle = DSU or DFS ignoring the parent edge !
  • Topo order exists iff DAG; Kahn leftover nodes with in-degree>0 ⇒ a cycle. Grid/matrix problems = implicit graph (cell = node, 4/8 neighbours = edges).

Union-Find (Disjoint Set Union)

Dynamic connectivity: find(x) (which set?) + union(x,y) (merge). Forest in a parent[] array; root is its own parent; same set ⇔ same root. Space O(n).

find(x):  # path compression
  if parent[x]!=x: parent[x]=find(parent[x])
  return parent[x]
union(x,y):
  rx,ry=find(x),find(y)
  if rx!=ry: parent[rx]=ry   # +by rank/size
  • Two optimizations, need BOTH for O(α(n)):
    • union by rank/size — hang smaller under larger, height O(log n)
    • path compression — re-point visited nodes at root.
    Either alone = O(log n) amortized !
  • α(n) (inverse Ackermann) ≤ 4 for any real n → "near-constant".

Gotchas / uses

  • Union only — no split / undo / delete in vanilla form ! Deletion needs a rollback DSU (drop path-compression so changes are revertible) or process ops offline in reverse (deletions become additions). Tells you whether connected, not the path !
  • Union by size gives component counts for free; by rank tracks a height bound — either yields O(log n) height. Don't update ranks during path compression (rank stays a loose upper bound, which is fine).
  • Kruskal MST (cycle test), count components (start n, dec on real merge), undirected cycle detect, accounts-merge, grid percolation. Prefer over BFS/DFS when merges+queries are interleaved & numerous.

Segment Trees & Fenwick (BIT)

Range query with updates. Prefix-sum array: O(1) query but O(n) update. These buy O(log n) both.

StructQuery / update / space
prefix-sumO(1) / O(n) / n — static only
Fenwick (BIT)O(log n) / O(log n) / n — invertible ops
segment treeO(log n) / O(log n) / ~4n — any assoc op
prefix(i):          update(i,d):
 s=0                 while i<=n:
 while i>0:            tree[i]+=d
  s+=tree[i]           i+=i&(-i)
  i-=i&(-i)          # low-bit trick
  • BIT is 1-indexed (low-bit needs i≠0). Range sum = prefix(r)−prefix(l−1).

Gotchas

  • Prefix-sum ≠ Fenwick — a plain array can't update cheaply ! BIT can't do min/max (not invertible — can't subtract a prefix) !
  • Range update on a seg-tree needs lazy propagation (stamp delta on covered nodes, push down only when a later query descends) or it's O(n log n) ! Size seg-tree ~4n (unbalanced when n≠2^k) or recursion indexes past the array & corrupts ! Static + idempotent (min) → sparse table instead.
  • BIT does range update via difference array: upd(l,+d); upd(r+1,−d); range-upd+range-query = two BITs. k-th smallest = BIT over value-freqs + binary-lifting on bits, O(log n). Seg-tree node can carry a struct (sum+min+max) with an assoc merge.

Skip Lists & Treaps

Sorted linked list + probabilistic "express lanes". Node promoted to level k+1 with prob p (≈0.5) → level i has ~n/2^i nodes, ~log n levels. Search: top-left, move right while ≤ target, drop a level on overshoot.

OpCost
search / insert / deleteO(log n) expected
rank / selectO(log n) via per-pointer span
  • vs balanced BST: trades guaranteed for expected O(log n), but no rotations/color rules → simpler code + far easier concurrency (local pointer splices, no global rebalance).
  • ~1/(1−p) pointers/node (~2 at p=0.5). Treap = BST + heap on random priorities → expected O(log n), easy split/merge.

Gotchas / uses

  • O(log n) expected, not worst — but randomness is internal (no adversarial worst case like hash flooding) ! Less cache-friendly than a B-tree.
  • Redis ZSET (score-ordered + rank via per-pointer spans), LevelDB/RocksDB memtable, Java ConcurrentSkipListMap.

B-Trees & B+ Trees

Balanced multiway search trees for block storage (disk/SSD/page): one node = one page, fanout 100–1000+, height O(log_b n) = 3–4 levels. Optimizes block transfers, not comparisons.

vs red-black (both O(log n))
fanout / height500 / ~4 vs 2 / ~30
disk reads/lookup3–4 (often 1) vs ~30 seeks
  • B+ tree: values only in leaves, internal = key-only routing (higher fanout), leaves linked → range scan = descend once + walk leaf chain, O(log n + k). Nearly all DB indexes.
  • Insert splits a full leaf, promotes median up — tree grows at the ROOT, keeps leaves equal-depth. Delete borrows/merges to stay ≥ half full.

Gotchas

  • "B" ≠ binary ! Node ~50–70% full (split slack) ! Hash index can't range-scan; B+ keeps order.
  • Write amplification (in-place page rewrite) → LSM-tree for write-heavy (sequential appends + compaction, read-amplification trade). LSM memtable is often a skip list; SSTables merge-compact in the background.
  • Cost model is block transfers, not comparisons — a red-black tree (~30 pointer hops = ~30 seeks) loses badly to a B+ tree's 3–4 page reads on disk, even at equal O(log n) !

Probabilistic Structures

Trade exactness for tiny space with bounded error. Store a fingerprint, not the elements — can't enumerate back.

StructAnswers / error
Bloom filtermembership — false positives, never false negatives
Count-Min Sketchfrequency — over-counts only
HyperLogLogdistinct count — ~2% err, ~1.5KB for billions
  • Bloom: m bits + k hashes; insert sets k bits, query = all-k-set? Any 0 ⇒ absent. m=−n·lnε/(ln2)², k=(m/n)ln2 ≈ 1.44·log₂(1/ε) bits/elem.
  • CMS: d rows × w cols, increment one/row, estimate = min across rows (min cancels collision inflation).
  • HLL: leading-zero run r ⇒ ~2^r distinct; bucket + harmonic mean.

Gotchas

  • Bloom has no false negatives — claiming otherwise is the classic error ! Can't delete from a plain Bloom (shared bits) → Counting Bloom (counters) !
  • ε degrades if filled past design n — size for expected n up front ! Mergeable: Bloom=OR, HLL=per-bucket max, CMS=add → per-shard then combine.
  • Placement: Bloom in front of a slow disk/DB skips lookups for definitely-absent keys (crawler "seen this URL?", LSM read path). HLL for "unique visitors" billions in ~1.5KB; CMS for "heavy hitters" / rate-limit approx.

Composite & Specialized

Pattern: pair two primitives, each covering the other's weakness, linked by an O(1) back-pointer/index, or augment a BST node with a derived summary.

LRU cache — O(1) get & put

  • Hash map key→node + doubly linked list (recency order). get: map locate O(1), splice to head O(1). Evict = pop tail. Doubly (not singly) so you unlink a held node in O(1) !
  • LFU harder: key→(val,freq) + freq→list + minFreq; on access bump freq & move node between freq-lists, evict from minFreq list's tail.

★ Structure-Choice Review Checklist

Operation profile

  • ☐ Enumerated every op + its frequency; optimized the hot-path op, not a rare one.
  • ☐ Complexity target inferred from input size & time budget before picking a tool.

Ordering & ranges

  • ☐ Chose hash only when order/range genuinely unneeded — not paying O(log n) for ordering you never use, nor breaking on required order.
  • ☐ "sorted" vs "insertion" order distinguished; no reliance on hash iteration order !

Complexity honesty

  • ☐ Stated worst case, not just happy path: hash O(1) is average (O(n) adversarial / DoS); append & DSU are amortized (spikes) !
  • ☐ Linked-list insert costed as O(n) unless a node reference is already held.

Invariants preserved

  • ☐ Map/tree keys immutable in their hash/compare fields for their lifetime !
  • ☐ BST validated by range, not neighbours; two-child delete promotes the successor.
  • ☐ Composite back-pointer/index updated on every move & delete !
  • ☐ DSU uses both compression + rank/size; seg-tree range-update uses lazy prop.

Memory & hardware

  • ☐ Fits in memory (matrix O(V²) sanity-checked); resize 3x-peak / pre-size considered.
  • ☐ Cache locality weighed — a contiguous array may beat an asymptotically-equal pointer structure.
  • ☐ Right cost model: block transfers (B+ tree on disk) vs comparisons (red-black in RAM).
