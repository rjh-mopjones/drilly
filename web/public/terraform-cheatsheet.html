The plan/apply Workflow

flowchart LR W["write HCL"] --> I["init
providers+backend"] I --> P["plan
refresh+diff → proposal"] P --> A["apply
converge"] A --> D["destroy"]

plan = refresh real state → build DAG → diff desired vs state vs reality → propose create / update / replace / destroy. apply executes it. apply is NOT transactional — it can fail mid-graph, leaving partial state. Save the plan (-out) and apply that exact artifact so what you reviewed is what runs.

  • Diff symbols: + create · ~ update in place · -/+ replace (destroy then create) ! · - destroy · <= read (data source).

IaC Tool Landscape

  • Terraform builds the house; Ansible furnishes the rooms. TF provisions cloud/SaaS; config-mgmt configures software on it — mature stacks use both.
  • Run-based (TF: acts only on apply) vs reconcile-loop (Crossplane/K8s: actively re-fixes drift, no apply needed).
  • HCL is a deliberately constrained DSL — no arbitrary control flow — so a plan is a low-magic, reviewable preview. Pain with for_each/dynamic/templatefile is the signal to step up to Pulumi/CDK !
  • Senior framing: name the provisioning vs configuration boundary and combine tools; don't argue "Terraform for everything."

HCL — Blocks & Types

resource "aws_instance" "web" {   # type + 2 labels
  ami           = var.ami         # arg = expr
  instance_type = "t3.micro"
  tags = { Name = "web" }         # map value
  root_block_device { size = 20 } # nested block
}

Uniform grammar: resource/variable/output/module/provider/data/terraform are all blocks + labels + arguments. Ref aws_instance.web.id is both a value and a graph edge.

dynamic blocks & templatefile

dynamic "ingress" {          # generate N nested blocks
  for_each = var.ingress_rules
  content {
    from_port   = ingress.value.from
    to_port     = ingress.value.to
    cidr_blocks = ingress.value.cidrs
  }
}
user_data = templatefile("${path.module}/init.sh.tftpl", {
  region = var.region, port = var.port })
# init.sh.tftpl — full expr lang inside
%{ for p in ports ~}
open ${p}
%{ endfor ~}
  • dynamic: for_each feeds the collection, content is the per-item template, ingress.value/.key = current item. For genuinely variable-length nested blocks only.
  • They add indirection — reader can't see concrete blocks. Small & fixed count → write blocks out explicitly; nested dynamic = write-only code !
  • Heredoc <<-EOT (the - strips indent) for short inline text; templatefile for substantial/reused content that wants its own file + highlighting. Supports %{ for } / %{ if } directives.

count vs for_each

# count: conditional single resource
count = var.enabled ? 1 : 0
# for_each: set/map of similar resources (STABLE keys)
resource "aws_instance" "n" {
  for_each      = toset(var.names)
  instance_type = "t3.micro"
  tags = { Name = each.key }
}
# transform a list → keyed map for for_each:
for_each = { for u in var.users : u.name => u }
countfor_each
overnumbermap / set
addressx[0]x["key"]
remove middleshifts & recreates all after it !only that key
  • Prefer for_each for collections of similar resources — index-independent addressing means adding/removing one doesn't churn the rest.
  • Keys must be known at plan time — a for_each over a computed value forces -target gymnastics !
  • count still wins for a pure on/off toggle (count = var.enabled ? 1 : 0) — one resource, no keying needed.

count → for_each without destroy

moved { from = aws_instance.svc[0]
        to   = aws_instance.svc["api"] }
# then: plan must show ONLY address moves, 0 create/destroy

Swapping the meta-arg alone re-addresses [0]→["api"] and plans a full destroy+recreate. moved blocks (or state mv per instance) tell TF the addresses moved — reviewable & reproducible.

Variables · Outputs · Locals

variable "env" {
  type        = string
  default     = "dev"
  description = "deploy target"
  nullable    = false
  validation {                        # 1.9: cross-var refs ok
    condition     = contains(["dev","prod"], var.env)
    error_message = "env must be dev|prod"
  }
}
locals { name = "${var.env}-app" }    # computed, DRY
output "id" { value = aws_instance.web.id
              sensitive = true }

Precedence (low → high)

default → env TF_VAR_x → terraform.tfvars / *.auto.tfvars → -var-file → -var (CLI wins).

  • Variables = module inputs; outputs = module outputs (the public API). Locals = internal aliases, not inputs.
  • sensitive=true redacts CLI/plan output only — value is still plaintext in state !
  • Prefer object-typed vars over many loose scalars for a clean module surface — optional(type, default) attrs keep the call site terse.
  • nullable = false forbids callers passing null; validation (1.9+ can cross-reference other vars) catches bad input at plan time with a clear message.
  • Locals compute once and are referenced many times (local.name) — DRY, but they're not inputs and can't be overridden per-call.

Providers

terraform {
  required_version = "~> 1.7"
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.0" }
  }
}
provider "aws" { region = "us-east-1" }
provider "aws" { alias = "west", region = "us-west-2" }
resource "aws_s3_bucket" "b" { provider = aws.west }
ConstraintMeans
~> 5.0>=5.0,<6.0 (pessimistic, allow patch/minor)
~> 5.30.0>=5.30.0,<5.31.0 (patch only)
>= 5.0, < 6.0explicit range
  • Commit .terraform.lock.hcl (pins exact versions + checksums → reproducible plans) ! init -upgrade to re-resolve/bump.
  • Pass aliased providers into modules explicitly (providers = { aws = aws.west }); never hardcode a provider inside a reusable module.
  • Never hardcode creds — env vars, shared config, OIDC, or assume-role.
  • Tiers: official (HashiCorp), partner (vendor-maintained, verified), community — check maintenance before depending on community ones.
  • Meta-provider chicken-egg !: a kubernetes/helm provider configured from an aws_eks_cluster you create in the same run can't be configured against infra that doesn't exist yet (provider config evaluates early). Split into two states — one builds the cluster, one manages workloads — wired by terraform_remote_state.

Resources & Data Sources

resource "aws_instance" "web" { ami = data.aws_ami.al.id }

data "aws_ami" "al" {          # READ-ONLY lookup, no lifecycle
  most_recent = true
  owners      = ["amazon"]
  filter { name = "name" values = ["al2023-*"] }
}
  • Resource = Terraform owns its full lifecycle (create/update/destroy). Data source = read existing state from a provider; refreshed each plan, never destroyed.
  • Use data sources to reference infra managed elsewhere (another state, ClickOps, a shared AMI/VPC) without importing it.
  • Computed attributes (IDs, ARNs) are unknown until apply — showing as (known after apply); you can't use them where a value must be known at plan time (e.g. for_each keys, count) !
  • terraform_remote_state data source reads another state's outputs (tight coupling); tag/name lookups are looser.
  • replace_triggered_by = [x.attr] forces a replace when a referenced attr changes; ignore_changes does the opposite (stops updates). Don't confuse them !
  • external data source shells out to a program returning JSON — an escape hatch for lookups no provider offers; keep it pure/read-only.
  • A data source that depends on a not-yet-created resource reads at plan time and fails or returns stale — reference the resource attr (or split the run) instead !

State — what & why

  • State = the map from config addresses → real resource IDs + cached attributes + dependency metadata. Terraform diffs config vs state vs reality; without it there's no way to know what it already owns.
  • State holds secrets in PLAINTEXT (DB passwords, keys, tokens) — whoever reads state reads them. Encrypt at rest, lock down access, keep it out of git !
  • Never hand-edit terraform.tfstate — use state subcommands / moved / import ! Hand edits are the fastest way to corrupt it.
  • Lose state → Terraform forgets it owns the infra → tries to recreate everything (or leaves orphans) ! Version the backend for recovery.
  • Config is disposable, state is precious. You can retype resource blocks by hand; you cannot recompute cloud-assigned IDs — the only rebuild path is import per resource.
  • serial = write counter (optimistic-concurrency / stale-write detection); lineage = unique id fixing a state's ancestry (warns if you point at the wrong/unrelated state). Terraform maintains both — another reason not to hand-edit.
  • Outputs live in state (top-level outputs) — that's how terraform_remote_state reads another config's values. Sensitive outputs are plaintext there too.
  • terraform.tfstate.backup = the immediately-prior local state (one-deep undo), not a backup strategy — use versioned remote storage for real recovery.
terraform state list
terraform state show aws_instance.web
terraform state pull > backup.json     # snapshot

Remote Backend & Locking

terraform {
  backend "s3" {
    bucket       = "acme-tfstate"
    key          = "prod/app/terraform.tfstate"
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true         # S3-native lock (1.10+)
    # dynamodb_table = "tf-locks"  # classic lock
  }
}
  • Remote state = team collaboration + locking so two concurrent applies can't corrupt state. S3+DynamoDB, Terraform Cloud, GCS, azurerm all support locks.
  • Partial config: leave secrets/env out of the block → pass with -backend-config=… or a file.
  • force-unlock <ID> only when you're certain no apply is running — force-unlocking a live apply → concurrent writes → corruption !
  • Isolate state per component + per env → small blast radius, independent lifecycles.
BackendLock · when
s3DynamoDB or .tflock · AWS
gcsbuilt-in (object generation) · GCP
azurermblob lease · Azure
remote/TFCrun queue · managed runs + policy
httpoptional LOCK/UNLOCK · GitLab, custom
localnone · throwaway only !

Match the backend to where infra + identity already live. Version the state bucket — recover a botched state push / partial apply / wrong state rm; the lock table stays ephemeral (don't version it).

State Operations

terraform import aws_instance.web i-0abc123  # or import{} block
terraform state mv  A  B      # rename/move, NO recreate
terraform state rm  ADDR      # forget (does NOT destroy real infra)
terraform apply -replace=ADDR # force recreate (was: taint)

Prefer declarative refactors (version-controlled)

moved   { from = aws_instance.a  to = aws_instance.b }
import  { to = aws_s3_bucket.logs  id = "acme-logs" }
removed { from = aws_instance.old }   # drop w/o destroy
  • moved/import/removed blocks survive across the team & CI — better than one-off state mv/rm ! Always plan to verify after.
  • Import to adopt brownfield: plan -generate-config-out=gen.tf scaffolds HCL; iterate until zero-diff plan, then apply. Zero diff proves config matches reality.
  • state rm then re-import = the manual way to move a resource between states.

Modules

module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 5.0"           # PIN registry/git modules !
  cidr    = "10.0.0.0/16"
  providers = { aws = aws.west }
}
# git:   source = "git::https://…/mod.git?ref=v1.2.0"
# local: source = "./modules/network"
subnet_id = module.vpc.public_subnets[0]
  • Root module = your config; child modules = reusable groups. Public API = variables (in) + outputs (out); internals stay hidden.
  • Design: single purpose, sensible defaults, minimal required inputs, composition over one god-module !
  • Don't wrap a single resource for no reason; don't hardcode providers/regions/creds inside reusable modules.
  • Pin registry & git modules by version/ref — unpinned = surprise breakage on the next init !
  • Nested modules are fine; deep nesting hurts readability — keep the tree shallow.
  • A child module has no backend — only root modules have state; the same module is reused by many thin per-env roots.
  • Publish approved modules via an internal registry (TFC or a git-tag convention) so teams consume versioned, reviewed building blocks.

lifecycle & Meta-args

lifecycle {
  create_before_destroy = true    # no-downtime replace
  prevent_destroy       = true    # guard prod DB / state bucket !
  ignore_changes        = [tags, desired_count]
  replace_triggered_by  = [aws_launch_template.x.latest_version]
  precondition  { condition = …  error_message = … }
  postcondition { condition = …  error_message = … }
}

Meta-args on any resource: count · for_each · provider · depends_on · lifecycle.

  • create_before_destroy needs a unique name/name_prefix or the new one collides with the old !
  • ignore_changes tolerates expected out-of-band drift (autoscaler count, tags) — but it can mask real config drift; scope it narrowly !
  • prevent_destroy stops this apply, but is bypassable by removing the resource block — not a substitute for IAM/backups.
  • precondition/postcondition assert invariants at plan/apply (e.g. "AMI is x86_64", "instance got a public IP") — fail fast with a message instead of a confusing downstream error.
  • Order of a replace under create_before_destroy: new created → dependents re-pointed → old destroyed. Without it: old destroyed first → downtime window !

Dependencies & the Graph

  • Terraform builds a DAG from resource references, then applies independent nodes in parallel (-parallelism=10); destroys in reverse order.
  • Implicit deps (a references b.id) are preferred — they're precise and self-documenting.
  • depends_on = [aws_iam_role_policy.x] only when there's no reference link (e.g. an IAM policy that must exist before an instance uses it). It's coarse — serialises and reduces parallelism !
  • "Cycle: A → B → A" → break with indirection: split a resource, move one side to a data source, or restructure depends_on. terraform graph | dot to visualise.
  • Over-using depends_on for ordering you could express by reference = slower applies + hidden coupling.
  • Destroy edges are inferred too: to delete b that a depends on, TF destroys a first. A depends_on that's really data lets you drop it once you wire the reference.

# → split one attr onto a separate resource, or use a

#   reference points one way only.

Provisioners — last resort

resource "aws_instance" "web" {
  # PREFER user_data / baked AMI / config mgmt over these !
  provisioner "remote-exec" {
    inline = ["sudo systemctl restart app"]
  }
  provisioner "local-exec" {              # runs on the runner
    command = "echo ${self.private_ip} >> hosts"
  }
  provisioner "local-exec" {
    when = destroy                        # cleanup hook
    command = "./deregister.sh"
  }
}
  • Provisioners are imperative escape hatches — not tracked in state, run once at create/destroy, and a failure marks the resource tainted (recreated next apply) !
  • Prefer immutable infra: bake images (Packer), pass user_data, or hand off to Ansible/cloud-init.
  • null_resource/terraform_data + triggers to run a provisioner on arbitrary change, but treat as a smell.

Drift Detection & Reconciliation

  • Drift = real infra diverges from state (console edits, other tools, autoscalers). Every plan refreshes and surfaces drift as a diff even with no config change.
SituationFix
config is source of truthapply → revert reality to config
the change is desiredupdate config to match, then apply
resource unmanagedimport it
accept reality into stateapply -refresh-only
expected churnlifecycle { ignore_changes }
  • Continuous detection: scheduled plan -detailed-exitcode in CI (exit 2 = drift), Terraform Cloud drift detection, driftctl.
  • Prevent it: least-privilege IAM so humans can't ClickOps prod !
  • Ask why drift happened: a recurring console edit is usually missing config or over-broad access, not just noise. Fix the source, not the symptom.
  • -refresh-only updates state to match reality without changing infra — the safe way to adopt drift you've decided is legitimate.

Testing, Validation & Policy

  • Cheap → expensive: fmt -check → validate → tflint → terraform test (1.6+, *.tftest.hcl) → Terratest (Go, spins real infra).
  • Static security scan: tfsec / checkov / Trivy — public buckets, open SGs (0.0.0.0/0), unencrypted volumes.
  • Policy-as-code: Sentinel (TFC/Enterprise) or OPA-Conftest (Rego over plan -json) → enforce "no public S3", tag standards, allowed instance types.
  • In-config assertions: variable.validation, precondition/postcondition, and standalone check blocks (1.5+) that assert without blocking apply.
  • Cost: Infracost diff in the PR. Wire the whole ladder into pre-commit + CI.
  • terraform test spins real resources in a temp state and asserts on plan/apply, then auto-cleans — integration confidence without Go. check blocks assert continuously (post-apply health) without failing the run.
  • Where possible test the module in isolation (its own fixtures) so a failure localises to the module, not the whole root.

CI/CD & Automation

  • plan-in-PR → review → apply-on-merge. Post plan as a PR comment; apply the saved -out plan so what's reviewed is exactly what runs.
  • Tools: Atlantis (PR-comment plan/apply + locking) · Terraform Cloud/Enterprise (remote runs, Sentinel, private registry) · GitHub Actions / GitLab CI.
  • OIDC / workload identity for cloud creds — no long-lived static keys in CI !
  • Gate apply behind required review + branch protection. Serialise applies per state (locking) so two merges can't race.
  • No undo — roll forward or revert the commit & apply. There's no automatic rollback.
  • Split creds: plan = read-only role, apply = write role — a leaked PR-CI token can't mutate infra. Prod apply behind a manual approval gate.
  • Scheduled plan -detailed-exitcode (exit 2 = drift) as a nightly job surfaces out-of-band changes before they bite a real deploy.

Security & Secrets

  • Secrets always land in state in plaintext — that's the core risk. Encrypt the backend, restrict who can read it, keep state out of git !
  • Never put secrets in code/tfvars/git. Source them at apply time: env vars, Vault provider, cloud secrets manager, or CI OIDC.
  • sensitive = true redacts CLI/plan output only — not state, and it propagates to any output derived from it !
  • 1.10+ ephemeral values/resources/write-only args keep some secrets out of state entirely — prefer where supported.
  • Least-privilege the Terraform role; separate plan (read) vs apply (write) creds; scan for exposed secrets (checkov/tfsec) and open SGs in CI.

Terraform at Scale

Organising principle = blast radius: how much can one apply break? One giant state hurts four ways:

ProblemWhy
slow plansevery plan refreshes every resource — thousands of API calls
huge blast radiusone bad plan can propose destroying unrelated critical infra !
lock contentionone lock per state → only one engineer across all teams applies at a time
coupled lifecyclesnetwork + app changes review & fail together
  • Decompose into layers by rate-of-change: foundation (VPC/DNS/IAM, monthly) → data (DB/buckets/queues) → app (many deploys/day). Each layer gets its own state → independent lock + lifecycle + blast radius.
  • Cross the seams deliberately: terraform_remote_state (tight — reads another state's outputs) or data-source/tag lookup (loose — discover by convention). Multiply the grid by env (dev/stage/prod).
  • Split state, share modules: many small versioned modules + thin per-env roots — not a god module (as coupled as a god state) !
  • DRY tooling: Terragrunt or native for_each over an env map + internal module registry + policy-as-code. Ownership = CODEOWNERS + separate backends.

Scenario Playbooks — safe moves

Reason from three anchors, in order: blast radius → state layout → plan/review/apply. Look before you leap, decide intent, make the smallest reversible change.

console change (drift)plan to see diff → revert (apply) or adopt (-refresh-only) or ignore_changes
plan wants to destroy prod DBSTOP — is it a -/+ replace? guard with prevent_destroy + human
stuck lockconfirm nothing running → force-unlock ID !
rename into a modulemoved block (preserves resource, no recreate)
adopt ClickOps infraimport block → iterate to zero-diff plan

  • Anti-patterns to flag on sight: hardcoded secrets, no locking, one giant state, unpinned modules, habitual -target, manual state edits, ClickOps.
  • An empty-looking plan isn't safe to auto-approve — a one-line change can trigger a fleet replacement or count-shift !

Upgrades & Troubleshooting

terraform init -upgrade         # bump providers, rewrite lock
TF_LOG=DEBUG TF_LOG_PATH=t.log terraform plan
  • Upgrade core one minor at a time (1.5→1.6→1.7); after init, plan should be empty (core upgrade changes state format, not infra). Pin required_version.
  • Provider bumps are where breaking changes bite — read the provider upgrade guide, widen constraint, init -upgrade, scrutinise the diff. State schema migrates automatically on first use.

★ Plan Review Checklist

  • ☐ Any destroy / replace (-/+) — is downtime / data-loss intended? Prod DB & state bucket guarded by prevent_destroy? !
  • ☐ Unexpected drift in the diff — did someone change it out-of-band?
  • ☐ Secrets in the diff / plan output leaking to CI logs? sensitive set on secret-bearing values?
  • ☐ A count index shift recreating unrelated resources? Prefer for_each.
  • ☐ Change scoped to the right state / workspace / env (not prod by accident)?
  • ☐ Providers & modules pinned; .terraform.lock.hcl committed.
  • ☐ No hardcoded creds; backend encrypted + locked; least-privilege apply role.
  • ☐ No stray -target / -replace hiding a partial apply.
  • ☐ Applying the saved plan (-out) — the exact reviewed artifact.
  • ☐ fmt/validate/tflint/policy scan green; refactors expressed as moved/import blocks.
