Three families & how to choose

80% of the decision is the first question. Everything else is detail.

Log-based — Kafka, Pulsar, Kinesis

Append-only retained commit log; broker dumb, consumer smart (tracks its own offset). Read ≠ delete; ages out by time/size. Owns: replay, event-sourcing, fan-out to many independent groups, huge throughput.

Queue / smart-broker — RabbitMQ, SQS

Broker smart (routing, per-msg ack, redelivery, priorities, TTL, DLX); message deleted on ack. Owns: task queues, RPC, work distribution, conditional routing. No replay.

Lightweight — Redis pub/sub, core NATS

In-memory, sub-ms, fire-and-forget. Signalling, cache invalidation, service chatter. Add JetStream / Redis Streams when you need durability.

Decision: replay / many readers / very high tput → log. Rich routing / priorities / "do once" → queue. Ephemeral signalling → lightweight. "We already run X" is a legit reason — one on-call rota beats a second best-fit system.

Messaging patterns & topologies

  • Point-to-point (queue): one message → exactly one consumer. Work distribution.
  • Pub/sub: one message → every subscriber. Fan-out / broadcast.
  • Competing consumers: N workers pull from one queue for horizontal scale — ! destroys ordering across workers unless sharded by key.
  • Fan-out: one event → many independent handlers (SNS→N·SQS; Kafka topic→N groups).
  • Request-reply (RPC): temp reply-queue + correlation-id; async messaging faking sync call.
  • Pipes & filters: chain stages, each consumes+produces; topic per stage.
  • Claim-check: big payload → blob store (S3), send a pointer on the bus. Keeps messages small (Kafka default message.max.bytes≈1MB).
  • Routing slip / scatter-gather: attach itinerary; fan out then aggregate replies.

Decouple in time (consumer offline), space (no direct addressing), and volume (buffer bursts).

Delivery semantics

GuaranteeAck timingFailure result
At-most-onceack before processingcrash → message lost
At-least-onceack after processingcrash → redelivered (dup)
Exactly-onceatomic process+ackhard; broker-scoped only

Pragmatic default: at-least-once + idempotent consumer. You cannot get end-to-end exactly-once across arbitrary side-effects (the two-generals problem) — you get effectively-once by deduping.

  • Kafka EOS = idempotent producer + transactions, but only Kafka→Kafka (read-process-write inside the cluster). A DB write or HTTP call breaks it.
  • The knob that sets your guarantee is when you ack/commit vs when the side-effect lands.
  • ! "Exactly-once" in marketing usually means at-least-once + broker dedup, not true EOS across systems.

Ordering & partitioning

Ordering is never global — it is scoped to a lane. The scope shapes your design.

  • Kafka/Kinesis/Pulsar: ordered per partition/shard only. Route a key to a lane: hash(key) % partitions.
  • RabbitMQ: FIFO per queue, single consumer. Consistent-hash exchange to shard by key.
  • SQS FIFO: order within a MessageGroupId.

Ordering ⇄ parallelism tradeoff: more partitions = more parallelism but weaker global order. Strict total order = 1 partition = throughput ceiling.

! Retries reorder. A failed-then-retried record can land after a later one. Fix: enable.idempotence=true (producer tags seq numbers, broker dedups + preserves order) and cap max.in.flight.requests.per.connection ≤5.

! Adding partitions later re-buckets keys → same key now in two partitions → order breaks. Partition count is near one-way.

Backpressure, flow control & lag

Push vs pull

Pull (Kafka, SQS, Redis Streams): consumer sets its own pace — natural backpressure, can't be overwhelmed. Push (RabbitMQ, SNS): broker sends; needs prefetch (basic.qos prefetch_count) to bound in-flight and stop a slow worker drowning.

Consumer lag

lag = log-end-offset − committed-offset

The #1 health metric for log brokers. Flat/growing lag = consumers can't keep up → scale out (≤ partition count), optimise processing, or shed load.

  • ! Unbounded queue anti-pattern: a queue with no depth limit + slow consumer = memory blowup → broker OOM (RabbitMQ) or disk fill (Kafka). Cap: TTL, max-length, DLQ overflow, MAXLEN.
  • Backpressure must propagate upstream — dropping, buffering to disk, or 429-ing the producer beats silent unbounded growth.
  • Prefetch tuning: too low (=1) starves fast consumers; too high hoards messages at one slow worker and unbalances the fleet. Start ~10–50 for uniform short tasks, drop toward 1 for long/uneven work.
  • ! RabbitMQ memory (vm_memory_high_watermark) or disk-free alarm blocks all publishers broker-wide until it clears — not per-queue.

Kafka architecture quick-ref

Distributed, replicated, append-only commit log with pub/sub bolted on — not a queue.

  • Topic = logical stream → N partitions. Partition = ordered immutable log; unit of ordering + parallelism + replication.
  • Offset = 64-bit permanent address in a partition; consumers commit it.
  • RF (prod default 3): 1 leader serves reads/writes, followers pull. ISR = replicas caught up within replica.lag.time.max.ms.
  • Durability contract: acks=all + min.insync.replicas=2 + RF=3 → survives 1 broker loss, still writable.
  • KRaft: built-in Raft metadata quorum, GA + default — ZooKeeper removed.
  • Rides OS page cache + sendfile zero-copy; partition is a file appended/read sequentially.

! Unclean leader election (unclean.leader.election.enable=true) lets an out-of-sync replica become leader → data loss for availability. Keep false for durability.

Kafka producer knobs

acks=all                 // 0 fire&forget, 1 leader-only, all=ISR
enable.idempotence=true  // no dup/reorder on retry (default now)
max.in.flight...=5       // ok w/ idempotence, else 1 for order
linger.ms=5              // wait to batch (latency↔throughput)
batch.size=32768         // bytes per partition batch
compression.type=lz4     // lz4/zstd/snappy/gzip
retries=MAX_INT          // + delivery.timeout.ms caps total
  • acks: 0=lose on crash, 1=lose if leader dies pre-replication, all=durable (w/ min.insync.replicas).
  • Batching: linger.ms + batch.size trade a few ms latency for large throughput/compression gains.
  • Partition choice: hash(key)%N if keyed, else sticky batching.
  • ! acks=1 is the classic silent-data-loss default — leader acks then dies before a follower copies.
  • ! Even acks=all loses data if min.insync.replicas=1 — "all ISR" can shrink to one replica when followers fall out. Pair with min.insync.replicas=2.
  • Sync vs async send: send().get() blocks per record (safe, slow); async send(rec, cb) pipelines but you must handle the callback exception or drop failures silently.

Kafka consumers & groups

  • Group = consumers sharing a subscription; broker assigns one partition → one consumer in the group. Parallelism ≤ partition count — ! extra consumers sit idle.
  • Offsets committed to __consumer_offsets. Auto-commit (enable.auto.commit, every 5s) → dup or loss window; manual commit after processing for at-least-once.
  • Rebalancing: membership change reassigns partitions. Eager = stop-the-world (all revoke). Cooperative (incremental) only moves what must move — prefer it.
  • Static membership (group.instance.id) skips rebalance on brief restarts within session.timeout.ms.
while(true){
  records = consumer.poll(100ms);
  process(records);          // do work first
  consumer.commitSync();     // then commit → ≥once
}

! Slow processing > max.poll.interval.ms → broker thinks you died → rebalance storm. Shrink max.poll.records or process async.

Kafka retention, compaction & txns

Retention (delete)

cleanup.policy=delete (default): drop whole segments older than retention.ms (e.g. 604800000 = 7d) or over retention.bytes. Consumption does not delete.

Log compaction

cleanup.policy=compact: keep the latest value per key forever; older values for that key GC'd. A durable "current state" table (e.g. CDC snapshots). Delete a key = publish a tombstone (key + null value).

Transactions / EOS

transactional.id + initTransaction/beginTransaction/commitTransaction: atomic multi-partition writes + offset commit → read-process-write EOS. Consumers set isolation.level=read_committed to skip aborted records.

! Compaction ≠ dedup; it keeps last-per-key, not "one copy per message". Tombstones age out after delete.retention.ms — read them before they vanish.

Kafka ecosystem & ops

  • Kafka Connect: declarative source/sink connectors (Debezium CDC, S3, JDBC) — no bespoke producer/consumer code. Runs as workers with converters + SMTs.
  • Kafka Streams: JVM library for stateful stream processing (joins, windows, aggregations); state in RocksDB backed by changelog topics.
  • ksqlDB: SQL over streams.
  • Schema Registry: central Avro/Protobuf/JSON schemas + compatibility enforcement (see Schema card).
  • MirrorMaker 2: cross-cluster/region replication (DR, aggregation). Offsets don't translate 1:1 — ! plan consumer failover.

Key metrics: consumer lag, under-replicated partitions (URP), ISR shrink/expand, request latency, disk usage, DLQ rate. Partition sizing: enough for target parallelism + headroom, not so many that controller metadata + open files explode.

RabbitMQ: AMQP model & exchanges

Producer → exchange → (binding) → queue → consumer. Producers never publish to a queue directly; the exchange + routing key + bindings decide placement.

ExchangeRoutes byUse
directexact routing-key = binding-keypoint routing, severity
fanoutignores key → all bound queuesbroadcast
topicpattern order.*.eu (*=1 word, #=n)flexible pub/sub
headersheader attrs (x-match all/any)multi-attr routing
  • DLX (x-dead-letter-exchange): rejected/expired/over-length msgs routed aside → retry/parking.
  • TTL per-message or per-queue; priority queues (x-max-priority).
  • Delayed delivery via delayed-message plugin or TTL+DLX trick.

! A queue with no consumers + no TTL/limit grows until the broker hits its memory/disk alarm and blocks all publishers.

RabbitMQ: reliability & clustering

  • Publisher confirms: broker acks the publish once safely enqueued/persisted — the producer-side reliability half. Without them, publishes are fire-and-forget.
  • Consumer acks: basic.ack after work (manual) → at-least-once; basic.nack/reject requeue or DLX. Auto-ack = at-most-once.
  • Prefetch (basic.qos prefetch_count=N): bound unacked messages per consumer — fair dispatch + backpressure. Default unlimited is a footgun.
  • Persistence: durable queue + persistent message + confirms survive restart. Any gap = loss.
  • Quorum queues (Raft) replaced mirrored/classic HA queues — mirroring is deprecated. Use quorum for replicated, data-safe queues.

! Durable queue with non-persistent messages still loses data on restart — both flags required.

Redis: pub/sub vs Streams

Pub/Sub — fire-and-forget

PUBLISH ch msg
SUBSCRIBE ch          // PSUBSCRIBE news.*

At-most-once, no storage, no groups. Offline subscriber misses everything. Good: cache invalidation, presence, ephemeral signals.

Streams — durable in-mem log

XADD s * k v                 // append, auto-ID
XADD s MAXLEN ~ 100000 * ...  // cap growth
XREADGROUP GROUP g c COUNT 10 STREAMS s >
XACK s g <id>                 // ack processed
XPENDING s g                 // PEL: unacked/redelivery

Consumer groups + per-message ack + PEL (pending entries list) → at-least-once, bounded replay. XAUTOCLAIM recovers a dead consumer's pending.

! Durability is memory-bound + tied to RDB/AOF — a crash loses recent entries. ! No MAXLEN → unbounded RAM.

Reliability patterns

Transactional outbox

Fixes the dual-write problem (DB commit + publish can't be atomic → one may fail). Write the event to an outbox table in the same DB txn; a relay/CDC (Debezium) tails it and publishes. No lost/phantom events.

Idempotent consumer

Dedup by a stable message/business key: store processed IDs (Redis SET / DB unique constraint), skip repeats. Turns at-least-once into effectively-once.

  • DLQ: after N failed retries, park the message for inspection — never block the main flow.
  • Retry + backoff: exponential + jitter; separate retry topics/queues so one poison msg doesn't stall the partition.
  • Poison message: repeatedly fails → cap attempts → DLQ, alert.
  • Saga: long-running distributed txn as steps + compensating actions (no 2PC). Choreography = services react to each other's events (decoupled, emergent flow). Orchestration = a central coordinator drives steps (explicit, but a hub). Compensations undo prior steps on failure (refund, release inventory) since you can't roll back a committed local txn.

! Ordering + idempotency together: keying for order still lets a redelivered older record re-apply — the idempotent write must be order-independent (condition on state / version), not just dedup by id.

Schema & evolution

Producers and consumers deploy independently → the wire format is a contract. Use a schema registry (Confluent) with Avro/Protobuf (compact, typed, IDs) over raw JSON.

CompatSafe changeUpgrade
Backwarddelete field / add optional w/ defaultconsumers first
Forwardadd field / delete optionalproducers first
Fullboth — additive onlyeither order
  • Additive, defaulted fields are always safe. Renaming/retyping/removing-required breaks.
  • Registry rejects incompatible schemas at publish — fail fast in CI, not at 3am.
  • ! A required field with no default is a breaking change — old consumers can't read it.
  • Avro = compact binary + separate schema (registry ships a schema id in the wire header); Protobuf = compact, field-number-based, great cross-language; JSON = human-readable but bulky, untyped, no enforced evolution. Prefer Avro/Protobuf on high-volume topics.

Event-driven architecture

Event styles

  • Event notification: thin "it happened" + id; consumer calls back for data. Low coupling, chatty.
  • Event-carried state transfer: event carries the full payload; consumers keep a local read model. No callback, but data duplication + staleness.
  • Event sourcing: the event log is the source of truth; state = fold(events). Full audit + replay/rebuild.

Coordination

  • Choreography: services react to each other's events — decoupled, but flow is emergent/hard to trace.
  • Orchestration: a central coordinator drives steps — explicit, but a hub.
  • CQRS: split write model (commands) from read model (projections built off events).

! Event-carried state = eventual consistency everywhere; design consumers to tolerate stale + out-of-order + duplicate events.

Operations, scaling & security

  • Partition/shard sizing: set for peak parallelism + headroom; increasing is disruptive (re-keys), decreasing usually impossible.
  • Security: TLS in transit, SASL (SCRAM/OAuth/mTLS) authn, ACLs per topic/group authz. Encrypt at rest on the broker disks.
  • Multi-region: MirrorMaker 2 (Kafka), stream replication (Pulsar geo), cross-region SNS/SQS. Active-active needs conflict handling.
  • Capacity: retention × ingest = disk; RF multiplies it.

Golden signals

Lag (are we falling behind), URP / ISR shrink (durability at risk), DLQ rate (poison flow), publish/consume latency, disk/memory alarms, rebalance frequency.

! Alert on lag trend, not absolute lag — a steady 10k is fine; a rising slope is an incident.

Cloud & lightweight brokers

  • SQS: managed queue. Standard = ≥once, best-effort order, ~unlimited tput. FIFO = strict order + EOS per MessageGroupId, ~300 msg/s (3000 batched). ≤14d, no replay. DLQ via redrive.
  • SNS: managed pub/sub fan-out. Canonical durable pattern SNS→N·SQS (each consumer gets its own queue). Filter by message attributes.
  • Kinesis: managed log; shards (fixed capacity each), per-shard order, 24h–365d + replay. Lower per-shard ceiling than Kafka; you manage shard counts.
  • GCP Pub/Sub: global auto-scaling; push+pull, 7d default, replay via seek/snapshot, optional ordering keys + EOS.
  • NATS core: sub-ms subject pub/sub, tiny ops; JetStream adds durable streams + replay + EOS-dedup.
  • Pulsar: log+queue on BookKeeper; compute/storage split, tiered storage, geo-repl, multi-tenant. Cost: brokers + BookKeeper (+ZK).

! Managed ≠ free: per-message/shard cost can dominate at volume, plus quotas + lock-in.

NATS · JetStream · Pulsar

NATS (core)

Tiny Go binary, millions msg/s, sub-ms. Subject addressing (orders.eu.new; wildcards *=1 token, >=rest). At-most-once — no subscriber connected = dropped. Native request/reply + queue groups (competing consumers). Reach for it: ultra-light internal signalling/RPC where loss is tolerable.

JetStream

Persistence layer inside modern NATS: durable streams (retention-bound), consumers with acks, replay by seq/time, at-least-once with a dedup window → effectively-once. The lightweight Kafka alternative when you want streaming without KRaft-scale ops.

Pulsar

Kafka-shaped log that splits serving from storage: stateless brokers dispatch, BookKeeper bookies store segments. So brokers add/remove instantly (no data move), storage scales independently. Wins: native multi-tenancy (tenant/namespace/topic), transparent tiered storage (offload to S3/GCS), built-in geo-replication, and one topic consumed as stream or shared queue via subscription type.

! Pulsar = more moving parts (brokers + bookies + metadata) and smaller ecosystem — Kafka stays default unless you need those specific wins.

MQTT & the edge (IoT)

Tiny pub/sub over TCP for constrained devices + flaky links. ~2-byte header (vs HTTP). All clients connect to a broker (Mosquitto, EMQX, HiveMQ, AWS IoT Core); topics home/room/temp, wildcards + (1 level) # (multi).

Transactional outbox (worked)

Fixes the dual-write: DB commit + broker publish can't be atomic, and retry can't save you (crash lands in the gap, ack can be lost on the wire). Write the event into an outbox table in the same DB txn as the state change.

BEGIN;
  INSERT INTO orders(id,total,status)
    VALUES('o-123',4200,'CREATED');
  INSERT INTO outbox(id,type,payload)   -- same txn
    VALUES('m-777','OrderCreated','{...}');
COMMIT;

A separate relay publishes committed rows, marking them done — safe to run many workers:

SELECT id,payload FROM outbox
  WHERE published_at IS NULL
  ORDER BY created_at
  FOR UPDATE SKIP LOCKED LIMIT 100;
-- publish each, then UPDATE published_at=now()
  • Relay is at-least-once (crash after publish, before UPDATE → republish) — fine, consumers dedup on the outbox id.
  • Polling relay = boring & correct (SQL, small latency). CDC (Debezium tails WAL) = low-latency, but ! an un-consumed replication slot pins WAL and can fill disk — monitor slot lag like consumer lag.

Idempotent consumer (worked)

At-least-once ⇒ you will see dups (relay republish, redelivery, rebalance). Two strategies:

1. Inbox / dedup table

BEGIN;
  INSERT INTO processed(msg_id,consumer)
    VALUES('m-777','billing')
    ON CONFLICT DO NOTHING;   -- 0 rows = dup → skip
  UPDATE accounts SET balance=balance-4200
    WHERE id='c-9';           -- same txn as dedup
COMMIT;

Dedup insert + business write in one txn → crash mid-way rolls back, redelivery retries cleanly.

2. Naturally idempotent write

  • Upsert by business key (ON CONFLICT DO UPDATE).
  • Set absolute, don't increment: SET status='PAID' not balance-=x.
  • Condition it: UPDATE ... WHERE status='PENDING'.

! Dedup key must be a stable message id (producer/outbox sets it once), not regenerated per delivery. The inbox is the consumer-side mirror of the outbox — outbox+inbox = exactly-once effect over plain at-least-once transport.

Worked: payment pipeline (no double-charge)

Classic senior design — "exactly-once effects, no lost charge, no double charge." You cannot buy true EOS delivery; you engineer the effect.

  1. Ingress: PaymentRequested carries a client-supplied idempotency key (= message id). Persist via outbox so the request event and order row commit together.
  2. Transport: at-least-once, keyed by accountId so one account's events stay ordered in one partition.
  3. Consumer: dedup on idempotency key in the same txn as the ledger write (inbox). Duplicate delivery → no-op.
  4. External charge: pass the same idempotency key to the payment gateway (Stripe et al. dedup on it) so a retry after a lost response doesn't double-charge.
  5. Failure: retries with backoff+jitter; exhausted → DLQ + alert, never loop.

Prove it by narrating four failures: broker node dies (acks=all+minISR survives), consumer crashes mid-process (redeliver → inbox dedups), consumer falls behind (lag alert, scale ≤partitions), poison message (retry cap → DLQ).

Kafka replay & offset reset

Offsets are just positions in a retained log, so a consumer can reposition anywhere within the retention window.

consumer.assign(List.of(tp));
consumer.seekToBeginning(List.of(tp));   // from earliest
consumer.seek(tp, 42000);                // exact offset
// by time (epoch ms):
var o = consumer.offsetsForTimes(Map.of(tp, ts)).get(tp);
if (o != null) consumer.seek(tp, o.offset());

offsetsForTimes maps a timestamp → first offset at/after it — the "reprocess everything since 09:00 after we fixed the bug" tool. Operationally:

kafka-consumer-groups --reset-offsets \
  --to-datetime <ts> --group g --topic t --execute
  # drop --execute for a dry run
  • ! auto.offset.reset (earliest/latest/none) only decides where a group with no committed offset starts — a first-run fallback, not a replay mechanism.
  • Can't seek beyond retention.ms/retention.bytes — tiered storage extends the reachable window.

RabbitMQ: connections, channels & vhosts

  • Connection = one TCP socket (AMQP handshake, auth, heartbeats) — expensive (fds, memory, TLS).
  • Channel = lightweight virtual connection multiplexed inside it; nearly every op (declare, publish, consume, ack) runs on a channel.

Idiom: one long-lived connection per process, one channel per thread. Channels are cheap; connections are not.

conn = BlockingConnection(params)   # once per process
ch = conn.channel()                 # one per worker thread
ch.basic_qos(prefetch_count=20)     # cap unacked
ch.basic_consume('tasks', on_msg)
  • ! Connection-per-publish is the #1 RabbitMQ scaling mistake — exhausts the broker.
  • ! Channels are not thread-safe — sharing one across threads corrupts framing.
  • Virtual hosts = logical namespaces (own exchanges/queues/perms) for multi-tenant isolation on one broker. pause_minority partition handling keeps only the majority side writable.

Structuring a messaging answer

Run every messaging / system-design question through one funnel — then let the broker fall out of it, don't lead with a product.

  1. Requirements first: throughput, ordering scope, and cost of loss vs cost of a duplicate.
  2. Default contract: at-least-once + idempotent consumer. Exactly-once delivery is a myth; you engineer exactly-once effects (outbox + idempotency + DLQ).
  3. Then pick the broker: Kafka = replayable high-tput log; RabbitMQ = rich routing / work queues; SQS/SNS = managed fan-out; Redis/NATS = lightweight low-latency.
  4. Prove it — narrate four failures: a broker node dies, a consumer crashes mid-process, a consumer falls behind, a poison message arrives.

If your answer names a tradeoff and survives that failure walk, you're reasoning like someone who has operated messaging in production — the exact signal the question exists to detect.

★ Choosing & designing checklist

  • ☐ Asked "log or queue?" first, then layered replay / ordering / routing / throughput / ops.
  • ☐ Ordering need mapped to a lane (partition key / message-group / hash exchange); accepted the parallelism cost.
  • ☐ Default = at-least-once + idempotent consumer (dedup key). Didn't promise cross-system exactly-once.
  • ☐ DLQ + retry/backoff+jitter from day one; poison messages parked, not looping.
  • ☐ Dual-write handled by transactional outbox, not best-effort publish.
  • ☐ Kafka durability: acks=all + min.insync.replicas=2 + RF3; unclean election off.
  • ☐ Consumers commit after processing; prefetch/poll bounded.
  • ☐ Queues bounded (TTL / MAXLEN / max-length) — no unbounded growth.
  • ☐ Schema in a registry; changes additive + compatibility-checked in CI.
  • ☐ Monitoring lag trend, URP, DLQ rate; alerting on slope.
  • ☐ Security: TLS + SASL + per-topic ACLs.
  • ☐ Chose the broker you already run unless the workload truly needs otherwise.
