Global Infrastructure & Shared Responsibility

  • Region = geographic area; AZ = ≥1 isolated datacenter in a region (design across ≥2). Edge = CloudFront/Route 53 PoPs.
  • Pick a region on: latency, cost (prices vary), compliance/residency, service availability (new services land in us-east-1 first).
  • Multi-AZ = high availability within a region; multi-region = DR / global reach.

Shared Responsibility !

AWS ("of" the cloud)You ("in" the cloud)
HW, region/AZ, hypervisor, managed-service internalsIAM, data, encryption, patching EC2, SG/NACL config, app code

Managed services shift more to AWS (S3 patches itself; EC2 you patch). Misconfig (open bucket, over-broad IAM) is always your side !

IAM — Policy Evaluation

{ "Effect":"Allow",
  "Action":["s3:GetObject"],
  "Resource":"arn:aws:s3:::my-bucket/*",
  "Condition":{"IpAddress":{"aws:SourceIp":"10.0.0.0/8"}}}

Decision order !

  • Explicit Deny → always wins.
  • Else explicit Allow → permitted.
  • Else implicit deny (default).
  • SCP / permission boundary / session policy must also allow — intersection.
  • Roles > long-lived keys: EC2 → instance profile, Lambda → execution role, cross-account → sts:AssumeRole. Never hardcode access keys !
  • Identity-based (on principal) vs resource-based (on S3 bucket/SQS/KMS — enables cross-account & needs no role assumption).
  • Least privilege; verify with IAM Access Analyzer. ABAC via tags for scale. aws sts get-caller-identity to confirm who you are.

  • Families: general (m/t), compute (c), memory (r/x), storage (i/d), accelerated (p/g). Graviton (ARM) = cheaper/greener.
  • Auto Scaling: target-tracking (easiest) / step / scheduled / predictive. Scale on the right metric, not just CPU.

  • Placement groups: cluster (low-latency HPC) · spread (anti-correlated failure) · partition (big distributed stores).

Lambda — Limits & Cold Starts

LimitValue
timeout15 min max
memory128 MB–10 GB (CPU scales with it)

concurrency1000/acct default (soft)
  • Cold start: new exec env init. Cut with smaller packages, provisioned concurrency, or SnapStart (Java). VPC-attached cold starts improved (Hyperplane ENIs).
  • Billed on GB-seconds + requests. Right-size memory (more memory = more CPU = often cheaper/faster).
  • Async invokes retry twice → send failures to a DLQ/destination !

Containers — ECS · Fargate · EKS

Two axes: orchestrator (ECS proprietary/simple vs EKS = real k8s) × compute (EC2 nodes you manage vs Fargate serverless). Any combo valid.

ECSEKS
APIAWS-native, simpleupstream k8s
portableAWS-onlyanywhere k8s runs
CP costfreehourly/cluster
bestall-in AWS, low opsk8s skills / multi-cloud
  • ECS terms: task definition (blueprint ≈ pod spec) → task (running) → service (keeps N alive behind LB) → cluster.
  • Fargate = no nodes, billed per vCPU-s + GB-s; no GPU/host access (ECS Exec, not SSH). EC2 launch type wins on steady high utilisation & GPUs.
  • Execution role (agent pulls image/writes logs) ≠ task role (your app's AWS perms) ! Mixing them breaks least privilege.
  • Default awsvpc networking (per-task ENI + SG). ECR = private registry (scan + lifecycle). Choosing EKS without k8s skills = over-engineering !
  • App Runner sits between Lambda and ECS/Fargate: give it an image/repo, get a scaling HTTPS service — no clusters/LB/networking. Skip for sidecars, non-HTTP, batch. Sidecars (FireLens/Fluent Bit logs, ADOT metrics/traces) attach per task.

  • 11 nines durability; strong read-after-write consistency (all ops).
  • Security: Block Public Access on by default; prefer bucket policy/IAM over ACLs; presigned URLs for temp access !
  • Encrypt: SSE-S3 / SSE-KMS (audited, use bucket keys to cut cost) / SSE-C. Enforce TLS + encryption via bucket policy Deny conditions.

Multi-AZ vs Read Replica !

  • Multi-AZ = sync standby for HA/failover, not read scaling.
  • Read replica = async copy for read scaling, not automatic failover (can promote manually).
  • Lambda + RDS → use RDS Proxy (connection pooling; Lambda exhausts DB connections) !
  • Aurora Global / DynamoDB Global Tables for cross-region.

DynamoDB — design

  • Model access patterns first, then keys. Partition key must spread load — avoid hot partitions !
  • Query (by key, cheap) not Scan (full table, avoid in hot paths) !
  • GSI = different PK, eventually consistent, own capacity; LSI = same PK/alt SK, at create time only.
  • Capacity: on-demand (spiky/unknown) vs provisioned+autoscale (steady/cheaper). Strong reads cost 2×.
  • Item ≤ 400 KB; offload big blobs to S3 (store the key).
  • Streams → Lambda for CDC; TTL for expiry; transactions & conditional writes (optimistic lock); DAX for µs reads.
  • Single-table design: model multiple entity types in one table around access patterns — you design keys from the queries, not normalize-then-query !
  • On-demand capacity tracks a spiky API; provisioned + autoscale is cheaper for steady load. Poison record can block a shard-consumer → set BisectBatchOnFunctionError + max-retry + on-failure destination.

Caching — ElastiCache · DAX

A cache is a bet the same data is read many times before it changes. Every cache decision is a staleness-tolerance decision — cache measured bottlenecks, not by reflex.

StrategyNote
cache-aside (lazy)app reads cache, on miss loads DB & fills; only hot data cached
write-throughwrite cache+DB together; always warm, slower writes, caches unread data
write-behindwrite cache, async flush; fast but loss risk !
  • Redis/Valkey (rich types, replication, multi-AZ, persistence) vs Memcached (multi-threaded pure KV). Default Redis.
  • ElastiCache ≠ durable — failover can lose writes. Need durable Redis? MemoryDB !
  • DAX = DynamoDB-only write-through cache (µs); not general purpose.
  • TTL bounds staleness; watch cache stampede (many misses on one expired hot key hammer the DB) ! Track hit ratio.

Messaging — SQS · SNS · EventBridge · Kinesis

ServiceUse
SQSdecouple, buffer work; consumer pulls
SNSpub/sub fan-out (push)
EventBridgeevent bus, content routing, SaaS/schedule
Kinesisordered streaming, replay, multiple consumers
  • SQS Standard (at-least-once, best-effort order) vs FIFO (ordered, dedup, lower TPS).
  • Visibility timeout must exceed processing time or you get duplicates ! Always set a DLQ.
  • Fan-out = SNS → many SQS. EventBridge for filtering/routing & 3rd-party.
  • Kinesis: shards + partition key (ordering per shard); replay via retention; Firehose = managed delivery to S3/Redshift.
  • Assume at-least-once everywhere → make consumers idempotent.

Integration — API GW · Step Functions

  • API Gateway: HTTP API (cheaper/faster, JWT) vs REST API (usage plans, API keys, VTL, caching) vs WebSocket. Authz: IAM / Cognito / Lambda authorizer.
  • Throttle + usage plans to protect backends; cache to cut cost/latency.
  • ALB vs API GW: ALB for simple container HTTP; API GW for managed auth/throttle/keys/serverless.
  • Step Functions: orchestrate workflows; Standard (long, auditable, exactly-once) vs Express (high-volume, short). Built-in retry/catch, Map/Parallel, direct SDK calls, saga for distributed txns.
  • Orchestration (Step Functions) vs choreography (EventBridge/SNS) — central control vs loose coupling.

Observability & Security

Observe

  • CloudWatch metrics + alarms (static/anomaly/composite) + Logs (Insights, metric filters). Memory/disk need the CloudWatch Agent !
  • X-Ray = distributed traces/service map. CloudTrail = API audit (who did what) — not monitoring. Config = resource compliance/history.
  • Three signals: metrics (CloudWatch alarms) · logs (Logs Insights, metric filters) · traces (X-Ray). An org-trail + Config aggregator in a central audit account covers every member account.
  • Alarm on DLQ depth, error rate, p99 latency, and throttles — a non-empty DLQ is an incident, page on it !

Secure

  • KMS envelope encryption; key policy + IAM; rotate; multi-region keys for DR.
  • Secrets Manager (auto-rotation, cost) vs SSM Parameter Store (cheap/simple, SecureString).
  • Edge: WAF (L7 rules, rate limit) + Shield (DDoS); GuardDuty (threat detection), Macie (PII), Inspector (vulns), Security Hub (aggregate).
  • Cognito: user pools (authn) vs identity pools (temp AWS creds).

IaC & CI/CD

  • CloudFormation: template (desired state) → stack (atomic unit, rolls back on fail). Always create a change set and read "Replacement: True" rows before prod update ! (can destroy an RDS).
  • Drift = console change diverging from template → template lies. Detect on schedule; lock prod console writes (SCPs) !
  • CDK synths to CFN — L1 raw / L2 sensible-defaults+.grant*() / L3 patterns. SAM for serverless.
  • Nested stacks = modularity in one account; StackSets = same baseline to many accounts/regions (landing-zone guardrails).
  • CFN vs Terraform: AWS-managed state + native drift vs multi-cloud + self-managed state (S3 + DynamoDB lock).

Deploy safely

  • Rolling (mutate fleet, rollback = another deploy) vs blue/green (parallel env, instant flip-back) vs canary (small % first, observe).
  • CodeDeploy hooks + CloudWatch alarm → auto-rollback. Immutable infra: replace, don't patch. Never bake secrets into images/logs !

Well-Architected & DR

6 pillars: operational excellence · security · reliability · performance efficiency · cost optimization · sustainability.

DR strategies (RTO/RPO ↓, cost ↑)

StrategyRTO/RPO
Backup & restorehours; cheapest
Pilot light10s of min; core running small

Multi-site active-active~0; priciest
  • RTO = time to recover; RPO = tolerable data loss.
  • Design stateless (externalize state to S3/Dynamo/ElastiCache); retries with backoff + jitter; idempotency.
  • Reduce blast radius (cells, multi-AZ). Quotas are a reliability risk ! Test with FIS game days.

Cost Optimization

  • Compute: Savings Plans/RI for baseline, Spot for fault-tolerant, Graviton, right-size, scale to zero.
  • Storage: S3 Intelligent-Tiering, gp3 over gp2, kill snapshot/log sprawl, lifecycle to Glacier.
  • Data transfer is the silent bill ! cross-AZ chatter, inter-region, internet egress, and NAT Gateway data processing charges.
  • Visibility: Cost Explorer, Budgets + anomaly detection, CUR, cost-allocation tags, Compute Optimizer, Trusted Advisor.
  • Reserved capacity also for RDS/ElastiCache/OpenSearch/Redshift.
  • Anti-patterns: idle/forgotten resources, over-provisioning, un-tiered logs, single huge NAT for cross-AZ.

Networking — Peering · TGW · Hybrid

Almost every connectivity bug is a mismatch between route table, security group, NACL, and IP/gateway — check those four, in that order !

ConnectTool
VPC ↔ VPC (few)Peering — simple, non-transitive
VPC ↔ VPC (many)Transit Gateway — hub, transitive
VPC → AWS serviceVPC endpoint (Gateway/Interface)
on-prem, encryptedSite-to-Site VPN (over internet)
on-prem, dedicatedDirect Connect (private line)
  • Peering is non-transitive: A↔B and B↔C does not give A↔C. Full mesh = N(N-1)/2 links → move to TGW past a handful !
  • TGW = regional hub; each VPC attaches once, TGW route tables can keep prod ⊥ dev while sharing an on-prem link.
  • Endpoints: Gateway (S3/DynamoDB, free) vs Interface/PrivateLink (ENI, hourly + per-GB) — expose one service, not the whole network.
  • VPN vs DX: VPN = quick/encrypted/variable or as backup; DX = consistent low latency, high throughput, cheaper egress at scale. Prod pattern = DX + VPN failover on a TGW.
  • Flow Logs capture traffic metadata (not payload) at VPC/subnet/ENI → CloudWatch/S3; each record has 5-tuple + ACCEPT/REJECT — the tool for "why is this blocked".
  • Access hosts via SSM Session Manager (no bastion, no open port 22, audited) over classic bastion !

Multi-Account — Organizations · SCP

  • Organizations = many accounts under one payer, grouped into OUs; consolidated billing pools volume/commitment discounts.
  • Account = the strongest blast-radius boundary — separate prod / dev / audit / PCI into their own accounts, connect only what's needed !
  • SCP = org guardrail on root/OU/account — sets the max permissions; never grants, only caps. You still need an Allow in an IAM policy !
  • Effective perms = SCP ∩ identity policy ∩ permission boundary; applies even to account admins (mgmt account is exempt → don't run workloads there).
  • Classic SCP uses: deny regions outside an allow-list (aws:RequestedRegion), deny disabling CloudTrail/deleting log resources (tamper-proof audit).
  • Permission boundary caps an individual role/user (e.g. let a team self-serve IAM without privilege escalation); SCP caps whole accounts.
  • Control Tower / Landing Zone = codified guardrails, a central security/audit account other accounts deliver into (org CloudTrail + Config aggregator), StackSets to push a baseline everywhere.
  • Identity Center (SSO) + temporary STS creds for humans — never long-lived IAM user keys. Root user: MFA, no keys, break-glass only !

Reference Architectures

HA 3-tier web (the baseline)

Route 53 → CloudFront → ALB → ASG across ≥2 AZs (stateless; sessions in ElastiCache/DynamoDB) → RDS Multi-AZ. Public subnet = ALB; private = app + data; NAT per AZ.

Image-upload pipeline

Client PUT via presigned URL straight to S3 (binaries never touch compute) → s3:ObjectCreated → SQS → Lambda (light) or Fargate (heavy/>15 min) → thumbnails to S3, metadata to DynamoDB → DLQ on failures → serve via CloudFront+OAC.

URL shortener (read-skewed)

Write: API GW → Lambda → base62 key → DynamoDB (PK=shortKey). Read (hot): GetItem → 301/302, fronted by CloudFront. 302 to keep click analytics (async to Kinesis); TTL for expiry. DynamoDB not RDS — pure key lookup at scale.

Event-driven orders

API GW → Lambda → DynamoDB + publish OrderPlaced to EventBridge → fan-out to payment / inventory / fulfillment, each its own queue + DLQ. Multi-step saga with rollback → Step Functions (payment → reserve → ship, compensate on fail). Idempotency keys everywhere (at-least-once).

Multi-Tenant SaaS & Migration

Tenant isolation model

ModelIsolation / cost
Silo (infra per tenant)strongest / high — strict compliance
Pool (shared, tenant-ID rows)weakest / lowest — many small tenants
Bridge (hybrid)medium / medium — mixed sizes
  • Pooled: shared API GW+Lambda, tenant ID from JWT (Cognito), DynamoDB single-table with tenant ID as PK prefix.
  • Always scope every query by tenant ID in a data-access layer — a leak here is a cross-tenant breach !
  • Noisy neighbours → per-tenant throttling (usage plans); silo the premium tenants who pay for it.

Monolith migration — the 6 R's

  • Rehost (lift-and-shift to EC2/containers) → Replatform (self-managed DB→RDS, cache→ElastiCache) → Refactor incrementally via strangler-fig (ALB/API GW peels one capability at a time into Lambda/microservice).
  • Big-bang rewrite is the classic failure ! Stay shippable; stop modernizing when ROI flattens. Don't split the DB reflexively.

RDS & Aurora — internals

  • Aurora decouples compute from a shared distributed storage layer — 6 copies across 3 AZs, auto-grows to 128 TiB; only redo-log records cross the wire (fast, cheap replication).
  • Up to 15 low-lag read replicas sharing that storage (vs RDS replicas that each copy the volume); failover promotes a replica in ~30s.
  • Aurora Serverless v2 scales ACU in fine steps for bursty/idle; Global Database = <1s cross-region replication for DR + local reads.
  • RDS: automated backups + PITR (retention 0–35 days), snapshots (manual, kept until deleted), parameter/option groups, Performance Insights.
  • Engine upgrade / storage change / class change may need a maintenance window — some are Replacement ops that cause downtime !
  • Read replica ≠ Multi-AZ standby: replica is async, for read scaling, manual promote; Multi-AZ standby is sync, for automatic failover — not readable !

KMS & Encryption

  • Envelope encryption: KMS holds the key-encryption key (CMK); it generates a per-object data key, you encrypt data with the data key and store the wrapped key alongside. KMS never sees your data.
  • Access needs both the key policy and IAM (key policy is authoritative — lock yourself out of the key policy and even root can't fix it easily) !
  • Customer-managed keys (rotation, cross-account, custom policy) vs AWS-managed (aws/service, free, auto-rotate) vs AWS-owned (invisible).
  • Multi-region keys for cross-region DR of encrypted data; S3 bucket keys cut KMS API calls (and cost) on high-volume SSE-KMS.
  • In transit: enforce TLS via a bucket/resource policy Deny when aws:SecureTransport=false.
  • Secrets Manager (auto-rotation via Lambda, ~$0.40/secret/mo) vs SSM Parameter Store SecureString (free tier, no built-in rotation).

CI/CD on AWS

  • CodePipeline orchestrates stages; CodeBuild compiles/tests (buildspec.yml); CodeDeploy ships to EC2/ECS/Lambda; CodeArtifact/ECR for artifacts/images.
  • Deploy strategies: rolling (mutate fleet) · blue/green (parallel env, instant flip-back) · canary (small % first, observe) · linear (ramp in steps).
  • CodeDeploy hooks + a CloudWatch alarm → automatic rollback on error/latency regression.
  • Immutable infra: replace, don't patch — bake an AMI/image, roll it out, keep the old one for instant rollback.
  • Never bake secrets into images, buildspecs, or logs — inject from Secrets Manager/SSM at runtime !
  • Gate prod on tests + manual approval + change set review; run IaC (CFN/CDK/Terraform), never click-ops.

Data-Transfer — the silent bill

The three bill meters are compute-time, storage-GB, and data-transfer — and transfer is the one that surprises. Rates rarely bite; chatty topology and idle/over-provisioned resources do !

  • Internet egress is billed, ingress is free; inter-region and cross-AZ traffic both charge per GB each way.
  • NAT Gateway: hourly + ~$0.045/GB processed on every byte — route S3/DynamoDB via free gateway endpoints to skip it entirely, and put one NAT per AZ so private subnets don't pay cross-AZ on top !
  • Interface/PrivateLink endpoints keep ECR image pulls + Secrets Manager calls off the NAT.
  • CloudFront egress is cheaper than raw S3 egress for repeated reads, and NLB charges cross-AZ data (ALB cross-zone is free).
  • Co-locate chatty tiers in one AZ where HA allows; cache to cut origin round-trips; question whether a workload needs internet egress at all.

Serverless — event sources & patterns

Invocation models

ModelBehaviour
sync (API GW, ALB)caller waits, eats latency/failure
async (S3, SNS, EventBridge)queued internally, 2 retries → DLQ/destination
stream (Kinesis, DynamoDB)polled in batches, ordered per shard
poll (SQS)event-source mapping long-polls
  • Async failures vanish after retries unless you set a DLQ/on-failure destination !
  • Stream: a poison record blocks the shard until it expires → set BisectBatchOnFunctionError, max-retry-age, and partial-batch-failure reporting.
  • EventBridge Pipes = point-to-point source→(filter/enrich)→target, no glue Lambda. Scheduler = cron/one-off at scale.
  • Reserve concurrency to protect a downstream DB from a spike; provisioned concurrency to kill cold starts on latency-critical routes.

★ Architecture Review Checklist

Security

  • ☐ No hardcoded keys — roles everywhere; least-privilege IAM; no * actions/resources without reason.
  • ☐ S3 Block Public Access on; encryption at rest (KMS) & TLS in transit.
  • ☐ Secrets in Secrets Manager/SSM, not env/plaintext; KMS key policies scoped.
  • ☐ Edge protected (WAF/Shield); security groups least-open; private subnets for data.
  • ☐ Task role ≠ execution role on ECS; IMDSv2 enforced on EC2.

Reliability

  • ☐ Multi-AZ for every stateful tier (DB, cache); no single-AZ prod DB.
  • ☐ Decoupled with queues; DLQs on async; retries with backoff+jitter; idempotent consumers.
  • ☐ Defined RTO/RPO & a tested DR strategy; health checks + failover.

Performance & Cost

  • ☐ Right service for the access pattern (Query not Scan; cache hot reads; CDN static).
  • ☐ Auto scaling on the right metric; right-sized instances / Lambda memory.
  • ☐ VPC endpoints to avoid NAT/egress cost; minimize cross-AZ traffic.
  • ☐ Budgets/alarms set; tags for cost allocation; no forgotten resources.

Operations

  • ☐ IaC (CFN/CDK/Terraform), not click-ops; change sets reviewed; env/account separation.
  • ☐ Metrics + logs + traces + alarms; CloudTrail on; auto-rollback on alarm; runbooks.
