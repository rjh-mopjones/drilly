Global Infrastructure & Shared Responsibility

  • Region = geographic area; AZ = ≥1 isolated datacenter in a region (design across ≥2). Edge = CloudFront/Route 53 PoPs.
  • Pick a region on: latency, cost (prices vary), compliance/residency, service availability (new services land in us-east-1 first).
  • Multi-AZ = high availability within a region; multi-region = DR / global reach.

Shared Responsibility !

AWS ("of" the cloud)You ("in" the cloud)
HW, region/AZ, hypervisor, managed-service internalsIAM, data, encryption, patching EC2, SG/NACL config, app code

Managed services shift more to AWS (S3 patches itself; EC2 you patch). Misconfig (open bucket, over-broad IAM) is always your side !

IAM — Policy Evaluation

{ "Effect":"Allow",
  "Action":["s3:GetObject"],
  "Resource":"arn:aws:s3:::my-bucket/*",
  "Condition":{"IpAddress":{"aws:SourceIp":"10.0.0.0/8"}}}

Decision order !

  • Explicit Deny → always wins.
  • Else explicit Allow → permitted.
  • Else implicit deny (default).
  • SCP / permission boundary / session policy must also allow — intersection.
  • Roles > long-lived keys: EC2 → instance profile, Lambda → execution role, cross-account → sts:AssumeRole. Never hardcode access keys !
  • Identity-based (on principal) vs resource-based (on S3 bucket/SQS/KMS — enables cross-account & needs no role assumption).
  • Least privilege; verify with IAM Access Analyzer. ABAC via tags for scale. aws sts get-caller-identity to confirm who you are.

  • Families: general (m/t), compute (c), memory (r/x), storage (i/d), accelerated (p/g). Graviton (ARM) = cheaper/greener.
  • Auto Scaling: target-tracking (easiest) / step / scheduled / predictive. Scale on the right metric, not just CPU.

Lambda — Limits & Cold Starts

LimitValue
timeout15 min max
memory128 MB–10 GB (CPU scales with it)
/tmp512 MB–10 GB
payload6 MB sync · 256 KB async
concurrency1000/acct default (soft)
  • Cold start: new exec env init. Cut with smaller packages, provisioned concurrency, or SnapStart (Java). VPC-attached cold starts improved (Hyperplane ENIs).
  • Billed on GB-seconds + requests. Right-size memory (more memory = more CPU = often cheaper/faster).
  • Async invokes retry twice → send failures to a DLQ/destination !
  • Design for idempotency (at-least-once). Reserve/limit concurrency to protect a downstream DB from a spike ! Not for long/steady heavy compute → Fargate/EC2.

Containers — ECS · Fargate · EKS

Two axes: orchestrator (ECS proprietary/simple vs EKS = real k8s) × compute (EC2 nodes you manage vs Fargate serverless). Any combo valid.

ECSEKS
APIAWS-native, simpleupstream k8s
portableAWS-onlyanywhere k8s runs
CP costfreehourly/cluster
bestall-in AWS, low opsk8s skills / multi-cloud
  • ECS terms: task definition (blueprint ≈ pod spec) → task (running) → service (keeps N alive behind LB) → cluster.
  • Fargate = no nodes, billed per vCPU-s + GB-s; no GPU/host access (ECS Exec, not SSH). EC2 launch type wins on steady high utilisation & GPUs.
  • Execution role (agent pulls image/writes logs) ≠ task role (your app's AWS perms) ! Mixing them breaks least privilege.
  • Default awsvpc networking (per-task ENI + SG). ECR = private registry (scan + lifecycle). Choosing EKS without k8s skills = over-engineering !

S3 — Classes & Rules

ClassUse
Standardhot, frequent
Intelligent-Tieringunknown/changing access (auto-tiers)
Standard-IA / One Zone-IAinfrequent (1-Zone = re-creatable only)
Glacier Instant/Flexible/Deeparchive; retrieval mins→12h; cheapest
  • 11 nines durability; strong read-after-write consistency (all ops).
  • Security: Block Public Access on by default; prefer bucket policy/IAM over ACLs; presigned URLs for temp access !
  • Encrypt: SSE-S3 / SSE-KMS (audited, use bucket keys to cut cost) / SSE-C. Enforce TLS + encryption via bucket policy Deny conditions.
  • Versioning + lifecycle to tier/expire; replication CRR/SRR for DR; Object Lock (WORM) for compliance.
  • Perf: auto-scales per prefix; multipart for >100 MB; watch retrieval + request + egress cost !

  • EBS = one attach (except io1/io2 multi-attach); EFS = shared across instances/AZs.
  • Snapshots are incremental → S3; copy cross-region for DR. AWS Backup centralizes policy + retention.

Multi-AZ vs Read Replica !

  • Multi-AZ = sync standby for HA/failover, not read scaling.
  • Read replica = async copy for read scaling, not automatic failover (can promote manually).
  • Lambda + RDS → use RDS Proxy (connection pooling; Lambda exhausts DB connections) !
  • Aurora Global / DynamoDB Global Tables for cross-region.

DynamoDB — design

  • Model access patterns first, then keys. Partition key must spread load — avoid hot partitions !
  • Query (by key, cheap) not Scan (full table, avoid in hot paths) !
  • GSI = different PK, eventually consistent, own capacity; LSI = same PK/alt SK, at create time only.
  • Capacity: on-demand (spiky/unknown) vs provisioned+autoscale (steady/cheaper). Strong reads cost 2×.
  • Item ≤ 400 KB; offload big blobs to S3 (store the key).
  • Streams → Lambda for CDC; TTL for expiry; transactions & conditional writes (optimistic lock); DAX for µs reads.

Caching — ElastiCache · DAX

A cache is a bet the same data is read many times before it changes. Every cache decision is a staleness-tolerance decision — cache measured bottlenecks, not by reflex.

StrategyNote
cache-aside (lazy)app reads cache, on miss loads DB & fills; only hot data cached
write-throughwrite cache+DB together; always warm, slower writes, caches unread data
write-behindwrite cache, async flush; fast but loss risk !
  • Redis/Valkey (rich types, replication, multi-AZ, persistence) vs Memcached (multi-threaded pure KV). Default Redis.
  • ElastiCache ≠ durable — failover can lose writes. Need durable Redis? MemoryDB !
  • DAX = DynamoDB-only write-through cache (µs); not general purpose.
  • TTL bounds staleness; watch cache stampede (many misses on one expired hot key hammer the DB) ! Track hit ratio.

Messaging — SQS · SNS · EventBridge · Kinesis

ServiceUse
SQSdecouple, buffer work; consumer pulls
SNSpub/sub fan-out (push)
EventBridgeevent bus, content routing, SaaS/schedule
Kinesisordered streaming, replay, multiple consumers
  • SQS Standard (at-least-once, best-effort order) vs FIFO (ordered, dedup, lower TPS).
  • Visibility timeout must exceed processing time or you get duplicates ! Always set a DLQ.
  • Fan-out = SNS → many SQS. EventBridge for filtering/routing & 3rd-party.
  • Kinesis: shards + partition key (ordering per shard); replay via retention; Firehose = managed delivery to S3/Redshift.
  • Assume at-least-once everywhere → make consumers idempotent.

Integration — API GW · Step Functions

  • API Gateway: HTTP API (cheaper/faster, JWT) vs REST API (usage plans, API keys, VTL, caching) vs WebSocket. Authz: IAM / Cognito / Lambda authorizer.
  • Throttle + usage plans to protect backends; cache to cut cost/latency.
  • ALB vs API GW: ALB for simple container HTTP; API GW for managed auth/throttle/keys/serverless.
  • Step Functions: orchestrate workflows; Standard (long, auditable, exactly-once) vs Express (high-volume, short). Built-in retry/catch, Map/Parallel, direct SDK calls, saga for distributed txns.
  • Orchestration (Step Functions) vs choreography (EventBridge/SNS) — central control vs loose coupling.

Observability & Security

Observe

  • CloudWatch metrics + alarms (static/anomaly/composite) + Logs (Insights, metric filters). Memory/disk need the CloudWatch Agent !
  • X-Ray = distributed traces/service map. CloudTrail = API audit (who did what) — not monitoring. Config = resource compliance/history.

Secure

  • KMS envelope encryption; key policy + IAM; rotate; multi-region keys for DR.
  • Secrets Manager (auto-rotation, cost) vs SSM Parameter Store (cheap/simple, SecureString).
  • Edge: WAF (L7 rules, rate limit) + Shield (DDoS); GuardDuty (threat detection), Macie (PII), Inspector (vulns), Security Hub (aggregate).
  • Cognito: user pools (authn) vs identity pools (temp AWS creds).

IaC & CI/CD

  • CloudFormation: template (desired state) → stack (atomic unit, rolls back on fail). Always create a change set and read "Replacement: True" rows before prod update ! (can destroy an RDS).
  • Drift = console change diverging from template → template lies. Detect on schedule; lock prod console writes (SCPs) !
  • CDK synths to CFN — L1 raw / L2 sensible-defaults+.grant*() / L3 patterns. SAM for serverless.
  • Nested stacks = modularity in one account; StackSets = same baseline to many accounts/regions (landing-zone guardrails).
  • CFN vs Terraform: AWS-managed state + native drift vs multi-cloud + self-managed state (S3 + DynamoDB lock).

Deploy safely

  • Rolling (mutate fleet, rollback = another deploy) vs blue/green (parallel env, instant flip-back) vs canary (small % first, observe).
  • CodeDeploy hooks + CloudWatch alarm → auto-rollback. Immutable infra: replace, don't patch. Never bake secrets into images/logs !

Well-Architected & DR

6 pillars: operational excellence · security · reliability · performance efficiency · cost optimization · sustainability.

DR strategies (RTO/RPO ↓, cost ↑)

StrategyRTO/RPO
Backup & restorehours; cheapest
Pilot light10s of min; core running small
Warm standbyminutes; scaled-down live
Multi-site active-active~0; priciest
  • RTO = time to recover; RPO = tolerable data loss.
  • Design stateless (externalize state to S3/Dynamo/ElastiCache); retries with backoff + jitter; idempotency.
  • Reduce blast radius (cells, multi-AZ). Quotas are a reliability risk ! Test with FIS game days.

Cost Optimization

  • Compute: Savings Plans/RI for baseline, Spot for fault-tolerant, Graviton, right-size, scale to zero.
  • Storage: S3 Intelligent-Tiering, gp3 over gp2, kill snapshot/log sprawl, lifecycle to Glacier.
  • Data transfer is the silent bill ! cross-AZ chatter, inter-region, internet egress, and NAT Gateway data processing charges.
  • Visibility: Cost Explorer, Budgets + anomaly detection, CUR, cost-allocation tags, Compute Optimizer, Trusted Advisor.
  • Reserved capacity also for RDS/ElastiCache/OpenSearch/Redshift.
  • Anti-patterns: idle/forgotten resources, over-provisioning, un-tiered logs, single huge NAT for cross-AZ.

★ Architecture Review Checklist

Security

  • ☐ No hardcoded keys — roles everywhere; least-privilege IAM; no * actions/resources without reason.
  • ☐ S3 Block Public Access on; encryption at rest (KMS) & TLS in transit.
  • ☐ Secrets in Secrets Manager/SSM, not env/plaintext; KMS key policies scoped.
  • ☐ Edge protected (WAF/Shield); security groups least-open; private subnets for data.
  • ☐ Task role ≠ execution role on ECS; IMDSv2 enforced on EC2.

Reliability

  • ☐ Multi-AZ for every stateful tier (DB, cache); no single-AZ prod DB.
  • ☐ Decoupled with queues; DLQs on async; retries with backoff+jitter; idempotent consumers.
  • ☐ Defined RTO/RPO & a tested DR strategy; health checks + failover.

Performance & Cost

  • ☐ Right service for the access pattern (Query not Scan; cache hot reads; CDN static).
  • ☐ Auto scaling on the right metric; right-sized instances / Lambda memory.
  • ☐ VPC endpoints to avoid NAT/egress cost; minimize cross-AZ traffic.
  • ☐ Budgets/alarms set; tags for cost allocation; no forgotten resources.

Operations

  • ☐ IaC (CFN/CDK/Terraform), not click-ops; change sets reviewed; env/account separation.
  • ☐ Metrics + logs + traces + alarms; CloudTrail on; auto-rollback on alarm; runbooks.
