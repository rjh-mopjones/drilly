LLM Fundamentals & Decode Knobs

  • Autoregressive: one forward pass per output token; input read in parallel (prefill). So output is the slow & expensive part !
  • Output is a probability distribution over the vocab; decoding samples from it. You bias the distribution, never command it.
  • Bounded compute per token → hard multi-step problems need more tokens to think across (why CoT works).
KnobEffect
temperature0 = greediest/most deterministic-ish; higher = more diverse. Use ~0 for extraction/classification.
top_pnucleus: sample from smallest set summing to p. Tune one of temp/top_p, not both.
max_tokensoutput cap — the cheapest cost+latency lever.
seedbest-effort repeatability; not a guarantee !

! temp 0 is not deterministic across calls/versions — kernels, batching, and backend changes still vary output.

Prompt Engineering

A prompt is a program in NL, run by a probabilistic interpreter. Treat it as versioned code with an eval harness — not a magic string.

LeverWhen
System vs usersystem = how to behave (durable); user = what to do now. Don't put per-request data in system !
Few-shot (ICL)fixes format/edge-cases; show the hard case; use fewest that work.
CoTgenuinely multi-step tasks only; wasted/harmful on lookup/classify & on reasoning-by-default models !
Delimitersfence untrusted data (<doc>…</doc>); refer to it by name.
Decomposesplit mega-task into a chain of focused prompts.

Order: role → rules → format → examples → data → restated key ask. Beginning & end get best attention (lost in the middle).

! System prompt is the strongest steering, not a security boundary — user input can override it. ! "Improved it" only means metric went up on a held-out eval set, never one lucky sample.

Structured Output & Constrained Decode

Two independent axes — conflating them is the classic error:

  • Syntactic validity (parses & matches schema shape/types) — constrained decoding solves this completely.
  • Semantic correctness (values are actually right) — constrained decoding does nothing for this !
TechniqueGuarantees
prompt-and-hopenothing → must validate+repair
JSON modevalid JSON, any shape
schema-constrainedstructure+field names+types+enums
fn-call-as-extraction= constrained (via tool iface)

Mechanism: a grammar/state-machine masks illegal next-tokens to -inf each step, so invalid chars cannot be emitted. Define schema once in Pydantic/zod (type + JSON-Schema + validator + error msgs for repair).

! A required non-nullable field forces fabrication when the answer is "absent". Give an explicit null/"unknown"/refusal branch. Always validate at the boundary even when constrained.

Function & Tool Calling

The model never runs your code. It emits structured text (name + JSON args); your runtime executes and feeds the result back. You own the loop and the trust boundary.

1 send: messages + tool schemas (+ tool_choice)
2 model → {id, name:"get_wx", args:{city}}   (finish=tool_calls)
3 YOU run get_wx(city) → "14C"
4 append assistant tool-call + tool-result{tool_call_id:id}
5 re-invoke with extended history
6 another call → 3, else text (finish=stop) → done
  • It's a loop, not one hop; the id glues results to calls (enables parallel calls).
  • tool_choice: auto / required / named / none.
  • Design: few, orthogonal, well-described tools beat an API dump — too many degrades selection !
  • The description is the prompt: the model picks by name+description, so write them for the model, not the docs. Ambiguous/overlapping tools → wrong-tool errors.
  • Parallel calls: model can emit several tool calls in one turn (independent lookups); execute concurrently, glue results back by id.
  • Return errors as tool results, not exceptions — let the model see "not found" and recover/branch rather than crashing the loop.

! Always cap iterations + token budget (model drives the loop → can spin). ! Tool code is yours; tool output is untrusted (web page, doc, DB row).

Agentic Systems (ReAct)

An agent is a control loop wrapped around a stateless model. Model proposes; the harness disposes — auth, gating, idempotency, audit, rate limits all live in the harness.

loop:
  reason  "need plan tier before quoting"
  act     get_account(user_id)
  observe {"tier":"enterprise"}   → into context
  reason  "enterprise → volume pricing"
  act     get_rate_card("enterprise") …
  → no more calls → done

Interleaving (see obs N before act N+1) beats a single-shot plan: real envs surprise you (empty search, 404), and the agent can recover/branch.

  • Terminate on: goal met / no tool call / error / budget cap (steps, tokens, wall-clock).
  • Multi-agent only for genuinely parallel or context-isolated sub-tasks — else it's latency+token+coordination overhead !

! "Done" is the one thing the model can lie about — never rely on it alone. ! temperature:0 does not make control flow deterministic.

RAG — Pipeline & Failure Map

RAG is an IR problem with an LLM on the end, not a model problem with search bolted on. Garbage in → fluent garbage out. Every stage is lossy.

StageDominant failure
Ingestmangled PDF/OCR, lost structure
Chunksplit mid-thought; answer spans 2 chunks
Embeddomain mismatch; jargon collapses
Store/ANNstale index, recall loss
Retrievelow recall (missed) / low precision (noise)
Augmentoverflow, bad order, no citations
Generateignores ctx / trusts wrong chunk

Two halves: indexing (offline batch) vs serving (per-query). Most wins are at ingest+chunk, not a bigger model. Serving latency is dominated by generation (seconds), not retrieval (tens of ms).

Debug order = pipeline order. Before blaming the model, check upstream: was the right chunk even retrieved (raise k / add hybrid)? Was it ranked into the prompt (rerank)? Only then is it a generation problem (grounding, lost-in-the-middle, overflow). A "hallucination" in a RAG app is usually a retrieval miss in disguise — the model fell back to parametric guessing.

Chunking Strategies

Core trade-off: small chunks retrieve precisely but answer incompletely; large chunks carry context but embed fuzzily & burn tokens.

StrategyNote
fixed-size + overlaptrivial, structure-blind; splits mid-sentence. Baseline only.
recursive / structuralsplit on headings→paras→sentences. Sensible default; needs real structure.
semanticcut where embedding sim drops; costs embeds, fragile thresholds.
sentence-windowindex sentences, return sentence+neighbours.
parent-documentindex child chunks, return parent section.

Key insight: decouple the retrieval unit from the generation unit — retrieve small & focused, then expand to surrounding context. Tables/code: chunk by logical unit (whole table/function), optionally embed a generated summary.

Retrieval: Sparse · Dense · Hybrid · Rerank

MethodStrength / weakness
BM25 (sparse)exact lexical overlap; cheap, no GPU. No synonyms.
Dense (embed)meaning/paraphrase; lossy on exact tokens !
Hybridfuse via RRF; production default.
RRF(d) = Σ 1 / (k + rank_of_d)   # k≈60, fuse ranks not scores

BM25 still wins on exact-match: SKUs, part/error codes, API names, ticket IDs, legal citations, rare proper nouns — and any corpus your embed model never trained on. Naming this unprompted is a senior tell.

Two-stage funnel

query → bi-encoder ANN → top ~150   (cheap, recall)
      → cross-encoder  → top ~5-10  (expensive, precision)

Bi-encoder: embeds q & d independently → precompute corpus, ms search. Cross-encoder: reads [q][SEP][d] together → far more accurate, but per-pair at query time.

! Rerank is a precision tool — it can only reorder what stage-1 recall surfaced. If the chunk isn't in top-150, nothing saves you.

Embeddings · ANN · Distance Metrics

Exact NN is linear → hopeless at millions/query. ANN trades a tunable slice of recall for sub-linear search.

IndexNote
HNSWmulti-layer proximity graph; best recall/latency, memory-hungry, awkward to update. Params: M, efSearch.
IVFcluster + probe nprobe nearest; memory-lean, shardable, drift-sensitive.
PQquantize/compress vectors — more recall traded for big memory cut.
cosine = dot(a,b)/(|a||b|)   # angle only
dot    = dot(a,b)             # angle AND magnitude
L2     = |a-b|

On unit-normalized vectors, cosine/dot/L2 give the same ranking. ! Raw dot on un-normalized embeds → magnitude leaks, long docs rank spuriously high. Match the index metric to the model's training metric or recall silently degrades.

Vector DBs & Index Choice

  • pgvector: reuse Postgres — transactions, joins, metadata filters, ACLs in one place. Great default until scale/latency forces a specialist.
  • Dedicated (FAISS-lib, HNSW-based services): scale & latency, but a separate system to sync/operate.
  • Metadata filtering is first-class: enforce access control at retrieval (pre/post-ANN), never in the prompt — a leaked chunk in context is a data breach !

Freshness & churn

  • Incremental index: content-hash/CDC → re-embed only changed docs. Re-embedding the whole corpus daily is the first thing to blow up on cost !
  • Tombstone superseded chunks — old chunks must be deleted, not just supplemented, or retrieval surfaces stale/legally-wrong text !
  • Heavy churn hurts HNSW updates → periodic rebuild or IVF.

Context Engineering & Memory

The window is a small expensive desk. The model is stateless — "memory" is you re-placing history each turn. Budget is zero-sum.

usable_input = ctx_window − reserved_output − margin
fit: system + history + retrieved ≤ usable_input

! Reserve output space — window is shared input+output; pack it full and the answer truncates mid-sentence. ! Lost in the middle: put the critical fact at start or end.

MemoryTrade
buffer (last N turns)exact, bounded, forgets old
summary / compactionkeeps gist, lossy — a one-off figure can vanish !
vector-backedRAG over past turns; recall on demand

Context (this call) ≠ memory (persistent store you draw from). More tokens ≠ better: they dilute attention, cost more, slow TTFT.

Caching (LLM-specific)

TypeWhat it does
Prompt cachingreuse provider-side compute for a repeated static prefix → cuts input cost & TTFT on the cached portion.
Semantic cachingreturn a stored answer for a semantically similar past query → skips the model call entirely.
  • Prompt cache: put the stable stuff first (system prompt, tool schemas, few-shot, long doc); dynamic tail last. Order the prefix to maximise hits.
  • Semantic cache: set a similarity threshold — too loose returns a wrong-but-close answer !; scope keys per user/tenant to avoid leakage.
  • Neither is an HTTP/CDN cache, and prompt caching is not cross-call memory.

Also cache: embeddings for unchanged docs, and full answers for hot repeated queries.

Cost & Latency Engineering

Output tokens are the expensive AND slow part (autoregressive). Input is parallel & cheap. Cost ≈ tokens × price × call-count — the sneaky multiplier is call-count.

Latency shape: TTFT (fixed-ish prefill) + generation (tokens ÷ tok/s) + tool/network round-trips.

ProblemLever
both cost+latencygenerate fewer output tokens (concise, max_tokens, enums)
repeated prefixprompt caching
skewed difficultycascade/route: cheap model first, escalate
perceived latencystream (TTFT sooner; total unchanged)
independent callsparallelise

! Shrinking the prompt barely moves latency — attack output length & model choice. ! Agent loops are 5–20 calls/action — cost multiplies by loop length. ! "Cheaper model" is only a win if it still passes your eval.

Attribute spend at the gateway per user / feature / prompt-version — a single monthly total tells you nothing about which feature is bleeding. Streaming improves perceived latency but you still pay for every token generated before a client disconnect, so cap max_tokens anyway.

Model Selection & Routing

  • Model sets your token prices, TTFT, ceiling capability, context size. Pick per-task, measured on your eval — not a leaderboard ! (benchmarks measure their task & are contaminated).
  • Closed (API): best quality, fastest to ship, no infra; lock-in, data-egress, price/deprecation risk.
  • Open (self-host): control, privacy, no per-token bill at scale; you own serving, GPUs, quantization.

Cascade / routing

cheap/small model  → confident? → return
        ↓ hard/low-confidence
strong/frontier model → return

Primary cost lever when difficulty is skewed (most queries are easy). Route by a classifier, heuristic, or self-reported confidence. Validate the router itself — a bad route sends easy queries to the pricey model or hard ones to the weak one.

Adaptation: Prompt vs RAG vs Fine-tune

They change different things — match lever to need, cheapest first.

LeverChangesUse for
Promptinstructions @ runtimetask/format/tone. Try first, always.
RAGknowledge @ runtimeprivate/current/large facts. Fresh, citable, deletable, ACL.
Fine-tunethe weightsbehaviour: rigid format, house voice, small model matching a big one, prompt-compression.

The rule: fine-tune for behaviour, retrieve for knowledge. ! Fine-tuning to inject facts is the canonical error — lossy, un-citable, stale day one, un-editable.

  • LoRA/QLoRA: train <1% params, freeze base, swappable adapters. Full fine-tune rarely needed & risks catastrophic forgetting.
  • Data + eval dominate, not the training run. A fine-tune is a static artifact that drifts from the improving base — maintenance debt.
  • Often the answer is both: RAG for facts + light fine-tune for format.

Evaluation

No compiler, no deterministic oracle — "correct-looking" is the trap. Build a layered instrument and distrust it like the system under test.

  • L1 deterministic: parses? schema-valid? citation real? PII absent?
  • L2 reference: metrics on a versioned golden set → CI regression gate.
  • L3 judgement: LLM-as-judge / human for open-ended.

RAG metrics — 2 stages

MetricCatches
Faithfulnessgen: answer supported by ctx → hallucination
Answer relevancygen: addresses the question
Context precisionretr: signal/noise of chunks
Context recallretr: needed info surfaced → retrieval gap

! LLM-judge has position, verbosity, self-preference bias — validate it. ! Offline win = the proxy moved; confirm online. Good retrieval metrics ≠ good answers (found ≠ used correctly).

Making an LLM-judge trustworthy

  • Validate the judge against human labels first — measure its agreement rate; an unvalidated judge is just a second opinion, not a metric.
  • Prefer pairwise (A vs B) over absolute 1–10 scores — models rank better than they calibrate. Randomise order to cancel position bias.
  • Give a rubric + reference answer; ask for the reason before the verdict; use a different model to dodge self-preference.
  • Watch the tail, not the mean — average score hides the catastrophic 3% of cases that actually hurt users.

Guardrails & Safety

Input validation + output sanitisation for a component you can't trust. Defence in depth — don't rely on the model to police itself.

system prompt = "please behave"  → request, best-effort
guardrail     = code that blocks → control, enforced

Two axes: input (topic/PII/injection/schema — before you spend tokens) vs output (moderation/PII/groundedness — before user sees it); deterministic (regex/schema/denylist — cheap, brittle) vs model-based (classifier/judge — flexible, adds latency/cost/error). Layer cheap-first.

  • Moderation = per-category scores vs tunable thresholds, not one yes/no. Threshold per context.
  • PII detect/redact on input & output; keep the bot on-topic without lobotomising it.
  • Order checks cheap-first: deterministic regex/schema/denylist before a model-based classifier, so the expensive check only runs on what survives.

! A system prompt is not a guardrail (inside the trust boundary). ! Fail-open vs fail-closed is a deliberate per-check call — open keeps product usable but may leak harm; closed is safer but a flaky guardrail = outage.

Prompt Injection & LLM Security

Root cause is architectural: the LLM mixes instructions & data in one channel (the context window) with no reliable boundary. Any text it reads can act as a command.

program: code (trusted) | input (data, never run)  ← boundary
LLM:     system + user + retrieved doc + tool out  ← one stream
  • Direct: user jailbreaks their own input. Indirect: instructions hidden in third-party content the model ingests (web page, doc, email, RAG chunk) — the more dangerous form; needs no user malice.
  • Model = confused deputy: acts with your privileges on the attacker's instructions.

Lethal trifecta !

private-data access + exposure to untrusted content + an exfil channel (tool call, markdown-image URL, outbound link) = data-leak vector. Break any one leg.

! You cannot prompt your way out — injection rides the same channel as your defence. Constrain what the model can do: least privilege, sandboxing, human-in-the-loop for consequential actions, output/URL filtering. ! Never treat model output as a trusted command (shell/SQL/eval/browser). Mitigate, never "solved".

Streaming & Real-Time

  • SSE token stream cuts perceived latency (first token sooner) — not total time or cost.
  • You must buffer a tool call before executing it — you can't act on half a JSON args blob.
  • ! Can't JSON.parse a stream: {"name":"Ali is a syntax error, not a partial object. Use a tolerant/partial parser for live field-by-field UIs, or just wait-and-parse for small machine-consumed objects.
  • ! A partial value is provisional — never fire a side-effect until the object is complete & validated (stream can error mid-way).
  • Handle mid-stream errors & client disconnects; you still pay for tokens already generated.

Inference & Serving (Self-Host)

Serving is a memory-bandwidth & memory-capacity problem, not raw FLOPs. Decode reads the whole model per token → you wait on bytes moved, not math. Every lever spends a surplus resource to buy the scarce one.

PhaseProfile
Prefillparallel read of the prompt → first token; compute-heavy, sets TTFT.
Decode1 token/pass, autoregressive; bandwidth-bound, sets throughput.
  • Batching amortises the weight-read across many requests → throughput scales with batch size ! but per-request latency rises.
  • KV cache stores K/V for every token×layer×request so decode doesn't recompute attention. Grows linearly with sequence → caps concurrency & is why long contexts are pricey !
  • Continuous batching (add/evict per step) + PagedAttention (KV in OS-style pages, ~0 fragmentation) = the vLLM/TGI throughput wins.
  • Speculative decoding: small draft model guesses K tokens, big model verifies in 1 pass → latency win, lossless quality; useless on a saturated batch.
weights ≈ params × bytes/param   (fp16=2, int8=1, int4≈0.5)
7B fp16 ≈ 14GB · 7B int4 ≈ 3.5GB · 70B fp16 ≈ 140GB (>1 GPU)
KV_free = GPU_mem − weights − ~15% overhead
concurrency ≈ KV_free ÷ KV_bytes_per_token

Quantization (int8≈lossless, int4 GPTQ/AWQ often close) is the top self-host lever — ! not free: eval the quantized model, take the most aggressive tier that still passes. Too big for one GPU → tensor (split each layer's matrices) / pipeline (put layer stages on different GPUs) parallelism.

! Self-host only wins on hard privacy or high steady utilisation — idle rented GPUs destroy the economics. API is the default.

App Architecture & Orchestration

Design like a backend engineer wrapping a flaky, non-deterministic third-party API. Push complexity to the edges; keep the model call a thin, swappable, inspectable seam.

client → AI gateway → orchestration → models
                                    → tools/data
         (observability spans all)
LayerOwns
Gatewaykeys, routing, rate/budget, fallback, cache, cost logs → model = config value.
Orchestrationprompt assembly, chain/graph, retries, output validation.
Observabilityfull trace: assembled prompt + raw response, versions, tokens, cost.
  • Chain = fixed linear pipeline (readable, testable). Graph = nodes + conditional/looping edges — only pay for it when branching/loops are real ! most "graphs" are a chain in costume.
  • Prompts & model versions = code: triage@v7, pinned model@snapshot, eval-gated, ship decoupled from deploys. "latest" silently changing under you = incident !
  • Resilience ladder: bounded timeout (vs p99) + stream → retry (backoff+jitter, cap ~2, retryable only) → circuit breaker → fallback model/provider → graceful degrade.

! Retry is not safe once a call has side effects — the ambiguous "succeeded but response lost" case double-fires. Idempotency lives at the action layer; separate "generate the plan" from "execute the plan".

! You can't reproduce a bad answer by re-running — you debug from the logged trace. Wire observability before you need it.

Hallucination & Reliability

A model is a next-token predictor optimised for plausibility, with no ground-truth signal. Fluency and factuality are decoupled — a fabricated citation is a high-probability continuation. It's structural, not a bug you patch.

  • ! Bigger model lowers the rate, never to zero; temperature:0 gives a deterministic wrong answer, not a right one.
  • OOD & sycophancy are the danger zones: rare entities / your jargon → interpolation; leading questions → confident agreement with a false premise.

You don't make the model reliable — you build a reliable system around it. Stack cheap-broad under expensive-precise:

LayerNote
Groundanswer only from retrieved sources + cite → removes the gap. Primary mitigation.
Self-consistencysample N, vote; spread = uncertainty. Misses systematic error; N× cost !
Verifyindependent check: tool/DB/schema (strong) > 2nd-model judge (weak).
Abstain"I don't know" beats a confident guess when wrong >> silent.

! Logprobs & verbalized confidence lie — they measure token likelihood, not truth; a fabrication is high-logprob. Real confidence comes from outside the generation (agreement / external verifier).

! Grounding shifts the failure, doesn't erase it: model can be unfaithful to correct evidence or faithful to wrong evidence. Put the human at the irreversible step; make residual errors visible & recoverable.

Multimodal & Beyond Text

Non-text inputs become tokens the same transformer consumes. An image is patchified → encoded → projected into token space, so it's many tokens, not one input — same per-token price & context budget as prose.

sentence      ~15-30 tok
low-detail img ~85 tok
high-detail   ~500-1500+ tok  (re-tiled → each sub-img encoded)
  • Reduce to text first. Digital PDF/DOCX → extract embedded text (cheap, exact); send the image only for a real scan/photo where info lives in pixels !
  • Boundary is lossy & silent: OCR mangles tables/columns, transcriber mis-hears names, VLM can't read fine print — and the LLM reasons fluently over the garbage !
ChoiceTrade
OCR→LLMcheap, fast; destroys layout — tables/forms collapse.
Layout-aware VLMrobust on tables/scans; pricey (image tokens).
STT→LLM→TTSobservable, swappable, guardrail-able; latency additive, loses prosody.
Native speech2speechlow-latency, keeps tone; black box, no transcript to audit.

Multimodal RAG: retrieve on a cheap proxy (caption / CLIP-style shared-space embedding), then feed the raw image to the VLM at generation. Extraction (receipt→JSON) = reliability problem: schema-constrain + business-rule validate (line items sum?) + confidence/bbox → human-review the tail.

! Image generation is an async, two-sided-moderated (prompt and output pixels), cost-capped subsystem — not a sync API call.

★ Design / Review Checklist

Reliability of the probabilistic component

  • ☐ Structured output schema-constrained where machine-consumed, and still validated at the boundary.
  • ☐ Nullable / "unknown" / refusal branch so honesty is representable — no forced fabrication !
  • ☐ Bounded validate→repair loop (1–2 tries) with the specific error fed back; failure routes to review, not an infinite spin.

RAG

  • ☐ Hybrid retrieval (BM25+dense) — exact-identifier queries covered.
  • ☐ Re-ranker on stage-1 candidates; index metric matches embed model; vectors normalized.
  • ☐ Incremental re-index + tombstoning of superseded chunks; ACL enforced at retrieval, not prompt !
  • ☐ "Answer only from sources; if absent, say so" + citations.

Agents / tools

  • ☐ Loop has step + token + wall-clock cap; not trusting model's "done".
  • ☐ Least-privilege tools; consequential writes gated (human-in-the-loop) + idempotency key.
  • ☐ Tool output treated as untrusted; no trifecta (private data + untrusted content + exfil).

Cost / latency / eval

  • ☐ max_tokens capped; prompt cache on static prefix; cascade for skewed difficulty; stream to the user.
  • ☐ Prompts versioned + gated by a golden-set regression check in CI; LLM-judge validated.
  • ☐ Guardrails as an independent layer; fail-open/closed chosen deliberately per check.

Reliability & architecture

  • ☐ Grounding is the backbone; abstention wired to retrieval/verification (not vibes); irreversible action has a human at the step.
  • ☐ Model behind a gateway (swappable config); prompt + model versions pinned & observable; assembled prompt + raw response logged per request.
  • ☐ Multimodal reduced to text where the signal allows; extraction schema-constrained + rule-validated + confidence-gated to human review.
  • ☐ Self-host justified by hard privacy or steady utilisation; quantization eval'd, not assumed; batch/latency policy set to an SLO.
