CI = integrate + build + test every change, keep main green. CD = deliver (human gate) or deploy (auto) that same artifact to prod, safely, with a tested rollback. Everything right of the artifact box is a re-point, never a rebuild.

CI vs CD & Pipeline Model

TermMeans
CImerge often + auto build/test on every change; keep main green
Continuous Deliveryevery green build is releasable; a human clicks deploy
Continuous Deploymentevery green build auto-ships to prod, no human
  • Pipeline = stages → jobs → steps, fired by events: push / PR / tag / cron / manual / API.
  • Jobs in a stage run in parallel; model dependencies as a DAG (needs/depends_on) so a job starts the moment its inputs are ready, not when the whole stage finishes.
  • Pipeline-as-code lives in the repo — reviewed, versioned, diffable. Beats click-configured jobs you can't audit !
  • Runner/executor picks up a job, provisions a clean env (VM/container), runs steps, reports status back to the commit.

CI Practices & Hygiene

  • Trunk-based: short-lived branches, merge to main within a day. Long-lived feature branches → integration/merge hell !
  • Keep main green: branch protection — required status checks, required reviews, no direct pushes, linear history.
  • Merge queue / trains: serialise merges and re-test each PR against the updated main, so two individually-green PRs can't combine to break it (semantic merge conflict) !
  • Fast feedback (single-digit minutes): parallelise, cache deps, shard tests, build only affected packages. A 40-min CI kills the practice — people stop running it !
  • Feature flags let you merge incomplete work behind an off switch — deploy ≠ release, branches stay short.
  • Every push runs the same pipeline; PR pipeline is a subset (no deploy). One source of truth for "is it green."

GH GitHub Actions — Fundamentals

name: ci
on:
  push: { branches: [main] }
  pull_request: {}
permissions:
  contents: read          # least-priv floor
concurrency:              # cancel superseded runs
  group: ci-${{ github.ref }}
  cancel-in-progress: true
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci && npm test
      - uses: actions/upload-artifact@v4
        with: { name: dist, path: dist/ }
  • Hierarchy: workflow → jobs (parallel, own runner) → steps (sequential, share filesystem). Order jobs with needs:.
  • Pin third-party actions by commit SHA, not a tag — a tag can be moved to malicious code !
  • Contexts: ${{ github.sha }}, secrets.*, env.*, needs.x.outputs.*.

GH Actions at Scale

Matrix — fan one job into N

strategy:
  fail-fast: false        # let every combo finish !
  max-parallel: 4
  matrix:
    node: [18, 20, 22]
    os: [ubuntu-latest, windows-latest]
    include: [{ node: 20, os: ubuntu-latest, cov: true }]
    exclude: [{ node: 18, os: windows-latest }]
runs-on: ${{ matrix.os }}

fail-fast:true (default) cancels siblings on first fail — you lose the full failure picture.

Cache vs Artifact — not the same tool

ArtifactCache
purposepreserve/share outputsspeed via reuse
guaranteed presentyes (until retention)no — evictable

correctness may dependyesnever !
- uses: actions/cache@v4
  with:
    path: ~/.npm
    key: ${{ runner.os }}-npm-${{ hashFiles('package-lock.json') }}
    restore-keys: ${{ runner.os }}-npm-
  • Exact key hit → restored, not re-saved. Prefix hit via restore-keys → nearest old cache restored, new one saved.
  • Put the lockfile hash in the key or you serve stale deps ! Caches are branch-scoped (read base/main, not siblings). Build must survive a cold cache.

GH OIDC & Least-Privilege

OIDC = the #1 modern CI security upgrade. No long-lived cloud keys stored anywhere: the run requests a short-lived signed identity token; the cloud, trusting GitHub's issuer, exchanges it for temporary role creds (mins).

permissions:
  id-token: write     # REQUIRED to mint OIDC token
  contents: read
steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123:role/gha-deploy
      aws-region: eu-west-1
  - run: aws s3 sync ./dist s3://acme-app
  • IAM trust policy conditions on the subject claim — e.g. only repo:acme/app:ref:refs/heads/main can assume it.
  • No static key to leak from a secret or log; rotation becomes a non-problem (no keys).
  • permissions: scopes GITHUB_TOKEN — every step incl. third-party actions gets it. Read-only floor, elevate per-job (packages: write) only where needed !

GH Fork-PR Secret Leak !

TriggerOn fork PR gets…
pull_requestPR code, read-only token, no secrets — safe
pull_request_targetbase context, write token, full secrets — but triggered by fork
# VULNERABLE — hands secrets to attacker's code
on: pull_request_target
steps:
  - uses: actions/checkout@v4
    with: { ref: ${{ github.event.pull_request.head.sha }} }
  - run: npm ci   # fork's postinstall reads secrets, exfiltrates
  • Poisoned-pipeline / secret-exfiltration: a fork's lifecycle script (postinstall) reads secrets/token and POSTs it out.
  • Fix: run untrusted code under plain pull_request (no secrets). Reserve pull_request_target for tasks that don't check out/run PR code (labelling). Gate privileged follow-ups behind workflow_run or an environment approval after a maintainer reads the diff.
  • Masking (***) is a safety net, not a guarantee — it misses transformed/base64'd values and can't stop exfiltration to an attacker's host !

GL GitLab CI/CD

stages: [build, test, deploy]
build:
  stage: build
  image: node:22
  script: [npm ci, npm run build]
  artifacts: { paths: [dist/], expire_in: 1 week }
test:
  stage: test
  needs: [build]          # DAG — start before stage done
  script: [npm test]
  coverage: '/Lines\s*:\s*(\d+.\d+)%/'
deploy_prod:
  stage: deploy
  environment: { name: production, url: https://acme.com }
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual        # click-to-deploy gate
  script: [./deploy.sh]
  • rules (modern) > only/except: decide if a job runs; needs = DAG cross-stage.
  • Review apps = ephemeral env per MR; built-in Container Registry, CI_* vars, include for templates.
  • Protected branches/variables gate prod; runners: shared/group/specific; tags to target executors.

Build & Test Stages

  • Build once up front; every downstream stage consumes that artifact — hermetic, reproducible, pinned toolchain.
  • Test pyramid: many fast unit → fewer integration → few e2e/smoke. Gate merges on the fast layers; run the slow ones post-merge / pre-deploy.
LayerSpeed / count
static (lint, typecheck, SAST)secs — cheapest gate
unitms each, thousands
integrationseconds, hundreds
e2e / smokeminutes, tens
  • Speed levers: cache deps, shard/parallelise tests, affected-only in monorepos (paths:, Nx/Turbo, dorny/paths-filter).
  • Flaky tests erode trust in green — quarantine + fix, never blanket-retry into the void !

Artifacts & Registries

  • Immutable + versioned: tag by git-SHA / semver / @digest. Store in a repository: Artifactory, Nexus, GitHub/GitLab Packages, a container registry.
  • Build once → promote the same artifact up the ladder. Config & secrets injected per env at deploy (12-factor) — never baked in !
  • The digest (sha256:…) is the true identity; a tag is a mutable pointer. Deploy & roll back by digest.
  • Attach provenance + SBOM, sign the artifact; set retention/GC so storage doesn't grow unbounded.
  • :latest is mutable and races across builds — never deploy :latest !

Container Image Pipelines

# multi-stage: fat build, slim runtime
FROM node:22 AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci                  # cached layer
COPY . .
RUN npm run build
FROM gcr.io/distroless/nodejs22 AS run
COPY --from=build /app/dist /app
CMD ["/app/server.js"]
  • Layer order = cache hits: copy lockfiles + install before copying source, so code edits don't bust the deps layer.
  • Small base (distroless/alpine) → smaller attack surface + faster pulls. Non-root USER. .dockerignore to keep secrets/junk out.
  • BuildKit cache mounts + registry cache for CI. Tag image@sha256:….
  • Pipeline: build → scan (Trivy/Grype) → sign (cosign) → push → deploy → verify signature at admission !

Progressive Delivery & Canary

  • Canary on autopilot: shift traffic in steps + automated analysis (error rate, p95/p99 latency, saturation) → promote or auto-abort.
  • Baseline comparison: judge canary vs the stable version running concurrently, not vs yesterday — controls for time-of-day/traffic !
  • Controllers: Argo Rollouts (Rollout CRD: setWeight → pause → analysis) / Flagger (Flux + service mesh).
strategy:
  canary:
    steps:
      - setWeight: 5
      - pause: { duration: 5m }
      - analysis: { templates: [{ templateName: error-rate }] } # abort→rollback
      - setWeight: 25
      - pause: { duration: 5m }
      - setWeight: 50

Traffic shift via ingress / mesh weights. Ring deploys: internal → early adopters → everyone.

Environments & Promotion

  • dev → staging → prod; parity matters — staging mirrors prod (data shape, config, scale-down). Avoid snowflakes !
  • Promote the same digest up the ladder; gate prod with required reviewers / manual approval (auditable, records who + when).
  • Config & secrets per env injected at deploy — kept OUT of the artifact. One binary, many envs.
  • Ephemeral preview envs per PR (review apps / per-PR namespace) — spin up on open, tear down on merge/close.
  • Separation of duties: who may deploy to prod, least-privilege deploy identity per env.
  • GH environment: adds required reviewers, wait timer, branch policy, scoped secrets, and a Deployments-API timeline.

GitOps — Pull-based CD

  • Git is the single source of truth for desired state; an in-cluster agent pulls and continuously reconciles.
  • Push (CI runs kubectl, needs cluster creds in CI) vs pull (ArgoCD/Flux; no cluster creds leave the cluster) — pull is safer !
  • ArgoCD: Application CRD, sync/health status, self-heal, app-of-apps. Flux: source + kustomize/helm controllers + image automation.
  • Self-heal reverts manual kubectl drift back to Git — no snowflake clusters.
  • Flow: CI builds+pushes image, then bumps the tag/digest in a config repo → GitOps agent deploys. Rollback = git revert (first-class audit trail).
  • Secrets: sealed-secrets / SOPS / external-secrets — never commit plaintext !

Release Management & Versioning

  • SemVer MAJOR.MINOR.PATCH = breaking / backward-compat feature / fix. Pre-release -rc.1, build +meta.
  • Automate: semantic-release / release-please / changesets derive version + changelog from Conventional Commits (feat:, fix:, feat!:), tag & publish in CI. "Release" becomes "merge the release PR."
  • Monorepo: release only changed packages (changesets/Nx) vs lockstep single-version.
  • Hotfix via cherry-pick onto a release branch; feature flags to deploy without releasing.
  • Tag immutably (v1.4.2); npm --provenance / signed tags for supply-chain integrity.
# tag-triggered release
on: { push: { tags: ['v*.*.*'] } }
permissions: { contents: write, packages: write, id-token: write }

Secrets & Supply Chain

  • OIDC → short-lived cloud creds instead of long-lived keys — the single biggest win !
  • Least-privilege pipeline identity & token perms; secret managers (Vault / cloud KMS / SM), masking, scope secrets to environments.
  • Fork PRs must NOT get secrets (no unsafe pull_request_target) — poisoned-pipeline exfiltration !
  • Pin actions/images by SHA/digest; scan deps (Dependabot/Renovate/Snyk); SAST + secret-scan + DAST gates.
  • SLSA provenance (how/where built) + sign (cosign) + verify at admission; SBOM (syft/Trivy) for what's inside.
  • Ephemeral, hardened, single-use runners; never attach self-hosted runners to public repos !
  • A compromised pipeline = compromised prod. Protect the CI system itself: RBAC, audit logs, protected branches.

Deploy Observability & Rollback

  • Deploy = a supervised transition: hypothesis ("≥ as healthy as last") → observation window → decision (promote / roll back), ideally automated.
  • Gate on readiness/health probes first (K8s won't route to a failing pod; rolling update pauses), then watch golden signals on the new version vs baseline: error rate, p95/p99 latency, saturation, throughput.
  • Automated rollback = explicit failure criteria + a re-point mechanism + a watcher. Vague ("looks bad") can't automate !
StrategyRollback / speed
recreateredeploy old (downtime) — slow
rollingkubectl rollout undo — medium
blue-greenflip router to blue — instant
canaryweight → 0 — instant
GitOpsgit revert → reconcile — fast

Roll back by default (restore service, then diagnose); roll forward only when an irreversible migration/data change makes revert unsafe. Feature-flag kill-switch = release rollback with no redeploy — huge MTTR cut.

DORA Metrics

Four metrics, throughput + stability together — you can trivially game one by sacrificing the other, so balance them.

MetricTypeElite
Deploy frequencythroughputon-demand, many/day
Lead time for changesthroughput< 1 day (hours)
Change failure ratestability0–15%
Time to restore (MTTR)stability< 1 hour
  • Elite performers deploy more and fail less — small batches are safer, not riskier !
  • Improve all four with the same levers: small batches, automation, fast rollback, trunk-based dev, good tests.
  • Deployment markers annotate dashboards so a metric shift ties to a release. Error budget (1 − SLO) governs release pace.
  • MTTR = restore service (rollback / flag-kill), not fix the bug. Blameless postmortems target systemic cause.

How Code Reaches Prod

  • 1. Branch → PR → PR pipeline: build, unit/integration tests, lint, typecheck, SAST, image scan, preview env.
  • 2. Review + required checks pass → merge to main (merge queue re-tests vs updated main, keeps it green).
  • 3. Main pipeline builds the immutable artifact once (image @git-sha) → scan → sign → push to registry.
  • 4. Auto-deploy the artifact to staging → e2e + smoke tests (+ optional manual QA).
  • 5. Promote the same digest to prod — approval gate (Delivery) or automatic (Deployment).
  • 6. Deploy via rolling / blue-green / canary; post-deploy smoke + health probes.
  • 7. Observe error rate / latency vs baseline → auto/manual rollback if unhealthy.
  • GitOps variant: CI commits the new tag/digest to a config repo → ArgoCD/Flux reconciles it into the cluster.

★ Pipeline Review Checklist

Build & artifacts

  • ☐ Artifact built once, promoted by digest — not rebuilt per env.
  • ☐ Immutable/versioned tag (git-sha/semver), never deploy :latest.
  • ☐ Config/secrets injected per env at deploy; nothing sensitive baked in or logged.

CI hygiene

  • ☐ Fast tests gate merges; main protected + required checks + merge queue.
  • ☐ Pipeline-as-code, reviewed & versioned; cache keys include lockfile hash; build survives cold cache.

Security / supply chain

  • ☐ OIDC / short-lived creds — no long-lived cloud keys in secrets.
  • ☐ Fork PRs can't reach secrets (no unsafe pull_request_target); actions/images pinned by SHA/digest.
  • ☐ Least-privilege token/deploy identity; image scanned + signed; SBOM/provenance; deps scanned.

Deploy & recovery

  • ☐ Prod behind approval / protected environment; deploys serialised (concurrency).
  • ☐ Safe strategy (rolling/blue-green/canary) with a tested rollback; migrations expand/contract.
  • ☐ Post-deploy smoke + health probes; deploy observability + auto-rollback criteria; feature-flag kill-switch.
  • ☐ DORA tracked (freq, lead time, CFR, MTTR) & balanced; deploy markers on dashboards.
