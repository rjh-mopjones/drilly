  • "Dealing with many things" vs "doing many things." Concurrency without parallelism = an event loop; parallelism without concurrency = SIMD/GPU lanes.
  • Amdahl: speedup ≤ 1/(s + (1−s)/N). A 5% serial part caps you at 20× no matter how many cores.
  • Gustafson: bigger inputs shrink the serial fraction — scaling out often means scaling up the problem.

Thread Lifecycle & States

A thread = private stack + PC + registers, shared heap + globals + fds. Locals are thread-private (confinement); heap objects are where races live.

StateMeaning
NEWobject made, no OS thread yet
RUNNABLErunning or ready (incl. blocking IO!)
BLOCKEDwaiting for a monitor lock (involuntary)
WAITINGwait()/join()/park() — until signalled
TIMED_WAITINGsame, with a timeout
TERMINATEDrun() returned/threw — cannot restart
  • BLOCKED vs WAITING: BLOCKED = lock contention; WAITING = signal-driven. Reading a dump: all BLOCKED on each other = deadlock; WAITING with no notifier = lost wakeup.
  • join() gives completion + happens-before — you see all the joined thread's writes with no extra sync.
  • ! Java: call start(), not run() — run() executes inline, no new thread.
  • Daemon thread doesn't keep the process alive; killed abruptly at exit (no finally). ! A forgotten non-daemon pool thread hangs the JVM after main.

  • Why not 1M OS threads: 1M × 1MB ≈ 1TB RAM, plus the kernel scheduler thrashes. Goroutines/virtual threads use KB growable stacks + user-space scheduling → 1M is routine.
  • M:N (Go GMP, Java Loom): write straight-line blocking code; runtime turns a block into cheap parking. Best of 1:1 (parallel) + N:1 (cheap).
  • ! Green threads' fatal flaw: one blocking syscall freezes every task on that carrier. M:N fixes it by unmounting.

Context-Switch Cost

  • Direct: save/restore registers + (kernel switch) mode switch + TLB flush ≈ 1–10µs. Small — until millions/sec.
  • Indirect (the killer): cache pollution. Incoming thread's working set evicts the outgoing one's lines; both run cold afterwards. Dwarfs the direct cost and hides from "switch = X µs" numbers.
  • ! Oversubscription: more runnable threads than cores → more switching + cache thrash → CPU-bound work gets slower. Size CPU pools near core count.
  • User-space (goroutine/virtual) switches skip the kernel round-trip → far lighter. Blocking costs twice: switch out, later switch back, each with cache cost.

Thread Confinement & Thread-Local

  • Confinement: don't share the state at all → no sync needed. Each thread's own copy; the strongest, simplest escape from races.
  • ThreadLocal: per-thread copy behind a shared name. Right for non-thread-safe scratch objects (SimpleDateFormat, Random, buffers) and implicit context (request/trace IDs, MDC).
static final ThreadLocal<SimpleDateFormat> FMT =
  ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));
// FMT.get() — no lock, never shared
  • ! Pooled-thread leak: threads are reused, so a value set in one task lingers into the next on that thread → memory leak + cross-request contamination. Always remove() in finally.
  • ! Doesn't follow work across async/executor hops. Use scoped values (Java 21+) / context-propagation libs.

Race Condition vs Data Race

  • Data race: 2 threads touch same memory, ≥1 write, no ordering → undefined behavior (C/C++/Go). Fix: sync or atomics.
  • Race condition: wrong result from timing; can exist even with atomics (check-then-act, TOCTOU).
// count++ is 3 ops, NOT atomic:
T1: load 0        T2: load 0
T1: add  1        T2: add  1
T1: store 1       T2: store 1   // lost update: 1 not 2 !

! volatile / an atomic read does NOT make x++ safe — it's read-modify-write. Use an atomic add (fetch_add) or a lock. Data-race-free is necessary, not sufficient, for correctness.

  • Coarse lock = simple, low concurrency; fine lock = scalable, deadlock-prone. Start coarse, split under proven contention.
  • ! Never do IO, sleep, or call unknown/callback code while holding a lock → lock convoy, deadlock, huge tail latency.
  • Spinlock only when CS < a context switch; else you burn a core. Adaptive mutexes spin briefly then park.

Read-Write Locks

  • RWLock: many concurrent readers, exclusive writer. Wins only when reads dominate and critical sections are non-trivial — otherwise the bookkeeping costs more than a plain mutex.
  • ! Writer starvation: a steady stream of readers can block writers forever. Prefer a writer-preferring or fair implementation.
  • ! Don't upgrade read→write lock while holding the read lock — two readers both trying deadlock. Drop then re-acquire (and re-check state).
  • Alternatives for read-heavy state: RCU, seqlock, copy-on-write, or an immutable snapshot swapped by one atomic pointer.

Producer–Consumer Pattern

// bounded buffer, 2 condvars
put(x): lock; while(full) notFull.wait();
        buf.add(x); notEmpty.signal(); unlock
take(): lock; while(empty) notEmpty.wait();
        x=buf.remove(); notFull.signal(); unlock; ret x
  • The bounded buffer is the whole point: it gives backpressure. An unbounded queue just relocates OOM to the consumer's lag.
  • In practice reach for a BlockingQueue / buffered channel instead of hand-rolling condvars.
  • ! Signal after mutating state, still under the lock. Signalling the wrong condvar → permanent stall.

Latches, Barriers & Phasers

PrimitiveCoordinates
CountDownLatchone-shot: wait till count hits 0
CyclicBarrierreusable: N parties rendezvous

SemaphoreN permits (pool / rate limit)
  • Latch = "wait for others to be ready": start N workers after a gate opens, or main waits for N tasks to finish. One-shot — count only goes down, can't reset.
  • Barrier = "all threads meet here, then all proceed" — reusable across rounds (iterative/BSP algorithms). Optional barrier action runs once when the last party arrives.
  • ! Latch signal is sticky (a counter, remembered) unlike a bare condvar notify — no lost-wakeup risk. Semaphore release is likewise counted.
  • For one-time coordination or fan-in, prefer these + CompletableFuture.allOf over hand-rolled wait/notify.

Memory Model & Happens-Before

  • Compiler & CPU reorder aggressively. Without a happens-before edge, one thread may never observe another's write.
  • Java (JMM): volatile = visibility + ordering (not atomicity); synchronized unlock→lock; final fields = safe publication.
  • C++ memory_order: relaxed < acquire/release < seq_cst. Pair a release-store with an acquire-load to build the edge.
// Double-checked locking (Java, correct):
private volatile Singleton inst;  // volatile essential !
Singleton get(){
  if(inst==null) synchronized(this){
    if(inst==null) inst = new Singleton();
  }
  return inst;
}

! Drop volatile and readers can see a non-null, half-constructed object (fields reordered after the reference publish).

Atomics & Lock-Free

  • CAS(addr, expected, new): atomically swap iff unchanged → retry loop. The building block of all lock-free code.
  • Progress: wait-free (every thread bounded) > lock-free (some thread advances) > obstruction-free > blocking.
// CAS push (Treiber stack)
do { old = top; n.next = old; }
while(!CAS(&top, old, n));   // retry on contention

! ABA: value goes A→B→A, CAS wrongly succeeds. Fix: tagged/versioned pointer, hazard pointers, or epoch/RCU reclamation.

! Lock-free ≠ faster. Under low contention a mutex usually wins; lock-free shines at high contention and for progress guarantees (no thread can stall the rest).

  • fetch_add beats a CAS loop for a pure counter — it's one uncontended instruction with no retry, where CAS may spin under contention.
  • ! A CAS loop under high contention degrades: many threads read the same value, one wins, the rest retry → wasted work + cache-line ping-pong. Back off or shard the counter.
  • LL/SC (ARM/POWER) sidesteps ABA structurally: the store-conditional fails if the line was written at all, not just if the value differs.

C++ memory_order Quick Ref

OrderGuarantee
relaxedatomicity only, no ordering
acquire (load)later ops can't float above
release (store)earlier ops can't sink below
acq_rel (RMW)both, for read-modify-write
seq_cstsingle global order (default, costliest)
  • Pair a release-store with an acquire-load of the same var → happens-before edge; everything before the release is visible after the acquire.
  • Cost ladder: relaxed < acquire/release < seq_cst. The expensive part of seq_cst is the two-way StoreLoad fence.
  • relaxed is safe only when you need no ordering vs other data — e.g. a statistics counter (fetch_add(relaxed)) whose value isn't a flag guarding other memory.
  • ! A CAS that publishes data needs release (and acquire to read it) — a relaxed CAS can let readers see the pointer before the pointee's fields.
  • ! Don't rely on x86 being strongly-ordered — it hides missing barriers that ARM/POWER will expose. Code to the model, not the chip.

Read-Mostly: RCU · Seqlock · COW

  • When reads vastly outnumber writes, avoid making readers pay for locks at all.
  • RCU (read-copy-update): readers run lock-free on the current version; a writer builds a new copy, swaps one atomic pointer, then waits for a grace period (all pre-existing readers gone) before freeing the old. Readers never block. Backbone of the Linux kernel.
  • Seqlock: writer bumps a sequence counter odd→even around its write; reader reads seq, reads data, re-reads seq — retries if it changed or was odd. Great for a few small fields (timestamps), ! readers can spin under write bursts and must not follow torn pointers.
  • COW / immutable snapshot: swap a whole immutable structure by one atomic reference; readers hold a consistent snapshot with zero sync. O(n) writes.
  • All three trade cheap/lock-free reads for more expensive writes + a reclamation problem (when is the old version safe to free? → grace periods, hazard pointers, epochs).

Deadlock & Friends

Needs all 4 Coffman conditions: mutual exclusion · hold-and-wait · no preemption · circular wait. Break any one → no deadlock.

T1: lock A; lock B     // classic
T2: lock B; lock A     // → deadlock
// fix: GLOBAL lock ordering (always A before B)
  • Livelock: threads keep reacting, no progress (two people dodging in a hallway). Starvation: an unlucky thread never gets the resource.
  • Priority inversion: low-priority holder blocks high-priority waiter → priority inheritance (Mars Pathfinder). !
  • Avoid: global order, lock hierarchy, tryLock+timeout+backoff, or one coarse lock. Never hold two locks if you can hold one.
// Deadlock-free bank transfer: order by identity
void xfer(Acct a, Acct b, long amt){
  Acct lo = a.id < b.id ? a : b, hi = lo==a ? b : a;
  synchronized(lo){ synchronized(hi){        // canonical order
    a.debit(amt); b.credit(amt); }}}
// tie-break equal ids with a tiebreak lock

! "Just add a timeout to every lock" is a bad general fix — it converts deadlock into livelock/spurious failures and hides the design flaw. Fix the lock order. Timeouts are a last resort where a static order is impossible.

Thread Pools & Executors

WorkloadThreads ≈
CPU-bound#cores (+1)
IO-boundN · (1 + W/C)

Formula: threads = Ncores · U · (1 + W/C), where U=target utilization, W=wait time, C=compute time per task. IO-heavy (W≫C) → many threads; pure CPU → ~cores.

  • Pool amortizes thread create/destroy cost. Fork-join = work-stealing deques for recursive divide-and-conquer.
  • ! Unbounded queue hides overload → OOM. Bound the queue + set a rejection policy (caller-runs, drop, throttle).
  • ! Blocking on a dependent task in the same fixed pool → thread-starvation deadlock. Isolate pools; virtual threads (Loom) relax this.

Futures, Promises & Async Composition

  • Future = read handle for a not-yet value; Promise = the write side that completes it.
  • Compose, don't block: thenApply/thenCompose (Java), .then/await (JS), ?+join (Rust). Fan-out with allOf/Promise.all, race with anyOf.
CompletableFuture
  .supplyAsync(this::fetch, pool)
  .thenApply(this::parse)
  .exceptionally(e -> fallback);   // handle failure !
  • ! future.get() inside async code re-introduces blocking and can deadlock a small pool. Stay in the async chain end-to-end.
  • ! A swallowed exception in one stage can leave downstream futures hanging forever — always attach an error handler.

Structured Concurrency

Child tasks respect lexical scope: the scope doesn't return until every child completes or is cancelled — concurrency mapped onto the call stack.

try (var s = new StructuredTaskScope.ShutdownOnFailure()){
  var u = s.fork(() -> fetchUser(id));
  var o = s.fork(() -> fetchOrder(id));
  s.join(); s.throwIfFailed();       // one fails → cancels sibling
  return new Resp(u.get(), o.get());
}  // close guarantees both done or cancelled
  • Fixes raw-future sins: leaks (orphaned futures), no cancellation propagation, lost errors.
  • Same idea: Kotlin coroutine scopes, Swift task groups, Go errgroup. The direction all modern async is heading.
  • ! Orphaned/fire-and-forget future with no terminal handler swallows its exception — "some charges just don't happen", zero errors logged. Always attach exceptionally/whenComplete; lint no-floating-promises.

Async / Await & Event Loop

  • One thread, many tasks; await yields at IO points (cooperative scheduling). Ideal for IO-bound, high fan-out (C10k).
  • ! Never block the loop — a CPU-heavy loop or sync-IO call freezes all tasks. Offload to a worker pool / thread.

Concurrent Data Structures

  • ConcurrentHashMap: CAS on bins / lock striping — reads are mostly lock-free, writes contend only per-bucket.
  • CopyOnWrite list/set: read-heavy, rare writes (listener registries). Writes are O(n).
  • BlockingQueue: backbone of producer-consumer; bounded variant gives backpressure.
  • ! Thread-safe methods ≠ thread-safe sequences: if(!m.containsKey(k)) m.put(k,v) still races → use putIfAbsent / compute / merge.
  • Immutable / persistent structures sidestep the whole problem — no shared mutable state, no sync.

Channels · CSP

// Go: share memory BY communicating
ch := make(chan int, 8)   // buffered → backpressure
go func(){ for v := range ch { work(v) } }()
select {                  // multiplex + cancel
case v := <-ch:        use(v)
case <-ctx.Done():     return
}
close(ch)                 // owner closes; range ends
  • Unbuffered = synchronous handoff (rendezvous); buffered = queue of depth N with backpressure at the rim.
  • ! Send on a closed channel panics; only the sender/owner closes. Unbuffered send with no ready receiver → deadlock.
  • ! A goroutine blocked forever on a channel is a leak — always give it a ctx.Done() / timeout exit.

False Sharing & Cache Coherence

  • False sharing: two hot vars land on one 64-byte cache line → cores ping-pong line ownership even with no logical sharing. !
  • Fix: pad to a cache line / @Contended (Java) / #[repr(align(64))]; give each thread its own counter and sum at the end.
  • MESI coherence: every write invalidates other cores' copies — cost is the coherence traffic, not the instruction.
  • NUMA: remote-socket memory is far slower; pin threads and shard data per node.
  • Symptom: perfect scaling to 4 threads, then it flatlines or regresses — suspect a shared line.

Scaling, Contention & Debugging

  • Little's Law: L = λ · W (in-flight = arrival rate × latency) — size pools/queues, don't guess.
  • USL: throughput rises, then falls as contention + coherence cost dominate. More threads past the knee = slower.
  • Fixes: shard / thread-local aggregate, read-mostly (RCU/seqlock), lock-free, batch to amortize sync.

Tooling: go test -race / TSan (data races), -fsanitize=thread, jstack / thread dumps (deadlock), async-profiler & flame graphs (lock contention), stress + fault injection.

! Concurrency bugs are non-deterministic (Heisenbugs) — reproduce with stress, logging, and sanitizers, not by staring.

Distributed & Async at Scale

  • Optimistic (version/CAS, retry on conflict) vs pessimistic (lock upfront). OCC wins under low contention.
  • Idempotency + at-least-once delivery → dedup keys make retries safe.
  • Backpressure & load shedding beat unbounded buffering every time.
  • Rate limit: token bucket. ! Distributed locks need fencing tokens — a lease can expire mid-operation and two holders think they own it.
  • Sagas + compensation instead of distributed 2PC (which blocks on coordinator failure).

  • Fewer contenders on an end → cheaper algorithm. Know the producer/consumer cardinality before picking a queue.
  • Ring buffer: fixed circular array + head/tail indices. Basis of the LMAX Disruptor — pre-allocated slots, sequence numbers, mechanical-sympathy (cache-line padded) → millions of msgs/sec, no per-op allocation.

Cancellation, Timeouts & Shutdown

  • Cancellation is cooperative: you can't safely yank a thread. The target must poll a flag / interrupt and unwind. Forceful kill (Thread.stop) leaves locks held and invariants broken — deprecated for good reason.
  • Java interrupt: sets a flag; blocking calls throw InterruptedException. ! Never swallow it — restore with Thread.currentThread().interrupt() or propagate, else cancellation is lost.
  • Go: pass context.Context; select on ctx.Done(). Every goroutine needs a cancellation exit or it leaks.
  • Timeouts are essential, not optional: an un-timed future.get() / blocking call can hang forever on a stuck dependency, cascading into thread-pool exhaustion.
var v = fut.get(500, TimeUnit.MILLISECONDS); // bounded wait
// graceful pool stop: no lost in-flight work
pool.shutdown();                       // stop accepting
if(!pool.awaitTermination(30,SECONDS)) // drain
    pool.shutdownNow();                // then interrupt

Backpressure & Flow Control

  • Backpressure = a slow consumer telling a fast producer to slow down. The alternative — unbounded buffering — just relocates OOM to wherever the lag piles up.
  • Mechanisms: bounded queue/channel (producer blocks or is rejected when full), request-N (reactive streams pull), credit-based flow control, TCP windowing.
  • Load shedding: when you can't slow the source (external traffic), drop — reject early, sample, or degrade. Better a fast 503 than a slow collapse.
  • ! Unbounded queue = hidden overload: latency climbs (Little's Law: L=λW), memory climbs, then everything dies at once with no warning. Always bound + choose a rejection policy.
  • Rate limit at the edge: token bucket (bursty) / leaky bucket (smooth).

Interview Playbook: "Design a concurrent X"

  • 1. Name the shared mutable state and its invariant — every race lives there.
  • 2. Correctness before contention: start with one coarse lock; prove it right via an explicit T1/T2 interleaving. "Make it right, then make it scale."
  • 3. Identify compound ops (check-then-act, RMW) → atomic primitive or hold the lock across both steps.
  • 4. Publication + visibility: how does another thread see the write? volatile/final/lock — not just assignment.
  • 5. Bound & shed: queues/mailboxes bounded, rejection policy chosen, every task has a cancellation exit.
  • 6. Only then scale: profile, then shard / thread-local aggregate / RWLock / lock-free — and only where contention is proven.
  • ! Reach for battle-tested primitives (BlockingQueue, Semaphore, j.u.c) over hand-rolled wait/notify in production; hand-roll only to prove understanding in the interview.

★ Review & Spot-the-Bug Checklist

  • ☐ Find the shared mutable state — that's where every race lives.
  • ☐ Compound op (check-then-act / read-modify-write)? Make it atomic or lock it.
  • ☐ Publication safe? Visibility via volatile/final/sync — not just "I assigned it".
  • ☐ Multiple locks? Impose a global order; hold briefly; no IO or callbacks under lock.
  • ☐ wait() inside a while, not an if; signal after mutating; notifyAll if predicates differ.
  • ☐ Queues & mailboxes bounded with a rejection/shed policy?
  • ☐ Every goroutine/task has a cancellation exit (ctx.Done()/timeout)?
  • ☐ Slower with more threads? Contention / false sharing / GIL / IO-bound / pool too small.
  • ☐ Pick the primitive: counter→atomic; pool→semaphore; pipeline→queue/channel; read-heavy→RWLock/COW.
  • ☐ Reason out loud via an explicit T1/T2 interleaving before claiming it's correct.
