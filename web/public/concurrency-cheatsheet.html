Concurrency vs Parallelism

ConcurrencyParallelism

goalresponsiveness, IO overlapthroughput / wall-time
  • "Dealing with many things" vs "doing many things." Concurrency without parallelism = an event loop; parallelism without concurrency = SIMD/GPU lanes.
  • Amdahl: speedup ≤ 1/(s + (1−s)/N). A 5% serial part caps you at 20× no matter how many cores.
  • Gustafson: bigger inputs shrink the serial fraction — scaling out often means scaling up the problem.
  • ! Coordination overhead can make more threads slower. Always benchmark against the serial baseline.

Race Condition vs Data Race

  • Data race: 2 threads touch same memory, ≥1 write, no ordering → undefined behavior (C/C++/Go). Fix: sync or atomics.
  • Race condition: wrong result from timing; can exist even with atomics (check-then-act, TOCTOU).
// count++ is 3 ops, NOT atomic:
T1: load 0        T2: load 0
T1: add  1        T2: add  1
T1: store 1       T2: store 1   // lost update: 1 not 2 !

! volatile / an atomic read does NOT make x++ safe — it's read-modify-write. Use an atomic add (fetch_add) or a lock. Data-race-free is necessary, not sufficient, for correctness.

  • Coarse lock = simple, low concurrency; fine lock = scalable, deadlock-prone. Start coarse, split under proven contention.
  • ! Never do IO, sleep, or call unknown/callback code while holding a lock → lock convoy, deadlock, huge tail latency.
  • Spinlock only when CS < a context switch; else you burn a core. Adaptive mutexes spin briefly then park.

Read-Write Locks

  • RWLock: many concurrent readers, exclusive writer. Wins only when reads dominate and critical sections are non-trivial — otherwise the bookkeeping costs more than a plain mutex.
  • ! Writer starvation: a steady stream of readers can block writers forever. Prefer a writer-preferring or fair implementation.
  • ! Don't upgrade read→write lock while holding the read lock — two readers both trying deadlock. Drop then re-acquire (and re-check state).
  • Alternatives for read-heavy state: RCU, seqlock, copy-on-write, or an immutable snapshot swapped by one atomic pointer.

// ALWAYS re-check predicate in a while:
synchronized(q){
  while(q.isEmpty())   // not if — spurious wakeups !
      q.wait();
  x = q.remove();
}
q.notifyAll();         // wake waiting producers/consumers

! if(cond) wait() is a bug. Use notifyAll (not notify) when several distinct predicates share one monitor, else a wakeup can be "lost" to the wrong waiter.

Producer–Consumer Pattern

// bounded buffer, 2 condvars
put(x): lock; while(full) notFull.wait();
        buf.add(x); notEmpty.signal(); unlock
take(): lock; while(empty) notEmpty.wait();
        x=buf.remove(); notFull.signal(); unlock; ret x
  • The bounded buffer is the whole point: it gives backpressure. An unbounded queue just relocates OOM to the consumer's lag.
  • In practice reach for a BlockingQueue / buffered channel instead of hand-rolling condvars.
  • ! Signal after mutating state, still under the lock. Signalling the wrong condvar → permanent stall.

Memory Model & Happens-Before

  • Compiler & CPU reorder aggressively. Without a happens-before edge, one thread may never observe another's write.
  • Java (JMM): volatile = visibility + ordering (not atomicity); synchronized unlock→lock; final fields = safe publication.
  • C++ memory_order: relaxed < acquire/release < seq_cst. Pair a release-store with an acquire-load to build the edge.
// Double-checked locking (Java, correct):
private volatile Singleton inst;  // volatile essential !
Singleton get(){
  if(inst==null) synchronized(this){
    if(inst==null) inst = new Singleton();
  }
  return inst;
}

! Drop volatile and readers can see a non-null, half-constructed object (fields reordered after the reference publish).

Atomics & Lock-Free

  • CAS(addr, expected, new): atomically swap iff unchanged → retry loop. The building block of all lock-free code.
  • Progress: wait-free (every thread bounded) > lock-free (some thread advances) > obstruction-free > blocking.
// CAS push (Treiber stack)
do { old = top; n.next = old; }
while(!CAS(&top, old, n));   // retry on contention

! ABA: value goes A→B→A, CAS wrongly succeeds. Fix: tagged/versioned pointer, hazard pointers, or epoch/RCU reclamation.

! Lock-free ≠ faster. Under low contention a mutex usually wins; lock-free shines at high contention and for progress guarantees (no thread can stall the rest).

Deadlock & Friends

Needs all 4 Coffman conditions: mutual exclusion · hold-and-wait · no preemption · circular wait. Break any one → no deadlock.

T1: lock A; lock B     // classic
T2: lock B; lock A     // → deadlock
// fix: GLOBAL lock ordering (always A before B)
  • Livelock: threads keep reacting, no progress (two people dodging in a hallway). Starvation: an unlucky thread never gets the resource.
  • Priority inversion: low-priority holder blocks high-priority waiter → priority inheritance (Mars Pathfinder). !
  • Avoid: global order, lock hierarchy, tryLock+timeout+backoff, or one coarse lock. Never hold two locks if you can hold one.

Thread Pools & Executors

WorkloadThreads ≈
CPU-bound#cores (+1)
IO-boundN · (1 + W/C)

Formula: threads = Ncores · U · (1 + W/C), where U=target utilization, W=wait time, C=compute time per task. IO-heavy (W≫C) → many threads; pure CPU → ~cores.

  • Pool amortizes thread create/destroy cost. Fork-join = work-stealing deques for recursive divide-and-conquer.
  • ! Unbounded queue hides overload → OOM. Bound the queue + set a rejection policy (caller-runs, drop, throttle).
  • ! Blocking on a dependent task in the same fixed pool → thread-starvation deadlock. Isolate pools; virtual threads (Loom) relax this.

Futures, Promises & Async Composition

  • Future = read handle for a not-yet value; Promise = the write side that completes it.
  • Compose, don't block: thenApply/thenCompose (Java), .then/await (JS), ?+join (Rust). Fan-out with allOf/Promise.all, race with anyOf.
CompletableFuture
  .supplyAsync(this::fetch, pool)
  .thenApply(this::parse)
  .exceptionally(e -> fallback);   // handle failure !
  • ! future.get() inside async code re-introduces blocking and can deadlock a small pool. Stay in the async chain end-to-end.
  • ! A swallowed exception in one stage can leave downstream futures hanging forever — always attach an error handler.

Async / Await & Event Loop

flowchart LR Q["task queue"] --> L{"event loop
(1 thread)"} L -->|run to await| L L -->|await IO| IO["OS async IO"] IO -->|ready| Q
  • One thread, many tasks; await yields at IO points (cooperative scheduling). Ideal for IO-bound, high fan-out (C10k).
  • ! Never block the loop — a CPU-heavy loop or sync-IO call freezes all tasks. Offload to a worker pool / thread.
  • Coroutines: stackless (async/await state machine, e.g. JS/Python/Rust) vs stackful (goroutines). JS drains microtasks (promises) fully before the next macrotask.

Concurrent Data Structures

  • ConcurrentHashMap: CAS on bins / lock striping — reads are mostly lock-free, writes contend only per-bucket.
  • CopyOnWrite list/set: read-heavy, rare writes (listener registries). Writes are O(n).
  • BlockingQueue: backbone of producer-consumer; bounded variant gives backpressure.
  • ! Thread-safe methods ≠ thread-safe sequences: if(!m.containsKey(k)) m.put(k,v) still races → use putIfAbsent / compute / merge.
  • Immutable / persistent structures sidestep the whole problem — no shared mutable state, no sync.

Channels · CSP

// Go: share memory BY communicating
ch := make(chan int, 8)   // buffered → backpressure
go func(){ for v := range ch { work(v) } }()
select {                  // multiplex + cancel
case v := <-ch:        use(v)
case <-ctx.Done():     return
}
close(ch)                 // owner closes; range ends
  • Unbuffered = synchronous handoff (rendezvous); buffered = queue of depth N with backpressure at the rim.
  • ! Send on a closed channel panics; only the sender/owner closes. Unbuffered send with no ready receiver → deadlock.
  • ! A goroutine blocked forever on a channel is a leak — always give it a ctx.Done() / timeout exit.

  • Actor = private state + mailbox; processes one message at a time → no locks inside an actor. State is reached only by messages.
  • Supervision trees restart failed actors (Erlang/Akka). Failures are isolated, not propagated by exception.
  • ! Unbounded mailboxes hide overload; a slow actor becomes a memory sink. Bound + shed. Message ordering only holds per sender→receiver pair.

False Sharing & Cache Coherence

  • False sharing: two hot vars land on one 64-byte cache line → cores ping-pong line ownership even with no logical sharing. !
  • Fix: pad to a cache line / @Contended (Java) / #[repr(align(64))]; give each thread its own counter and sum at the end.
  • MESI coherence: every write invalidates other cores' copies — cost is the coherence traffic, not the instruction.
  • NUMA: remote-socket memory is far slower; pin threads and shard data per node.
  • Symptom: perfect scaling to 4 threads, then it flatlines or regresses — suspect a shared line.

Scaling, Contention & Debugging

  • Little's Law: L = λ · W (in-flight = arrival rate × latency) — size pools/queues, don't guess.
  • USL: throughput rises, then falls as contention + coherence cost dominate. More threads past the knee = slower.
  • Fixes: shard / thread-local aggregate, read-mostly (RCU/seqlock), lock-free, batch to amortize sync.

Tooling: go test -race / TSan (data races), -fsanitize=thread, jstack / thread dumps (deadlock), async-profiler & flame graphs (lock contention), stress + fault injection.

! Concurrency bugs are non-deterministic (Heisenbugs) — reproduce with stress, logging, and sanitizers, not by staring.

Distributed & Async at Scale

  • Optimistic (version/CAS, retry on conflict) vs pessimistic (lock upfront). OCC wins under low contention.
  • Idempotency + at-least-once delivery → dedup keys make retries safe.
  • Backpressure & load shedding beat unbounded buffering every time.
  • Rate limit: token bucket. ! Distributed locks need fencing tokens — a lease can expire mid-operation and two holders think they own it.
  • Sagas + compensation instead of distributed 2PC (which blocks on coordinator failure).

★ Review & Spot-the-Bug Checklist

  • ☐ Find the shared mutable state — that's where every race lives.
  • ☐ Compound op (check-then-act / read-modify-write)? Make it atomic or lock it.
  • ☐ Publication safe? Visibility via volatile/final/sync — not just "I assigned it".
  • ☐ Multiple locks? Impose a global order; hold briefly; no IO or callbacks under lock.
  • ☐ wait() inside a while, not an if; signal after mutating; notifyAll if predicates differ.
  • ☐ Queues & mailboxes bounded with a rejection/shed policy?
  • ☐ Every goroutine/task has a cancellation exit (ctx.Done()/timeout)?
  • ☐ Slower with more threads? Contention / false sharing / GIL / IO-bound / pool too small.
  • ☐ Pick the primitive: counter→atomic; pool→semaphore; pipeline→queue/channel; read-heavy→RWLock/COW.
  • ☐ Reason out loud via an explicit T1/T2 interleaving before claiming it's correct.
