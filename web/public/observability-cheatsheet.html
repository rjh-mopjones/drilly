How to read & print

The Three Pillars

PillarAnswersCost
MetricsIs something wrong? (aggregated, numeric)cheap, bounded
LogsWhat happened? (discrete events)expensive, high-volume
TracesWhere / why? (request across services)medium, sampled
  • Observability ≠ monitoring. Monitoring = known dashboards/alerts for known failures; observability = ability to ask new questions of your system without shipping new code.
  • High cardinality + high dimensionality is what lets you slice by unknown-unknowns. Metrics can't hold it ! — that's what traces/wide-events are for.
  • Correlate the pillars: trace_id in logs, exemplars link a histogram bucket → a trace.
  • Rule of thumb on which pillar to reach for: metrics answer "is it broken and how badly", traces answer "which hop is slow", logs answer "what exactly did that one request do". Start cheap (metrics) and drill down only as needed !

Which signals?

  • RED (request-driven services): Rate · Errors · Duration.
  • USE (resources): Utilisation · Saturation · Errors.
  • Four Golden Signals (SRE book): latency, traffic, errors, saturation.
  • Prefer histogram over summary so you can aggregate and re-derive any quantile. _bucket is cumulative (le).

PromQL Quick-ref

# per-second error rate over 5m
rate(http_requests_total{code=~"5.."}[5m])

# error ratio (aggregate, then divide)
sum(rate(http_requests_total{code=~"5.."}[5m]))
  / sum(rate(http_requests_total[5m]))

# p99 latency from a histogram
histogram_quantile(0.99,
  sum by (le) (rate(http_latency_bucket[5m])))
  • rate = avg per-sec over range (smoothed, use for alerts); irate = last 2 samples (spiky, graphs only) !
  • Range vector [5m] only on counters/gauges before rate/increase; instant vector for math.
  • sum by(le) before histogram_quantile, never after !
  • Recording rules pre-compute expensive queries; alerting rules fire on expressions for a duration.
  • Make the rate window ≥ 4× scrape interval so a missed scrape doesn't produce "no data" ! (a [1m] window on a 30s scrape has ~2 samples).
  • rate is reset-aware (counter restart → adds pre-reset value, no negative spike) and extrapolates to window edges — so it can return non-integer values for integer counters.
  • Don't rate() a gauge — use deriv()/delta(). And never compare a raw counter total (x_total > 100) — it only grows since process start !

Regex & matchers

  • Matchers: = != =~ (regex) !~. Regex is fully anchored — =~"api" matches only api, use =~".*api.*" for substring !
  • {label=""} matches series missing the label or with it empty. Match the name via {__name__=~"node_.*"}.
  • "No data" debug: strip to bare metric → add matchers one at a time → check regex anchoring → check vector-match label sets → check type (range vector needs a range fn). Bisect.

Prometheus Architecture

  • Pull model: Prometheus scrapes /metrics targets found via service discovery (k8s, Consul, files).
  • Local TSDB (2h blocks → compacted); not clustered/HA for long-term by itself.
  • Pushgateway only for short-lived batch jobs — not for services ! (breaks up/down semantics, becomes a stale sink).
  • up==0 is your scrape-health signal; staleness markers handle disappeared series.
  • Alerts evaluated locally → pushed to Alertmanager (dedupe/route/notify).
  • Scrape config: scrape_interval (15–60s typical) sets resolution and load; relabel_configs rewrite/drop targets pre-scrape, metric_relabel_configs drop series post-scrape (cardinality control) !
  • A missing target just stops producing samples — alert on up == 0 and on absent() for metrics that must always exist, or a dead exporter fails silently !

SLI / SLO / Error Budget

  • SLI = a measured ratio, e.g. good/total requests. SLO = target over a window (99.9% / 30d). SLA = contract + penalty.
  • Error budget = 1 − SLO. 99.9% over 30d ≈ 43m 12s of allowed badness.
SLODowntime / 30d
99%7h 18m
99.9%43m
99.95%21m
99.99%4m 20s
  • Budget spent → freeze feature launches, prioritise reliability. Budget healthy → ship faster. It aligns dev vs ops incentives.
  • Pick user-centric SLIs (did the request succeed fast?) not machine metrics (CPU) !
  • SLI = ratio of good / valid events — define "valid" carefully (usually exclude client-fault 4xx from availability; only count what you own).
  • Latency SLI is a threshold ratio ("% of requests ≤ 800ms"), not a percentile target — it composes cleanly into a burn-rate budget.
  • Window matters: a 99.9%/30d SLO judged over a rolling 28-day window is standard; shorter windows are noisier, longer ones forgive incidents too readily.

Alerting & Burn Rate

  • Alert on symptoms (SLO burn), not causes. Page on "users see errors", not "CPU 90%".
  • Burn rate = how fast you're spending budget. 1× = exactly on budget for the window; 14.4× burns 30d budget in ~2 days.
BurnWindowSev
14.4×1h & 5mpage
6×6h & 30mpage

  • Multi-window multi-burn-rate: long window = precision, short window = fast reset (stops firing when fixed) !
  • Every page must be actionable + urgent. Symptom-based, few, documented. Kill noisy alerts — fatigue is an outage in waiting.

Alertmanager

  • Routing tree: match labels → receiver (PagerDuty/Slack/email). continue: true to hit multiple.
  • Grouping: collapse related alerts into one notification (group_by, group_wait, group_interval).
  • Inhibition: a firing "cluster down" suppresses the 100 downstream "pod down" alerts !
  • Silences: time-boxed mutes during maintenance. Repeat interval re-notifies unacked.
  • Alertmanager itself should be HA (gossip-clustered) — dedupes across replicas.

Logging & Aggregation

  • Structured logs (JSON k/v), not printf strings — queryable, machine-parseable. Include trace_id, service, level.
  • Levels: ERROR (actionable) · WARN · INFO (business events) · DEBUG (off in prod). Log at boundaries, not every line.
  • Sampling high-volume logs; keep 100% of errors. Cardinality/PII hygiene at ingest !
  • Pipeline: app → agent (Fluent Bit/Vector) → buffer (Kafka) → store (Loki/Elasticsearch/ClickHouse) → query (Grafana/Kibana).
  • Loki indexes labels only (cheap); ELK indexes full text (rich, costly). Never index high-cardinality fields as labels !
  • Retention tiers: hot (searchable, days) vs cold/archive (object store, cheap). Sample noisy INFO, keep 100% ERROR.
  • Deriving metrics from logs (LogQL rate) works when you lack a real metric but is slower/costlier than a counter — reach for it as a stopgap, not a design !
  • Redact PII at ingest (in the agent/Collector), not after storage — once it's in the index it's a compliance problem.

Distributed Tracing

  • A trace = tree of spans; each span has trace_id, span_id, parent_id, start/dur, attributes.
  • Context propagation across services via headers (W3C traceparent) — the one thing that must be threaded everywhere ! (broken propagation = orphan traces).
  • Sampling: head (decide at start, cheap, may miss rare errors) vs tail (decide after seeing whole trace, keeps all errors, needs a collector buffer).
  • Use traces to find the slow span in a p99 request and see cross-service causality; pair with logs via trace_id.
  • Propagation formats must agree on both ends: W3C traceparent (standardise on this) vs B3 (Zipkin) vs proprietary. A mismatch = disconnected traces !
  • Async hops (SQS/Kafka/EventBridge) don't carry HTTP headers — inject trace context into the message, extract on the consumer, or producer→consumer linkage breaks.
  • Keep the sampling decision consistent across a trace (it must propagate) — otherwise you keep some spans and drop others → incomplete traces.
  • Clock skew across hosts makes waterfalls look wrong (negative/overlapping spans) even when propagation is fine — check NTP.

OpenTelemetry (OTel)

  • Vendor-neutral standard: signals = traces + metrics + logs + profiles. API + SDK + wire protocol (OTLP).
  • Auto-instrumentation for common libs; manual spans for business logic.
  • Collector = receive → process (batch, filter, redact, tail-sample) → export to any backend. Run as agent (per-node) + gateway (central).
  • Decouples app from vendor: swap backends without re-instrumenting ! Prefer OTel over proprietary SDKs for portability.

Metrics at Scale & Cost

  • Single Prometheus doesn't scale infinitely: shard by service, then federate. Long-term/HA via Thanos / Cortex / Mimir (object-store blocks + global query).
  • Cardinality is the #1 cost/OOM driver: series = ∏(label value counts). Never put user_id/request_id/email in a label !
  • Control cost: drop unused metrics at scrape (metric_relabel_configs), downsample old data, tune retention per tier.
  • A single runaway label (unbounded values) can 10× your TSDB overnight — cardinality-limit + alert on series growth.

Kubernetes & Cloud-Native

  • kube-state-metrics = object state (deployments, replicas, pod phase); cAdvisor/kubelet = container resource usage; node-exporter = node.
  • Discovery via Prometheus Operator ServiceMonitor / PodMonitor CRDs.
  • Watch: pod restarts/CrashLoopBackOff, OOMKilled, throttling (container_cpu_cfs_throttled), pending pods, PVC saturation.
  • Resource requests/limits drive scheduling + QoS; alert on saturation (near limits) not just utilisation !
  • CFS throttling (container_cpu_cfs_throttled_periods_total) bites even below 100% average CPU — a container hitting its limit in bursts is throttled and slow while looking "fine" on a mean gauge !
  • OOMKilled (exit 137) = memory limit hit; CrashLoopBackOff = repeated restart. Alert on restart rate, not just current phase.
  • Pod names/IDs are high-churn labels — don't aggregate by(pod) in recording rules; the index bloats even when few pods are live.

Dashboards, RUM & Profiling

Grafana dashboards

  • One RED dashboard per service; template variables for env/instance; link panels to traces via exemplars.
  • Show rate/error/latency + SLO burn on the top row; avoid vanity panels.

Frontend / Synthetic

  • RUM = real users (Core Web Vitals: LCP≤2.5s, INP≤200ms, CLS≤0.1, p75 field). Synthetic = scripted probes catch outages before users.

Continuous profiling

  • Always-on CPU/heap flamegraphs (pprof/Pyroscope/Parca) — the 4th pillar for "why is this span slow inside the process".

Incident Response & On-Call

  • Roles: IC (coordinates, doesn't fix), comms lead, ops lead. Declare severity early.
  • MTTD (detect) · MTTA (ack) · MTTR (resolve) — observability shrinks MTTD/MTTR.
  • Mitigate first (rollback/feature-flag/scale), diagnose later. Rollback beats root-cause under fire.
  • Blameless postmortems: timeline, contributing factors, action items with owners. Culture > individuals.
  • Sustainable on-call: sane rotations, actionable pages only, runbooks linked from every alert.
  • Track alert quality: page → real-incident ratio, false-positive rate, and toil per rotation. A page that never needs action should be deleted or downgraded to a ticket !
  • Escalation policy: ack timeout → escalate to secondary → manager. Every sev has a defined comms cadence and a customer-facing status page for the big ones.

TSDB Internals & Retention

  • A time series = unique metric name + label set, storing (timestamp, float) samples. Series identity is the label set — change one label value and it's a brand-new series !
  • Prometheus TSDB: recent samples in an in-memory head block backed by a WAL (crash recovery); every 2h flushed to an immutable on-disk block; background compaction merges blocks.
  • Samples are delta-of-delta + XOR compressed → ~1–2 bytes/sample on average. Cheap to store, expensive to index (the label inverted index is the memory hog).
  • Retention by time (--storage.tsdb.retention.time) or size. For long-term, remote-write to Thanos/Mimir and downsample (5m/1h rollups) old data.
  • Churn (series that appear/disappear constantly — e.g. pod names in labels) bloats the index even if few are active !

Instrumentation & Exporters

  • Client libraries (prometheus-client, OTel SDK) expose /metrics; Prometheus scrapes it. Name metrics <namespace>_<unit>_total (e.g. http_requests_total).
  • Exporters translate third-party systems into metrics: node_exporter (host), blackbox (probe), postgres/redis/kafka exporters.
  • Base units + suffixes: seconds not ms, bytes not MB, _total for counters (Prometheus convention) !
  • Labels describe dimensions (method, route, code) — keep the set small and bounded; a label is a new time series per value.
  • Push (StatsD/OTLP) vs pull (Prometheus): pull gives target-health for free (up); push suits short-lived/serverless.

Correlate the Pillars

  • The power move: jump metric → trace → log for one request. Requires a shared trace_id everywhere.
  • Exemplars: attach a trace_id to a histogram sample so "click the p99 spike → open the exact slow trace".
  • Wide/structured events (one fat event per request with dozens of dimensions) let you slice by high-cardinality fields metrics can't hold — the "observability 2.0" idea.
  • APM tools stitch this automatically; DIY = propagate context + log trace_id + emit exemplars.
  • Debugging loop: alert (metric) → find affected requests (trace) → read the error detail (log) → confirm fix (metric). ! A gap in any pillar breaks the chain.

Querying Logs (LogQL-style)

# Loki: stream selector + filter + metric
{app="api",level="error"} |= "timeout"
  | json | latency_ms > 500

# rate of 5xx from logs over 5m
sum(rate({app="api"} |= "status=5" [5m]))
  • Select by labels first (indexed), then filter the line (|= contains, |~ regex), then parse (json/logfmt).
  • Derive metrics from logs when you lack a metric — but it's slower/costlier than a real counter !
  • Retention tiers: hot (searchable days) vs cold/archive (cheap object store). Sample noisy INFO, keep all ERROR.

PromQL Advanced Patterns

# join per-pod metric to version metadata
rate(http_requests_total[5m])
  * on(pod) group_left(version) kube_pod_info

# hour-over-hour comparison
rate(x[5m]) / rate(x[5m] offset 1h)

# max 5m-rate seen over last hour (subquery)
max_over_time( rate(x[5m])[1h:1m] )

# capacity: disk full within 4h?
predict_linear(node_fs_avail_bytes[6h], 4*3600) < 0
  • Vector matching: pairs by full label set (1:1). on()/ignoring() pick join keys; group_left/group_right mark the "many" side for many-to-one (the info-metric join above).
  • Both sides of a ratio need matching grouping — add by(job) to one, add it to the other or you get "no data" !
  • Subqueries expr[range:res] are expensive (inner query runs per step) — promote hot ones to recording rules.
  • Recording-rule naming: level:metric:operations e.g. job:http_errors:rate5m. Prevents re-aggregating an aggregate (double-count).
  • predict_linear is a linear fit — great for slow-trending gauges (disk/mem/cert runway), bad for bursty/sawtooth signals.

Histograms Deep Dive

  • _bucket{le} is cumulative (count ≤ boundary). Accuracy is bounded by your bucket layout — histogram_quantile interpolates linearly within a bucket, so coarse buckets (1s→10s) give a wild p99 !
  • p99 landing in the +Inf bucket → you get the last finite boundary back = buckets too small; add higher boundaries.
  • Never avg(p99) across instances — percentiles aren't linearly combinable. Aggregate buckets (sum by(le)), then quantile once.
# WRONG: averages per-instance quantiles
avg(histogram_quantile(0.99, rate(d_bucket[5m])))
# RIGHT: merge distribution first
histogram_quantile(0.99,
  sum by(le)(rate(d_bucket[5m])))
  • Native/exponential histograms (newer Prometheus/OTel): auto-scaling buckets, far cheaper than one series per le — the fix for classic histogram cardinality.
  • Ship latency as a histogram not a summary if you ever need fleet-wide or per-route percentiles — summaries can't merge.

Alerting Rules & for:

- alert: HighErrorRate
  expr: |
    sum by(job)(rate(http_requests_total{code=~"5.."}[5m]))
    / sum by(job)(rate(http_requests_total[5m])) > 0.05
  for: 10m
  labels: { severity: page }
  annotations:
    summary: "{{ $labels.job }} 5xx > 5% for 10m"
  • Expression returns a non-empty vector → each series is an alert instance. pending → firing only after for: holds continuously.
  • for: is your anti-flapping guard: too short = 3am noise, too long = slow detection. Multi-burn-rate formalises this (short window fast-burn, long window slow-burn).
  • Back SLI ratios with recording rules so alert and dashboard use the same cheap, consistent series.

Dead-man's Switch & Coverage Gaps

  • A threshold alert on a series that disappeared never fires — no data, no evaluation. "Green because the exporter was dead" !
  • absent(up{job="api"}) fires when the target's gone; absent_over_time(...[10m]) is stricter (needs the whole window missing, ignores one missed scrape).
  • Dead-man's switch = an always-firing alert routed to a watchdog that pages if it ever stops arriving — catches Prometheus itself being down (which local absent() can't).

"No alert fired" — why?

  1. No alert exists for this failure mode (most common)
  2. Threshold/for: too lax
  3. The signal itself died (stale/absent)
  4. Alert fired, delivery failed (silence left on, routing broken)
  5. Wrong SLI — stayed green while users hurt

Fix the gap, but prefer symptom/SLO alerts (cover a class of failures) + absence alerts + periodic end-to-end alert-path tests.

Design: Reference Architectures

Work outside-in: user experience → SLIs/SLOs → symptom alerts → instrumentation that produces them. Name tools, justify each.

PillarOSS "LGTM" pick
MetricsPrometheus → Mimir/Thanos (object store, multi-tenant)
LogsLoki (label-indexed, cheap)
TracesTempo (object store, no span index)
CollectOTel Collector agent+gateway
View/alertGrafana + Alertmanager
  • Everything on object storage (sub-linear cost), OTLP vendor-neutral, Collector gateway is the single sampling/cardinality choke point.
  • Legacy monolith: black-box first (synthetic probe + LB RED, zero code) → structured logs + request ID → white-box golden signals on hot paths → auto-instrument tracing → 1-2 SLOs.
  • Serverless: push not scrape (OTLP / CloudWatch EMF), duration + cold-starts + throttles are first-class, Lambda OTel extension ships without blocking, context propagation across async hops is the hard part !
  • Multi-region: collect+alert locally (survives partition, no global SPOF) → remote_write to Thanos/Mimir → one global Grafana. region is a bounded label; mind egress.
  • Managed vs self-host = engineering-time vs billing-exposure. Managed meters punish cardinality/per-host/per-GB; self-host wins past the crossover if you have cardinality discipline.

Debug Funnel: symptom → cause

Metrics locate (what/where) → traces isolate (which hop) → logs explain (why). Never random-walk dashboards.

  1. Confirm scope + user impact: SLO burning? one service/endpoint or all? p99-only (tail) vs p50-too (everything)?
  2. Correlate with events — what changed? deploy marker, cron/batch, autoscale, traffic. Check USE (CPU/mem/pool).
  3. Exemplar → slow trace: waterfall shows the slow hop (DB, downstream, external, lock/queue).
  4. Pivot trace_id → logs of that span: the actual error/slow query/timeout.
  5. Confirm with resource metric, mitigate, add alert if none fired.
# which route spiked?
histogram_quantile(0.99,
  sum by(le,route)(rate(http_req_dur_bucket[5m])))
# post-deploy: compare error ratio by version
sum by(version)(rate(http_requests_total{status=~"5.."}[5m]))
/ sum by(version)(rate(http_requests_total[5m]))
  • Deploy-correlated error spike: mitigate first — roll back now, investigate after. Error tracker (Sentry) release-tags the new exception fastest.
  • 2am + tail-only latency screams scheduled job / backup / batch contention or cold cache / pool exhaustion / GC.

Sampling & Alert Fatigue

Trace sampling

  • Head: decide at trace start — cheap, but statistically drops rare slow/error traces (the ones you want) !
  • Tail: decide after the whole trace is seen — keeps all errors/slow, needs a Collector buffer holding spans until decision.
  • Watch otelcol_exporter_send_failed_spans + receiver/queue metrics for dropped spans (backpressure, export failure, batch timeout).

Fixing alert fatigue

  • North star: every page urgent + actionable + needs a human. Measure first — noisy top offenders cause most pain.
  • Convert cause-alerts → symptom-alerts (page on SLO burn, not CPU 80%). Downgrade the rest to ticket/dashboard.
  • Add for:, grouping/inhibition (one incident = one page), and a runbook per alert. An alert that fired and needed no action gets tuned/deleted in the postmortem.
  • Signal-to-noise is safety — alert quantity is not.

  • MTTD is an alerting/coverage problem; MTTR is a correlation/runbook/rollback problem.

Incident Walkthrough: page → postmortem

  1. Detect (MTTD): multi-burn-rate SLO alert pages — fired on the symptom (users failing checkout), not a cause. On-call acks; alert links dashboard + runbook.
  2. Triage: dashboard shows SLO burning, RED spiking on POST /checkout for one version, correlated with a deploy marker 10m ago.
  3. Mitigate first: roll back the release now — MTTR beats root-causing live. Budget stops burning.
  4. Diagnose (funnel): exemplar → failing trace → span erroring on payments call → pivot trace_id → logs show a NullPointer from a bad migration. Error tracker confirms, tagged v2.4.0.
  5. Root cause: schema change incompatible with in-flight requests — trace + logs + release tag agree.
  6. Fix forward + verify: corrected migration, watch SLO recover, traces clean.
  7. Blameless postmortem: detect fast enough? catch pre-prod? anything invisible? Action items: canary + auto-rollback on SLO burn, migration-compat test, runbook tweak — feed learnings back so next MTTD/MTTR are lower.

Detect on symptom → triage on RED → mitigate by rollback → diagnose exemplar→trace→logs → fix → postmortem that hardens the observability itself.

Cardinality Hunt (OOM / Bill)

Prometheus memory tracks active series; the managed bill tracks custom metrics per tag combo — same disease, same hunt.

# 1. is it cardinality, and growing?
prometheus_tsdb_head_series          # high + climbing = smoking gun

# 2. which metric owns the series?
topk(10, count by(__name__)({__name__=~".+"}))

# 3. confirm the unbounded label
count(count by(user_id)(suspect_metric))
  • Culprit is almost always an unbounded label: user_id, request_id, session_id, an error-message string, or a raw URL with IDs baked in !
  • Fix at source: stop emitting it — normalise path to a route template, move the identifier to a trace/log where high cardinality belongs.
  • Fast mitigate at scrape: metric_relabel_configs labeldrop/drop; set sample_limit/label_limit so a bad target is rejected, not OOMing you.
  • Guardrail so it can't recur: per-target sample_limit, per-tenant max_global_series_per_user quota (Mimir), + alert on prometheus_tsdb_head_series growth.
  • A single runaway label can 10× your TSDB overnight — series count = ∏(label value counts).

RED · USE · Golden Signals

MethodApplies toSignals
REDrequest-driven servicesRate · Errors · Duration
USEresources (host/queue/pool)Utilisation · Saturation · Errors
Goldenany user-facing system (SRE book)Latency · Traffic · Errors · Saturation
  • They overlap by design: RED is the request cut, USE the resource cut; a service dashboard usually shows RED on top, USE below (the "why").
  • A request-duration histogram gives you all of RED at once: latency via histogram_quantile, traffic via _count rate, errors via a status-class counter alongside.
  • Saturation is the early-warning signal — alert on near-limit (pool almost exhausted, queue filling) not just utilisation, because saturation predicts the cliff !
  • Split latency percentiles from success and failure — a fast 500 can flatter your p99 while users fail.

Metrics at Scale — Deep

  • Single Prometheus isn't clustered/HA for long-term. Scale path: shard by service → federate → move to Thanos / Cortex / Mimir (object-store blocks + global query + multi-tenant quotas).
  • Thanos: sidecar per Prometheus uploads blocks to object storage; Querier fans out + dedupes HA pairs; Compactor downsamples (5m/1h rollups) old data.
  • Remote-write ships samples to a central store (Mimir) — decouples ingest from a single node and gives global query.
  • Cost levers: drop unused metrics at scrape, downsample old data, tiered retention per resolution, recording rules for what you actually query then shorten raw retention.
  • Pull vs push: pull gives target-health for free (up); push (StatsD/OTLP) suits short-lived/serverless. Pushgateway only for batch jobs — never services (stale sink, breaks up/down) !

On-Call Dashboard Layout

Ordered like the debug funnel — is the user hurt → where → why → what changed. A triage tool, not a data dump.

  • Top — "should I care": SLO status + error-budget burn, RED summary (rate, error ratio, p50/p95/p99).
  • Middle — "where": RED split by route and by version/instance + top errors by type — localises to an endpoint or bad deploy instantly.
  • Below — "why": USE for dependencies — CPU/mem, connection-pool saturation, queue depth, GC, downstream latency/errors.
  • Context: deploy markers overlaid, exemplar links to traces, links to logs + runbooks.
  • Percentiles not averages, rates not raw counts, a handful of high-signal panels — the 3am on-call shouldn't hunt !

★ Design / Review Checklist

Signals & SLOs

  • ☐ Every service emits RED (or USE for resources); histograms not summaries for latency.
  • ☐ SLOs are user-centric with an explicit window + error budget; alerts fire on burn rate, not raw CPU.

Cardinality & cost

  • ☐ No unbounded labels (user_id/request_id/email) on metrics !; high-cardinality lives in traces/logs.
  • ☐ Retention tiered; unused metrics dropped at scrape; series-growth alert in place.

Correlation & alerts

  • ☐ trace_id in logs; exemplars link metrics → traces; context propagation verified end-to-end.
  • ☐ Every page is actionable, urgent, deduped/grouped, and has a linked runbook. No noisy/cause-based pages.
