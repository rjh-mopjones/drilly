How to read & print

  • Central law: an ML system is code + data + model — all three drift, so all three get versioned, tested, monitored. DevOps only ever versioned code.
  • Governing SLA: models fail silently — they keep returning well-formed, confidently wrong numbers while ops dashboards stay green.
  • Focus: the operate-in-prod bar — reproducibility, latency/cost, drift, safe rollout. Last 2 cards = design playbook + symptom→cause.

Foundations: why ML ≠ DevOps

  • DevOps ships code; MLOps ships code + data + model, and behaviour depends on data seen at train time — no amount of code review shows it.
  • Train/serve skew ! — the #1 silent bug: features computed one way in the batch training job, a different way in the serving path (different code, freshness, or units). Model sees a distribution it never trained on. Fix: one feature definition for both (feature store).
  • Reproducible = you can answer "which data + code + params + env produced this exact model?" Miss any axis → can't rebuild it.
  • Roles & seams: DS (notebook) → ML eng (pipeline) → SRE (serving). Failures cluster at the handoffs — "works in my notebook" is a handoff smell.

Data-version tools

  • DVC = "git for data": commits pointers/hashes, blobs live in S3/GCS. Small repo, big storage elsewhere.
  • lakeFS = git-like branches/commits over an object store (branch a 50 TB lake, merge).
  • Delta Lake = ACID + time-travel (VERSION AS OF) on a table.
  • Point-in-time correctness ! — join labels to feature values as they were at event time, never "latest". Latest-value joins leak the future into training.
  • GDPR delete: version pointers, purge underlying PII — don't rely on immutable blobs holding a deleted user forever.

Experiment Tracking

Log every run so a result is reproducible science, not a lucky notebook. MLflow (open, self-host) · W&B (best UI/sweeps) · Neptune.

Log per run

  • Params (hyperparams, feature set), metrics (train/val, per-slice), artifacts (model, plots), code git-SHA + data version + env.
  • Tag the run → the winner gets registered to the model registry (run → registry handoff carries lineage).
with mlflow.start_run():
  mlflow.log_params(cfg)
  mlflow.log_metric("val_auc", auc)
  mlflow.set_tag("git_sha", sha)
  mlflow.log_artifact("model.onnx")
  • Don't log raw datasets or every epoch's weights — log the version reference, not the bytes.
  • Tracking ≠ registry: tracking is the lab notebook (all runs); registry is the release shelf (chosen versions + stages).

Feature Store

  • Solves two problems: train/serve skew (one definition, both paths) and feature reuse across teams.
StoreRole
offlinebatch, big, point-in-time joins → training/backfill (warehouse/parquet)
onlinelow-latency KV (Redis/Dynamo) → serving reads by entity key, single-digit ms
  • Same transform materialises both → consistency by construction.
  • Freshness↔latency↔cost tradeoff: streaming features are fresh but expensive; batch-nightly is cheap but stale.
  • Feature registry = discover/own/version feature definitions (not just values).
  • Feast (open, bring-your-own infra) · Tecton (managed, streaming). ! Overkill if you have no real-time features — a nightly table + shared transform lib is enough.

Training Pipelines & Orchestration

Not a notebook — a DAG of steps: ingest → validate → featurize → train → eval → register. Parameterized, cached, idempotent.

ToolSweet spot
Airflowgeneric scheduling / ETL-shaped
KubeflowK8s-native, container-per-step, ML-first
MetaflowDS-ergonomic, Python-first
Flytestrongly-typed, cached, reproducible
  • Step caching — skip a step if inputs+code unchanged (hash). Turns a 3h rerun into minutes.
  • Idempotent ! — re-running a step yields the same result, no dup writes; required for safe retries.
  • Artifacts pass between steps by reference (URI), not in-memory globals.
  • Test it: unit-test transforms; run the pipeline on a tiny fixture in CI (smoke).

Continuous Training (CT)

CI/CD ships code; CT ships a re-fit model. Loop: trigger → retrain → validate → canary → promote.

TriggerWhen
schedulepredictable decay, simple
driftreact to real distribution change
perf decaylabels show metric drop
new data volenough fresh labels landed

Guardrails ! (a bad retrain must not ship)

  • Validate new data (schema/distribution) before training — garbage in, garbage model.
  • No-regression gate vs current prod model, on a frozen eval set + slices.
  • Canary the challenger on a traffic slice; auto-rollback on guardrail breach.
  • ! "Retrain on schedule and auto-deploy" with no gates = an automated way to ship a broken model on a bad-data day.

Model Registry & Versioning

  • Source of truth: versions + stages/aliases (Staging / Production / Archived), lineage, model cards, approvals.
  • Decouples training from deployment: training registers; deployment reads "the Production alias" — retrain without touching serving code.
  • Rollback = re-point the Prod alias to a prior version. Seconds, no rebuild. ! Fails if the new model changed the feature schema — the old model needs the old features; keep both feature versions live during rollout.
  • Lineage: version → run → data version → git SHA → dataset. Answers "what made this model?" and "who approved Prod?".
  • Governance: RBAC on who can promote to Production; promotion = reviewed, gated, audited event.
  • ! Timestamped pickles in S3 = no stages, no lineage, no rollback, no approvals — the anti-pattern a registry replaces.

  • The artifact is preprocessing + weights + post-processing together ! — split preprocessing = train/serve skew.
  • requirements.txt pins alone are not reproducible — pin the container (base image, CUDA, OS libs, seeds).
  • Non-determinism sources: RNG seeds, GPU non-determinism, data-loader order, lib versions. Control what you can; log the rest.
  • Separate train env (heavy, GPU) from serve env (lean, CPU-often); the model bridges them.

CI/CD/CT for ML — test 3 things

TestChecks
codeunit-test transforms/features (pure fns)
dataschema, ranges, nulls, distribution — GE / TFDV / pandera
modelmetric gates: min AUC, no-regression vs prod, per-slice + fairness
  • No-regression vs prod is essential ! — an absolute "AUC > 0.8" passes a model worse than what's live. Compare to the champion.
  • Per-slice not just aggregate: overall up while a key segment collapses is a shipped bug hidden by averaging.
  • Integration-test the serving artifact (container answers a real request correctly), not just the model object.
  • No live labels at pipeline time → gate on proxies: prediction-distribution sanity, invariants, golden inputs.
  • GitOps: pipeline defs, configs, thresholds live in git; deploy = a reviewed PR.

Serving at Scale: latency · throughput · cost

cost per 1k preds = (instance $/hr) / (preds/hr) * 1000
budget: 10k QPS @ p99 < 50ms, cheaply
  • p99, not p50 ! — SLOs and users live in the tail; batching inflates the tail specifically.
  • Dynamic/adaptive batching = the #1 GPU throughput lever: coalesce concurrent requests, wait a few ms to fill. Costs tail latency, wins throughput. Tune batch/wait against p99, not p50.
  • Do less work: request/feature cache; optimize the model — quantize (FP32→FP16/INT8), distill (small student mimics teacher), prune; compile via ONNX Runtime / TensorRT.
  • Right-size hardware: CPU for small models, GPU for big/high-QPS. ! An underfed A100 is pure waste — a quantized model on CPU may hit SLO at 1/10 the cost.
  • Replicas raise capacity, not single-request latency — a slow model is slow no matter how many copies.
  • Split the budget: feature-fetch + inference + network. The bottleneck is often feature-fetch, not the model.

Online / Real-Time / Streaming Inference

  • Online path = feature lookup (online store) + model call, under a hard SLA; fallback required ! — feature store miss/timeout → serve a default/cached/simpler-model prediction, never error the user.
  • Streaming features: compute on the event stream (Flink/Kafka) so the online store is always fresh; watch for late/out-of-order events.
  • Log sampled inputs+predictions on this path ! — it's the raw material for monitoring, drift, and the next retrain. If you don't log it, you can't debug or improve it.
  • Latency budget dominated by the feature fetch often, not inference — cache hot keys, precompute.

Monitoring — two layers

A model can be 100% up and completely wrong. Two monitors on two clocks:

LayerWatch
operational (fast clock)latency p50/p99, QPS, errors, saturation — SRE, pages at 3am
ML (slow/stopped clock)prediction dist, feature dist, quality (when labels land), business KPI — opens a ticket
  • Silent failure ! — a broken web service throws 500s; a broken model returns well-formed, confidently wrong numbers. Ops stays green.
  • Ground-truth / label delay ! — accuracy is knowable only when labels arrive (days later, or never). So monitor proxies you can see now: prediction shift, feature health, drift.
  • Feature monitoring (nulls/ranges/cardinality) is the earliest signal of an upstream pipeline break.
  • Sampled logging feeds analysis + retraining; don't log 100% at scale.

Drift Detection

P(x,y) = P(y|x) * P(x)
PSI = Σ_bins (actual% - expected%) * ln(actual%/expected%)
  <0.1 ok | 0.1–0.25 watch | >0.25 shift
TypeShift / detect
data/covariateP(x) — inputs move; no labels needed
conceptP(y|x) — rule changed; needs labels; most harmful
label/priorP(y) — base rate moves (fraud 1%→5%)
predictionoutput dist moves — instant proxy
  • Tests: KS (continuous, CDF distance) · chi-square (categorical) · PSI (binned index) · KL/JS/Wasserstein · embedding drift (text/images).
  • ! Drift ≠ a proven performance drop. Inputs can shift with accuracy intact; accuracy can fall with no input drift. Drift = "investigate," not "degraded" or "retrain now."
  • ! At scale, tiny meaningless shifts test as significant — use effect-size bands (PSI) + business impact, not raw p-values.

Performance Monitoring & Feedback Loops

  • True quality lands only with labels; until then track the proxy chain: feature health → prediction dist → drift → business KPI.
  • Delayed labels: join predictions to outcomes when they arrive; compute accuracy/AUC on a rolling window per slice.
  • Feedback loop ! — the model's own predictions shape future data (a recommender only sees clicks on what it showed). Training on that data reinforces itself and hides degradation. Mitigate with randomized exploration / holdout traffic that the model doesn't control.
  • Offline-online gap: offline metric up ≠ live metric up. The online experiment is the judge.

A/B Testing & Online Experiments

The final judge — a randomized live test, not offline AUC. Split by stable hash(user) so the model is the only systematic difference.

  • Primary metric (OEC): one, chosen upfront, test powered to move it. Guardrails: metrics that must not get worse (latency, error, revenue, complaints).
  • Power / MDE → sets sample size & duration; run full business cycles (≥1 week for weekly patterns).
  • Discipline: fix design → collect → decide once.

Invalidators !

  • Peeking — checking repeatedly & stopping at first "win" inflates false positives. Use sequential/fixed-horizon tests.
  • Novelty/primacy — temporary lift because it's new, not better.
  • Network effects — one unit's treatment affects another (breaks independence).
  • Simpson's paradox — aggregate reverses within segments.
  • Alt designs: bandits (minimize regret, adaptive) · interleaving (sensitive, ranking) · shadow (validate before A/B). Champion/challenger = the standing loop.

ML Infra & Compute

  • GPU/TPU on K8s; queue + schedule training jobs; bin-pack for utilization.
  • Spot/preemptible + checkpointing ! — cheap compute, but must checkpoint often or a preemption wastes hours. Save + resume state.
  • Cost levers: autoscale to load, scale-to-zero idle, right-size GPUs, share clusters, quota per team.
  • Separate train (bursty, GPU-heavy) from serve (steady, often CPU) capacity — different scaling shapes.

Governance, Security & Responsible ML

  • Lineage + audit: reconstruct which data/code/params/approver produced any prod prediction (regulated domains demand it).
  • Model cards: intended use, training data, metrics per slice, limitations, owner.
  • Bias/fairness gates in CI + per-slice monitoring; document mitigations.
  • PII/security ! — encrypt features/artifacts, RBAC on registry & data, scan for leaked PII in logs, watch for adversarial/poisoning inputs.
  • Right-to-be-forgotten collides with immutable data versions — plan deletion of underlying PII while keeping version pointers.

LLMOps — what changes

  • Often no fine-tune/retrain → the artifacts to version are prompts, RAG corpus/index, and eval sets, plus model/provider + params.
  • Eval-in-CI ! — no single accuracy number; use an eval suite (LLM-as-judge, golden Q&A, rubric scores). Regression = a scored eval drop, gated like a metric.
  • Monitor cost/token, latency, refusal/hallucination rate; cache; route small→big models by difficulty.
  • RAG "drift" = the knowledge base going stale, not weights — re-index on a schedule.
  • Guardrails: prompt-injection filtering, output validation, PII redaction. (See AI Engineering primer.)

★ Design & Review Checklist

Reproducibility

  • ☐ Data + code + params + env all versioned; run reconstructs the exact model.
  • ☐ No pickle in prod; preprocessing packaged with weights; container pinned, not just requirements.txt.

Train/serve consistency

  • ☐ One feature definition for train & serve (no skew); point-in-time joins in training (no leakage) !

Rollout & rollback

  • ☐ Registry stages/aliases; rollback = re-point alias (seconds); prior feature schema kept live during migration !
  • ☐ Canary/shadow with metric gates + auto-rollback; model behind a feature flag.

Validation gates

  • ☐ Data validated before training; no-regression vs prod; per-slice + fairness, not just aggregate.
  • ☐ CT has guardrails — a bad-data day can't auto-ship a broken model !

Monitoring

  • ☐ Both layers: ops (latency/errors) AND ML (feature/prediction dist, quality, KPI).
  • ☐ Inputs+preds logged (sampled); drift thresholds set; label-delay path to compute true quality.

Decisioning

  • ☐ New model proven by an A/B with guardrails, powered, full cycle, no peeking — not offline metrics !
  • ☐ Feedback loop broken with randomized/holdout traffic.
