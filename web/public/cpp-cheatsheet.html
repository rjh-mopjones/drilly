RAII & Smart Pointers

RAII: a resource's lifetime = an object's lifetime. Acquire in the ctor, release in the dtor. Cleanup is automatic and exception-safe — no manual delete, no finally.

TypeUse
unique_ptr<T>sole owner, move-only, zero overhead. Default choice.
shared_ptr<T>shared ownership; atomic refcount + control block ! (not free)
weak_ptr<T>non-owning observer; breaks shared_ptr cycles; .lock() to use
auto p = std::make_unique<Widget>(args);   // never `new`
auto s = std::make_shared<Widget>(args);   // 1 alloc (obj+ctrl)
std::unique_ptr<FILE, decltype(&fclose)>
    f(fopen(path,"r"), &fclose);           // custom deleter
  • Prefer make_unique/make_shared — exception-safe, one allocation.
  • Cycle = leak ! two shared_ptrs pointing at each other never hit refcount 0 → make one a weak_ptr.
  • Pass params by const T&/T*; take unique_ptr by value only to transfer ownership.
  • shared_ptr control block holds two counts: strong (owns the object) and weak (keeps the block alive). make_shared co-allocates object+block in one chunk — but a live weak_ptr then keeps that whole chunk (object storage included) alive until the last weak dies.
  • enable_shared_from_this<T> when an object must hand out shared_ptrs to itself — never build a second shared_ptr from a raw this (double free !).
  • Raw pointers/references are fine as non-owning observers — "borrowed, I won't free it." Ownership is the thing smart pointers express.

Rule of Five / Zero

The five special members: destructor, copy ctor, copy assign, move ctor, move assign.

struct Buf {
  Buf(const Buf&);            // copy ctor
  Buf& operator=(const Buf&); // copy assign
  Buf(Buf&&) noexcept;        // move ctor
  Buf& operator=(Buf&&) noexcept;
  ~Buf();                     // dtor
};
  • Rule of Zero prefer: own nothing raw — hold vector/string/unique_ptr members, write none of the five, let the compiler default them.
  • Rule of Five: if you write one (because you manage a raw resource), you almost always need all five.
  • Declaring a dtor/copy suppresses the implicit move ! → silent expensive copies.
  • Make move ops noexcept — else vector reallocation copies instead of moving !
  • =default / =delete to be explicit.

Move Semantics & Value Categories

  • lvalue = has a name/address; rvalue (prvalue/xvalue) = temporary, safe to pilfer.
  • std::move(x) is just a cast to T&& — it moves nothing; it lets the next overload move.
  • std::forward<T>(x) — perfect-forward inside a T&& template (forwarding ref).
template<class T>
void wrap(T&& x) {            // forwarding ref
  sink(std::forward<T>(x));   // keeps lvalue/rvalue-ness
}
auto v2 = std::move(v1);      // v1 now valid-but-unspecified
  • A moved-from object is valid but unspecified — only safe to destroy or reassign. Reading its value is a bug !
  • Don't return std::move(local) — it disables NRVO/copy-elision ! Just return local;.
  • Guaranteed copy elision (C++17) for prvalues: return Widget{...}; constructs in place.

const · constexpr · Casts

  • const-correctness: mark member fns const when they don't mutate; pass read-only params by const&.
  • const = runtime immutable; constexpr = usable at compile time; consteval = must run at compile time (C++20); constinit = static init, no dynamic-init order issues.
  • mutable = a member that stays writable through a const method (caches, mutexes).
CastUse
static_castrelated types, up/down (no check), numeric
dynamic_castchecked down-cast on polymorphic types (RTTI)
const_caststrip const — writing through it if the object is truly const is UB !
reinterpret_castbit reinterpret — aliasing/UB minefield !

Avoid C-style casts — they silently pick any of the above. Prefer enum class over plain enum (scoped, no implicit int conversion, no name leakage).

  • Top-level vs low-level const: const int* p = pointer to const (data locked); int* const p = const pointer (rebind locked). Read right-to-left.
  • West vs East const is style only (const T ≡ T const); pick one and be consistent.
  • [[nodiscard]] on a function/type makes ignoring the return a warning — use it on expected-returning and error-code APIs.

STL Containers — pick & cost

ContainerLookupNote
vectorO(1) idxdefault; contiguous, cache-friendly; reserve()
array<T,N>O(1)fixed size, on stack, no alloc
dequeO(1) idxfast push front/back; not contiguous
listO(n)stable iterators; rarely worth it
map/setO(log n)ordered (RB-tree)
unordered_mapO(1) avghash; O(n) worst; load_factor
  • Iterator/reference invalidation ! vector: any reallocation (push_back past cap) invalidates all; erase invalidates from the point on. map/list: only the erased node.
  • emplace_back(args...) constructs in place; push_back may copy/move.
  • vector<bool> is a bit-packed proxy — not a real container of bool !
  • Views (non-owning): string_view, span<T> — cheap params, but must not outlive the data !
  • reserve(n) before a known number of push_backs — amortised O(1) growth still reallocates+moves log n times; reserve makes it one allocation.
  • Ordered map/set = red-black tree, node-per-element (pointer chasing, cache-unfriendly) but stable iterators + ordered traversal. unordered_* needs a good hash; a bad one degrades to O(n) buckets.
  • C++23 flat_map/flat_set = sorted vector under the hood: cache-friendly lookups, slow inserts — great for build-once-query-many.

Iterators & Algorithms

Categories: input · output · forward · bidirectional · random-access · contiguous (C++20).

std::sort(v.begin(), v.end());
std::sort(v.begin(), v.end(),
          [](auto& a, auto& b){ return a.k < b.k; });
auto it = std::find(v.begin(), v.end(), x);
auto n  = std::count_if(v.begin(), v.end(), pred);
std::transform(a.begin(), a.end(),
               std::back_inserter(out), f);

erase–remove idiom !

v.erase(std::remove_if(v.begin(), v.end(), pred),
        v.end());          // remove_* only reorders!
// C++20: std::erase_if(v, pred);
  • remove/remove_if don't erase — they shuffle kept elements front and return the new logical end.
  • std::sort is unstable — use stable_sort to preserve ties.
  • Beware the accumulate init-type trap: accumulate(v.begin(),v.end(), 0) sums as int even for doubles !

Templates & Concepts (C++20)

template<std::integral T>        // concept-constrained
T gcd(T a, T b){ return b? gcd(b, a%b) : a; }

template<class T>
concept Addable = requires(T a, T b){ a + b; };

if constexpr (std::is_pointer_v<T>) { ... }  // compile-time branch
  • Definitions live in headers — templates instantiate at the call site !
  • Concepts replace most SFINAE/enable_if — clearer errors, constrained overloads.
  • if constexpr discards the untaken branch at compile time (no instantiation).
  • Variadics + fold expressions (C++17): (... + args) (unary left), (init + ... + args) (binary) — collapse a pack with no recursion.
  • Watch template code bloat: each type combo = a fresh instantiation → binary size + compile time. Factor type-independent logic into a non-template base.
  • Need typename/template disambiguators for dependent names (typename T::iterator, obj.template get<0>()).
  • Full specialisation picks an exact type; partial specialisation matches a shape (Foo<T*>). Function templates can't partially specialise — overload instead.
  • CTAD (C++17): std::pair p{1, 2.0}; deduces pair<int,double> — add deduction guides for your own class templates.

Lambdas & std::function

int base = 10;
auto f = [base](int x){ return x + base; };  // capture by value
auto g = [&](int x){ total += x; };          // capture by ref !
auto h = [p = std::move(ptr)]{ use(*p); };   // init-capture (C++14)
auto gen = [](auto x){ return x*x; };        // generic (C++14)
  • Capture by ref only if the lambda won't outlive the referent — else dangling !
  • Capturing this captures the pointer; the object must outlive the lambda. Use [*this] (C++17) to copy.
  • [=] on a member fn captures this, not the members — surprise dangling !
  • std::function = type erasure → heap alloc + indirect call. Prefer a template/auto param on hot paths.
  • Prefer lambdas over std::bind.

Polymorphism & the vtable

flowchart LR obj["Derived object
[vptr | fields]"] --> vt["vtable (per class)"] vt --> f1["&Derived::foo"] vt --> f2["&Base::bar"]

Each polymorphic object stores a hidden vptr → its class vtable of function pointers. A virtual call = load vptr, index, indirect call (one extra indirection, defeats inlining).

  • Virtual destructor on any class deleted through a base pointer ! else UB / partial destruction.
  • Object slicing ! copying a Derived into a Base value drops the derived part. Store base */references, never by value.
  • Mark overrides override; use final to seal.
  • Don't call virtuals from ctors/dtors — dispatch resolves to the current type, not the derived one !

Exceptions & Error Handling

Safety guarantees

LevelMeaning
nothrownever throws (noexcept)
strongcommit-or-rollback; state unchanged on throw
basicvalid but unspecified state; no leaks
nonecan leak/corrupt — avoid
  • RAII gives exception safety for free — unwinding runs dtors.
  • Never let a destructor throw ! → std::terminate during unwinding.
  • catch (const std::exception& e) — by const ref, never by value (slicing).
  • Zero-cost model: no penalty on the happy path; throwing is expensive — not for control flow.
  • Alternatives: std::optional (maybe), std::expected<T,E> (C++23), std::error_code. -fno-exceptions builds exist (embedded).
  • Throw by value, catch by const&; derive your types from std::exception. Order catch blocks most-derived first.
  • The strong guarantee's canonical recipe = copy-and-swap: do the work on a copy, then swap (a noexcept op) to commit — a throw leaves the original untouched.
  • Reserve exceptions for genuinely exceptional, cross-cutting failures; use optional/expected for expected "not found"/"invalid input" outcomes on hot paths.

Concurrency

std::jthread t([](std::stop_token st){    // C++20: auto-joins
  while(!st.stop_requested()){ ... }
});
{
  std::scoped_lock lk(m1, m2);   // deadlock-free multi-lock
  ...
}
std::condition_variable cv;
cv.wait(lk, []{ return ready; }); // predicate form — no spurious wakeups
ToolUse
lock_guard/scoped_lockRAII lock; scoped_lock takes many (ordered)
unique_lockmovable, works with condition_variable
shared_mutexmany readers / 1 writer
call_once/once_flagthread-safe lazy init
async/futurerun + get a result later
  • A data race is UB ! — any concurrent access with ≥1 write and no synchronisation.
  • Always lock multiple mutexes in a consistent order (or use scoped_lock) to avoid deadlock.
  • Run TSan (-fsanitize=thread) in CI.
  • Prefer message-passing / higher-level tools (async, thread pools, queues) over hand-rolled locks; the less shared mutable state, the fewer races.
  • condition_variable: always wait with a predicate and re-check on wake — spurious wakeups are real, and you must hold the mutex to change the condition then notify.
  • thread that is neither joined nor detached at destruction calls std::terminate ! — that's why jthread (auto-joins, carries a stop_token) is the C++20 default.
  • Guard against false sharing: two atomics on the same cache line ping-pong between cores — pad to hardware_destructive_interference_size.

Memory Model & Atomics

std::atomic<int> cnt{0};
cnt.fetch_add(1, std::memory_order_relaxed); // counter: no ordering needed

// publish pattern:
data = compute();
flag.store(true, std::memory_order_release);
// reader:
if (flag.load(std::memory_order_acquire)) use(data);
OrderMeaning
seq_cstdefault; single total order; safest, priciest
acquire/releasepairwise publish/consume of data
relaxedatomicity only, no ordering (counters)
  • release store synchronizes-with an acquire load of the same var → establishes happens-before.
  • compare_exchange_weak in a loop (may spuriously fail); watch the ABA problem !
  • volatile is not atomic and gives no cross-thread ordering ! (it's for memory-mapped I/O, not threading).
  • An atomic op isn't automatically lock-free — check std::atomic<T>::is_lock_free(); large T falls back to a hidden mutex.
  • Default to seq_cst and only weaken (acquire/release/relaxed) once a benchmark proves it matters and you can justify the ordering — this is where lock-free code goes subtly wrong.

UB = the optimizer assumes it never happens and rewrites your code around it. Not "works differently" — anything may happen !

Compilation · Headers · ODR · Build

Pipeline: preprocess → compile (per TU) → link. Each .cpp is a translation unit.

  • ODR: every entity defined once across the program (inline/templates exempt but definitions must be identical) !
  • Headers: declarations + inline/constexpr/templates. #pragma once (or include guards).
  • Never using namespace in a header !
  • inline = "multiple identical definitions OK" (linkage), not just an inlining hint.
  • static/anonymous namespace = internal linkage (TU-local).
  • PIMPL hides implementation, cuts rebuild coupling & compile time.
  • extern "C" disables name-mangling for C interop.
# fast, strict dev build
g++ -std=c++20 -Wall -Wextra -O2 \
    -fsanitize=address,undefined app.cpp

Speed: forward-declare, PCH, unity builds, C++20 modules.

Object Model, Init & Lifetime

A build runs each .cpp independently: preprocess (paste headers/macros → a translation unit) → compile (TU → .o + symbols) → link (resolve every symbol to one definition). No VM, no interpreter — native code.

  • Value semantics: a variable is the object. Widget b = a; is an independent copy — no hidden handle, no sharing (contrast Java/C# reference semantics). You opt into sharing via pointers/shared_ptr.
  • Object = a typed region of storage with a lifetime; an int is an object too. Lifetime begins when construction completes, ends at destruction. Touching it outside that window is UB !
  • Storage duration: automatic (scope) · static (program) · dynamic (new) · thread (thread_local). RAII is just "tie a resource to an automatic object."
  • struct vs class: only default access differs (public vs private). Both are full class types.
TraitQuestion it answers
trivialdefault ctor/copy/dtor are compiler-generated → memcpy-safe
standard-layoutC-ABI compatible layout (interop / offsetof)
PODboth of the above (split into the two in C++11)
  • Automatic int i; is indeterminate, not zero — reading it is UB ! Only static storage zero-inits.
  • auto strips top-level const/ref — use const auto& when you mean it. Always nullptr, never NULL/0 (wrong overload / template breakage).
  • Brace-init {} forbids narrowing, but ! vector<int>{3} is one element 3, vector<int>(3) is three zeros — initializer_list hijacks the overload.

Type Traits & TMP

TMP = compile-time computation with the template system as interpreter: types are values, a metafunction is a class template exposing ::type (a type) or ::value (a value). Recursion replaces loops; specialisation replaces branching. Modern code prefers constexpr + concepts.

TraitDoes

is_integral_v<T>query: numeric category

remove_cvref_t<T>strip ref + cv (C++20)
decay_t<T>pass-by-value model

// SFINAE via enable_if (pre-C++20)

  std::enable_if_t<std::is_integral_v<T>,int> = 0>
T half(T x){ return x/2; }

using R = decltype(std::declval<T>() + std::declval<U>());
  • _v/_t aliases kill ::value / typename …::type noise.
  • declval<T>() = "an expression of type T" in unevaluated contexts (decltype/sizeof/noexcept) — no ctor needed, no runtime definition.
  • ! decltype(x) = declared type; decltype((x)) = expression type → adds a ref (int& for a local).
  • Tag dispatch (pass an empty tag type) drives std::advance per iterator category; use over enable_if for a discrete tag hierarchy.
  • Reach for if constexpr (in-function branch) or a concept (affects overload resolution) before writing SFINAE.

  • C++20 widened it hugely: new/delete, constexpr vector/string, virtual fns, try — you can build & sort a vector at compile time (every allocation must be freed before eval ends).

Ranges & Views (C++20)

A range has begin()/end(). A view is a non-owning, O(1)-to-copy, lazy adaptor — building it does no work; elements compute on demand as you iterate.

std::vector<int> v{1,2,3,4,5,6};
auto pipe = v | std::views::filter([](int x){return x%2==0;})
              | std::views::transform([](int x){return x*x;});
// nothing computed yet — one fused pass on iteration
for(int x: pipe) use(x);          // 4 16 36
// materialise:  auto out = pipe | std::ranges::to<std::vector>(); // C++23
  • range | adaptor ≡ adaptor(range); reads in data-flow order, fuses into one pass, no intermediate containers. take(n) means the rest is never computed.
  • Projection: ranges::sort(ws, {}, &Widget::price) — sort "by field" with no comparator lambda. Signature: algo(range, cmp={}, proj={}).
  • std::ranges::sort(v) takes the whole range (no begin/end), is concept-constrained (clean errors), composes with views.
  • ! Views are non-owning — piping off a temporary container dangles. Ranges defend the algorithm case: ranges::find(std::vector{...},x) returns std::ranges::dangling (won't compile as an iterator). Borrowed ranges (string_view, span, lvalue containers) stay valid.
  • Where they bite: debug builds (unfused adaptor layers) far slower than a raw loop; lazy side-effecting predicates re-run on every traversal; harder to step in a debugger.

Coroutines (C++20)

A function that can suspend mid-body, return control, and later resume with locals intact. Becomes one purely by using co_await/co_yield/co_return — no signature keyword.

std::generator<int> fib(){          // C++23 std::generator
  int a=0,b=1;
  while(true){ co_yield a; std::tie(a,b)=std::pair{b,a+b}; }
}
Task<std::string> fetch(Url u){
  auto c = co_await connect(u);     // suspend until connected
  co_return co_await c.read();
}
  • Frame: holds locals, a copy of params, the promise, resume point — usually heap-allocated, but HALO may elide it when the lifetime is bounded.
  • Promise type (Ret::promise_type): compiler-driven hooks — get_return_object, initial_suspend (lazy vs eager), yield_value/return_value, final_suspend (noexcept), unhandled_exception.
  • Awaiter triad: await_ready (skip suspend?) → await_suspend(h) (stash handle for later resume; return a handle = symmetric transfer, constant stack) → await_resume (yields co_await's result).
  • ! Reference/string_view/span parameters dangle: the frame copies the reference, not the referent. Take coroutine params by value.
  • C++20 shipped only the machinery — no standard task; std::generator arrived in C++23. Real async needs an executor (Asio, cppcoro, stdexec/P2300 in C++26) — the executor gap.
  • Single-threaded & cooperative — a coroutine is not a thread; concurrency comes from the scheduler.

Performance & Data Layout

Measure before optimising — profile (perf, VTune, google-benchmark), find the hot 3%, fix that. Guessing is how you make code uglier and slower.

  • Cache locality dominates. A main-memory miss is ~100× an L1 hit — algorithmic constant factors are usually about memory access, not instruction count.
  • AoS → SoA: if a loop touches one field of many objects, store fields in parallel arrays (struct-of-arrays) so each cache line carries only useful data; enables auto-vectorisation.
  • vector beats list/map for traversal almost always — contiguous, prefetch-friendly. Prefer reserve() to kill reallocations.
  • Zero-overhead abstraction: templates/inlining/RAII compile to the same code you'd hand-write. std::function, virtual calls, and shared_ptr refcounts are the non-zero-cost ones — avoid on hot paths.
  • Prefer emplace_back + move; pass const&/string_view/span to avoid copies.
  • Small-buffer optimisation (SSO): short std::strings live inline, no heap — don't fear small strings.
  • Look at the asm on godbolt / -S; check what actually inlined and vectorised under -O2 -march=native.
  • ! Signed overflow & strict aliasing are UB the optimiser exploits — bugs that appear only at -O2. Use -fsanitize=undefined.

★ Code Review Checklist

Memory & ownership

  • ☐ No raw new/delete; ownership expressed via smart pointers/containers.
  • ☐ Right pointer: unique_ptr (sole) vs shared_ptr (shared) vs weak_ptr (break cycle).
  • ☐ RAII for every resource (file, socket, lock, handle); no leak/double-free path.
  • ☐ No returning a ref/pointer to a local or expired temporary.

Special members & const

  • ☐ Rule of Zero where possible; if any of the five, all correct; move ops noexcept.
  • ☐ No accidental deep copies of heavy objects (pass const& / std::move).
  • ☐ const-correct APIs; no const_cast/C-casts; enum class; no narrowing.

Lifetime & UB traps

  • ☐ No dangling string_view/span; no use-after-move; members initialised.
  • ☐ No iterator/reference invalidation across a container mutation.

Concurrency & errors

  • ☐ Shared state guarded; consistent lock order; correct memory-order on atomics.
  • ☐ Exception safety (strong/basic) held; no throwing dtor; noexcept accurate.

STL, headers & gates

  • ☐ Right container for the access pattern; algorithm over hand-rolled loop; reserve where sizes known.
  • ☐ string_view/span params over owning copies where non-owning.
  • ☐ Include-what-you-use; no ODR violation; no using namespace in headers.
  • ☐ clang-format clean; clang-tidy / -Wall -Wextra -Werror; ASan/UBSan/TSan on tests.
