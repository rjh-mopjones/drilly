Architecture

flowchart TD U["kubectl / CI"] --> API["kube-apiserver"] API --> ETCD["etcd (state)"] API --> SCH["scheduler"] API --> CM["controller-mgr"] API --> KUBELET["kubelet (per node)"] KUBELET --> CRI["containerd → Pods"] KUBELET --> KP["kube-proxy"]

Control plane = api-server + etcd + scheduler + controller-manager (+ cloud-controller-mgr). Node = kubelet + kube-proxy + CRI runtime. Everything funnels through the api-server; only it talks to etcd; etcd is the single source of truth (back it up).

Control Plane & Reconcile

  • api-server = only front door + only etcd client. Every request: authn → authz (RBAC) → admission (mutate→validate) → persist.
  • scheduler binds unscheduled Pods to nodes (writes nodeName) — it does not start them !
  • controller-manager hosts the built-in loops (Deployment, ReplicaSet, Node, Job, EndpointSlice…).
  • kubelet runs Pods bound to its node via CRI; reports status.

Level- vs edge-triggered !

Controllers re-list actual state and diff vs desired every loop — they don't react once to an event. A missed event, crash, or restart still converges. That's why K8s self-heals.

apply → running Pod

kubectl → api-server (persist Deploy) → Deploy ctrl makes ReplicaSet → RS ctrl makes Pods (unscheduled) → scheduler binds → kubelet pulls image + runs via CRI + CNI wires net → status back. Every arrow crosses the api-server.

Pods: Sharing, Init, Sidecars

Shared in a Pod: network namespace (one IP, reach each other on localhost, share port space !), IPC, mounted volumes, node+lifecycle. Not shared: filesystem root, PID (unless shareProcessNamespace), resource accounting. A hidden pause container holds the namespaces so app containers restart without losing the Pod IP.

Multi-container patterns

  • Sidecar (log shipper, mesh proxy), ambassador (outbound proxy), adapter (reformat output). Only when tightly coupled & must share node/net/vol — else separate Pods.
  • Init containers run in order, to completion, before app containers (migrations, wait-for-dep). Native sidecar = init container with restartPolicy: Always (starts early, stays running).

Phases & states

Phase: Pending / Running / Succeeded / Failed / Unknown. Container state: Waiting (ImagePullBackOff, CrashLoopBackOff) / Running / Terminated (Completed, OOMKilled, Error). Never create bare Pods — node dies, nothing recreates it !

  template:

    spec:
      containers:

        ports: [{ containerPort: 8080 }]

          requests: { cpu: 100m, memory: 128Mi }

---

kind: Service
metadata: { name: web }
spec:
  selector: { app: web }   # must match Pod labels !
  ports: [{ port: 80, targetPort: 8080 }]

Service selector and Deployment spec.selector both target the Pod template labels. Mismatch = no endpoints.

Rollouts & Rollback

Changing the Pod template makes a new ReplicaSet (0 replicas), then scales new up / old down a few Pods at a time, gated by each new Pod going Ready. Old RS parked at 0 = fast rollback (just scale it back up, no image re-pull).

strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 25%        # Pods ABOVE desired
    maxUnavailable: 0    # Pods BELOW desired
GoalSetting
zero capacity lossmaxUnavailable:0, maxSurge>0 (needs spare)
resource-constrainedmaxSurge:0, maxUnavailable:1
can't both be 0rollout can't progress !
  • Recreate strategy = kill all old then start new → downtime; use when two versions can't coexist (schema).
  • progressDeadlineSeconds exceeded → rollout marked stuck (bad probe/image). rollout pause/resume for baking a canary.
  • Zero-downtime needs readiness probes + PDB; old ReplicaSets kept per revisionHistoryLimit.

Canary / blue-green with primitives

Native rollout is a coarse rolling update — no metric-gated promotion. Canary: run a second Deployment (few replicas, same Service labels) so a fraction of traffic hits the new version, watch signals, then scale up. Blue-green: two full Deployments, flip the Service selector from blue→green for instant cutover + instant rollback. For weighted/header splits + auto-rollback use Argo Rollouts, Flagger, or the Gateway API !

StatefulSet identity

  • Stable DNS via headless Service (clusterIP: None, serviceName): web-0.nginx.ns.svc.cluster.local.
  • volumeClaimTemplates → one PVC per pod (data-web-0…); disk follows pod on reschedule. PVCs not deleted on scale-down/delete (default) !
  • Ordered by default (OrderedReady): web-0 Ready before web-1. web-0 stuck ⇒ rest never start !
  • StatefulSet ≠ HA — it gives identity/ordering/storage; replication + failover live in the app (Patroni, Raft, ISR) !

Storage: PV / PVC / SC / CSI

  • PVC = a pod's claim ("10Gi RWO"); PV = the actual volume; StorageClass = template for dynamic provisioning (PVC → SC → auto-creates PV).
  • Access modes: RWO (one node, block/most cloud disks), ROX, RWX (many nodes — needs NFS/CephFS/EFS, not EBS/GCE-PD) !
  • Reclaim policy: Delete (default on dynamic — deletes real disk when PVC goes !) vs Retain (keep data, manual cleanup). Use Retain for prod data.
  • volumeBindingMode: WaitForFirstConsumer delays binding until scheduling so the disk lands in the pod's zone (topology) !
  • CSI replaced in-tree drivers; enables snapshots, expansion (allowVolumeExpansion), cloud plugins.
  • ReadWriteOncePod = exactly one pod (stronger than RWO's one node) — use for leader-only writers.
  • VolumeSnapshot (CSI) = point-in-time PVC copy → restore or clone. Expand a PVC in place by editing its request (needs allowVolumeExpansion: true).

Probes & Lifecycle

ProbeFail →
livenesskubelet restarts container
readinessremoved from Service endpoints (no restart)
startupguards slow start; gates the other two
  • Liveness ≠ readiness. A liveness probe that checks a dependency (DB, downstream) → cascading restarts across the fleet !
  • Tune initialDelaySeconds/failureThreshold — aggressive liveness on a slow-starting app = CrashLoop. Prefer a startupProbe for slow boots.
  • Shutdown: SIGTERM → terminationGracePeriodSeconds (30s default) → SIGKILL. Add a preStop sleep to cover the endpoint-removal race (LB still sending) !
  • PodDisruptionBudget (minAvailable/maxUnavailable) protects availability during drains/upgrades.

Resources & QoS

  • requests = what the scheduler reserves (drives placement); limits = hard runtime cap.
  • Over memory limit → OOMKilled (137). Over CPU limit → throttled (CFS), not killed !
  • CPU in millicores (500m = ½ core); memory Mi=1024², M=1000² !

  • Node allocatable < capacity (kubelet/system reserved). Overcommit allowed on requests; memory pressure → eviction by QoS.
  • LimitRange = per-pod defaults/bounds; ResourceQuota = per-namespace aggregate cap.

Scheduling

  • nodeSelector = simple label equality. Node affinity = required (hard) / preferred (soft) expressions.
  • Taints repel, tolerations allow. Control-plane/GPU/spot nodes are tainted; effects NoSchedule / PreferNoSchedule / NoExecute (evicts running pods).
  • Pod (anti-)affinity co-locates/spreads by topologyKey (e.g. hostname, zone) — expensive at scale.
  • topologySpreadConstraints (maxSkew) = the modern way to balance replicas across zones/nodes.
  • PriorityClass + preemption: high-priority Pending pod evicts lower-priority pods.
  • Scheduler works in two phases: filter (feasible nodes — fit, taints, affinity) then score (rank — spread, least-allocated) → binds the winner. It never starts the pod; the kubelet does !

Autoscaling

ScalerScales
HPApod replicas (CPU/mem/custom)
VPApod requests/limits (recreates pod)
Cluster Autoscalernodes (on Pending pods)
Karpenterjust-in-time right-sized nodes

  • HPA target: desired = ceil(replicas × current/target); needs requests set + metrics-server or it does nothing !
  • HPA + VPA on the same metric conflict (both fight over the pod) — split metrics or use VPA in recommend-only !
  • Stabilization windows / behavior policies prevent flapping. HPA scales pods → creates Pending → Cluster Autoscaler adds nodes.
  • Local storage / restrictive PDBs / no-controller pods block node scale-down !
  • Example: 4 pods at 80% CPU, target 50% → ceil(4×80/50)=7 pods. Scale-down is deliberately slow (default 5m stabilization) to avoid flapping; scale-up is fast.
  • Karpenter (vs Cluster Autoscaler) provisions right-sized nodes directly from pending pods — no pre-defined node groups — and consolidates/bin-packs to cut cost. KEDA scales on queue depth, Kafka lag, cron, etc., and to zero.

RBAC & Security

  • Pipeline: authn → authz (RBAC) → admission. K8s has no user DB — trusts external identity (certs, OIDC, cloud IAM, SA tokens).
  • Role/RoleBinding = namespaced; ClusterRole/ClusterRoleBinding = cluster-wide. Rule = apiGroups × resources × verbs.
  • Pods authenticate via a mounted ServiceAccount token (short-lived, audience-scoped bound/projected JWT — not the old forever-secret). Least-privilege; avoid cluster-admin/wildcard verbs !
  • Test: kubectl auth can-i <verb> <res> --as=…. Set automountServiceAccountToken: false if the pod needs no API access.

No User object — K8s has no user DB; identity is asserted externally. 401=authn failed (bad/expired token/cert); 403=authenticated but not authorized ! RBAC is allow-only + additive (no deny rules) — effective perms = union of all bindings.

Pod hardening

  • SecurityContext: runAsNonRoot, drop: [ALL] caps, readOnlyRootFilesystem, allowPrivilegeEscalation:false, no privileged/hostNetwork/hostPath !
  • Pod Security Admission = baseline / restricted profiles per namespace (replaced PodSecurityPolicy).
  • NetworkPolicy: default is allow-all; once a policy selects a pod it flips to default-deny for that direction. Needs a CNI that enforces it (Calico/Cilium) !

Networking & DNS

  • Model: every pod gets a unique routable IP; pods talk pod-IP→pod-IP without NAT. A CNI wires it (Calico/Cilium/Flannel/AWS-VPC-CNI).
  • kube-proxy programs Service VIPs via iptables (default, O(n) rules) or IPVS (hash, scales better); Cilium/eBPF can replace kube-proxy entirely.
  • CoreDNS resolves Services/pods. Watch ndots:5 — unqualified names fan out into many lookups + latency ! NodeLocal DNSCache helps.
  • Cross-namespace: use FQDN svc.other-ns.svc.cluster.local; flat pod network means ns is not a network boundary without NetworkPolicy !
  • Service mesh (Istio/Linkerd) = mTLS + traffic mgmt + observability — often more complexity than you need !

Helm · Kustomize · GitOps

  • Helm: templated charts + values.yaml; helm install/upgrade/rollback, release history. Powerful but string-templating YAML is error-prone.
  • Kustomize: template-free bases + per-env overlays/patches; built into kubectl -k. Diffs stay readable.
  • GitOps (Argo CD / Flux): Git = desired state; pull-based reconcile + drift detection + auto-sync — beats kubectl apply from CI (no cluster creds in CI, audit trail).
  • Secrets in Git: sealed-secrets / SOPS / External Secrets — never plaintext !
  • Not either/or: common to run Kustomize over a Helm-rendered base, or Helm for third-party charts + Kustomize for your own apps.
  • Kustomize patches: strategic merge (merge YAML by field) vs JSON patch (RFC6902 precise ops). Helm hooks (pre-install/post-upgrade) run migration Jobs.
  • Argo sync waves order resource apply; app-of-apps = one Application managing many. Drift detection re-converges the live cluster to Git.

Cluster Ops & etcd

  • Upgrade order: control plane first, then nodes. Kubelet may lag api-server by up to 3 minors but never lead; go one minor at a time !
  • Node maintenance: cordon (stop new) → drain (evict, respects PDBs) → replace → uncordon.
  • etcd: odd member count (3/5) for quorum, tolerates (N-1)/2 losses; lose quorum → writes stop, cluster read-only ! etcdctl snapshot save is non-negotiable.
  • HA control plane: multiple stateless api-servers behind LB; scheduler/controller-mgr use leader election (one active).
  • Backups: Velero (objects + PV snapshots). Managed (EKS/GKE/AKS) runs control plane + etcd for you.
  • Cost: right-size requests, spot pools, Cluster Autoscaler/Karpenter, bin-packing.

Namespaces & Multi-tenancy

A namespace is a virtual cluster: it scopes object names (a Deployment api can exist in both dev and prod) and is the attachment point for RBAC Roles, ResourceQuota, and LimitRange. It is an organisational + policy boundary, not a network or hard-security one !

Controllers, CRDs & Operators

Kubernetes doesn't do things once, it keeps them true. A controller loops forever: observe desired (spec) → observe actual (world) → diff → take one idempotent step → update status → requeue. Deployment, ReplicaSet, Node, Job are all just built-in controllers.

for {
  key := queue.Get()          // needs reconcile
  desired := spec(key)        // from informer cache
  actual  := observeWorld(key)
  if actual != desired { stepToward(desired) } // idempotent
  updateStatus(key); queue.Done(key)  // or AddRateLimited
}
  • Informer = client-side watched cache feeding a rate-limited, deduplicating work queue of object keys — not a hammering poll.
  • CRD registers a new API kind (OpenAPI schema, printer columns, /status & /scale subresources). A CRD alone is inert data !
  • Operator = CRD + a controller encoding day-2 ops (backup, failover, upgrade) for a stateful app. Reconcile runs thousands of times → must be idempotent + safe to re-run.
  • ownerReferences drive cascading GC (delete parent → children collected). Finalizers block deletion for an external-cleanup hook.
  • Admission webhook = synchronous validate/mutate on write (OPA/Gatekeeper, Kyverno); a controller is asynchronous convergence after the object is stored.

Scenario Playbooks (worked)

Every workload flows through a pipeline: admitted → scheduled → image pulled → started → probes pass → endpoints added → served. A failure is stuck at one stage and K8s names it in plain text. Move outward: pod → controller → node → scheduler → network.

Unschedulable despite free capacity

Capacity ≠ schedulability: check taints without a toleration, anti-affinity/topologySpread that no node satisfies, an unbound PVC pinned to a zone (WaitForFirstConsumer), or requests that fit no single node. describe pod events name it.

Intermittent 5xx during a deploy

Almost always the endpoint-removal race: pod gets SIGTERM + is pulled from endpoints, but in-flight LB connections still arrive. Fix = preStop sleep (5–15s) + app drains on SIGTERM + a real readiness probe. Add a PDB so a drain can't take too many at once !

NotReady node

describe node conditions: MemoryPressure/DiskPressure/PIDPressure → kubelet evicts BestEffort/Burstable first. Network/kubelet down → node lease stops → pods marked for eviction after the toleration window (default 5m for node.kubernetes.io/not-ready).

api-server / etcd latency

Everything crosses the api-server; slow etcd = slow everything. Check etcd disk latency (fsync), object churn (a hot-looping controller), and --raw /metrics request durations. Large Secrets/ConfigMaps and huge list calls hammer etcd !

★ Troubleshooting Playbook

Pending / Unschedulable

  • ☐ describe pod events → insufficient cpu/mem, taints w/o toleration, affinity unsatisfiable, unbound PVC, quota exceeded.

CrashLoopBackOff

  • ☐ logs --previous, exit code, bad config/cmd, missing dep, too-aggressive liveness probe.

  • ☐ image name/tag typo, private registry needs imagePullSecrets, registry auth/network.

  • ☐ memory limit too low or a leak — raise limit / fix app; check describe last state.

Service returns nothing

  • ☐ get endpoints <svc> empty → selector mismatch / no ready pods / wrong targetPort / NetworkPolicy.

DNS failing

  • ☐ CoreDNS pods/logs, ndots, test with kubectl run -it --rm dnsutils -- nslookup svc.

Stuck Terminating

  • ☐ finalizers, node gone, grace period; remove finalizer only as last resort !

Namespace stuck Terminating

  • ☐ a resource with a finalizer (often a CRD whose controller is gone) — patch out the finalizer.

☐ Manifest Review Checklist

  • ☐ resources.requests & limits set (mem limit == request → Guaranteed for critical apps).
  • ☐ readiness probe present; liveness/startup where apt; liveness never checks a dependency !
  • ☐ Image is a pinned tag/digest, never :latest; imagePullSecrets if private.
  • ☐ SecurityContext: runAsNonRoot, drop ALL caps, read-only rootfs, no privileged/hostPath/hostNetwork.
  • ☐ Least-privilege ServiceAccount + RBAC; automountServiceAccountToken:false if unused.
  • ☐ Labels match Service/selector; selector is immutable; multiple replicas + PodDisruptionBudget.
  • ☐ preStop sleep + terminationGracePeriodSeconds for graceful shutdown.
  • ☐ NetworkPolicy restricting ingress/egress; no secrets in env plaintext / baked in image.
  • ☐ StatefulSet: correct storageClassName, reclaim policy, PVC retention understood.
  • ☐ Rollout strategy + maxSurge/maxUnavailable suit capacity; progressDeadlineSeconds set.
