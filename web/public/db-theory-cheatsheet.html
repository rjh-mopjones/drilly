Relational Model & Keys

  • A relation is a set of tuples over named attributes, each drawn from a domain. "Set" ⇒ no duplicate tuples, no row order, no column order — a table is a physical, ordered, duplicate-allowing approximation !
  • Every value is atomic w.r.t. the relational operators (1NF). The model is value-based: rows are identified by data (keys), never by physical address or insertion order.

Key taxonomy

Surrogate vs natural !

  • Surrogate (auto-int / UUID): stable, opaque, no business meaning — safe PK default. Natural (email, ISBN): meaningful but mutable ⇒ cascading updates.
  • Random UUIDv4 as a clustered PK fragments B-tree inserts ! — prefer bigint identity or UUIDv7/ULID (time-ordered).

  • Algebra is closed: every operator takes relations and returns a relation ⇒ composable, and the basis for the optimizer's rewrite rules (join reorder, predicate pushdown).
  • SQL is bag (multiset)-based, not set-based: SELECT keeps duplicates unless DISTINCT; UNION dedupes but UNION ALL doesn't. ORDER BY adds ordering the model doesn't have. So SQL is only "mostly" relational !

NULL & Three-Valued Logic

  • NULL = "unknown/absent", not a value. Any arithmetic or comparison with NULL yields UNKNOWN, which behaves like false in a WHERE (rows kept only on TRUE).
NULL = NULL   -> UNKNOWN   (not TRUE!)
NULL <> 5     -> UNKNOWN
x IN (1,NULL) -> TRUE or UNKNOWN, never FALSE
NOT IN (subq with a NULL) -> drops ALL rows !
OpTFU
AND—F winsU
ORT wins—U
  • Test with IS NULL / IS DISTINCT FROM, never = NULL !
  • Aggregates skip NULLs: COUNT(col) ignores them, COUNT(*) doesn't; AVG divides by non-null count.
  • UNIQUE allows multiple NULLs (they're "not equal"). Use NOT NULL + defaults to sidestep the whole hazard where you can.

Functional Dependencies

  • X → Y: X determines Y — any two tuples agreeing on X must agree on Y. FDs encode business rules and drive normalization.
  • Partial dependency: a non-key attr depends on part of a composite key ⇒ breaks 2NF. Transitive: non-key → non-key ⇒ breaks 3NF.

Armstrong's axioms

RuleMeaning
reflexivityY⊆X ⇒ X→Y
augmentationX→Y ⇒ XZ→YZ
transitivityX→Y, Y→Z ⇒ X→Z
  • Closure X⁺ = all attrs derivable from X. If X⁺ = all attributes, X is a super key. This is how you find candidate keys.
  • A determinant is any left side of an FD; BCNF requires every determinant be a super key.

Normal Forms (1NF → BCNF)

NFRequires (given prior NF)
1NFatomic values; no repeating groups / arrays-as-columns
2NFno partial dep — non-key attrs depend on the whole key
3NFno transitive dep — non-key attrs depend on nothing but the key
BCNFevery determinant is a super key (stricter 3NF)
4NFno non-trivial multivalued dep
5NFno non-trivial join dep

Mnemonic: "the key, the whole key, and nothing but the key — so help me Codd." 3NF ≈ the target for OLTP.

  • Decomposition must be lossless-join (natural join reconstructs the original) and ideally dependency-preserving. BCNF can force giving up dependency preservation ! — 3NF always preserves both.
  • 4NF/5NF matter only with independent multi-valued facts in one table (rare, often a modeling smell).

Anomalies & Denormalization

What normalization prevents

AnomalySymptom
insertcan't add a fact without an unrelated one (need a course to store an instructor)
updatea fact stored N times ⇒ update misses some ⇒ contradiction !
deletedeleting a row destroys an unrelated fact

Root cause = one relation storing two independent facts. Split them.

Denormalize deliberately

  • Trade write-cost + redundancy for read speed: precomputed aggregates, duplicated hot columns, materialized joins. Justified when reads ≫ writes and joins are the bottleneck.
  • You now own consistency: keep copies in sync via triggers, app logic, or materialized views — and accept staleness ! Normalize first, denormalize with evidence.

ACID — property → mechanism

PropGuaranteeMechanism
Atomicityall-or-nothingundo log / WAL rollback
Consistencyconstraints hold before→afterPK/FK/CHECK + app
Isolationconcurrent = some serial orderlocks / MVCC
Durabilitycommitted survives crashWAL + fsync
  • C is the odd one out !: it's not a DB algorithm, it's your invariants (balances ≥ 0). The DB enforces declared constraints; the rest is on you.
  • ACID's C ≠ CAP's C. ACID-C = integrity constraints; CAP-C = a single up-to-date value across nodes (linearizability). Same letter, unrelated concepts !
  • BASE (Basically Available, Soft state, Eventual consistency) trades I/C for availability + scale — accept temporary disagreement, converge later. Right when writes must never block and stale reads are tolerable.

Transaction Lifecycle & Durability

BEGIN;
  UPDATE acct SET bal=bal-100 WHERE id=1;
  SAVEPOINT s1;
  UPDATE acct SET bal=bal+100 WHERE id=2;
  -- ROLLBACK TO s1;   -- partial undo
COMMIT;   -- durable point
  • Atomic on crash mid-commit: the commit is decided by a single durable act — the WAL commit record hitting disk. Before it → recovery undoes (rolls back); after → recovery redoes. No half-states survive.

Durability = WAL + fsync

  • Write-ahead rule: the log record is flushed before the data page. Sequential log writes are cheap; random page writes lazily follow.
  • "Committed" only means as durable as the flush: fsync + battery-backed cache. synchronous_commit=off / group commit trades a few ms of data loss for throughput !
  • Checkpoint flushes dirty pages + records a log position ⇒ bounds redo work (recovery time) at the cost of I/O spikes.

Read phenomena

  • Dirty read: see another txn's uncommitted write.
  • Non-repeatable read: re-read a row, value changed (committed update).
  • Phantom: re-run a range query, new rows appear (committed insert).
  • Write skew: two txns read an overlapping set, each writes a disjoint part; both valid alone, together break an invariant.

! Engine names lie: Oracle/PG "SERIALIZABLE" was historically SI. Know the guarantee, not the label.

Snapshot Isolation & Its Hole

  • SI: each txn reads a consistent snapshot as of its start; writers don't block readers. First-committer-wins on write-write conflicts ⇒ no lost update on the same row.
  • SI stops dirty/non-repeatable/phantom but allows write skew — the classic SI gap !

Write skew — on-call doctors

-- invariant: >=1 doctor on call
-- T1 & T2 each read count=2, each think
-- "safe to go off", each remove self:
UPDATE oncall SET on=false WHERE me;
-- both commit -> 0 on call. Broken !

Fixes

  • Materialize the conflict: SELECT … FOR UPDATE on the read set, or a guard row both must lock.
  • SERIALIZABLE (SSI in PG) — detects rw-dependency cycles and aborts one; retry on serialization failure.
  • Push the invariant into a constraint the DB can enforce (exclusion/CHECK).

Lost Update & How to Stop It

-- read-modify-write race:
x = SELECT qty FROM inv WHERE id=1; -- 10
-- (other txn does the same, writes 9)
UPDATE inv SET qty = x-1 WHERE id=1; -- writes 9, lost !
FixHow
atomic writeSET qty = qty-1 — let the DB do the arithmetic
pessimisticSELECT … FOR UPDATE locks the row for the txn
optimisticWHERE version = :v; 0 rows ⇒ retry (CAS)
  • Optimistic wins under low contention (no lock held across think-time); pessimistic wins under high contention / long critical sections.
  • App-side "read then write" without one of these is a bug at RC/RR !

Locking & 2PL

  • 2PL: a growing phase acquires locks, then a shrinking phase releases — never acquire after releasing. Guarantees serializability. Strict 2PL holds all X-locks to commit ⇒ prevents cascading aborts (standard).

Lock modes

ModeCompatible with
S (shared/read)other S
X (exclusive/write)nothing
intent (IS/IX)coarse marker for hierarchy
gap / next-keylocks a range ⇒ blocks phantoms

Granularity & escalation

  • row → page → table: finer = more concurrency but more lock overhead. Engines escalate to coarser locks under many-row txns — a latent concurrency cliff !
  • MVCC engines (PG) don't take read locks at all; writers still lock rows.

MVCC

  • Multi-Version Concurrency Control: each write creates a new row version stamped with txn id; a reader sees the newest version committed as of its snapshot. Readers never block writers, writers never block readers.
  • Visibility = "which versions can this snapshot see" (xmin/xmax vs snapshot's active-txn list).

The costs !

  • Version bloat: dead tuples accumulate; need garbage collection — Postgres VACUUM (and autovacuum). A long-running or idle-in-transaction txn holds back the GC horizon ⇒ tables bloat, indexes slow.
  • Update-heavy tables ⇒ index write amplification (each version indexed; mitigated by HOT updates).
  • Contrast with 2PL: MVCC pays storage + GC to buy lock-free reads; 2PL pays blocking to avoid versions.

Deadlocks

Indexing — B-tree & friends

  • B+tree is the default: balanced, high fan-out ⇒ height 3–4 for millions–billions of rows ⇒ point lookup in ~3–4 page reads. Leaves are linked ⇒ range scans are sequential & cheap. Keeps data sorted ⇒ serves ORDER BY, < > BETWEEN, prefix LIKE 'ab%'.

Composite & leftmost prefix !

INDEX (a, b, c) serves:
  WHERE a=?              yes
  WHERE a=? AND b=?      yes
  WHERE a=? ORDER BY b   yes
  WHERE b=?              NO  (skips a)
  WHERE a=? AND c=?      partial (a only)
  • Column order = access pattern. Put equality columns first, range/sort last.
  • Covering index (INCLUDE extra cols): query answered from the index alone — no heap/table fetch (index-only scan).

Selectivity / cardinality

  • Selectivity = fraction of rows a predicate keeps. Low selectivity (few rows) ⇒ index wins; matching a large fraction ⇒ a full scan is cheaper (random I/O per row beats one sequential pass) !
  • Rule of thumb: index helps below ~5–10% of the table. Low-cardinality columns (boolean, status) rarely benefit from a plain B-tree.

Clustered vs secondary

  • Clustered / index-organized: table rows are the B-tree leaves (InnoDB PK, SQL Server). One per table; PK order = physical order.
  • Secondary index stores the key + a row locator ⇒ a lookup pays a second hop (bookmark lookup) to the heap/clustered index.

B-tree vs LSM-tree

writesin-place, randomappend memtable → flush SSTables

  • LSM (RocksDB, Cassandra): sequential writes ⇒ high write throughput; reads check memtable + levels, using bloom filters to skip SSTables. Compaction is background write-amp + a latency-jitter source !
  • B-tree favors read-heavy / mixed OLTP; LSM favors write-heavy, high-ingest, time-series.

Storage & Physical Layout

  • The DB reads/writes fixed-size pages (4–16KB), not rows. The buffer pool / page cache holds hot pages in RAM; a cache miss = disk I/O — the unit that dominates cost estimation.
  • Heap-organized: rows wherever they fit; PK is just another index. Index-organized: rows live in PK order (fast PK range, slower secondary).

Crash recovery (ARIES)

  • Analysis (find dirty pages + active txns from last checkpoint) → Redo (replay all logged changes, repeat history) → Undo (roll back losers). WAL LSNs make redo idempotent.

Query Processing & Optimization

  • Pipeline: parse (AST) → bind/rewrite (resolve names, view expansion, simplify) → optimize (choose plan by cost) → execute (operator tree / iterators). The optimizer's output is a physical plan.

Cost-based optimizer

  • Enumerates plans, costs each from statistics: table size, column histograms, distinct counts, index clustering. Picks the cheapest estimated I/O+CPU.
  • Cardinality estimation is the hard part — errors compound multiplicatively across joins. Correlated columns + stale stats ⇒ wildly wrong row counts ⇒ bad plan ! Keep stats fresh (ANALYZE).
  • Rewrites: predicate pushdown, join reordering, subquery flattening, constant folding — all safe because algebra is closed.

Sargability !

  • Wrapping the indexed column kills the index: WHERE date(ts)=…, WHERE col+0=…, leading-wildcard LIKE '%x'. Rewrite as a range on the raw column, or add a functional/expression index.

CAP & PACELC

  • CAP: under a network Partition you must choose C (linearizable reads) or A (every node answers). "Pick two" is misleading — P is not optional in a real distributed system, so the live choice is C vs A during a partition.
PartitionCP doesAP does
client writereject / block (no quorum)accept, reconcile later
guaranteecorrect or unavailableavailable but maybe stale

PACELC — the fuller picture

  • If Partition → A or C; Else (normal ops) → Latency or Consistency. Most single-node ACID DBs are PC/EC; Dynamo/Cassandra are PA/EL; Spanner ≈ PC/EC (pays latency for consistency).
  • Even with no partition you trade sync-replication latency for consistency ! — CAP alone hides this.

Replication & Consistency (quick)

  • Leader-follower: writes to leader, replicated to followers; reads can fan out. Sync replication ⇒ no data loss on failover but higher latency; async ⇒ fast but a failover can lose the tail !
  • Replication lag breaks read-your-writes and monotonic reads — user writes to leader, reads a stale follower. Fix: read-from-leader-after-write, sticky routing, or version tokens.
  • Quorum (Dynamo): R + W > N guarantees read/write sets overlap ⇒ latest value seen. Sloppy quorum + hinted handoff trade consistency for availability.

Consistency spectrum

linearizable > sequential > causal > read-your-writes/monotonic > eventual. Moving up costs latency/availability. Causal is the strongest model an always-available system can provide.

Partitioning vs Replication

  • Replication copies the same data → availability, read throughput, locality. Partitioning (sharding) splits distinct data → capacity + write throughput. Orthogonal; production does both (shard, then replicate each shard) !
  • Horizontal = split by rows (every node has full schema, subset of rows) = "sharding". Vertical = split by columns (hot narrow cols vs cold blob).

Escalate before you shard

optimize queries → scale up → add read replicas → then shard. Sharding is a one-way door: it costs cheap joins, easy transactions, global indexes — permanently.

Two query classes

  • Names the partition key ⇒ single-shard, fast, linearly scalable. Doesn't ⇒ scatter-gather across every shard, bounded by the slowest, slower as shards grow ! Design the key so the dominant query is class 1.

Core tradeoff = locality vs uniformity. Range → time-series/BETWEEN; hash → even write spread.

Hot partitions

  • Write skew: monotonic key (timestamp, seq id) sends every insert to the tail shard under range partitioning.
  • Access skew (celebrity): one key read/written far more; hashing can't fix it — all their activity shares one key !
  • Fixes: high-cardinality evenly-accessed key (user_id > country > is_premium); hash away monotonicity; salt a known-hot key (bucket 0..9, key) (trades read fan-out for write spread); isolate whales via directory.

Consistent Hashing

  • node = hash(key) % N breaks on resize: N→N+1 remaps ~N/(N+1) of keys (10→11 nodes ⇒ ~91% move) ⇒ full reshuffle + cluster-wide cold cache !
  • Consistent hashing: hash keys and nodes onto one ring; a key is owned by the first node clockwise. Adding a node steals keys only from its clockwise neighbor — only ~K/N keys move.
ring wraps 0→MAX→0; key walks
clockwise → first node hit owns it.
add node ⇒ only its arc's keys move.

Virtual nodes

  • Few real nodes ⇒ lumpy ring; a leaver dumps all load on one neighbor. vnodes = many tokens/node (Cassandra ~256) ⇒ smooth distribution, spread a departing node's load over many peers, weight bigger boxes. Used by Dynamo, Cassandra, Riak.

  • Local (Cassandra, ES shards): insert updates same-shard index — trivially consistent; but "find status=X" fans out to all shards.
  • Global (DynamoDB GSI): lookup by term hits one partition; write may update an index partition on a different node ⇒ typically async / eventually consistent — index lags the table !
  • "Pay on write vs pay on read" — no free lunch.

Cross-Shard Operations

  • Anything spanning shards forfeits single-node guarantees. Query without the key ⇒ scatter-gather (tail-latency bound). Join ⇒ ship/repartition data over the network. Transaction ⇒ 2PC (blocks holding locks) or sagas (no isolation) !

Design so you don't have to

  • Co-locate: pick a key that keeps things you join/transact on one shard (order + lines by order_id) — Spanner interleaved tables, Vitess keyspaces. The partition key is the join & transaction boundary.
  • Denormalize to kill the join; keep a read model (CQRS/materialized view) for the cross-cutting query; accept eventual consistency via sagas for genuinely cross-entity flows.
  • Can't avoid analytics-across-all? Wrong system — push to an OLAP store via CDC.

2PC & 3PC (atomic commit)

Phase1 VOTE: coord--PREPARE-->parts
  each durably logs, replies YES/NO
Phase2 DECIDE: all YES->COMMIT
                any NO ->ABORT
  • Once a participant votes YES it's prepared/uncertain: gave up the right to abort, must hold locks until it hears the decision. Decision is final when the coordinator writes its commit record.
  • Blocking failure !: coordinator dies after votes but before the decision ⇒ prepared participants can't commit or abort — stuck holding locks. A peer that also voted YES knows nothing more.
  • 3PC adds a PRE-COMMIT round to remove blocking — but is unsafe under partitions (two sub-groups can decide differently), so ~never used.
  • Modern fix: back the commit decision with consensus (Spanner/CockroachDB run 2PC over Paxos/Raft) ⇒ a dead coordinator is replaced, decision survives.

Sagas & Compensation

T1 reserve → T2 charge → T3 ship → T4 X
compensate: C2 refund ← C1 unreserve
  • Multi-service txn as a sequence of local ACID txns; each Tₕ has a compensating Cₕ that semantically undoes it. No global lock, no prepared state.
  • Compensation ≠ rollback: rollback erases uncommitted changes (nobody saw them); compensation runs a new txn after the original committed & was visible — you don't un-charge, you refund. Must be idempotent; some actions aren't cleanly compensable.
  • Gives up isolation !: intermediate state is visible — use pending/reserved states + idempotency keys.
  • Sagas: cross-service, long-lived flows. 2PC (consensus-backed): short, tightly-coupled, need real atomic isolation.

Consensus, Raft & FLP

Consensus = agree on one value (leader, next log entry, commit outcome) despite crashes/lost msgs. Turns unreliable nodes into one replicated state machine.

PropertyMeaning
Agreementno two correct nodes differ (safety)
Validitydecided value was proposed (safety)
Terminationevery correct node decides (liveness)
  • Quorum = majority; any two majorities overlap ⇒ can't decide conflicting values. 5 nodes tolerate 2 failures.
  • Raft: terms (one leader each); randomized election timeouts break split votes; leader appends, commits once a majority persists; up-to-date vote rule keeps committed entries. Paxos = same guarantees, harder to reason about.
  • FLP !: no deterministic algo guarantees termination in a fully async net with 1 crash (can't tell crashed from slow). Attacks liveness, not safety. Escape via timeouts (partial synchrony) + randomization — safety unconditional, termination eventual.

Idempotency & Exactly-Once

  • Idempotent: applying N times = applying once. SET bal=100 yes; bal=bal+10 no. Makes retries safe.
  • Exactly-once delivery is impossible !: no ack ⇒ sender can't tell "msg lost" from "ack lost" ⇒ retry (at-least-once, dup risk) or don't (at-most-once, loss risk). No third option.
  • Get exactly-once effect: at-least-once delivery + idempotent processing.
INSERT INTO processed(key,result)
VALUES('req-9f3a',...)
ON CONFLICT(key) DO NOTHING;
-- 0 rows ⇒ replay, return stored result
  • Techniques: idempotency keys (Stripe), producer-id+seq dedup (Kafka), atomic dedup — write the marker in the same txn as the effect. Non-transactional effect (email, external API) ⇒ push idempotency downstream !

Consistency Models Spectrum

strict serializable  txn + real-time  most coord

  • Linearizable ≠ serializable !: linearizability = single object, real-time recency (no stale read after ack). Serializability = multi-object txns equal to some serial order — can return stale snapshot data. Both ⇒ strict serializable (Spanner, CockroachDB).
  • Stronger = more synchronous cross-replica agreement on the write path ⇒ higher p99 + refuse writes on the minority partition side. Pick the weakest model that's still correct.
  • Causal is the strongest model an always-available system can offer.

Session Guarantees & CRDTs

Per-session (cheap, no global coord)

  • Read-your-writes: your later reads see your write. Monotonic reads: never see an older value than you already saw. Monotonic writes: your writes apply in issue order. Writes-follow-reads: a reply orders after the message it replies to. All four ≈ per-session causal.

CRDTs

  • Merge is commutative + associative + idempotent ⇒ replicas converge with no coordination or conflict logic — order/dupes/grouping don't matter.
  • G-Counter: per-replica vector, increment own entry, merge = element-wise max, value = sum ⇒ concurrent increments both survive. OR-Set: tag each add with an id; remove deletes only observed tags ⇒ concurrent add/remove is "add-wins".
  • Convergence is free; you live with the merge semantics the type encodes !

OLTP vs OLAP & Star Schema

One axis: OLTP = few rows, many columns; OLAP = many rows, few columns. Everything else follows.

OLTPOLAP
storagerow storecolumn store
indexmany B-treesfew; zone maps / pruning
schema3NFdenormalized star
latencymssec–min
  • Star schema: central fact (large, append-mostly, numeric measures + FKs) surrounded by dimensions (small, descriptive). Denormalize dims — no concurrent writers ⇒ no update anomalies, and every join over a billion-row fact costs real time. Snowflake normalizes dims (more joins).
  • Columnar wins by reading less (touch only queried cols) + compressing better: RLE (value+run), dictionary (distinct→int code, filter on codes), delta/bit-packing. Don't run analytics on the OLTP primary — replicate to a columnar warehouse; layouts are physically incompatible !

★ Design & Review Checklist

Schema

  • ☐ PK on every table; surrogate unless a stable natural key exists; FK constraints declared (not just app-enforced).
  • ☐ Normalized to 3NF/BCNF by default; each denormalization has a documented reason + a sync mechanism.
  • ☐ NULLable columns intended; no =NULL, no NOT IN over a nullable subquery !

Transactions

  • ☐ Isolation level matches the invariant; read-modify-write uses atomic update / FOR UPDATE / version CAS — not bare read-then-write.
  • ☐ Write-skew invariants protected (SERIALIZABLE, guard row, or constraint).
  • ☐ Locks acquired in a consistent order; app retries serialization/deadlock errors.
  • ☐ No long-running / idle-in-transaction txns (locks + MVCC bloat) !

Indexing & queries

  • ☐ Composite index column order = equality-then-range/sort; covering where hot.
  • ☐ Predicates are sargable (no function on the column, no leading wildcard, no implicit cast).
  • ☐ Plan checked with EXPLAIN ANALYZE; est vs actual rows sane; stats fresh.
  • ☐ No unbounded result sets; pagination keyset-based, not OFFSET on deep pages.
