How to read & print

  • ! footgun / classic trap   ☐ reasoning step
  • Golden rule: test behavior, not implementation. A test that breaks on a refactor (same behavior) is a bad test.
  • Goal of tests: confidence to change — not proof of correctness.
  • Print: Ctrl/⌘-P → A4, margins None, scale 100%, background graphics on. 4 columns built-in.

Pyramid vs Trophy

  /\      e2e   (few, slow, flaky)
 /  \     integration
/____\    unit  (many, fast)   ← Pyramid

 [====]   integration  (fat)
 [==]     unit
 [=]      e2e
  __      static       ← Trophy

More tests lower down = faster + cheaper. ! An ice-cream cone (mostly e2e) = slow & flaky.

AAA + FIRST

test('adds two numbers', () => {
  const calc = new Calc();       // Arrange
  const sum = calc.add(2, 3);    // Act
  expect(sum).toBe(5);           // Assert
});
  • Fast · Independent · Repeatable · Self-validating · Timely.
  • One logical assertion; name = behavior under test. ! No test-order dependence.

  • Stub = state; mock = interaction verification.
  • ! Over-mocking → tests couple to impl & break on refactor. Don't mock what you don't own; mock at boundaries.

TDD: Red-Green-Refactor

RED    write a failing test
GREEN  simplest code to pass
REFACTOR clean up, tests still green
        ↻ repeat, small steps
  • Test-first = design pressure + built-in coverage.
  • ! The refactor step is not optional — that's where design happens.
  • TDD isn't slower once counting debug/rework; not mandatory everywhere.

BDD (Gherkin)

Feature: checkout
  Scenario: apply valid coupon
    Given a cart totalling 100
    When I apply coupon "SAVE10"
    Then the total should be 90

BDD = collaboration + living docs (ubiquitous language), not just a tool. Given-When-Then = AAA in prose.

Test Design Techniques

  • Equivalence partitioning: one case per class of input.
  • Boundary values: test min-1, min, max, max+1 — ! off-by-one lives here.
  • Decision table: combos of conditions → actions.
  • State transition: valid + invalid transitions.
  • Pairwise: cover all pairs, not full cross-product.

// property: encode∘decode == identity

  • Assert invariants over generated inputs, not fixed examples.
  • Shrinking finds the minimal failing case.
  • Fuzzing (AFL/libFuzzer) hammers parsers/security for crashes.
  • Mutation testing: surviving mutant = a missing assertion.

Testing Async / Concurrent

  • ! Never sleep(500) — use awaits, fake timers, latches, or poll-with-timeout.
  • Fake the clock for time-dependent logic.
  • Race bugs: stress-run + -race/TSan; controlled interleavings.
  • Make tests order-independent & idempotent.

Flaky Tests

Causes: timing/async · order dependence · shared state · network · time/randomness · animations.

  • ! Fix them, don't just retry — retries hide real bugs and erode trust.
  • Quarantine, then make deterministic (fake clock/network, isolate data).
  • Smells: fragile, eager, assertion roulette, mystery guest.

Testability & Test Data

  • Hard-to-test = bad design. Fix with DI, pure functions, seams, humble object.
  • Avoid statics/singletons/global state/direct time & random. !
  • Factories/builders for data; each test sets up + tears down its own (transaction rollback / truncate).
  • Legacy: characterization tests first, then break dependencies.

Testing in Production

  • Canary + feature flags → small blast radius, instant rollback.
  • Chaos engineering: inject failure on purpose (GameDays).
  • Synthetic monitoring + smoke-in-prod; shadow traffic; A/B.
  • Observability (metrics/logs/traces) = continuous testing.

☐ "How would you test X?" Playbook

  • ☐ Clarify the contract: inputs, outputs, side effects, failure modes.
  • ☐ Happy path + boundaries + invalid input + error paths.
  • ☐ Pick the level: pure logic→unit; with DB/API→integration; critical journey→one e2e.
  • ☐ Isolate deps with the right double (stub state, mock interactions).
  • ☐ Name each test by the behavior; one reason to fail.
  • ☐ Deterministic (no sleeps, fake clock/random); independent.
  • ☐ Cover the risk, not the line count; add a property test if invariants exist.
  • ☐ "It's flaky" → reproduce, find nondeterminism, fix the cause, don't retry.
