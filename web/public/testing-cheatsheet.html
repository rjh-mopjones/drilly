Why We Test — the Real Value

  • Tests are a change-enablement tool, not a correctness proof. Their value is the confidence to refactor and ship fast — a green suite is permission to change code.
  • Verification = "did we build it right" (matches spec). Validation = "did we build the right thing" (matches user need). Tests do verification; only users/PMs do validation !
  • Passing tests never prove absence of bugs — only presence of the behaviours you asserted. Dijkstra: testing shows the presence, not the absence, of bugs.
  • Cost-of-a-bug curve: a bug caught at code time costs ~1×; at QA ~10×; in production ~100×+. Fast feedback shifts detection left.
  • A regression test locks in a fixed bug so it can't silently return — the compounding asset that makes a suite worth more over time.

! "No time to write tests, we need to ship" — untested code is the thing that slows shipping next week. Frame tests as speed, not ceremony.

Pyramid vs Trophy

flowchart TD E["E2E — few

Pyramid (Cohn): mostly unit, fewer integration, fewest e2e. Trophy (Dodds): fattest layer is integration — "write tests that resemble how software is used." Both agree the anti-pattern is the ice-cream cone (mostly e2e/manual). Pick by blast radius: integration tests catch the wiring bugs unit tests can't, at a fraction of e2e cost.

Which level catches which bug

  • Wrong algorithm / edge case → unit.
  • Wrong SQL, bad migration, serialization mismatch, N+1 → integration ! (unit mocks hide these).
  • Broken deploy, auth flow, cross-service contract → e2e / smoke.

Rule: push each test to the lowest level that can still catch the bug — cheaper, faster, less flaky.

Anatomy of a Good Unit Test

AAA / Given-When-Then

test("applies 10% discount for gold tier", () => {
  const cart = makeCart({ tier: "gold", total: 100 }); // Arrange
  const out = applyDiscount(cart);                      // Act
  expect(out.total).toBe(90);                           // Assert
});

FIRST principles

  • Fast · Isolated (no shared state/order dependence) · Repeatable (no clock/network/random) · Self-validating (pass/fail, no eyeballing) · Timely (write near the code).
  • One logical assertion per test — not literally one expect, but one behaviour. A test asserting three unrelated things hides which broke.
  • Name = spec: method_condition_expectedResult. The name should read as a sentence when it fails in CI.
  • A unit is a unit of behaviour, not necessarily one class — a small cluster of collaborators is fine.

Test Behaviour, Not Implementation

The single most important rule. Assert on observable outputs / effects, never on private internals or call sequences a refactor could change.

// BAD — coupled to implementation !
expect(service._cache.size).toBe(1);
expect(repo.save).toHaveBeenCalledTimes(1);

// GOOD — coupled to behaviour
expect(await service.get("id")).toEqual(user);
expect(await repo.find("id")).toEqual(user); // real effect
  • Litmus test: "if I refactor internals but keep behaviour, does this test still pass?" If no → it tests implementation !
  • Over-asserting interactions (mockist over-reach) produces brittle tests that break constantly and get deleted — worse than no test.
  • Tests double as documentation: a reader learns the contract from behaviour-level tests, not from _privateHelper assertions.

Test Doubles — the Five

DoubleWhat it does
Dummyfiller passed but never used (satisfy a signature)
Stubreturns canned answers — feeds state
Spya stub that records how it was called
Mockpre-set with expectations — verifies interactions, fails if unmet
Fakeworking lightweight impl (in-mem DB/repo)
  • Stub vs Mock: stub = state verification (assert the result). Mock = interaction verification (assert the call happened). Prefer state.
  • Fake when you need real behaviour cheaply (in-memory repo enforcing uniqueness) — best fidelity-to-cost for integration-ish tests.
  • Doubles require dependency injection: pass collaborators in, don't new them inside — untestable otherwise.

Mocking — When & How Much

  • Mock at architectural boundaries you own: DB, payment gateway, clock, network — the slow/nondeterministic edges. Use real objects for your own pure domain logic.
  • ! Don't mock what you don't own. Mocking a third-party lib bakes in your assumption of its behaviour; the mock stays green while the real lib changes. Wrap it in a thin adapter you own and mock the adapter, or use a fake/contract test.
  • Over-mocking = every collaborator stubbed → the test asserts your code calls the code you wrote, i.e. it tests the mock wiring, not behaviour. Rewrite to state verification with real collaborators + one edge stubbed.

Schools

  • London / mockist: mock all collaborators, verify interactions, outside-in.
  • Detroit-Chicago / classicist: real collaborators, mock only awkward edges, verify state. Default classicist — fewer brittle tests.

Killing Nondeterminism (Time & Random)

The two commonest flakiness sources. Never read the wall clock or Math.random() directly in logic under test.

// Inject the clock / seed — don't reach for globals
function isExpired(token, now = Date.now) {   // seam
  return token.exp < now();
}
// test: pass a frozen now
isExpired(t, () => 1_000);        // deterministic

// libs: jest.useFakeTimers(); jest.setSystemTime(...)
// seeded RNG for property/data gen
const rng = seededRandom(42);
  • Fake timers also let you advance time to test debounce/retry/timeout without real waiting.
  • Same seam for UUIDs, now() in DB defaults, and time-zone-sensitive formatting !

TDD — Red / Green / Refactor

  1. Red: write the smallest failing test for the next behaviour. Watch it fail (proves the test can fail).
  2. Green: simplest code to pass — even hardcoding. Fake it till you make it.
  3. Refactor: clean up with the safety net green. Not optional ! — skip it and TDD just produces messy code faster.
  • Test-first buys: a spec before implementation, guaranteed-testable design (you feel bad seams early), and no "test written to match the bug."
  • Triangulation: add a 2nd/3rd example to force generalising past a hardcoded return.
  • Inside-out (Detroit): build domain core first. Outside-in (London): start at the entry point, mock downward, discover collaborators.
  • TDD a bug fix: write the failing test that reproduces the bug first — it's your regression guard and done-signal.

BDD / Specification

  • BDD = TDD in business language: Given-When-Then scenarios non-engineers can read (Gherkin / Cucumber / SpecFlow). Given/When/Then maps 1:1 to Arrange/Act/Assert.
  • Value: shared vocab + executable acceptance criteria — the spec is the test. Cost: a step-definition glue layer that rots if scenarios drift ! Use for acceptance flows with real stakeholders; don't force Gherkin onto unit tests.

Coverage — Use & Abuse

MetricWhat it measures
Line/statementlines executed — weakest
Brancheach if/else side taken — better
Condition/MC-DCeach boolean sub-condition — safety-critical
Pathcombinations of branches — explodes
  • ! Coverage is a find-the-gaps tool, not a quality target. 100% coverage with zero assertions catches nothing — execution ≠ verification.
  • Goodhart: mandate a % and people write assertion-free tests to hit it. Use coverage to spot untested branches, then judge whether they matter.
  • Reasonable floor ~70–80% branch on core logic; don't chase the last 5% into getters/generated code.
  • Mutation score tells you what coverage can't (next card).

Property-Based & Fuzz Testing

Attack the blind spot of example tests: the inputs you didn't think of. State a rule for all inputs; let the framework hunt counterexamples and shrink them to a minimal repro (fast-check, Hypothesis, QuickCheck, jqwik).

fc.assert(fc.property(fc.array(fc.integer()), (xs) => {
  expect(reverse(reverse(xs))).toEqual(xs);   // round-trip
}));

Property patterns

  • Round-trip: decode(encode(x))===x (highest value).
  • Idempotence: f(f(x))===f(x) (normalise, dedupe).
  • Oracle/model: fast impl vs slow reference.
  • Metamorphic: relate inputs when no oracle (sin(x)===sin(x+2π)).
  • Invariant: sort(xs) is ordered and a permutation of xs.

Fuzzing: coverage-guided random/malformed bytes at parsers & untrusted-input paths (libFuzzer, AFL, go test -fuzz) to find crashes/hangs/UB. ! Shrinking + a saved seed make failures reproducible — not flaky.

Mutation Testing

  • Measures test-suite quality, not code coverage. The tool mutates your source (>→>=, +→-, delete a line, negate a condition) and reruns tests.
  • Killed mutant = a test failed → good, tests caught the change. Survived mutant = all green despite the bug → a gap your coverage hid !
  • Mutation score = killed / total. The honest answer to "do my assertions actually assert anything?" — the thing 100% line coverage lies about.
  • Tools: Stryker (JS), PIT (Java), mutmut/cosmic-ray (Py). Cost: slow (N× reruns) → run on core modules / nightly CI, not every push.
  • Equivalent mutants (semantically identical change) can't be killed — the noise floor; don't chase 100%.

  • Report percentiles (p95/p99), not averages ! — the mean hides the tail users feel. Track throughput (RPS), latency dist, and error rate together.
  • Define SLO/SLA targets first; a load test with no pass/fail threshold is a benchmark, not a test.

Testing Async & Concurrent Code

  • ! Never sleep(n) to wait — the #1 cause of slow, flaky tests. Sleep is a bet the op finishes in n ms; it loses under CI load.
  • Instead await the promise, poll a condition with a timeout (waitFor(() => cond)), or use an explicit signal/callback.
  • Fake timers to fast-forward debounce/retry/backoff deterministically.
  • Race conditions: hard to reproduce by construction. Reduce shared mutable state, inject a controllable scheduler, or run a race detector (go test -race, TSan). A stress loop (run 1000×) surfaces intermittency.
  • Assert on final observable state, not on intermediate timing that varies run to run.

Integration Testing — Real Deps

  • Catches what unit tests structurally cannot: real SQL/migrations, ORM mapping, serialization, transaction boundaries, connection config, N+1 queries !
  • Testcontainers > in-memory DB (H2/sqlite): run the real Postgres/Redis/Kafka in a throwaway container. In-mem DBs have subtly different SQL dialects and lull you into false green.
  • Isolation on a shared DB: wrap each test in a transaction and roll back, or truncate/reset between tests. Never let test order matter.
  • External 3rd-party APIs: don't hit the live service — record/replay (VCR/WireMock) or run their sandbox; add a contract test to catch real drift.

Contract testing (Pact)

  • Microservice integration without a full e2e matrix: consumer writes expectations vs a mock provider → generates a pact; provider replays it in its CI to prove it still satisfies every consumer independently (no shared env, no coordinated deploy).
  • Catches breaking API changes (renamed field, changed type) at build time. Consumer-driven — encodes only what consumers use. ! Verifies shape/interaction, not the provider's business logic — pair with the provider's own tests.

E2E / UI Testing

  • Exercises the whole stack via the real UI/API — highest confidence, highest cost. Keep a handful of critical-path journeys (login, checkout), not a full regression suite !
  • Selectors: use data-testid / roles / accessible text. Never CSS-class or XPath position — they break on any restyle.
  • ! No hard sleeps — use auto-waiting / retrying assertions (Playwright/Cypress do this natively).
  • Page Object Model: encapsulate a page's selectors + actions in one class so a UI change is a one-file fix.
  • Auth: log in once via API and inject the session/token — don't drive the login form in every test.

CI & Test Automation

  • Stage by speed: static+unit on every push (seconds); integration on merge; e2e/smoke on deploy (nightly for the slow rest). Fail fast — cheapest tests first.
  • Every test runs in CI on a clean machine — "passes on my laptop" is not passing. Pin versions; provision deps via containers.
  • Test data: build objects via factories/builders (Object Mother), not giant shared fixtures. Each test creates and tears down its own data → isolated, parallel-safe.
  • Quarantine flaky tests (tag + track), don't blanket-retry green — retries mask real races and rot the suite's trust !
  • Gate merges on green + coverage-didn't-drop; block on -race/lint where relevant.

Testability & Design for Test

  • Hard-to-test code is a design smell, not a testing problem. If you're fighting to test it, the design is too coupled.
  • Dependency injection: pass collaborators in → swap for doubles. Reaching for globals/singletons/new inside logic kills testability !
  • Humble Object: push logic out of hard-to-test shells (UI, framework callbacks) into plain testable functions; leave the shell dumb.
  • Pure functions are easiest to test — same input, same output, no setup. Push side effects to the edges (functional core, imperative shell).
  • Seam: a place to substitute behaviour without editing the code under test (a param, interface, env). Design them in deliberately.

Testing in Production & Observability

  • Pre-prod tests can't cover real traffic, data, and scale. Complement (not replace) with prod techniques:
  • Canary / progressive rollout: ship to 1% → watch metrics → widen. Feature flags: decouple deploy from release, kill-switch on regression.
  • Synthetic monitoring: scripted critical-path checks running against prod continuously (e2e that never sleeps).
  • Shadow / dark traffic: mirror real requests to the new version, compare, don't serve.
  • Requires observability — logs, metrics, traces, SLOs — so you can detect the regression tests missed. Testing in prod without monitoring is just prod bugs !

Test Data — Fixtures, Factories, Builders

Test data is part of the spec, not offscreen setup. The test should read as a sentence: "given a user with an expired sub, when they check out, then…". State only what the assertion depends on; let defaults handle the rest.

PatternIsWeakness
Fixturestatic baseline (rows/files/beforeEach)rots when shared/large
Object Mothernamed exemplars: Mother.premiumUser()method explosion as variants grow
Factorygenerates objects w/ defaults, overridablemagic defaults hide too much
Builderfluent chain of only what mattersverbose per object
User u = aUser()
  .withSubscription(expired())  // only what the test cares about
  .build();                     // everything else = safe default
  • Default = factory (esp. DB-backed); layer a builder for readable one-offs; keep an Object Mother for a few canonical cases; plain fixtures only for small stable baselines.
  • Minimal + realistic: set only the fields the behaviour touches, meaningfully. All-"test"/zero data can accidentally satisfy a condition and hide bugs !
  • Unique defaults (random email/UUID) in the builder prevent inter-test collisions for free — a parallelism win.
  • Add a required column → fix one default in the factory, not 400 tests. That indirection is what lets a suite survive years of schema churn.

Test Isolation & Parallelism

Isolation = a test's result is independent of what else ran, in what order, in parallel or not (the I & R of FIRST). Non-negotiable: it buys trust (a red means that test broke) and parallelism (you can only shard state-free tests).

Keeping DB/integration tests isolated

StrategyNote
Transaction rollbackfastest; begin → test → rollback. Can't test code that commits
Truncate / clean-slateworks when code commits; truncate touched tables in FK order
Unique data per testuser-{uuid}, per-test tenant → never collide, high parallelism
Per-worker DB/schemaeach shard gets its own DB → no cross-shard contention
  • ! The canonical bug: "passes alone, fails in the suite" = broken isolation — a mutated singleton, a leftover row, a global cache, a fixed ID that collides.
  • Debug it: run in random order (pytest -p randomly, --shuffle) to confirm order dependence, then bisect to find the poisoner, then fix ownership — never "run in this order."
  • ! Mystery guest: a test asserting on user_42 from a distant fixture can't be understood in isolation. Create the relevant data inline so the setup is the spec.
  • Combine for parallel CI: per-worker DB + rollback-per-test + unique IDs + unique Kafka topic/consumer-group per test.

Secrets & config in tests

  • Container-generated throwaway credentials; inject config (never hardcode); fake keys in a test profile — safe to commit only because they're fake. ! Never point tests at prod or commit a real sk_live_….

Security Testing — SAST / DAST / SCA

Layer cheap+early ("shift left") with deep+late — each tool has an opposite blind spot; stacking narrows the gap but never closes it.

TypeWhat / weakness
SASTstatic source scan; sees all code, can't judge reachability → false positives
DASTattacks running app black-box; only tests paths it reaches → false negatives
IASTagent instruments running app → code precision + runtime confirmation
SCAscans deps vs known CVEs (Dependabot, Snyk, Trivy)
Pentestskilled humans chain weaknesses; deep but point-in-time
  • SCA is often highest-ROI: most of your code is other people's; attackers scan for known CVEs at scale (Log4Shell). Fully automated, fix = bump the version. Fail CI on high/critical.
  • ! "We run all four → we're secure" is false: business-logic flaws (refund yourself twice), cloud/IAM misconfig, and every commit since the last scan are unverified surface. Security is a continuous property, not a test you pass.

Testing the two dominant API bugs

  • Broken access control (IDOR/BOLA) — highest-value API test: user A can't touch B's resource by changing an ID → 403, not 200 with B's data. Also test vertical escalation, missing/forged token → 401.
  • Injection — send '; DROP TABLE users;--; assert it's treated as a literal (parameterised), table survives, no 500. OWASP Top 10 is the checklist.

Specialized Types — Fit & Traps

Each is a lens for a failure mode functional tests structurally miss. Senior instinct: match lens to risk, don't cargo-cult all of them.

  • Accessibility (a11y): axe-core/Lighthouse in CI catch only ~30–40% (alt text, contrast, ARIA, labels) ! The rest — keyboard-only nav, focus order, screen-reader sense, focus traps — needs a human + assistive tech. Automated = a floor, not compliance.
  • Snapshot: serialize output, diff vs stored file. Asserts "same as last time," not "correct" ! Trap = reflex jest -u to mass-update until green → enshrines bugs. Keep tiny, human-readable, reviewed as a real diff.
  • Visual regression: screenshot + diff vs baseline; catches layout/overlap DOM assertions miss. Flaky reputation is a config problem — use a stable container renderer, mask dynamic regions, disable animation, perceptual threshold (not raw-pixel).
  • Exploratory: structured, unscripted human investigation — time-boxed session-based testing with a written charter, not "clicking around." Finds unknown-unknowns automation never can (automation only re-checks what you already knew). New features deserve an exploratory pass before you know what to automate.
  • Localization (i18n/l10n): catches hardcoded strings, text expansion (German ~30–40% longer → overflow), date/decimal/currency formats, RTL mirroring, encoding/mojibake. Test with pseudo-localization ([!!! Ĉħĕĉķŏŭţ !!!]) without real translators.

Risk-Based Strategy — Spend Where It Hurts

Testing is risk management under a budget, not a quest for certainty. Inputs are infinite; every strategy is an allocation: where does a test buy the most reduced risk per unit cost? Risk = likelihood × impact.

        IMPACT
  high | test solidly   | TEST HARDEST    |
       | (rare+critical)| (payments,auth) |
  low  | minimal/smoke  | light checks    |
       | (static footer)| (cosmetic UI)   |
       +------------------------------------ LIKELIHOOD
            low                  high
  • The senior signal is using this to justify not testing something: "no E2E for the admin export button — low traffic, a break costs minutes" is a stronger answer than "test everything."
  • A strategy explicitly decides what NOT to test and why. Coverage % is a floor, not a strategy !
  • Push each behaviour to the lowest level that can verify it; reserve slow/flaky E2E for the few money paths. Ask "what's the cheapest test that fails if this breaks?"
  • Apply the pyramid/trophy logic, not the shape dogmatically — I/O-bound services weight integration heavier.

"How Would You Test X" — Playbook

Interviewers score systematic enumeration, not one exotic case. For any "how would you test X" walk: happy path → boundary/edge → error/failure → security/auth → concurrency → non-functional — and assign each a level.

Login / auth

  • Happy: valid creds → session/token. Sad: wrong pw, unknown user — same generic error (no user-enumeration leak) !
  • Security = the heart: rate-limit/lockout, token expiry/rotation/invalidate-on-logout, forged token → 401, passwords hashed+salted (verify you can't read plaintext), CSRF, session fixation.

Rate limiter

  • Boundary: 100 ok, 101 → 429 (off-by-one). ! Inject a fake clock, never sleep(60s), to test window rollover.
  • Fire N parallel at the boundary → exactly the limit passes (atomic counter). Per-key isolation; shared Redis for distributed.

Shopping cart

  • Ops + boundaries (qty 0/neg/max, same item twice → merge), money (tax, coupons valid/expired/stacked, rounding — minor units, never floats).
  • Sneaky real bugs: guest cart merges with saved cart on login; price/stock changes between add and checkout. Logic → unit, persistence/merge → integration, one E2E.

Payments

  • Idempotency (double-submit ≠ double-charge) + concurrent capture/refund races are the hard part — test hardest & lowest. State machine: reject every illegal transition. Contract test the gateway.

★ Test Review Checklist

Behaviour, not implementation

  • ☐ Asserts observable output/effect — survives an internals-only refactor !
  • ☐ No assertion on private fields, call counts, or internal call order unless the interaction is the contract.

Determinism

  • ☐ No wall-clock / random / network / filesystem in a unit test — seams injected.
  • ☐ No sleep() — awaits or polls a condition with timeout !
  • ☐ No order- or shared-state dependence; runs isolated & in parallel.

Doubles

  • ☐ Mocks only at owned boundaries; not mocking third-party libs directly !
  • ☐ State verification preferred over interaction; not over-mocked.

Shape

  • ☐ One logical behaviour per test; name reads as a spec on failure.
  • ☐ Clear AAA; no logic/branches/loops in the test body.
  • ☐ Boundary + edge cases covered, not just the happy path.
  • ☐ Test can actually fail — seen red at least once (mutation-check the critical ones).
