One feature, two stores, one definition. Offline keeps full history for point-in-time training; online keeps the latest value for ms serving. The online store is materialized from the offline computation, never a second independent write — that is how you dodge skew at the storage layer.

Feature = First-Class Artifact

A feature is not a column — it is a named, owned, versioned artifact keyed by entity + timestamp, with a definition, an owner, docs, and lineage.

  • entity + timestamp key ! — "value of txns_7d for user=42 as of T". The timestamp is what makes point-in-time joins and reproducibility possible; entity-only keys leak the future.
  • Definition vs materialised values: the transform logic is versioned separately from the rows it produced. A model pins a definition version.
  • Ownership: a feature has an on-call owner, freshness SLA, and a contract — orphaned features rot silently.
  • Feature group / view: features sharing an entity + source, materialised together (one join, one freshness).

Lifecycle

idea → define → backfill history → register (discoverable) → serve online+offline → monitor → version on change → retire (models rebind or stay pinned).

! Every team re-deriving the same feature = N subtly different definitions = N skew sources. Register & reuse.

Batch Feature Pipelines

Scheduled Spark/SQL/dbt job over bounded partitions → materialise feature rows to the store. Freshness hours–days; cheap; the source of truth that streaming must match.

Non-negotiables

  • Idempotent ! — re-running a date must overwrite, not append. Use partitionOverwrite / MERGE on (entity, feature_date), never blind INSERT (double-counts on retry).
  • Partition by date — prune scans, enable clean backfills, isolate a bad day.
  • Backfill = same transform over history, point-in-time correct. One deterministic function drives daily runs and backfills — two code paths = skew.
  • Full vs incremental refresh: incremental (only new partitions) for append-only; full recompute when the definition or upstream history changes.
# ONE transform, reused for daily + backfill
feats = transform(events)            # deterministic
feats.write.mode("overwrite") \
  .option("partitionOverwriteMode","dynamic") \
  .partitionBy("feature_date").save() # idempotent per day

! Job succeeded but model degraded → suspect schema change, null spike, or upstream late data, not the code.

Streaming Feature Pipelines

Standing query over an unbounded log. Kafka topic keyed by entity → stateful processor (RocksDB state) → upsert latest value into online KV. Freshness = seconds.

BatchStreaming
inputbounded partitionunbounded log
engineSpark/dbt/SQLFlink / Spark SS / Kafka Streams
timepartition "complete"event-time + watermark
costcheap, periodicalways-on, pricier
usedaily aggregates, trainingfraud, real-time recs, pricing

Decision rule

Start every feature as batch. Promote to streaming only with evidence (offline experiment shows fresher features lift the metric). Streaming ~triples ops surface + adds a skew path. Need it when the signal is recent-behaviour-dependent (txns_5m), the decision is real-time high-stakes, or session cold-start.

# count txns in trailing 5m, per user
stream.keyBy(user)
  .window(Sliding(5m, 1m))   # event-time
  .aggregate(count)          # -> upsert online KV

! Engine choice: Flink for true event-time + low-latency stateful; Spark SS if already on Spark (micro-batch); Kafka Streams for a library, no cluster.

Windows, Event-Time & Watermarks

Event-time vs processing-time !

  • Event-time = when it happened (payload ts). Processing-time = when the engine saw it (wall clock).
  • Default event-time for anything trained on or replayed. Processing-time is nondeterministic → replays give different numbers → backfills & PIT correctness break → instant skew vs batch.

Windows

TypeShape / use
Tumblingfixed, non-overlapping; each event in one (5-min blocks)
Slidingfixed size, smaller step, overlapping (last 5m every 1m)
Sessiongap-bounded (ends after 30m idle) — user sessions

Watermark

Moving assertion "no events older than T still expected." Decides when to close a window and how long to hold for late data. ! It does not stop lateness — it bounds your patience, trading completeness for latency. Wider watermark = more complete, higher latency + memory.

Dual-write problem !

Computing the feature independently into each store lets them diverge (one write fails, different code, different time) = storage-layer skew. Fixes:

  • Compute once, materialise online FROM offline — online is a subset of offline by construction.
  • One definition, two runners — same DSL/code drives both engines.
  • Reconciliation monitor — diff a sample of online vs offline, alert on delta.

TTL / freshness: online rows expire; a stale online value with a fine offline value ⇒ materialisation job lagging. Online can't keep full history (cost/latency) — it holds current, offline holds the timeline.

Point-in-Time Correctness

Join each label to the feature value known as of the label's timestamp — never the latest. Using latest values leaks post-decision information (the churn is the login collapse you joined).

-- labels(entity_id, label_time, y)
-- feature_history(entity_id, event_time, value)
SELECT l.entity_id, l.label_time, l.y, f.value
FROM labels l
LEFT JOIN LATERAL (
  SELECT fh.value
  FROM feature_history fh
  WHERE fh.entity_id = l.entity_id
    AND fh.event_time <= l.label_time   -- no peeking !
  ORDER BY fh.event_time DESC
  LIMIT 1                              -- latest known then
) f ON true;
  • Correctness lives in two clauses: event_time <= label_time and ORDER BY event_time DESC LIMIT 1.
  • Add a lower bound event_time >= label_time - 30d to also match serving's max staleness.
  • Time-travel (Delta/Iceberg VERSION AS OF) regenerates the exact table state; a PIT/as-of join aligns per-row timestamps. Use both.

! 0.98 AUC offline, dies in prod = classic leakage from a latest-value join.

Train/Serve Skew — the #1 Bug

The feature is computed differently in training vs serving, so the model scores on a distribution it never trained on. No error thrown; quality quietly drops.

Sources

  • Two code paths (notebook pandas vs online service) !
  • Two data sources / different freshness (batch table vs live event)
  • Time misalignment (latest value in train, trailing window at serve)
  • Different missing-value handling in each path

Fixes (best last)

  • One shared transform / feature store definition — physically the same code.
  • Log-and-wait gold — log the exact feature values served online, wait for labels, train on the logged values. Training then matches serving by construction, whatever the offline path does.

Detect (it throws no error)

Compare serving-input stats to training stats (TFDV skew detection); reconcile online vs offline samples; watch feature distributions at the pipeline, not just model metrics.

Data Validation for ML

Treat incoming data as untrusted; gate it before training and before serving. Moves detection upstream (named failed expectation) vs downstream (diffuse metric drop weeks later).

Four check categories

KindExample
Schemaage int, present, in [0,120]; no extra cols
Missing / cardinalityemail null-rate <1%; id unique; ~50 categories not 1 or 5M
Distribution vs refamount mean/quantiles within X% of baseline — catches $→¢ unit flip !
Cross-fieldend >= start; total == sum(items)
  • Tools: Great Expectations (suites), TFDV (ML schema + skew/drift), Pandera (typed dataframes), dbt tests (SQL models).
  • Gate = pass / block / quarantine + alert — not a warning nobody reads !
  • Data contract: enforced schema+semantics agreed with the upstream producer.

! "Loads without error" ≠ valid — the worst data loads fine and is subtly wrong.

Missing, Late & Duplicate Data

Golden rule !

Whatever you do to a missing value — impute, flag, drop — do it identically in train and serve. This is the most-violated rule in production ML.

  • Compute imputation stats (mean/median/mode) on the training set only, persist them, reuse the exact constants at serve. Per-batch means leak/skew.
  • Add a missingness indicator (was_null) so the model learns from absence, not just the fill.
  • Implement in one shared transform, not two copies.

Late / out-of-order

Key on event-time; watermark + reprocessing window (allowed lateness) to re-emit updates. Late data systematically undercounts the freshest windows — the ones the model leans on !

Duplicates

At-least-once delivery duplicates. Dedup by idempotency key (event_id) so a replay is a no-op. Exactly-once = effect applied once, not delivered once.

Label Quality & Management

  • Label noise: random dilutes (needs more data, lower ceiling); systematic (a class/slice consistently wrong) biases — no data volume fixes it !
  • IAA, not % agreement ! — at 95% prevalence two raters agree ~90% by chance. Use Cohen's kappa (2 raters) / Fleiss' kappa (many), chance-corrected.
  • Low agreement usually = ambiguous task, fix the guidelines, don't blame annotators. Ambiguity is the enemy.
  • Reconcile: consensus / majority vote, then adjudication (expert resolves disagreements).
  • Gold set: expert-verified items to score annotators + measure noise. Noise in test labels blinds your metrics.
  • Version labels — definitions drift ("spam" 2024 ≠ 2026); pin the label version a model trained on.
  • Label leakage: target or a post-outcome proxy sneaks into features → fake accuracy, prod collapse.

Data & Feature Versioning

Version the inputs so a run is reproducible months later. Three distinct things (confusing them is a classic fail):

  • Data — the bytes/tables.
  • Feature definitions — the transform logic.
  • Training-set snapshot — the exact (features + labels) rows a model saw.

Reproducible = code SHA + data version + feature-def version + label version + config, pinned together.

Pointer (DVC/lakeFS)Table format
whatgit holds a hash, bytes in object storeimmutable Parquet + txn log
givesdata follows code commitsACID, time travel, schema evolution
toolsDVC, lakeFSDelta, Iceberg, Hudi
  • Time travel ≠ backups (queryable history, different retention). SELECT ... VERSION AS OF 42 regenerates an exact training set.
  • Schema evolution: additive is safe; dropping/narrowing a column a feature reads silently breaks it !

Lineage & Reproducibility

  • Lineage traces how a dataset was produced and which model consumed it: feature → source columns, model → exact training snapshot.
  • Versioning answers "what data"; lineage answers "how & who" — together: "rebuild exactly what model v7 saw."
  • Uses: impact analysis (this upstream column changed — which features/models break?), audit, debugging a bad model back to its inputs, compliance (GDPR: where did this PII flow?).
  • ! Versioning the model artifact alone is not reproducible — without the data + feature logic that produced it, you cannot rebuild or explain it.
  • Model registry / experiment runs (MLflow) = MLOps primer; this side owns the data provenance.

Big-Data & Deep-Learning Data

Feature engineering at scale (Spark)

  • Wide transforms trigger a shuffle — the cost centre. Watch join/key skew (one hot key → one straggler task) !; salt or broadcast-join small sides.
  • Columnar Parquet; partition + predicate pushdown; sample for dev iteration.

DL input pipelines

  • tf.data / PyTorch DataLoader: parallel load, prefetch, cache, num_workers.
  • Shard to sequential formats (TFRecord / WebDataset) — millions of tiny files kill throughput.
  • Augment train-only — never on val/test !
  • ! The input pipeline is often the bottleneck: a starved GPU sits idle. Profile and keep the GPU fed.

Ingestion & Integration

  • CDC (Debezium → Kafka) streams DB row changes without hammering the source — the clean way to get operational data into the lake.
  • Batch ingest (nightly extract) vs streaming ingest (events/CDC): match to the feature's freshness need.
  • Medallion: bronze raw → silver cleaned/validated → gold features. Validate at the bronze→silver boundary (the ingest contract) !
  • Schema-on-read flexibility vs schema-on-write guarantees — ML wants a contract, so enforce schema early.
  • Idempotent, replayable ingestion; capture ingest timestamp separately from event-time for lineage & debugging.

Governance, Privacy & PII

  • ! A model can memorise PII — deleting the source row does not untrain it. Right-to-erasure (GDPR/CCPA) is a real design constraint, not a delete query.
  • Minimise / anonymise / hash / tokenize before features; pseudonymise identifiers.
  • Consent & retention: track lawful basis + purpose; expire data on schedule.
  • Access control on features — sensitive features (income, health) gated; audit reads.
  • Lineage answers "where did this subject's data flow" for a deletion/audit request.
  • Differential privacy / aggregation where individual rows are too sensitive to expose.

Pipeline Reliability & Monitoring

  • ! A stale feature = silent model decay. Monitor freshness (age of newest value) with an SLA + alert, not just job success.
  • Monitor at the pipeline, upstream of model metrics: null-rate spikes, distribution shift, row-count anomalies, cardinality collapse/explosion.
  • Alert on late / failed / null-spiking features; page the feature owner.
  • Safe backfills: idempotent, partition-isolated, PIT-correct — a re-run must not double-count or leak future.
  • "Job succeeded" ≠ "data correct" — SLAs on data, not just on the DAG being green.
  • Reconciliation: periodic offline↔online diff to catch materialisation drift.

Cost, Scale & Storage

The triangle

freshness ⟷ latency ⟷ $ — you pick a corner per feature.

  • Materialise (precompute, store) for hot/reused features: fast reads, storage + staleness cost.
  • Compute-on-read for rarely-used features: always fresh, slow, no storage — but risks train/serve skew if the two paths differ.
  • Batch beats streaming whenever hourly/daily is fine — streaming ~triples ops cost. Only pay for freshness that moves the metric.

Storage

  • Offline: columnar Parquet on object store, partitioned, tiered to cold. Table format for ACID + time travel.
  • Online: KV (Redis/DynamoDB), latest value only + TTL — history there is unaffordable and unneeded.
  • Compression + partition pruning + retention tiers are the main levers ! unbounded feature history quietly dominates the bill.

★ Design & Review Checklist

Consistency / skew

  • ☐ One transform (or one feature-store definition) feeds train and serve; no second independent write to the online store !
  • ☐ Missing-value / imputation policy identical offline & online, stats frozen from training.
  • ☐ Log served features and train on them where skew risk is high (log-and-wait).

Time correctness

  • ☐ Training join is point-in-time (event_time <= label_time), never latest-value.
  • ☐ Streaming features key on event-time with a watermark; windows match the batch definition.

Pipeline hygiene

  • ☐ Batch jobs idempotent (overwrite/merge per partition); backfills can't double-count or leak future.
  • ☐ Dedup by idempotency key; late-data / reprocessing window defined.

Gate & provenance

  • ☐ Validation gate (schema + distribution + missing/cardinality) blocks/quarantines before train & serve.
  • ☐ Data + feature-def + label versions pinned; lineage lets you rebuild exactly what the model saw.
  • ☐ Freshness SLA + distribution monitoring at the pipeline, alerting the owner.
  • ☐ Labels: guidelines + gold set + kappa threshold + adjudication + versioning; no label leakage.
  • ☐ PII minimised/anonymised; erasure & retention path exists.
