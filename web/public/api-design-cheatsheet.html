Design Principles & the Contract

  • An API is a contract, not code: once a client depends on a field/status/shape, it's frozen. Design the surface deliberately — you can add, rarely remove !
  • Least astonishment: same verb/status/naming everywhere. createdAt here and created there = "inconsistent" bug report.
  • Hide internal models: expose a DTO shaped for the client, never your DB rows. Coupling the wire to the schema means every migration is a breaking change !
  • Postel's law ("be liberal in what you accept") — now contested: strict input validation catches bugs early & blocks injection. Be liberal on unknown fields (ignore them), strict on known ones.

REST & Resource Modeling

  • Resources = nouns, plural collections: /v1/orders, /v1/orders/{id}. Verbs live in the HTTP method, not the path ! (/getOrder is RPC-in-disguise).
  • Statelessness: every request carries its own auth/context; no server session between calls → horizontal scale + any node serves any request.
  • Nest one level max for ownership: /posts/{id}/comments. Deeper (/users/x/posts/y/comments/z) is brittle — link by id instead !

Non-CRUD actions

  • Model state transitions as sub-resources or controller verbs: POST /orders/{id}/cancel, POST /posts/{id}/publish. Pragmatic; still noun-ish.
  • Or model the state as a resource: PUT /orders/{id}/status {"state":"cancelled"}.

Richardson Maturity: L0 single endpoint/RPC → L1 resources → L2 HTTP verbs+status (most "REST" APIs) → L3 HATEOAS (hypermedia links; rarely fully built).

HTTP Methods — Safe & Idempotent

MethodSafeIdem-potentBody
GETyesyesno !
HEADyesyesno
POSTnonoyes
PUTnoyesfull
PATCHnono*delta
DELETEnoyesopt
  • Safe = no observable state change (cacheable, prefetchable). Idempotent = N identical calls = same effect as 1.
  • PUT replaces the whole resource (send all fields; omitted = cleared). PATCH applies a partial delta (JSON Merge Patch RFC 7386 / JSON Patch RFC 6902).
  • *PATCH can be idempotent (set absolute value) or not ({"balance":"+5"}) — depends on the delta semantics !
  • GET must have no side effects and generally no body — proxies/caches may drop it, and prefetchers will fire it !

Request / Response Payloads

  • Pick one case & keep it: snake_case or camelCase — consistency > the choice itself.
  • Types: dates = RFC 3339 UTC (2026-07-26T10:00:00Z); money = minor-unit integer or decimal-string + currency, never float !; IDs = opaque strings (room to change scheme).
  • null vs absent vs required: null = known-empty; absent = "don't touch" (matters for PATCH); required = reject if missing. Document which.
  • Envelope vs bare: {"data":{...}} gives room for meta/links/errors; bare is simpler. Pick one API-wide.
{ "data": { "id":"ord_123", "state":"paid",
    "amount": {"value":1299,"currency":"USD"} },
  "meta": { "requestId":"req_abc" } }
  • DTO, not the entity: serializing the DB row leaks columns & enables mass assignment — bind only an allow-list of writable fields !
  • Ignore unknown incoming fields (forward-compat); add new response fields freely (additive = non-breaking).

Error Model (RFC 9457 / 7807)

HTTP/1.1 422 Unprocessable Entity
Content-Type: application/problem+json
{ "type":"https://api.ex.com/errors/validation",
  "title":"Validation failed",
  "status":422,
  "code":"INVALID_FIELD",
  "detail":"email is not a valid address",
  "instance":"/v1/users",
  "errors":[
    {"field":"email","code":"format","message":"invalid"},
    {"field":"age","code":"range","message":"must be >= 0"}
  ],
  "requestId":"req_abc" }
  • Separate a stable machine code (clients branch on it) from the human message (may change / localize). Never make clients regex the message !
  • Return all field errors at once (array), not the first — one round-trip fixes a form.
  • Never leak stack traces / SQL / internal hosts in 5xx bodies ! — log them server-side with the requestId, return a generic message + id.
  • Signal retryability: 5xx / 429 = retry with backoff; add Retry-After. 4xx (except 429) = don't retry unchanged.
  • Keep the same error shape on every endpoint so clients write error handling once; carry the request_id both in the body and a response header for support tracing !

Pagination

Offset/limitCursor (keyset)
Query?limit=20&offset=40?limit=20&cursor=eyJ…
Deep pagesslow (scan+skip)fast (index seek)
Stable under writesno — skips/dupes !yes
Jump to page Nyesno (next/prev only)
  • Default to cursor for large/append-heavy feeds; offset only for small, bounded, admin-style lists.
  • Cursor = opaque base64 of the last sort key(s) (e.g. (created_at,id)). Never expose it as a raw offset — clients will do math on it !
  • Always cap limit (e.g. max 100) and echo it; return next/prev links + optional total (expensive — make it opt-in).
  • Cursor must encode the full sort key — sorting by a non-unique column (created_at alone) skips/dupes ties; append id as a tiebreaker so the keyset is strictly ordered !
  • Ranked/personalized feeds break naive keyset — snapshot a materialized ordering per user and page over that, or the list reshuffles mid-scroll.
{ "data":[…],
  "meta":{ "next_cursor":"eyJ…", "has_more":true } }

Filtering, Sorting, Field Selection

  • Filter: ?status=open&created_after=2026-01-01. For operators, either flat (?price_gte=10) or structured (?filter[price][gte]=10) — pick one, allow-list the fields (not arbitrary columns) !
  • Sort: ?sort=-created_at,name (- = desc). Whitelist sortable fields; unbounded sort on an unindexed column = table-scan DoS !
  • Sparse fieldsets: ?fields=id,name,email trims the payload — good for mobile/list views.
  • Expansion / embedding: ?expand=customer inlines a referenced object instead of just customer_id — saves an N+1 round-trip; cap depth & the set of expandable relations.

! Search / filter is the top injection & performance surface — parameterise queries, bound result sets, and index every filterable + sortable field.

Versioning & Evolution

StrategyNote
URI path /v1/most common, cache/route friendly, visible
Header Accept: …;version=2clean URLs, harder to test/curl
Query ?version=2easy, pollutes every URL
  • Non-breaking (no bump): add optional field, add endpoint, add enum value*, relax validation, add optional param.
  • Breaking (bump): remove/rename field, change type, tighten validation, change status/error codes, change default behaviour, restructure nesting !
  • *Adding an enum value can break clients that exhaustively switch — document that clients must tolerate unknowns.
  • Deprecation: announce → Deprecation/Sunset headers → dual-run old+new → metrics show ~0 traffic → remove. Never yank a live version !
  • Prefer additive evolution + tolerant readers over minting a new major version every quarter.
  • Run v1 as an adapter over the new impl where possible — don't maintain two full stacks; retire the old version with 410 Gone only after usage metrics trend to ~0 and stragglers are contacted.

Idempotency & Reliability

Problem: client POSTs, times out, retries → double charge ! POST isn't idempotent by default.

POST /v1/payments
Idempotency-Key: 4b1f…-client-generated-uuid
{ "amount":1299, "currency":"USD" }

# 1st: execute, store result under key
# retry same key: return the SAME stored 200, no new charge
  • Client generates the key (UUID) once per logical op; server stores key → (status, response) for a TTL (e.g. 24h) and replays it.
  • Scope keys per-endpoint / per-account; if the same key arrives with a different body, reject 422 (misuse) !
  • Handle the in-flight race: lock the key so two concurrent retries don't both execute (return 409 on the loser).
  • Make writes safe: idempotency keys, dedup on natural keys, or PUT/upsert semantics. Retries need exponential backoff + jitter, capped, and only on 5xx/429/timeouts.

Conditional Requests & Concurrency

  • ETag = version fingerprint of a resource. Client caches it, revalidates cheaply:
# server → client
ETag: "v3"
# client revalidate
GET /orders/9  If-None-Match: "v3"
→ 304 Not Modified            (nothing sent)

# optimistic lock on write
PUT /orders/9  If-Match: "v3"
→ 200 (ETag now "v4")   |   412 Precondition Failed
   if someone else already bumped it !
  • Solves the lost-update problem: two clients read v3, both edit; If-Match makes the 2nd write 412 instead of silently clobbering ! (or use a version field → 409).
  • If-None-Match on GET → 304 saves bandwidth; on PUT with * = "create only if absent".

  • Only GET/HEAD are cacheable by default. Cache reads; never cache authed/personalized responses in a shared cache !
  • Vary: Accept, Authorization so caches key correctly — forgetting Vary leaks one user's data to another !
  • Layers: client → CDN/edge → gateway → app → DB. Push cacheable content to the edge; use ETag revalidation for the rest.

AuthN & AuthZ

SchemeUse
API keyserver-to-server, coarse, rotate-able
OAuth2 bearerdelegated user access, scopes
JWTstateless claims; verify sig+exp !
mTLSservice mesh / high-trust
HMAC signaturewebhooks, request integrity
  • AuthN (who) → 401. AuthZ (allowed?) → 403. Keep them separate layers.
  • Always credentials over TLS; short-lived access tokens + refresh tokens; scopes least-privilege.
  • BOLA / IDOR (OWASP API #1): every object access must check the caller owns it — GET /orders/{id} must verify order.owner == caller, not just "is logged in" !
  • BFLA: enforce authz on the server, not by hiding UI buttons — the endpoint is wide open otherwise !
  • JWT footguns: verify alg (reject none), check exp/aud/iss; can't revoke early → keep TTL short.
  • Sessions vs tokens: opaque session id (server-side store, instantly revocable, stateful) vs stateless JWT (no lookup, but revocation needs a short TTL or a denylist). Pick per revocation needs.
  • Refresh flow: short access token + long refresh token; rotate refresh tokens on use & detect reuse (a replayed old refresh token = theft → revoke the whole chain) !

GraphQL

query { order(id:"9") {
  id state
  customer { name email }   # no N+1 round-trip
} }
  • Single POST /graphql endpoint; client asks for exactly the fields it needs → no over/under-fetching. Strongly typed schema = built-in contract + introspection.
  • Three op types: query (read), mutation (write, run serially), subscription (live over WS/SSE).
  • ! HTTP status is usually 200 even on errors — errors live in the errors[] array. Clients must check the body, not just the code.
  • ! Footguns: N+1 resolvers (fix with DataLoader batching); unbounded query depth/complexity = DoS (add depth limit, cost analysis, persisted queries); HTTP caching is hard (everything's a POST).
  • Schema evolution: add fields/types freely (additive); to remove, mark @deprecated(reason:) and watch field-usage metrics before deleting. No URL versioning — the schema evolves in place.
  • Authz must be enforced per-field/per-resolver, not per-endpoint — there's only one endpoint, so a missing field-level check is an instant BOLA !
  • Great for varied client shapes (mobile+web) & graph-y data; overkill for simple CRUD.

gRPC & Protobuf

service Orders {
  rpc GetOrder(GetOrderReq) returns (Order);
  rpc Watch(WatchReq) returns (stream Event); // server-stream
}
message Order { string id = 1; int64 amount = 2; }
  • HTTP/2 + protobuf binary. Contract-first .proto → codegen'd clients/servers in every language. Fast, compact, strongly typed.
  • 4 modes: unary, server-stream, client-stream, bidi-stream. Built-in deadlines, cancellation, flow control, multiplexing.
  • Wire compat: field numbers are the contract — never reuse/renumber; add new fields with new tags; reserved removed ones ! Names are cosmetic.
  • Uses its own status codes (OK, NOT_FOUND, INVALID_ARGUMENT, DEADLINE_EXCEEDED…), not HTTP ones.
  • Field rules: number 1-15 = 1-byte tag (put hot fields there); everything proto3-optional & defaulted, so absent ≠ error — tolerant by design. Reuse a retired tag and old clients misread the bytes !
  • Best for internal service-to-service (low latency, polyglot). Weak in browsers (needs gRPC-Web/proxy) & not human-curl-able.

Async, Events & Webhooks

Long-running work

  • Return 202 Accepted + a job resource; client polls GET /jobs/{id} (processing→done) or you push a callback. Don't hold the connection open !

Webhooks (server → client push)

  • Sign every payload (HMAC over body + timestamp header); receiver verifies → blocks spoofing & replay !
  • Delivery is at-least-once → receivers must be idempotent (dedup on event id) !
  • Retry with backoff on non-2xx; give up to a dead-letter queue; expose a redelivery API.
  • Receiver returns 2xx fast (ack + enqueue), does work async — slow handlers cause retries/duplicates.

Event-driven: publish domain events to a broker (Kafka/SQS); consumers decoupled. Choose delivery: at-most / at-least / exactly-once (usually at-least-once + idempotent consumer).

Gateways, Docs & Governance

API Gateway — the front door

  • Cross-cutting concerns in one place: authN, rate limiting, routing, TLS termination, request/response transform, logging, caching. Keep business logic out of it !
  • Watch it becoming a single point of failure & a deploy bottleneck.

Contracts & docs

  • OpenAPI/Swagger (REST), .proto (gRPC), SDL (GraphQL) = the machine contract → codegen, mocks, docs, contract tests.
  • Lint the spec in CI (Spectral); run contract tests so impl can't drift from spec.
  • DX Good docs = quickstart + auth + every endpoint + examples + error catalog + changelog. Consistency is a governed style guide, not luck.

Content Negotiation & Key Headers

  • Negotiation: client's Accept: application/json says what it wants back; Content-Type declares what's in the body. Mismatch → 406 Not Acceptable (can't produce) or 415 Unsupported Media Type (won't accept the body) !
  • Location on 201 = URI of the created resource (client follows it). Content-Location = canonical URI of the returned body.
  • Accept-Encoding: gzip, br → server compresses; huge win on JSON (5-10×). Pair with Vary: Accept-Encoding.
  • Vary lists request headers the response depends on so caches key correctly (Accept, Accept-Language, Authorization) ! Miss it → wrong-variant cache poisoning.

ETag/If-Matchversion tag · concurrency
Idempotency-Keyreq · dedup retries
Retry-Afterresp · 429/503 backoff hint
Deprecation/Sunsetresp · lifecycle signal
  • ! The X- prefix for custom headers is deprecated (RFC 6648) — register a plain name. Don't put secrets or PII in headers you log.

    Partial Updates — Merge Patch vs JSON Patch

    Merge Patch (7386)JSON Patch (6902)
    Media typemerge-patch+jsonjson-patch+json
    Shapepartial objectop array
    Delete fieldnull{op:"remove"}
    Array editsreplace whole array !per-index ops
    Conditionalnotest op
    # Merge Patch — change only email, leave rest
PATCH /v1/users/42  Content-Type: application/merge-patch+json
{ "email": "new@ex.com", "nickname": null }   # null = delete

# JSON Patch — ordered ops, testable
[ {"op":"test","path":"/version","value":9},
  {"op":"replace","path":"/status","value":"shipped"} ]
    • Merge Patch can't distinguish "set null" from "delete" cleanly, and can't append to an array without resending it — that's where JSON Patch wins !
    • Idempotency depends on ops: replace is idempotent; add to an array or an increment-style delta is not. Design retries as if PATCH isn't idempotent.

    Async, Long-Running & Bulk Ops

    Long-running work

    POST /v1/exports          → 202 Accepted
Location: /v1/jobs/j_9
{ "id":"j_9", "status":"processing" }

GET /v1/jobs/j_9  → 200 { "status":"done",
  "result_url":"/v1/exports/e_5" }
    • Return 202 + a job resource; client polls GET /jobs/{id} (processing→done/failed) or you fire a webhook. Never hold the connection open for minutes !

    Bulk / batch endpoints

    • Accept an array; on mixed outcomes return 207 Multi-Status (or 200 + a per-item results array) so one bad row doesn't fail the batch !
    • Cap batch size; make the whole batch idempotent (one Idempotency-Key) or dedup per item. Decide up front: all-or-nothing (transactional) vs partial-success.

    Contracts, Testing & Observability

    The machine contract

    • OpenAPI (REST), .proto (gRPC), SDL (GraphQL) → codegen clients/servers, mock servers, docs, and contract tests from one source of truth DX.
    • Spec-first: write & review the spec before code; lint it in CI (Spectral) so style rules are enforced, not hoped for.
    • Contract tests (e.g. consumer-driven / Pact) pin the provider to what consumers actually rely on — impl can't silently drift from the published shape !

    Observability

    • Propagate a request_id (and W3C traceparent) through every log line and downstream call — one id ties a user report to the exact failing hop !
    • Track RED per endpoint: Rate, Errors, Duration (p50/p95/p99). Alert on error-rate & latency SLO burn, not raw counts.
    • Structured JSON logs; never log tokens, full bodies, or PII. Emit deprecation-hit metrics so you know when a version is safe to retire.

    Timeouts, Retries & Resilience

    • Every remote call gets a timeout — no timeout = a stuck dependency exhausts your thread/connection pool and cascades !
    • Retry only idempotent ops on 5xx/429/timeout, with exponential backoff + jitter, a capped attempt count, and a retry budget (cap % of traffic that is retries) so you don't DDoS a struggling backend !
    • Circuit breaker: after N consecutive failures, open (fail fast) for a cooldown, then half-open to probe — stops pile-up on a dead dependency.
    • Deadline propagation: pass the remaining budget downstream (gRPC deadlines / a deadline header) so nobody works on a request the caller already abandoned.
    • Connection reuse: keep-alive / HTTP/2 multiplexing avoids per-call TLS handshakes; watch HTTP/1.1 head-of-line blocking on chatty clients. Bound pool size.

    ! Retries + no idempotency key = the double-charge bug. Retries and idempotency are two halves of one design.

    The Interview Loop — reason out loud

    • 1 Clarify before drawing anything: public or internal? who authenticates? scale? read- or write-heavy? consistency needs? Juniors dive in on assumptions !
    • 2 Model resources (nouns + relationships) before endpoints — endpoints fall out of a clean model.
    • 3 Happy path with correct methods/codes, narrating each ("POST → 201 + Location").
    • 4 Attack the hard parts unprompted — the ones the prompt is really testing: cursor pagination, idempotency keys, versioning, the object-level auth (BOLA) check, rate limits, a consistent error envelope.
    • 5 State tradeoffs: "cursor over offset because the feed drifts." Owning the tradeoff beats pretending there isn't one.
    • 6 Invite feedback: "deeper on webhook retries or the auth model?"

    DX A slightly imperfect design narrated with clear reasoning beats a perfect one produced in silence — they're hiring the person who makes these calls on the team.

    Review a bad API: prioritise security & correctness → consistency → polish. Lead with BOLA and client-controlled authz (?admin=true), then RPC-verb URLs, data over-exposure, missing version. Leading with the security flaws signals seniority.

    ★ API Review Checklist

    Contract & naming

    • ☐ Nouns + plural collections; verbs in the HTTP method, not the path.
    • ☐ Case, date/money/ID formats, and envelope style consistent API-wide.
    • ☐ Response is a DTO — no DB columns leaked; writable fields allow-listed !

    HTTP semantics

    • ☐ Correct method (idempotency matches intent); correct status (201+Location, 202, 304, 409 vs 422).
    • ☐ GET has no side effects / no body.

    Reliability

    • ☐ Non-idempotent writes accept an Idempotency-Key; retries use backoff+jitter !
    • ☐ Concurrent writes guarded by ETag/If-Match or version (no lost updates).
    • ☐ Long ops are 202 + job/poll, not a held connection.

    Errors & limits

    • ☐ problem+json with stable machine code; all field errors returned; no stack traces !
    • ☐ Rate limits + 429/Retry-After; pagination capped & cursor for big lists.

    Auth & versioning

    • ☐ 401 vs 403 correct; per-object ownership + per-function role checked server-side !
    • ☐ Change is additive, or version bumped + deprecation path; unknown fields tolerated.
