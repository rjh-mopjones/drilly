Fundamentals — CIA & Principles

CIA triad = the goals security exists to protect:

GoalBroken by → control
Confidentialityleak / eavesdrop → encryption, access control
Integritytamper → hashing, signatures, MAC
AvailabilityDoS / outage → redundancy, rate limits

Add authenticity (who) + non-repudiation (can't deny) as extensions.

Core principles

  • Least privilege: every principal gets the minimum access to do its job — scoped tokens, scoped DB users, no wildcard IAM !
  • Defense in depth: layered controls, no single point of failure — WAF + input validation + parameterized queries + least-priv DB.
  • Fail secure / secure defaults: on error, deny. The default config must be the safe one — opt into risk, never opt out.
  • Complete mediation: check every access, every time — no cached "already authorized".
  • Minimise attack surface: fewer endpoints, ports, deps, features = less to exploit.

Model early (design time). Steps: decompose (data-flow diagram, mark trust boundaries) → enumerate (STRIDE per element) → rank (likelihood×impact) → mitigate.

  • Trust boundary = where data crosses privilege levels (browser→server, service→DB). Validate on cross.
  • Vuln (weakness) × threat (actor/event) = risk (probability×impact). You fix vulns to reduce risk.
  • Confused deputy: a privileged component is tricked into misusing its authority for a caller — SSRF, CSRF are instances !

The three people confuse

  • Hashing = one-way, fixed-size, no key. Integrity / password storage.
  • Encryption = two-way, reversible with a key. Confidentiality.
  • Encoding (Base64/URL/hex) = reversible without a key, zero secrecy. "We Base64'd the keys" = plaintext !

! Never roll your own crypto. Use vetted primitives in vetted constructions (libsodium, Tink, platform AEAD). Bugs are silent — it "works" and is still broken.

Symmetric Encryption & AEAD

  • Use AEAD (Authenticated Encryption w/ Associated Data): AES-GCM or ChaCha20-Poly1305 — confidentiality + integrity in one, detects tampering. Plain CBC does not !
  • ECB is broken — identical plaintext blocks → identical ciphertext, leaks structure (the "ECB penguin"). Never use !

IV / nonce — the reuse trap !

  • IV/nonce is not secret but must be unique per key. Store it alongside the ciphertext.
  • GCM nonce reuse is catastrophic: reuse under one key → attacker recovers the auth key & forges/decrypts. Use random 96-bit or a strict counter.
# Python (cryptography): AES-GCM done right
key   = AESGCM.generate_key(bit_length=256)
nonce = os.urandom(12)              # unique per message
ct    = AESGCM(key).encrypt(nonce, data, aad)
# store (nonce, ct); decrypt verifies the tag,
# rejecting any tampered ciphertext

Hashing, Signatures & HMAC

Secure hash properties

  • Pre-image, 2nd pre-image, collision resistance. MD5/SHA-1 have practical collisions — dead for integrity & signatures !
  • Fast hashes (SHA-256) are right for integrity, wrong for passwords (GPU brute-force at billions/sec).

Signature vs MAC

KeyGives
Signatureasymmetric (sign priv / verify pub)integrity + authenticity + non-repud.
HMACsymmetric (shared secret)integrity + authenticity
  • HMAC(key,msg) ≠ hash(key‖msg) — the construction resists length-extension attacks that naive prefixing suffers !
  • Compare MACs/tokens with a constant-time compare (hmac.compare_digest) — == leaks via timing !

Passwords & Key Management

Store passwords

  • Argon2id (preferred, memory-hard) or bcrypt/scrypt. Per-user random salt defeats rainbow tables — modern hashes embed it.
  • Pepper = extra secret in a KMS/HSM, not in the DB — survives a DB-only dump.
  • Work factor must be tunable & raised as HW improves (bcrypt cost ≥12, Argon2 memory ≥19MB).
SHA-256(pwd)       # ❌ GPU-crackable, unsalted
Argon2id(pwd,salt) # ✅ memory-hard, salted, tunable

Key hierarchy

  • Envelope encryption: a per-object DEK encrypts data; a KEK in KMS encrypts the DEK. Rotate the KEK cheaply, no data re-encrypt.
  • KMS = managed key service; HSM = tamper-resistant hardware, keys never leave.
  • Keys live in KMS/secret manager, never in code/repo/config ! Rotate on schedule + on suspected compromise.
  • Use a CSPRNG (os.urandom, crypto.randomBytes) for keys/tokens/IVs — never Math.random/rand() !

TLS Handshake & PKI

TLS 1.3 (1-RTT): ClientHello (ciphers + key share) → ServerHello (cipher + key share + cert) → both derive a shared secret via ECDHE → Finished. App data uses a symmetric AEAD.

  • Asymmetric only sets up the session; symmetric does the bulk work (fast).
  • Forward secrecy (PFS): ephemeral ECDHE keys mean a later private-key leak can't decrypt past traffic. Mandatory in 1.3.
  • 1.3 drops RSA key transport, CBC, RC4, renegotiation — fewer footguns than 1.2.

Certificates / chain of trust

  • A cert binds a public key to an identity, signed by a CA. Client validates the chain to a trusted root + name, expiry, revocation (OCSP/CRL).
  • MITM fails because the attacker can't forge a CA-signed cert — unless the client skips validation ! Never disable cert checks.
  • In transit (TLS) ≠ at rest (disk). Need both — HTTPS doesn't protect the stored DB.

Authentication

Factors: know (password), have (phone/TOTP/passkey), are (biometric). MFA = 2+ different categories (password+TOTP, not password+PIN).

MethodNote
TOTPshared secret + time, offline. Phishable (code relayable)
SMS OTPweakest 2FA — SIM-swap, interceptable !
WebAuthn / passkeysFIDO2, public-key, phishing-resistant (origin-bound)

NIST 800-63B (modern)

  • Length > complexity; allow long passphrases; no forced periodic rotation; screen against breached lists. Composition rules are out.

Footguns

  • User enumeration: "invalid password" vs "no such account" leaks valid users. One generic message + uniform timing !
  • Credential stuffing (reused breached creds) beats lockout — defend w/ MFA, breached-pw checks, rate limit, device signals.
  • Password reset is often the weakest link — treat the reset token like a credential (single-use, short TTL, no enumeration).

Rate limit & lockout

  • Rate-limit auth by account + IP + device, with exponential backoff — pure IP limits miss distributed stuffing; pure account limits let an attacker lock out victims (a DoS) !
  • Prefer soft controls (backoff, CAPTCHA on anomaly, MFA, breached-pw check) over hard N-strike lockout, which is itself a DoS lever.

Sessions & Tokens

Session cookies — set every flag

Set-Cookie: sid=...; HttpOnly; Secure;
            SameSite=Lax; Path=/; Max-Age=3600
  • HttpOnly (JS can't read → XSS can't steal) · Secure (HTTPS only) · SameSite (CSRF defense).
  • Session fixation: regenerate the session ID on login (and on privilege change) so a pre-set ID is useless !
  • Server-side sessions can be revoked instantly; the cookie holds only an opaque random ID.

JWT pitfalls !

  • alg:none & alg-confusion (RS256→HS256: verify the public key as an HMAC secret) — pin the algorithm server-side.
  • Stateless → hard to revoke; keep access-token TTL short (minutes) + a revocable refresh token. No secrets in the (readable) payload.
  • Store tokens in HttpOnly cookies, not localStorage (XSS-readable).

Authorization & Access Control

AuthN = who you are; AuthZ = what you may do. Enforce authz on every request, server-side, deny-by-default.

ModelDecides by
ACLper-object list of principals
RBACrole → permissions (coarse, common)
ABACattributes/context (fine, dynamic)

Broken Access Control = OWASP #1

  • IDOR / BOLA: GET /orders/123 — the server must check this user owns 123, not just that they're logged in !
  • UUIDs are not a fix — obscurity, not authorization. Still check ownership.
  • Function-level (may call admin route?) and object-level (owns this record?) — you need both.
  • Vertical escalation = gain higher role; horizontal = access a peer's data. ?role=admin honored = client-trusted authz !
  • Multi-tenant: scope every query by tenant_id from the session, never the request body.

Injection — SQL / Cmd / NoSQL

Root cause: untrusted data mixed with code/query structure. Fix = separate structure from data, not "sanitize input".

# ❌ SQLi: input concatenated into the query
db.query("SELECT * FROM u WHERE name='" + n + "'")
# ✅ Parameterized: structure & values sent apart
db.query("SELECT * FROM u WHERE name = ?", [n])
TypeDefense
SQLparameterized / prepared stmts
Commandarg array, no shell (execFile not exec)
NoSQLtype-check; reject operator objects ({$ne:...})
LDAP/XPathescape/parameterize per grammar
  • ORMs help but raw/interpolated queries still inject ! — parameterize even in raw mode.
  • Can't parameterize a column/table name → allowlist against known columns, never interpolate.
  • Layered: least-priv DB user caps blast radius; input validation is defense-in-depth, not the primary fix.
  • Blind SQLi (no visible output) still exfiltrates via boolean/time-based inference — "no error shown" is not "not vulnerable" !
  • Stored procedures help only if they parameterize internally — dynamic SQL built inside a proc injects just the same.

XSS & Content Injection

TypeWhere
Storedpayload persisted (DB), served to others — worst
Reflectedechoed from the request (search, error)
DOMclient JS writes untrusted data to the DOM

Defense: context-aware output encoding !

  • Encode on output, per context (HTML body, attribute, JS, URL, CSS) — the same string is safe in one, dangerous in another.
  • Auto-escaping templates (React/Angular) handle most — escape hatches reintroduce it: dangerouslySetInnerHTML, innerHTML, v-html !
  • Sanitize rich HTML with DOMPurify; never regex-strip tags.
  • CSP as a second layer: default-src 'self', nonce/hash for scripts, drop unsafe-inline. Limits impact if XSS slips through.

Injection vs XSS: injection = data becomes server-side code/query; XSS = data becomes script in the victim's browser. Different fix, same root (structure/data mixing).

CSRF & SSRF

CSRF — forged request rides the user's cookie

  • Browser auto-sends cookies → attacker page triggers a state-changing request as the victim.
  • Defenses: SameSite=Lax/Strict cookies (baseline) + anti-CSRF token (synchronizer / double-submit) on state-changing routes; check Origin/Referer.
  • Only affects cookie/ambient auth — bearer-token-in-header APIs are largely immune ! GET must be side-effect-free.

SSRF — server fetches an attacker URL

  • Attacker makes your server hit internal targets: 169.254.169.254 (cloud metadata / IAM creds), localhost, internal admin !
  • Defenses: allowlist destinations; block private/link-local ranges + redirects; validate the resolved IP (defeat DNS rebinding); disable unused URL schemes; enforce IMDSv2.

Secrets & Supply Chain

Secrets management

  • Secrets in a vault / secret manager (Vault, AWS/GCP Secrets Mgr), injected at runtime — never in code, config, baked env, or logs !
  • A committed secret is burned — rotate immediately; deleting the commit doesn't undo history/mirrors. Scan w/ gitleaks/trufflehog pre-commit.
  • Prefer short-lived, workload-identity creds (OIDC) over long-lived static keys.

Supply chain

  • SCA scans deps for known CVEs (Dependabot, Snyk). Pin versions + lockfile; verify integrity hashes.
  • Typosquatting / dependency confusion — attacker publishes a public pkg matching your internal name ! Scope registries.
  • Sign build artifacts (Sigstore); produce an SBOM; protect CI/CD secrets & runners — the build system is a high-value target (cf. SolarWinds).

  • Shift left — cheapest to fix at design/code time; combine tools (none is complete). SAST + SCA in CI, DAST in staging.
  • SSDLC: security in every phase — threat model (design), secure coding + review (build), scan (test), harden (deploy), monitor (run).
  • Design flaws (business logic, missing authz) evade SAST/DAST — only threat modeling & design review catch them. A passing scan ≠ secure !
  • Gate CI on new high-severity findings only (not the whole backlog) so security doesn't block the team; triage the rest async.

Network, Transport & Cloud

  • Segment the network into public / app / data tiers; DB not internet-reachable. Security groups = deny-by-default, allow only needed ports.
  • Zero trust: no implicit trust from network location — authenticate & authorize every request, even internal (mTLS between services).
  • A WAF is a speed bump, not a fix for the underlying bug !

Cloud footguns

  • Public storage buckets — the classic breach. Default private, block public ACLs at the account level !
  • Over-broad IAM (*:*) — scope by service/resource; roles not long-lived keys.
  • Protect the instance metadata endpoint (IMDSv2) — SSRF to it steals role creds.
  • Shared responsibility: cloud secures of the cloud; you secure in it (config, data, IAM).

Containers & Kubernetes

  • Don't run as root in the container; drop Linux capabilities; read-only root FS; no --privileged !
  • Minimal base image (distroless/alpine) = smaller attack surface + fewer CVEs. Scan images (Trivy/Grype).
  • A container is not a strong security boundary like a VM — shared kernel; a kernel escape = host compromise !
  • No secrets in image layers (they persist even if later deleted). Use K8s Secrets (encrypt etcd at rest) / external vault.
  • Pin base images by digest not :latest; rebuild to pick up patches; sign images (cosign) & verify on admission.

K8s controls

  • RBAC least-priv service accounts; NetworkPolicies (default-deny); Pod Security Standards (restricted).
  • Protect the API server & kubelet; audit logging on; admission control (OPA/Kyverno) to enforce policy.

Memory Safety & Low-Level

  • C/C++ footguns: buffer overflow, use-after-free, double-free, integer overflow, format-string — the root of a huge share of critical RCEs !
  • Stack overflow can overwrite the return address → control-flow hijack → shellcode / ROP.
  • Mitigations (raise cost, not eliminate): ASLR, DEP/NX, stack canaries, CFI, PIE, FORTIFY_SOURCE.
  • Best fix: memory-safe languages (Rust, Go) or safe abstractions; bounds-checked APIs; never gets/strcpy.
  • Insecure deserialization of untrusted data → RCE — never deserialize untrusted input into live objects; use data-only formats + schema.
  • Integer overflow in a size/length calc → undersized allocation → heap overflow. Validate arithmetic; use checked/saturating ops.

Incident Response & Monitoring

NIST IR lifecycle: Prepare → Detect & Analyze → Contain → Eradicate → Recover → Post-incident (lessons learned).

  • Containment first — isolate, don't tip off the attacker; preserve evidence (don't wipe) for forensics.
  • Log security events: authN success/fail, authZ denials, admin actions, validation failures. Centralize (SIEM), tamper-evident, time-synced.
  • Never log passwords, tokens, full card numbers, secrets ! — logs leak.
  • Alert on anomalies; you can't respond to what you can't see (A09). Write the IR runbook before you need it.
  • Blameless post-mortem — fix systems & processes, not people.
  • MTTD/MTTR — time to detect / respond are the metrics that matter; a breach you find in minutes beats one exposed for months.
  • Breach-notification clocks are legal, not optional: GDPR ≤72h to the regulator. Have a comms + disclosure plan pre-agreed with legal.

Secure Design & Privacy

  • Secure defaults, fail closed, complete mediation, least privilege, separation of duties, economy of mechanism (simple — complexity hides bugs).
  • Don't trust the client — validate/authorize on the server; client checks are UX only !
  • Positive (allowlist) validation beats blocklist — enumerate what's allowed, reject the rest.

Privacy & compliance

  • Data minimization — collect only what you need; you can't leak what you don't hold.
  • Privacy by design/default; encrypt PII at rest & in transit; define retention & deletion.
  • GDPR (rights, breach notice ≤72h), PCI-DSS (cardholder data), HIPAA (PHI). Pseudonymize where possible.

OAuth 2.0, OIDC & Federation

OAuth 2.0 = delegated authorization (grant an app scoped access). OIDC = a thin identity layer on OAuth — adds a signed ID token (a JWT) proving who logged in. Don't use bare OAuth for login !

ParamJob
stateOAuth CSRF guard — random, bound to session, verified on callback
nonceOIDC — echoed inside the ID token, defeats token replay
PKCEbinds code to the client (S256(verifier)) — stops code interception
  • Auth-code + PKCE is the flow for all clients now (OAuth 2.1); implicit flow is dead. A stolen code is useless without the code_verifier that never left the client.
  • redirect_uri = exact-match allowlist — no prefix/substring/wildcard. Loose matching → attacker redirects the code to their server (app.example.com.evil.com) !
  • Omitting state → login CSRF (victim logged into attacker's account).

Refresh-token rotation

  • Each use of a refresh token issues a new one & invalidates the old (single-use). Replay of a used token → treat as theft, revoke the whole family, force re-login.
  • Store refresh tokens hashed, device-bound, with an absolute lifetime; access token TTL short (5–15 min).

SAML vs OIDC

  • SAML = XML signed assertions, enterprise/B2B SSO (Okta/ADFS) — heavier, XML-signature-wrapping bugs. OIDC = JSON/JWT, modern/API/mobile. Both trust signature validation — the SAML analog of the JWT alg trap is accepting an unverified assertion.

Clickjacking, Open Redirect & CORS

Clickjacking (UI redress)

  • Your page framed transparently on an attacker site; victim's click lands on your button with their session. Fix by forbidding framing:
Content-Security-Policy: frame-ancestors 'none'
X-Frame-Options: DENY            # legacy fallback

frame-ancestors is the modern control ('none'/'self'/allowlist). Frame-busting JS is bypassable ! Re-auth high-risk actions.

Open redirect

  • redirect(request.args["next"]) → ?next=https://evil.com. Minor alone, a phishing force-multiplier — victim trusts your domain, bypasses OAuth/SSRF/scanner allowlists.
  • Fix: redirect to a relative path or server-side map (next=dashboard→/dashboard). If you must take a URL, parse & compare host — //evil.com and \@you.com defeat prefix checks !

CORS ≠ CSRF defense !

  • CORS grants read access to responses; it never blocks a request being sent. CSRF doesn't read anything, so CORS is irrelevant to it.
  • Classic misconfig: reflecting the request Origin back + Allow-Credentials: true → any site reads the victim's data. Allowlist exact origins; never reflect; * + credentials is browser-rejected.

File & Parser Attacks

Path / directory traversal

  • ../ (or %2e%2e%2f, absolute paths) escapes the base dir. Blocklisting ../ loses to encoding tricks !
  • Fix = canonicalise then verify containment: realpath resolves ..+symlinks, then confirm still under base. Best: map an opaque ID to a known file so input never forms a path.

Insecure deserialization → RCE

  • Type-resolving serializers (Java native, Python pickle, PHP unserialize, .NET BinaryFormatter) instantiate arbitrary types → gadget-chain RCE during reconstruction. Validation after is too late !
  • Fix: data-only formats (JSON/Protobuf) bound to one known type; if forced, allow-list types + sign the payload. (OWASP A08.)

XXE

  • XML entity <!ENTITY x SYSTEM "file:///etc/passwd"> reads files / SSRF / DoS. It's a parser-config bug — fix = disable DTDs & external entities, not sanitise XML.

SSTI

  • User input built into a template → evaluated as code ({{7*7}}→49) → often RCE. Fix: pass input as context data to a static template, never concatenate into template source.

Logic Flaws, Races & Vuln Triage

Business-logic flaws

  • Abuse of functionality working as coded: reuse a single-use coupon, order negative quantity for a refund, skip payment to the confirmation endpoint. Scanners can't find them — no injectable sink !
  • Defend at design time: enumerate abuse cases, enforce invariants + a state machine server-side, atomic redemption, rate limits.

TOCTOU / race conditions

  • Time-Of-Check ≠ Time-Of-Use: resource swapped in the gap (symlink swap; double-spend). Fix = eliminate the gap — atomic op on a handle (O_NOFOLLOW), or DB SELECT … FOR UPDATE/atomic conditional update, not read-check-write.

Mass assignment

  • Framework auto-binds the whole body → attacker adds {"isAdmin":true}. Fix: bind an explicit DTO / allow-list of permitted fields, never the raw model !

CVE / CVSS triage

  • CVE = the identity; CVSS 0–10 (Base/Temporal/Environmental) = severity. Don't sort a scan by Base score and march top-down !
  • Rank by reachability (is the path called with attacker input?) + exposure (internet-facing/unauth) + known-exploited (CISA KEV) + blast radius. A 9.8 in dead code < a 6.5 on your auth flow.
  • Vuln (the weakness) vs exploit (technique using it) vs payload (delivered action). Zero-day = no patch yet.

★ Secure-Review Checklist

Access control

  • ☐ Every endpoint checks authZ server-side, deny-by-default; object-level ownership verified (no IDOR) !
  • ☐ Tenant/user scope from the session, never the request body; no client-supplied role/isAdmin trusted.

Injection & output

  • ☐ All queries parameterized; commands use arg arrays; column names allowlisted.
  • ☐ Output context-encoded; no raw innerHTML/dangerouslySetInnerHTML on untrusted data; CSP set.

Auth & sessions

  • ☐ Passwords via Argon2id/bcrypt + salt; MFA available; generic login errors + uniform timing.
  • ☐ Cookies HttpOnly; Secure; SameSite; session ID regenerated on login; JWT alg pinned, short TTL.

Crypto & secrets

  • ☐ AEAD (AES-GCM), unique nonce, CSPRNG; no MD5/SHA-1/ECB; TLS enforced, cert validation on.
  • ☐ No secrets in code/config/logs; stored in a vault; rotated; constant-time compares for tokens.

Platform

  • ☐ Deps scanned (SCA), pinned, lockfile; container non-root, minimal image; SSRF egress allowlisted.
  • ☐ Security events logged (no PII); errors don't leak stack/config; debug off in prod.
