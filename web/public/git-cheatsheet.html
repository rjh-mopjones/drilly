Object Model

  • Four object types: blob = file bytes (no name) · tree = a directory listing (names → blob/tree SHAs + mode) · commit = one root tree + parent(s) + author/committer + message · tag = annotated-tag object.
  • Everything is content-addressed: id = SHA-1(type + size + content). Identical content is stored once (dedup); change one byte → new hash → every ancestor commit's hash changes too → history is effectively immutable / append-only.
  • Snapshots, not diffs: each commit references a full tree of the project. Deltas exist only inside packfiles as a storage optimisation, not in the model.
  • A ref (branch, tag, HEAD, origin/main) is just a file under .git/refs holding a commit SHA — a cheap, movable pointer.
git cat-file -p HEAD      # pretty-print an object
git cat-file -t <sha>      # its type
git ls-tree HEAD          # the root tree
git hash-object -w file   # store a blob, print its SHA
git rev-parse HEAD~2      # resolve a ref → full SHA

Basics & Refspeak

git status -sb            # short + branch/upstream
git add -p                # stage individual hunks
git commit -m "msg"       git commit --amend   # fix last (unpushed!)
git diff                  # working vs index
git diff --staged         # index vs HEAD (what will commit)
git log --oneline --graph --all --decorate
git show HEAD:path        # a file as of a commit
git blame -L 10,20 file   # who last touched each line
  • Relative refs: HEAD~3 = 3rd first-parent ancestor; HEAD^ = 1st parent, HEAD^2 = 2nd parent (merge's other side); @ = HEAD.
  • Ranges: A..B = reachable from B but not A (the "what's new" set); A...B = symmetric difference (either side, not both).
  • Commit subject imperative, ≤50 chars; blank line; body wraps ~72 and explains why, not what.

Branches & HEAD

  • A branch is a 40-char file that moves to the new commit each time you commit while it's checked out. Creating one is O(1) — write one small file.
  • HEAD is a symbolic ref normally pointing at your current branch (ref: refs/heads/main). Commit → branch advances, HEAD follows.
  • Detached HEAD: HEAD points straight at a SHA/tag, not a branch. Commits there belong to no branch; switch away and they look "lost" (reflog / fsck recovers) !
git switch -c feature/x     # create + switch
git switch main             git switch -    # last branch
git branch -vv              # upstream + ahead/behind
git branch -d done          git branch -D force
git branch -m old new       # rename
git switch --orphan gh-pages  # history-less branch

Delete a branch = delete a pointer; the commits survive until GC prunes the unreachable ones after the reflog window.

Commits & History

  • Author = who wrote the change (preserved across rebase/cherry-pick); committer = who last applied it (updated by those ops) — that's why a rebased commit keeps the author but gets a new committer + new SHA.
  • Parent pointers form the commit DAG: 0 parents (root), 1 (normal), 2+ (merge). Traversal of this graph powers log, merge-base, bisect.
  • Conventional Commits: feat: / fix: / chore:… → drives changelogs + semver bumps (feat→minor, fix→patch, !/BREAKING→major).
git log -S"funcName"       # pickaxe: commits adding/removing text
git log -G"regex"          git log -p file    # patch per commit
git log --oneline v1..HEAD # since a tag
git show <sha>              git shortlog -sn   # counts by author

! --amend rewrites the last commit (new SHA) — safe only if unpushed.

Merge vs Rebase

mergerebase
historytrue, with bubbleslinear, clean
commitspreserved + merge commitrewritten (new SHAs)
contextkeeps when/how branches joineddrops the branch topology
conflictsonce, at the tippossibly per-commit
safe on shared?yesNO !
  • Fast-forward: target is a direct ancestor → just slide the pointer, no new commit. --no-ff forces a merge bubble (keeps the feature grouping).
  • 3-way merge: combine the two tips + their merge-base → a 2-parent commit; conflicts only when both sides touch the same lines.
  • Rebase replays your commits one-by-one onto a new base → new SHAs. Great before a PR; never on commits others have.
  • Golden rule: don't rewrite commits others have pulled ! Your own PR branch → push --force-with-lease.

Rebasing

git rebase main             # replay current branch onto main
git pull --rebase           # fetch + rebase (linear pulls)
git rebase --onto main old  # move commits after 'old' onto main
git rebase --continue | --skip | --abort
  • --onto A B transplants the commits after B onto A — the surgical form for splitting a branch off the wrong base.
  • Conflicts pause the rebase per commit: fix, git add, --continue. Same conflict repeatedly? enable rerere to auto-replay resolutions !
  • --rebase-merges preserves merge topology while rebasing; --autosquash auto-orders fixup!/squash! commits.
  • Lost commits after a rebase? git reflog → the pre-rebase SHA is still there. --force-with-lease refuses to clobber a teammate's new pushes !

Undo — reset / revert / restore

Three different jobs — don't blur them: reset moves the branch pointer (history) · revert adds a new inverse commit (history-safe) · restore/checkout only touch files (no pointer move).

git reset --soft HEAD~1     # uncommit, keep staged
git reset HEAD~1            # (--mixed) uncommit + unstage
git restore --staged file   # unstage, keep edits
git restore file            # discard edits (LOSS!) !
git revert <sha>             # new commit undoing it (shared-safe)
git revert -m 1 <merge>      # revert a merge (pick mainline parent)
git reset --hard origin/main  # nuke local → match remote !

Rule: local/unpushed → reset; shared/pushed → revert. ! git clean -fd deletes untracked files/dirs irrecoverably — dry-run -n first.

reset — the three modes

modeHEADindexwtree
--softmovekeepkeep
--mixed (default)moveresetkeep
--hardmoveresetreset !
  • --soft: changes stay staged → recombine several commits into one (reset --soft HEAD~3 then re-commit).
  • --mixed: unstages too → work back in the working tree, ready to re-stage selectively.
  • --hard: throws away index and uncommitted edits. The one that loses work ! — anything committed is still in the reflog; uncommitted edits are gone.
  • Path form git reset <sha> -- file unstages a path (never moves HEAD).

Stash & Reflog

git stash push -u -m "wip"   # -u also stashes untracked
git stash list               git stash show -p stash@{0}
git stash pop                # apply + drop (top)
git stash apply stash@{1}    # apply, keep in list
git stash branch fix stash@{0}  # pop onto a new branch
git reflog                   # every HEAD move (safety net!)
git reset --hard HEAD@{1}    # undo a bad reset/rebase
git switch -c recover <sha-from-reflog>
  • A stash is really a couple of commits on a hidden ref — it survives branch switches. pop can conflict; resolve like any merge.
  • Reflog logs where HEAD/branches have been (~90 days for reachable, 30 for unreachable) → recover after reset/rebase/amend/branch-delete !
  • git fsck --lost-found surfaces dangling commits when even the reflog can't help.

Merge Conflicts

<<<<<<< HEAD        (ours)
your change
||||||| base        (zdiff3 shows the ancestor)
=======
their change
>>>>>>> branch     (theirs)
  • Edit to the intended result, delete all markers, git add, then commit / --continue. Bail out: merge --abort or rebase --abort.
  • Enable merge.conflictStyle=zdiff3 (shows the common ancestor) and rerere.enabled=true (records + replays resolutions) !
  • In a rebase, "ours" = the branch you're rebasing onto — the sense flips vs a merge !
  • git checkout --ours/--theirs file takes one whole side. A clean text merge can still be semantically broken → run tests.

Cherry-pick & Bisect

git cherry-pick <sha>        # replay one commit here (new SHA)
git cherry-pick A..B         # a range (exclusive of A)
git cherry-pick -x <sha>      # note origin in the message
git cherry-pick --continue | --abort
git bisect start
git bisect bad; git bisect good v1.0
git bisect run ./test.sh     # AUTOMATE the search
git bisect reset
  • Cherry-pick to backport a fix onto a release branch, or lift a good commit off a wrong branch.
  • Bisect = binary search for the first bad commit — O(log n) checkouts. bisect run drives it via a script's exit code (non-zero = bad, 125 = skip).
  • Atomic, self-contained commits make both tools far more effective.

Remotes: fetch / pull / push

git remote -v               git remote add origin <url>
git fetch                   # download refs+objects, NO merge (safe)
git pull                    # fetch + merge (or --rebase)
git push -u origin feature  # push + set upstream
git push origin --delete old
git push origin v1.2.0      # tags aren't pushed by default!
  • origin/main is a read-only remote-tracking ref: a cache of the remote as of your last fetch. "ahead 2, behind 1" compares your branch to it.
  • fetch is always safe — it never touches your working tree; pull is fetch + integrate, and can conflict.
  • "rejected — non-fast-forward" = the remote has commits you lack → fetch + rebase/merge first; do not blind-force !
  • git clone = init + add origin + fetch all + checkout default branch.

Rewriting History & Recovery

# purge a file/secret from ALL history (preferred tool)
git filter-repo --path secrets.env --invert-paths
git filter-repo --replace-text expressions.txt
# (BFG is the older alternative; filter-branch is deprecated)
  • Rewriting every commit changes all SHAs downstream → everyone must re-clone/reset. Coordinate; only do it on shared history for a real reason (leaked secret, huge blob).
  • ! A committed secret is already compromised — filter it out and rotate the credential. Removal ≠ safety; caches/forks/mirrors keep copies.
  • After a rewrite: git push --force-with-lease, expire reflogs, git gc --prune=now to drop the old objects.
  • Recover anything "lost" via reflog first, fsck --lost-found second — objects live until GC after the grace window.

Tags & Releases

git tag -a v1.2.0 -m "release"   # annotated (preferred)
git tag v1.2.0                   # lightweight (bare pointer)
git tag -s v1.2.0                # GPG-signed release
git push origin v1.2.0           # or: git push --tags
git push origin :refs/tags/v1.2  # delete remote tag
git describe --tags              # v1.2.0-14-gabc123
  • Annotated = a real object (tagger, date, message, optional signature) → use for releases. Lightweight = just a ref, for private bookmarks.
  • Tags are not pushed by default and don't move — retag only in emergencies (forces re-fetch for everyone) !
  • git describe gives a human version relative to the nearest tag — handy in build metadata.

Internals · Packfiles · Speed

  • .git/: objects/ (the store), refs/ (branches, tags), HEAD, config, index (staging), logs/ (reflog), hooks/.
  • New objects land loose (one zlib file each); git gc rolls them into packfiles — delta-compressed against similar objects + reachability-pruned. Deltas exist only here, not in the model.
  • Git is fast because most ops are local and hash-indexed: branch/commit/diff/log touch pointers and trees, not the network. History is a DAG walk, not a server round-trip.
  • porcelain = user commands (add, commit, log); plumbing = scriptable primitives (cat-file, hash-object, rev-parse, update-ref).

Submodules, Subtrees & Big Repos

  • Submodule = a pinned pointer (recorded SHA) to another repo. clone --recurse-submodules, or submodule update --init --recursive. Superproject tracks which commit, not the files → easy to forget to bump/commit the pointer !
  • Subtree = the other repo's files copied into yours (git subtree add/pull) — no extra clone step, but history merges in.
  • Scale big repos: shallow clone --depth 1 (CI), partial --filter=blob:none, sparse-checkout (subset of paths), Git LFS for large binaries.
  • ! Never commit large binaries raw — every clone then carries every version forever. Use LFS or keep them out.

Branching Strategies & PRs

  • Trunk-based (short-lived branches off main + feature flags + strong CI) = modern default; GitHub Flow (main + PRs) is the lightweight sibling; GitFlow (develop/release/hotfix) is heavy, for scheduled releases. Long-lived branches → merge hell !
  • PR merge modes: merge commit (full history + bubble) · squash (one tidy commit per PR — most popular) · rebase (linear, keeps individual commits).
  • Branch protection: required reviews + green CI, up-to-date branch, CODEOWNERS, no direct push to main, optional signed/linear-history rules.
  • Keep a PR current: rebase onto main (then --force-with-lease) for linear, or merge main in when others share the branch.

Config, Hooks & Ignore

git config --global user.name "Alice"
git config --global user.email "alice@…"
git config --global pull.rebase true
git config --global merge.conflictStyle zdiff3
git config --global rerere.enabled true
git config --global alias.lg "log --oneline --graph --all"
  • Precedence: system → global → local (repo .git/config wins). --show-origin tells you where a value came from.
  • Hooks (pre-commit, commit-msg, pre-push) are local + advisory → real enforcement lives in CI / branch protection. Share via pre-commit / Husky / Lefthook.
  • .gitignore only stops untracked files; an already-tracked file keeps being tracked → git rm --cached <path> to stop it !

★ Recovery Playbook

  • ☐ Committed to the wrong branch: git switch -c right, then on the wrong one git reset --hard HEAD~1 — or cherry-pick across.
  • ☐ Undo last commit, keep work: git reset --soft HEAD~1.
  • ☐ Undo a pushed commit: git revert <sha> (never reset+force on shared).
  • ☐ Lost commits (bad reset/rebase/amend): git reflog → git reset --hard HEAD@{n}.
  • ☐ Force-push clobbered main: recover the old SHA from a reflog / a colleague's clone → reset + push.
  • ☐ Bad merge: git revert -m 1 <merge-sha> (mind the re-merge gotcha: revert the revert or rebase to re-land).
  • ☐ Committed a secret: git filter-repo to purge from ALL history + ROTATE it !
  • ☐ Which commit broke it: git bisect run ./test.sh.
  • ☐ Deleted the wrong file, already committed: git restore --source=HEAD~1 -- path.

☐ Safe-Habits Checklist

  • ☐ Only rewrite local/unpushed history; on shared branches use revert.
  • ☐ --force-with-lease, never a bare --force.
  • ☐ fetch & review before you act; pull --rebase or --ff-only for clean history.
  • ☐ Small, atomic commits + imperative messages (better review / bisect / revert); tidy the branch before a PR.
  • ☐ Enable zdiff3 + rerere; keep a real .gitignore; set global identity + commit signing.
  • ☐ git clean -n before -f; reset --hard only when you're sure — check status first.
  • ☐ Never commit secrets or large binaries; protect main (no force-push, required CI + review).
  • ☐ When in doubt, it's in the reflog — don't panic, don't re-clone blindly.
