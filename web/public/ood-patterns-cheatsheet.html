Four Pillars of OOP

  • Encapsulation — hide state, expose behaviour; the object protects its own invariants. Not "private fields + getters/setters" (that's an anemic leak) ! — expose operations, not data.
  • Abstraction — model the essential, drop the rest. Encapsulation hides the how; abstraction chooses the what.
  • Inheritance — is-a reuse via subclassing. Powerful, over-used; prefer composition !
  • Polymorphism — one interface, many impls; resolved by dynamic dispatch on the runtime type.

Polymorphism & Dispatch

  • Override = same signature, subclass replaces base behaviour (runtime). Overload = same name, different params (compile time) ! — don't confuse them.
  • Identity (a == b, same object) vs equality (a.equals(b), same value). Override equals+hashCode together !
  • Duck typing — "if it quacks…"; conformance by shape, not declared type (Python/JS).

SOLID — violation → fix

Rule / smell it kills
SSingle Responsibility — one reason to change (one actor). God class → split by cohesion.
OOpen/Closed — extend by adding a class, not editing a growing switch.
LLiskov — subtype substitutable for base; no stronger preconditions / weaker postconditions.

! Square extends Rectangle breaks L: setWidth silently changes height, surprising code written to the base. is-a in English ≠ behavioural substitutability. Model them separately.

They interlock — one style: small classes, single responsibility, depending on interfaces, extended not edited. DIP is the principle; DI is just the mechanism.

Core Principles & GRASP

  • DRY — one authoritative source of knowledge, not "no similar-looking code" ! (accidental duplication ≠ real duplication).
  • KISS / YAGNI — simplest thing that works; don't build for imagined futures.
  • Composition over inheritance — has-a is swappable at runtime; is-a is fixed at compile time.
  • Program to an interface, not an implementation.
  • Encapsulate what varies — the meta-principle behind nearly every pattern.
  • Law of Demeter — talk to friends: a.getB().getC().go() is a train-wreck ! Tell-Don't-Ask instead.

GRASP quick hits

  • Information Expert — give a job to whoever holds the data.
  • Creator · Controller · Low Coupling · High Cohesion — the assignment heuristics.

Dependency Injection — 3 forms

  • Constructor (default) — deps mandatory, object always valid, easy to test.
  • Setter — optional/reconfigurable deps.
  • Interface/method — per-call collaborators.

! Prefer constructor injection; a container (Spring/Guice) is optional plumbing, not the principle.

Telescoping ctor → fluent Builder

// smell: Pizza(size, cheese, pepperoni, olives, ...)
Pizza p = new Pizza.Builder(LARGE)
    .cheese().pepperoni()      // optional, readable
    .build();                  // validate invariants here !
  • Builder yields immutable results and named args; a Director (optional) encodes a fixed recipe.
  • ! Don't reach for Builder with 2–3 params — a constructor or named args is simpler.

Singleton — the careful one

// Java: safest = enum
enum Config { INSTANCE;
  private final Map<String,String> v = load();
}
// or lazy holder (thread-safe, no locks):
class Cfg { static class H { static final Cfg I = new Cfg(); }
  static Cfg get(){ return H.I; } }
  • ! Singleton = global mutable state → hidden coupling, order-dependent init, hard to test (can't swap it). Widely treated as an anti-pattern.
  • Prefer a single instance wired via DI — one object, no global access point.
  • Naive lazy if(inst==null) is a data race under threads ! — use enum / holder / double-checked volatile.
  • Related: Object Pool reuses expensive instances (DB conns, threads). Key decisions: max size, block-vs-fail on exhaustion, validate-on-borrow, idle eviction. ! Pool vs Flyweight — pool reuses mutable instances one-at-a-time; Flyweight shares immutable intrinsic state concurrently.
  • Enum defends against reflection & serialization attacks that break a plain-class Singleton (both can forge a second instance) !

Decorator — canonical

Coffee c = new Milk(new Sugar(new Espresso()));
c.cost();  // each layer adds to inner.cost()

Stackable, order-independent responsibilities without a subclass explosion (MilkSugarEspresso…). Java I/O streams are the textbook case.

  • Object adapter (compose + delegate) > class adapter (multiple inheritance) — the former works in single-inheritance languages and adapts subclasses too.
  • Adapter = the ports-and-adapters (hexagonal) boundary: the domain defines a port interface; each external SDK/DB gets an adapter, keeping third-party types out of the core !
  • Deep decorator stacks cost debuggability (long wrap chains) and add per-call indirection — flatten if a fixed combo dominates.

The interview "big four": Strategy · State · Observer · Command. Know these cold.

Strategy vs State

Identical UML, different intent — resolve by who triggers the switch !

Strategy — canonical

interface Pay { void pay(int cents); }
class Card implements Pay { ... }
class Cash implements Pay { ... }
class Checkout {
  private final Pay s;              // compose, don't extend
  Checkout(Pay s){ this.s = s; }    // inject
  void charge(int c){ s.pay(c); }   // program to interface
}

New payment type → new class, zero edits to Checkout (OCP). First-class functions collapse Strategy to a lambda.

Observer · Command · Template · Chain

  • Observer — subject keeps a list of observers, notify() on change; decouples publisher from subscribers. ! Watch update storms & leaked listeners (unsubscribe!).
  • Command — encapsulate action + args as an object with execute()/undo(); enables queues, macros, redo.
  • Template Method — base defines the algorithm skeleton, subclasses fill hook() steps. Inheritance-based; Strategy is its composition cousin.
  • Chain of Responsibility — each handler either handles or passes on (middleware, event bubbling, approval flows). ! Ensure someone handles it (default tail).

Iterator · Mediator · Visitor · Memento

  • Iterator — sequential access without exposing internals; language built-ins (for..of, Iterable) already give it to you.
  • Mediator — objects talk through a hub instead of N² direct refs (chat room, form-field coordinator). Risk: the mediator becomes a God object !
  • Visitor — add new operations over a fixed class hierarchy without editing it; uses double dispatch. ! Terrible when the hierarchy (not the ops) is what changes — you edit every visitor.
  • Memento — snapshot & restore state without breaking encapsulation (undo, save games).

Iterator — internal vs external

Access elements sequentially without exposing representation. Collection stores; iterator traverses (SRP split). Buys: multiple simultaneous walks (each holds its own position), swap array→tree with clients unchanged, and lazy/infinite sequences (generators, Stream).

ExternalInternal
drivesclient (hasNext/next)collection (forEach)
early exiteasy (break)awkward
zip 2 collseasyhard
hides traversalnofully

Invalidation: mutate a collection mid-walk and the cached position desyncs. Java is fail-fast (modCount → ConcurrentModificationException); mutate via it.remove() instead !. Fail-safe/snapshot (CopyOnWriteArrayList) never throws but may miss latest state; C++ invalidation is UB.

Mediator vs Observer

Mediator turns N↔N mesh into a star: colleagues talk only to a hub that holds the coordination logic. Add an interaction rule = edit one place; colleagues become reusable (no peer refs). ! Risk: the hub swells into a God object — keep it scoped (one per dialog), not global.

MediatorObserver
topologystar (hub)1→N broadcast
directionbidirectionalusually one-way
knows participantsyesanonymous list
holds logicyes (routes)no (just notify)

Crisp: Observer broadcasts (one source, many blind reactors); Mediator coordinates (many peers, one hub with the rules). Intermediary holds interaction rules → Mediator; merely forwards → Observer/pub-sub.

Visitor & Double Dispatch

Add new operations over a stable hierarchy without editing every class. Each op lives in one visitor; each element gets accept(v). Replaces a scattered, repeated instanceof type-switch.

interface Shape { <R> R accept(Visitor<R> v); }
class Circle implements Shape {
  public <R> R accept(Visitor<R> v){ return v.visitCircle(this); }
}                       // dispatch 1: on Shape → dispatch 2: on Visitor
  • Double dispatch = pick a method by the runtime types of two objects (element × visitor). OO gives single dispatch; the two-step accept→visit bounce recovers the second axis ! — no instanceof.
  • Applied to a Composite tree (AST, file tree) it's the standard "walk + operate" combo.
  • Modern sealed types + exhaustive switch/when/match often obsolete classic Visitor with compile-time exhaustiveness.

Expression Problem

Types × operations form a grid; you can make adding rows or columns cheap, not both, without editing existing code.

+ new type+ new op
methods on classes (normal OO)easy (1 class)hard (edit all)
Visitorhard (edit all visitors)easy (1 visitor)
  • Decision rule: Visitor when types are stable but operations grow — compilers (fixed AST, ever-more passes: type-check, optimise, codegen).
  • ! Types churning? Visitor is a "touch every visitor" tax — put methods on the classes instead.
  • Naming this tradeoff honestly (not "Visitor is always good") is the senior signal.

Memento & Undo/Redo

Snapshot private state so it can be restored later — without breaking encapsulation. Three roles: Originator (creates/restores), Memento (opaque snapshot), Caretaker (holds it, can't read it).

class Editor {                    // Originator
  private String content;
  Memento save(){ return new Memento(content); }
  void restore(Memento m){ content = m.state; }
  static final class Memento {   // opaque to all but Editor
    private final String state;
    private Memento(String s){ state = s; }
  }
}
  • Java: memento as a static nested class w/ private fields (nested classes see each other's privates). C++: friend. Python/TS: by convention.
  • Command vs Memento undo: Command stores the inverse op (cheap, needs invertibility); Memento stores state (any op, costs memory). Non-invertible op (sort, auto-format) → Memento !
  • Memory: bound the stack, store deltas not full copies, copy-on-write share, spill cold history to disk.

Interpreter (rarely) & the last GoF

  • Interpreter — one class per grammar rule; a sentence is a tree (AST), evaluation is a recursive interpret(ctx). Essentially Composite over a grammar, often walked by a Visitor.
  • Fits: tiny stable DSLs — boolean rule engine, query filter, arithmetic. ! Avoid for anything non-trivial/perf-sensitive: reach for a real parser (ANTLR) and compile rather than tree-walk. A hand-rolled Interpreter beyond a micro-DSL is a red flag.

Undo/redo (multi-pattern LLD)

  • Command reifies each action (execute()/undo()); cleanly invertible ops (add/move) need no memento.
  • Memento for the non-invertible ones (flatten, filter).
  • Two stacks: execute → push undo + clear redo; undo → pop, run undo(), push redo.
  • Iterator decouples rendering from storage. Naming which pattern does which job is the senior answer.

Thread-Safety by Design

Concurrency safety is mostly an encapsulation problem — you can only guard state you control. Strategies, most-preferred first:

statelessno mutable state → nothing to race
immutablefixed at ctor, share freely, safe map key
confinethread-local / stack / instance — never shared
guardprivate state + one lock (Monitor Object)
  • Reach for immutability first: all fields final, no mutators (changes return a new instance), class final, no leaked internals. Most "thread-safety bugs" are "we shared a mutable object we shouldn't have".
  • Monitor Object — object owns its state and the lock; every public method synchronises on one lock (add wait/notify for blocking queues). Coarse → can bottleneck !
  • Value object (equal by value, immutable) vs entity (equal by id, mutable). Model as many value objects as possible; concentrate concurrency effort on the few mutable entities.

Safe Publication & Escaping Refs

Per-method synchronized is not enough: compound actions race. Below, both methods are atomic but the sequence isn't — expose an atomic op (putIfAbsent) instead.

if (!map.has(k)) map.put(k, v);  // check-then-act: NOT atomic !
  • Safe publication — a reader can see the reference before the field writes; publish via final field, volatile/Atomic, a lock, a static initialiser, or a concurrent collection. This is why broken DCL Singleton needs volatile !
  • Escaping reference — returning a live internal collection or leaking this from a ctor bypasses your locking. Fix: return copies/unmodifiable views, defensively copy inputs, never let this escape during construction.
  • Document the contract: @ThreadSafe/@NotThreadSafe/@Immutable, and @GuardedBy("lock") per field. A clearly not-thread-safe class beats a silently half-safe one.

LLD Interview — 8-step loop

Progressive refinement down a ladder; say step names aloud and checkpoint after 1 & 3.

1Clarify & scope — functional + non-functional; state assumptions
2Nouns → classes, verbs → methods, adjectives → state (CRC cards)
3Map relationships — assoc / aggregation / composition / is-a
4Interfaces first — signatures before internals (DIP)
5Apply patterns only where a force/axis exists
6Code the core flow end-to-end; skeletons for the rest
7Edge cases & extensions — the "now add X" follow-up
8Concurrency — where's shared mutable state, name the race

! Top failure = jumping to step 6. Steps 1–2 win interviews. They watch how you think, not a memorised canonical answer. Design for the follow-up they will ask — put a polymorphic seam on the axis of variation so "add a payment type" is a new class, not an if.

Bridge, Composite, Proxy, Flyweight — deeper

  • Bridge — split an abstraction from its impl so two axes vary independently. Shape × Renderer would be Circle×SVG, Circle×Canvas, Square×SVG… — an M×N class explosion. Bridge makes it M+N: Shape holds a Renderer reference. Pre-planned; Adapter retrofits after the fact !. Bridge vs Strategy: same composition, but Bridge varies structure/impl, Strategy varies an algorithm.
  • Composite — one Node interface over leaf & container so clients never branch on type. Transparency vs safety: put add/remove on the base (uniform but leaves must no-op/throw) or only on containers (type-safe but clients type-check) !.
  • Proxy flavours: virtual (lazy-load), remote (network stub), protection (permission guard). Same interface as the subject — differs from Decorator by intent (control access vs add behaviour).
  • Flyweight — share intrinsic (context-free) state; pass extrinsic (per-use) state as args. A million trees = one TreeType (mesh, texture) shared, position passed in. ! Pointless if little state is shared or objects are already few.

Refactoring moves (smell → move)

Refactoring = behaviour-preserving structural change. Not a rewrite (that changes behaviour), not a bug fix (smells often work fine). Two hats: refactor or add behaviour, never both in one step !

SmellMove
long methodextract method to name a concept (not to hit a line count)

primitive obsessionintroduce value object (Money, PhoneNumber)
data clumpintroduce parameter object

Engine: small, safe, reversible steps behind green tests (Beck's Tidy First). Extraction has a cost too — indirection — so extract to reveal intent, not reflexively.

Domain Modeling — rich vs anemic

  • Anemic model ! — data-only classes (getters/setters) with logic in "service" procedures. It's OO in name only; behaviour and the data it guards drift apart. Push behaviour onto the data (Information Expert).
  • Rich model — objects own the operations on their state and protect their invariants (account.withdraw(amt) validates, not an external AccountService).
  • Entity = identity, mutable lifecycle, equal by id. Value object = defined by attributes, immutable, equal by value (Money, DateRange, Color).
  • Model the domain as as many value objects as possible — immutable, shareable, thread-safe for free — and keep the small set of mutable entities where lifecycle really lives.
  • ! Money is never a double — integer minor units in a value object, or rounding corrupts every ledger.

Not every LLD is a pattern hunt

Some prompts are data-structure design, not GoF. Recognising which is senior judgment.

LRU cache — O(1) get/put

  • HashMap (key → node) + intrusive doubly-linked list (recency order). Get → move node to head; put over capacity → evict tail. Both O(1), no search.
  • The eviction policy (LRU / LFU / FIFO) can be a Strategy; the core is pointer manipulation.

Board games — rules vs state

  • Split rules (what's a legal move) from state (turn, board, status). Tic-tac-toe → chess share one Game/Board/Move skeleton; only legality differs.
  • ! Avoid one Board.isValidMove with a giant switch(pieceType) — push canMove() onto each Piece subclass (OCP). Game status via State.

Producer/consumer LLD shapes

Pub/sub, logging, and notifications all separate "something happened" from "who reacts" — the Observer family. Reusable move: model the event as an object, keep a registry of subscribers/handlers, iterate.

SystemShape
notification / pub-subObserver (+ broker/topic decouples subject from observer)
logging frameworkChain of Responsibility — level filters + appenders (sinks); reconfigurable at runtime
middleware / filter chainChain — each handler handles or forwards
Splitwise split typesStrategy (equal / exact / percentage) + Money ledger

! CoR is not an if/else list — each handler independently decides handle-or-pass, and the chain is assembled at runtime. Ensure a default tail handles the unhandled.

★ LLD Interview Checklist

Requirements & scope

  • ☐ Clarify functional + non-functional scope before any code; state assumptions aloud.
  • ☐ Extract nouns → entities, verbs → methods; list the core objects first.

Responsibilities & structure

  • ☐ Each responsibility owned by one class (SRP / Information Expert) — no God object.
  • ☐ Relationships chosen deliberately: composition vs aggregation vs inheritance; is-a only when substitutable (LSP) !
  • ☐ Prefer composition; inheritance only for genuine is-a with shared behaviour.

Interfaces & extensibility

  • ☐ Define interfaces before implementations; depend on abstractions (DIP), inject collaborators.
  • ☐ Identify the axis of change and put a seam there (OCP) — new variant = new class, no edits.
  • ☐ Interfaces small & role-focused (ISP); no client stubbing methods it never calls.

Patterns & restraint

  • ☐ Apply a pattern only where a force demands it (usually Strategy / State / Factory / Observer). Name the force !
  • ☐ No patternitis, no speculative generality; simplest design that absorbs the change you can see.

Finish

  • ☐ Walk one concrete flow end-to-end; then edge cases, thread-safety, extensibility.
  • ☐ Narrate trade-offs out loud — that reasoning is the signal.
