Pure Functions & Side Effects

A function is pure iff: (1) same input → same output (deterministic), and (2) no observable side effects — no mutating args/globals, no I/O, no clock/random, no throwing for control flow.

// pure: referentially transparent
const add = (a, b) => a + b;
// impure: reads clock, mutates, does I/O
let total = 0;
function charge(x){ total += x; log(now()); }

What purity buys

  • Referential transparency — replace a call with its result, meaning unchanged. Enables memoization, CSE, reordering.
  • Test with assertEquals — no mocks, no setup, no clock.
  • Safe to parallelize (no shared mutation → no data races).
  • Local reasoning: the signature is the whole contract core value

! "Returns a value" ≠ pure. getUser(id) hits a DB — impure. Hidden effects (logging, lazy cache fills, ambient config) are the sneaky ones.

You can't make everything pure — a program with zero effects does nothing. FP answer: functional core / imperative shell — pure decisions in the middle, effects at the thin edges (see Effects/IO card).

Immutability & Persistent Structures

Don't mutate — produce a new value. Aliases can't surprise you; "who changed this?" bugs vanish; snapshots are free.

LangImmutable binding / data
Kotlinval + data class .copy(); listOf
JS/TSconst, Object.freeze, spread {...o}, readonly
Javafinal, record, List.of
Pythontuple, frozenset, @dataclass(frozen=True)
Rustimmutable by default; mut is opt-in

! const/val freeze the binding, not the object. const a=[]; a.push(1) works. final ≠ deep-immutable. Freeze the data too.

Persistent = structural sharing

  • Naive copy-on-write is O(n). Persistent structures share unchanged subtrees → copy is O(log n), old + new both valid.
  • Backbone is the HAMT (hash array-mapped trie, ~32-way) for maps/sets; RRB-tree for vectors. Clojure, Scala, Immutable.js, Immer.
  • Update walks one root-to-leaf path (~log₃₂ n ≈ 6-7 hops for millions), copies only those nodes.

HOF: map / filter / reduce / fold

Higher-order function = takes and/or returns a function. The core three replace hand-rolled loops: map (1:1 transform), filter (keep), reduce/fold (collapse to one). Loop mechanics disappear; intent remains.

Same op, different names

      .map { it.total }

fold is universal — map and filter are both folds. Signature fold(init){acc,x->acc} threads an accumulator; give it the seed + combine.

! reduce (no seed) throws on empty; fold takes an initial value → total. Prefer fold. reduce's type is fixed to the element type.

Closures & the Loop-Var Trap

A closure = a function + the environment it captured at definition. It closes over variables by reference to the binding (most langs), not a snapshot of the value.

function counter(){ let n = 0;
  return () => ++n; }   // n lives on past return

The classic bug !

// JS var: all print 3 — one shared binding
for (var i=0;i<3;i++) setTimeout(()=>log(i));
// Fix: let → fresh binding per iteration → 0,1,2
for (let i=0;i<3;i++) setTimeout(()=>log(i));
LangLoop-capture & fix
JSlet per-iter binding (not var)
Javavar must be effectively final; copy inside loop
Pythonlate-binding ! — bind via default arg lambda i=i:
Gopre-1.22 shared; 1.22+ per-iter var
Rustmove closures take ownership; borrow-checked

Uses: callbacks, partial application, encapsulated private state, memo caches, event handlers.

Recursion & Tail-Call Optimization

FP loops via recursion. Naive recursion grows the call stack → StackOverflow on deep inputs !. Fix: tail recursion — the recursive call is the last action, so the frame can be reused (a jump, O(1) stack).

// NOT tail: work (`n *`) happens AFTER the call
fun fac(n)= if(n<=1) 1 else n*fac(n-1)
// tail: accumulator carries the result
tailrec fun fac(n, acc=1L): Long =
  if(n<=1) acc else fac(n-1, n*acc)

Trick: add an accumulator param to move the pending work before the call.

RuntimeTCO?
Scala @tailrec, Kotlin tailrecYes (compiler rewrites to loop; verified)
Haskelllazy — uses guarded recursion / accumulators
JVM (Java), Python, most JS enginesNo ! — will overflow

No TCO → rewrite as an explicit loop/fold, or use a trampoline. tailrec/@tailrec annotations fail to compile if the call isn't actually in tail position — use them as a guarantee.

Currying & Partial Application

Two distinct things people conflate:

  • Currying: turn f(a,b,c) into f(a)(b)(c) — a chain of 1-arg functions. Structural.
  • Partial application: fix some args now, get a function of the rest. An act, not a shape.
// partial application
const add = (a,b)=>a+b;
const inc = add.bind(null, 1);   // inc(x)=x+1
const inc2 = (b)=>add(1,b);       // arrow

// curried
const mul = a => b => a*b;
const double = mul(2);           // double(5)=10
LangPartial application
Pythonfunctools.partial(f, a)
JS/TSf.bind, arrow chains
Kotlinlambda { b -> f(a, b) }
Haskellauto — every fn is curried, apply fewer args
Rustclosures capturing the fixed arg

Why: pre-configure functions for pipelines/HOFs — map(multiplyBy(3)), a logger with the level baked in, dependency injection without a framework.

Composition & Pipe

Build big functions from small ones. compose(f,g)(x)=f(g(x)) — right-to-left (math order). pipe(f,g)(x)=g(f(x)) — left-to-right (reading order, data-flow).

const compose = (...fs)=>x=>fs.reduceRight((a,f)=>f(a),x);
const pipe    = (...fs)=>x=>fs.reduce((a,f)=>f(a),x);
pipe(trim, toLower, slugify)("  Hi There ");
LangPipe idiom
Kotlinlet chains / scope fns

Haskell. compose, & pipe
Rustmethod-chain iterators

Point-free (tacit)

Define functions without naming args: const clean = pipe(trim, toLower). ! Over-used it gets unreadable and murders stack traces. Point-free is a tool, not a virtue — name the arg when it's clearer.

Composition only lines up when types match end-to-end; Option/Either returns need Kleisli composition (compose via flatMap).

ADTs & Pattern Matching

Model data by composition: product types (AND — struct/record/tuple: has a name AND an age) and sum types (OR — a value is exactly one of N variants). Sum types are the ones most langs lack good tools for.

// Rust sum type + exhaustive match
enum Shape { Circle(f64), Rect(f64,f64) }
fn area(s: Shape) -> f64 { match s {
  Shape::Circle(r)  => PI*r*r,
  Shape::Rect(w,h)  => w*h,
}}  // adding a variant → compile error until handled
LangSum type / match
Rustenum + match
Kotlinsealed class/interface + when
Scalasealed trait + match
Java 21sealed + switch pattern
TSdiscriminated union (kind tag)
Haskelldata + case

The win is EXHAUSTIVENESS key — the compiler forces you to handle every case; add a variant and every non-total match becomes a compile error. That's a to-do list from the type checker.

! A default/else branch defeats exhaustiveness — it silently swallows new variants. Match each case explicitly.

Option / Either — Errors as Values

Absence and failure are data, not exceptions. Option/Maybe = value or nothing; Either/Result = success or a typed error. The signature tells the truth: parse(s): Result<Int, Err> can't lie about failing.

fun half(n:Int): Option<Int> =
  if(n%2==0) Some(n/2) else None
// chain: map transforms, flatMap sequences fallible steps
findUser(id)
  .flatMap { it.primaryAccount() }   // returns Option
  .map { it.balance }                // returns plain value
  .getOrElse { ZERO }

Railway-oriented

  • Happy path flows straight; the first failure short-circuits to the end. No nested if pyramid.
  • map when the fn returns a plain value; flatMap/and_then when it returns another wrapper (else you nest Option<Option> !).
  • Extract at the edge: getOrElse, orElse, fold(onErr,onOk), Rust ?.

vs exceptions: exceptions are invisible in the type, unwind the stack, and are for the truly exceptional. Use values for expected failures (parse, lookup, validate); reserve exceptions/panics for bugs & unrecoverable states.

Lazy Evaluation & Streams

Eager = compute now (default most langs). Lazy = defer until the value is demanded; compute at most once. Lets you express infinite data and only pay for what you consume.

// infinite + take — only 5 ever computed
generateSequence(1){ it+1 }        // Kotlin Sequence (lazy)
  .map { it*it }
  .take(5).toList()                // [1,4,9,16,25]
Eager (whole list)Lazy (element-at-a-time)
Kotlin List.mapKotlin Sequence/asSequence
Java eager collectionsJava Stream
Python listgenerator / yield, itertools
Rust VecIterator (lazy until collect)
Scala ListLazyList / view; Haskell all-lazy
  • Short-circuit: lazy pipelines fuse — find/any/take stop early, no intermediate collections.
  • ! Laziness + side effects = surprising ordering / effects that never fire because nothing pulled them. Keep lazy pipelines pure.
  • ! Haskell space-leak: unforced thunks pile up; force with strictness where needed.

Types & Inference

Polymorphism: parametric (generics — one impl, any type: List<T>) vs ad-hoc (per-type behaviour via overloading / type classes / traits).

InferenceReach
Hindley-Milner (Haskell, ML, OCaml)global — infers most signatures with no annotations
Local (Rust, Kotlin, Java var, TS, Scala)infers locals; annotate public API boundaries
// make illegal states unrepresentable
// BAD: bool soup lets contradictions compile
data class Conn(loading:Bool, data:D?, err:E?)
// GOOD: ADT — only valid states exist
sealed interface Conn { object Loading; data class Ok(d:D); data class Err(e:E) }
  • Make illegal states unrepresentable — encode invariants in types (NonEmptyList, Positive, sum types) so bad states won't compile core FP move
  • Variance: out T/+T covariant (producer, read-only), in T/-T contravariant (consumer), invariant otherwise. ! mutable containers must be invariant.

Type Classes & Ad-hoc Polymorphism

A type class defines behaviour a type can support, declared separately from the type. Rust trait, Scala given/using (implicits), Haskell class, Swift protocol.

// Rust: add Display to a type you don't own
trait Summary { fn summary(&self) -> String; }
impl Summary for Article {
  fn summary(&self) -> String { self.title.clone() }
}

Key difference from OOP interfaces

  • Retroactive extension the win — implement a type class for a type you don't own (e.g. Ord for a stdlib type), without editing it or subclassing. OOP interfaces must be declared at the class definition.
  • Resolved statically by the compiler (dictionary passing), often monomorphized → no vtable cost.
  • Enables the Functor/Monad hierarchy as a real, nameable interface (needs higher-kinded types — Haskell/Scala have them; Rust/Kotlin/Java don't).

This is one answer to the expression problem: type classes make adding new operations over existing types easy (see FP-vs-OOP card).

★ The Functor → Applicative → Monad Ladder

Three rungs, each a container/context with more power. You already use all three daily; these are just the names.

RungOpSuperpower
Functormaptransform value(s) inside, keep the shape
Applicativeap/map2combine independent wrapped values; accumulate errors
MonadflatMapchain dependent steps; short-circuit
functor:     F[A]            + (A=>B)      -> F[B]  // map
applicative: F[A], F[B]      + ((A,B)=>C)  -> F[C]  // map2
monad:       F[A]            + (A=>F[B])   -> F[B]  // flatMap
  • Functor law: map(f).map(g) == map(g∘f) — the permission slip to fuse two passes into one.
  • Applicative combines values that don't depend on each other → can run all + gather every validation error (Cats Validated, Arrow zipOrAccumulate). A monad's flatMap stops at the first failure.
  • Monad = applicative + flatMap: the next step can depend on the previous result.

Rule: reach for the weakest tool that works — independent → applicative (parallel, accumulate); dependent → monad (sequence, short-circuit). Functor ⊂ Applicative ⊂ Monad.

Monads — the everyday view

Minus the mysticism: a monad is a design pattern for sequencing computations in a context. A functor (map) + wrap (of/return/pure) + chain (flatMap/bind/>>=). flatMap = map then flatten — flattening M<M<B>> to M<B> is the whole point.

Everyday monads

  • Option (nullability) · Either/Result (typed failure) · List (nondeterminism, cross-product) · Promise/Future (async) · IO/Task (effects) · State/Reader.

The 3 laws

  • Left identity: of(a).flatMap(f) == f(a)
  • Right identity: m.flatMap(of) == m
  • Associativity: grouping of a chain doesn't matter, only order.

Laws are what make chains safely refactorable and let do-notation exist.

Do-notation = sugar over flatMap

Haskell doScala for/yield
Rust ?JS async/await
Kotlin Arrow either{}.bind()

! Promise.then IS flatMap — returning a Promise from the callback auto-flattens. (Also does map for plain returns → overloaded.) return/of means wrap, not imperative return.

Managing Effects & IO

Purity forbids effects but programs need them. Answer: don't ban effects — organise where they live.

Functional core / imperative shell

  • Onion: effects on the skin, decisions in the middle. Shell reads the world (SELECT, fetch, clock) → hands plain data to a pure core → gets a decision/description back → shell performs it.
  • Payoff: ~90% of logic is a pure function testable with assertEquals — no DB, no mocks, no clock.
  • Push effects to the edges; keep the core deterministic and reusable.

IO monad = effect as a value

// building the description is PURE; nothing runs yet
val program: IO<Unit> = readLine.flatMap { name ->
  putLine("hi $name") }
program.unsafeRunSync()   // run ONCE, at the edge ("end of the world")
  • IO[A]/Task/() => Promise represents an effect, stays inert until run. Composing is pure; only running does I/O, in one place.
  • Inject effects (clock, rng, repo) as params → swap fakes in tests, no mocking framework.
  • Algebraic effects / effect systems (ZIO, Effect-TS, Koka) generalize this.

Immutable State & Data Transformation

State without mutation: model change as a pure function of the old state. New state in, old state untouched.

// reducer: (state, action) -> state
fun reduce(s: State, a: Action): State = when(a) {
  is Add    -> s.copy(items = s.items + a.item)
  is Remove -> s.copy(items = s.items - a.item)
}
  • Reducer (state, action) → state — Redux, Elm, TCA, actor state. A pure fold over the action stream.
  • Event sourcing = the state IS a fold over events: state = events.fold(init, apply). Store events, replay to rebuild; audit + time-travel for free.
  • Deep updates: spread/copy for shallow; lenses/optics (Arrow Optics, Immer produce) for nested immutable update without hand-spreading every level.
// Immer: write "mutation", get immutable copy
next = produce(state, d => { d.user.addr.city = "NYC" });

! Shallow copy shares nested refs — spread one level and mutating a nested object still aliases. Copy the path you change.

FP Concurrency & Parallelism

FP's concurrency superpower is a consequence of immutability: no shared mutable state → no data races → values can be shared across threads lock-free.

  • No locks needed for reads — immutable data is safe to share by reference; nothing can change under you.
  • Parallel map: pure element transforms have no dependencies → run on N cores (parallelStream, Rayon par_iter, pmap).
  • Parallel reduce needs an associative combine (and identity = monoid) so the runtime can split & merge in any grouping. ! non-associative reduce → wrong answer under parallelism.

Models

Actorsisolated state, message passing (Erlang, Akka)
STMtransactional memory, retry on conflict (Clojure, Haskell)
CSPchannels + processes (Go, core.async)

Purity + immutability make all three easier: less shared state to coordinate.

FP vs OOP — Decision Table

Not enemies — different default axes of extension. The tension is the expression problem: you want to add both new types and new operations without editing old code. You get one cheaply.

Easy to addCostly
OOP (classes)new types (new subclass implements the interface)new operation (touch every class) !
FP (ADT + match)new operations (new function over the ADT)new variant (touch every match) !

Choose by which axis churns: many operations over a fixed shape → FP; many types under a fixed protocol → OOP. Type classes / pattern-visitor split the difference.

★ "Think Functionally" Checklist

Structure

  • ☐ Effects pushed to the edges; the decision core is pure & testable without mocks.
  • ☐ Data modelled with ADTs (sum + product); illegal states don't compile.
  • ☐ Absence/failure as Option/Either, not null or thrown exceptions (reserve those for bugs).

Transformation

  • ☐ map/filter/fold over hand-rolled loops where it reads clearer.
  • ☐ Immutable by default; new values not mutation; deep updates via copy/lens.
  • ☐ flatMap when the step returns a wrapper, map when it returns a plain value.
  • ☐ Weakest tool that works: applicative for independent, monad for dependent.

Matching

  • ☐ Pattern matches are exhaustive — no catch-all default hiding new variants !
  • ☐ Recursion is tail-recursive on runtimes without TCO (or use a fold/loop).

Don't over-rotate

  • ☐ Not forcing purity where the language fights it (idiomatic Go/Java beats fake monads).
  • ☐ Point-free only where it stays readable; name the arg otherwise.

Pitfalls & When NOT to Use FP

When NOT to reach for FP

  • Hot inner loops / tight memory — persistent structures & allocation can lose to in-place mutation. Measure.
  • Idiomatic imperative code — hand-rolling monads in Go where if err != nil is the convention adds friction.
  • Team unfamiliarity — an Arrow either{} or hand-rolled Validated can cost more reviewer time than it saves. Match the codebase.
  • Deeply stateful/effectful I/O — keep the effect at the edge; don't ceremony-wrap trivial scripts.

FP is a set of defaults (purity, immutability, values), not a religion. Use the parts that pay.
