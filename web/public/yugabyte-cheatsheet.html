Distributed SQL: YSQL (real Postgres query layer) + YCQL (Cassandra API) over one storage engine, DocDB. YB-Master = control plane, NOT in the data path. YB-TServer = data + query execution. Spanner-inspired, shared-nothing, strongly consistent.

The one-line answer

"A shard of the data is a tablet; each tablet is a Raft group (leader + followers) over its own RocksDB; the query layer on any node routes the request to the right tablet leader. Add nodes → tablets rebalance → linear scale."

Distributed SQL / NewSQL & CAP

  • NewSQL = SQL + ACID + horizontal scale + HA — RDBMS guarantees at NoSQL scale. Arc: RDBMS → NoSQL (dropped SQL/ACID for scale) → NewSQL (got both back).
  • CAP: CP — strongly consistent, never split-brain; a minority partition rejects writes rather than diverge.
  • PACELC: on Partition → PC (consistency); Else → EC (favours consistency, pays latency). Not a low-latency-first store.
  • Lineage = Google Spanner paper (Raft/Paxos + a time authority).

  • "Master is the brain, not the gatekeeper" — clients cache tablet locations and talk straight to TServers; reads/writes keep flowing even if all masters are down (until you need metadata changes) !
  • 3 masters = tolerate 1 master loss (Raft majority). More TServers than masters because they scale data, not metadata.
  • Request flow: client → any TServer's query layer → looks up tablet → routes to tablet leader (local or remote) → Raft commit → reply.
  • Heartbeats: TServers heartbeat masters (~1s); missed beats → under-replication detected → re-replication + leader elections.
  • Colocate a master + tserver per node for small clusters; separate on large ones. Web UIs: master :7000, tserver :9000.

DocDB — the Storage Engine

  • DocDB = a distributed document store over a heavily-modified RocksDB (LSM-tree). One RocksDB instance per tablet (actually two — regular + intents).
  • Why RocksDB, not PG heap? LSM = append-only, write-optimised, compresses well, natural fit for MVCC versions and sharding.
  • Write path (LSM): WAL (Raft log) → memtable → flush to immutable SSTables → background compaction merges/drops tombstones. Writes are sequential & fast; read amplification is the tradeoff !

Row → key/value encoding

// each column is its own KV entry, MVCC-versioned:
key   = <tablet>, <hash|range of PK>, colId, hybridTime
value = column value  (or tombstone for delete)
  • Multiple versions per column, ordered by hybrid time; read merges them and picks versions ≤ your read point (MVCC → readers never block writers).
  • Deletes/TTL write tombstones; space reclaimed at compaction. Reads use bloom filters + block cache to skip SSTables.
  • Same engine serves relational YSQL and semi-relational YCQL — both are just documents of KV entries.

Sharding & Tablets

  • Rows map to tablets (shards) by the PK. Each tablet = unit of distribution, replication (Raft), and parallelism.
  • Auto-split when a tablet exceeds a size threshold → two tablets, spreadable to other nodes, no re-sharding.
  • Presplit for bulk/large tables to skip the cold-start single-tablet bottleneck: 
    -- hash: N tablets up front
... SPLIT INTO 24 TABLETS;
-- range: explicit boundaries
... SPLIT AT VALUES ((1000),(2000),(3000));
  • Tablet count tradeoff: too few = no parallelism; too many = Raft/heartbeat overhead per tablet !
  • A tablet is the unit of three things at once: distribution (which node), replication (its Raft group), and parallelism (a scan fans one RPC per tablet). More tablets → more scale-out headroom but more per-group cost.
  • Auto-split is online and non-blocking — reads/writes keep flowing; the new halves can then rebalance to emptier nodes via the master load balancer.

PK / Sharding Data Modeling

  • The PK IS the sharding key — it decides distribution and performance, not just uniqueness. #1 thing interviews test.
  • ((col) HASH) = spread for point lookups. col ASC/DESC = ordered for range scans.
-- distribute users by id
CREATE TABLE users (
  id uuid, email text,
  PRIMARY KEY ((id) HASH));

-- orders: hash the tenant, range within it
CREATE TABLE orders (
  user_id uuid, order_ts timestamptz, amt numeric,
  PRIMARY KEY ((user_id) HASH, order_ts DESC));
  • The #1 pitfall — monotonic key on a range shard: SERIAL/timestamp/sequence sends every new write to the last tablet → one hot node no matter the cluster size !
  • Fixes: hash-shard the key, random UUIDv4, or a bucket/salt column ((bucket, ts), bucket = hash % N).
  • Composite ((tenant_id) HASH, created_at DESC): spread tenants, keep each tenant's rows ordered & co-located for range reads.
  • Global SERIAL/sequences contend at scale → prefer UUIDs or cached sequences (CACHE 1000) !

Replication & Raft

flowchart LR L["tablet LEADER"] -->|append WAL| F1["follower 1"] L -->|append WAL| F2["follower 2"] F1 -. ack .-> L L -->|commit on majority| S["state machine (DocDB)"]
  • Every tablet is its own Raft group. RF=3 → leader + 2 followers. A write commits once a majority (quorum) persists it → strong consistency + durability.
  • Write path: client → leader → append to Raft log (WAL) → replicate → quorum ack → apply to DocDB → reply. One WAN-free round-trip for single-shard.
  • Leader lease: only the lease-holding leader serves linearizable reads without a quorum round-trip; prevents a stale ex-leader answering during a partition !
  • Leader dies → election in seconds; a follower with the latest log wins. No SPOF, no manual failover.
  • Follower reads = read a local follower at bounded staleness (offload leaders, cut latency) — not linearizable.
  • Raft log (ordered WAL) vs the DocDB state machine (applied result) are distinct; a cluster runs one Raft group per tablet → thousands.

Placement & Replication Factor

  • RF = copies of each tablet. Must be odd (3, 5) so a majority always exists → no split-brain.
  • Fault math: RF=N survives ⌊N/2⌋ losses. RF3 → survive 1; RF5 → survive 2 (quorum = ⌊N/2⌋+1).
RFQuorumTolerates
321 node/zone

  • Placement policy spreads the 3 replicas across fault domains (node → zone → region). Fault-tolerance level = the domain you spread across: 3 zones → survive a zone; 3 regions → survive a region !
  • RF ≠ node count. RF is copies per tablet; you can have RF3 on 12 nodes (tablets scattered, each still 3 copies).
  • Preferred zones / leader placement: pin tablet leaders to a region so writes stay local.
  • Read replicas = extra async, read-only, non-voting copies (own RF); don't count toward write quorum — pure read offload/DR.
  • Add/remove node → YB-Master load balancer rebalances tablets & leaders; blacklist to drain before decommission.

Consistency & Isolation

Two axes — don't conflate. Linearizability = single-key real-time order (Raft quorum + leader lease). Isolation = how concurrent txns see each other (MVCC over hybrid time).

YSQL level= PostgresProperty
Snapshot Isolation (default)REPEATABLE READtxn-wide snapshot; allows write skew
SerializableSERIALIZABLEno anomalies; more retries
Read CommittedREAD COMMITTEDper-statement snapshot; fewer client retries
  • ! YSQL default is Snapshot Isolation, NOT Read Committed like stock Postgres. No dirty reads at any level.
  • Write skew (SI hole): two txns read overlapping rows, each writes a disjoint part, together break an invariant (classic "≥1 doctor on call"). Fix = Serializable or explicit locking.
  • MVCC: readers never block writers & vice versa. Real conflicts → one txn aborts (no lock-wait-forever) → 40001 serialization failure → app must retry !
SET default_transaction_isolation = 'serializable';
-- or per-txn: BEGIN ISOLATION LEVEL SERIALIZABLE;

Rule: Serializable for correctness-critical invariants; SI/RC for throughput & PG-app compatibility.

Distributed Transactions (2PC)

Multi-tablet ACID via a 2-phase-commit-style protocol coordinated through a transaction status record.

1. WRITE INTENTS: writes go to each tablet's INTENTS store
   as provisional records, tagged {txn_id, hybridTime}.
   Tentative — visible only to this txn.
2. COMMIT: coordinator flips status record to COMMITTED
   via ONE Raft write to the txn status tablet.  <- ATOMIC
3. APPLY (async): each tablet resolves its intents into
   normal committed records at the commit time.
  • Atomicity across independent Raft groups = the single status flip decides all intents at once. Visibility happens at step 2, not step 4 !
  • The status tablet is itself Raft-replicated → no fragile standalone coordinator like classic 2PC.
  • Reader hits an intent → looks up the owner's status: COMMITTED & commit-time ≤ read point → visible; PENDING → ignore/conflict; ABORTED → dead.
  • Conflict detection: two intents collide on a key → lower priority txn aborts (40001). Under Serializable, read intents participate too (catches write skew).
  • Single-shard = fast path: one tablet → one Raft write, no intents, no status tablet. Keep txns single-shard & short !
  • Savepoints are supported — partial rollback inside a txn (SAVEPOINT / ROLLBACK TO), same Postgres semantics, useful to retry a sub-step without aborting the whole txn.
  • Timestamps: reads use a chosen read hybrid-time; the commit gets a single commit hybrid-time stamped on all intents at apply — that's what orders it against concurrent txns.

Hybrid Logical Clocks (HLC)

  • Orders events cluster-wide with HLC = (physical, logical): physical = NTP wall-clock µs; logical = monotonic Lamport counter to break ties & preserve causality.
  • Timestamps track real time (good for snapshots) and give strict happens-before order (good for correctness) — no atomic clocks.
Spanner TrueTimeYugabyte HLC
hardwareGPS + atomic clockscommodity NTP/chrony
uncertaintymeasured (ε)assumed bound

  • max_clock_skew_usec (default 500ms) = the assumed skew bound & safety margin. Keep NTP tight — if real skew exceeds it, guarantees can break !
  • Read restart: a read landing inside the skew ambiguity window retries at a higher timestamp — a correctness mechanism, not a bug. Reduce by tightening clocks, not suppressing.
  • Bigger skew bound = safer vs violations but wider ambiguity window → more read restarts + latency. It's a trade, not a free dial.

YSQL — Postgres Compatibility

  • PG Reuses the real PostgreSQL query layer (parser/planner/executor) bolted onto DocDB — not a reimplementation.
  • Works mostly unchanged: joins, secondary indexes, FKs, triggers, PL/pgSQL, views, extensions, PG drivers/ORMs. Shell: ysqlsh.
CREATE TABLE users (
  id uuid DEFAULT gen_random_uuid(),
  email text UNIQUE,
  created_at timestamptz DEFAULT now(),
  PRIMARY KEY ((id) HASH));

CREATE INDEX ON orders ((user_id) HASH)
  INCLUDE (status, amt);   -- covering

Differences vs stock PG !

  • Tracks a specific PG version (not always latest).
  • SERIAL/sequence contention at scale (global counter) → prefer UUID / CACHE.
  • Default isolation = Snapshot, not Read Committed.
  • Distributed-execution nuances: cross-tablet joins shuffle; connections are heavy PG backends → pool them.

YCQL vs YSQL — pick the API

  • PG YSQL: full relational Postgres API — joins, rich SQL, FKs. Default choice for new apps.
  • CQL YCQL: Cassandra-CQL API over the same DocDB engine.

Indexes

  • Secondary indexes are distributed, global & strongly consistent (their own tablets, Raft-replicated) — unlike Cassandra's local 2i.
  • Every write to the base table also writes the index → index write cost; don't over-index write-heavy tables !
  • Covering index (INCLUDE (cols)) → index-only scan: query served entirely from the index, no second RPC to the base table.
  • Indexes take their own sharding: CREATE INDEX ... ((col) HASH) — same hotspot rules apply.
  • Unique & partial indexes supported (YSQL). Match indexes to access patterns, not "every column."
CREATE UNIQUE INDEX ON users ((email) HASH);
CREATE INDEX idx ON orders ((user_id) HASH, order_ts DESC)
  INCLUDE (amt);            -- index-only for amt lookups
CREATE INDEX ON t (status) WHERE status='active'; -- partial

Query Execution & Pushdowns

  • Query layer (on one TServer) fans RPCs out to tablet leaders, gathers, finalises. Fewer RPCs / less shuffle = faster.
  • Pushdowns — sent down to DocDB so less data crosses the network:
    • filter (WHERE) predicate pushdown
    • projection (only needed columns)
    • aggregate & LIMIT pushdown
  • Cross-tablet joins shuffle rows across nodes → slow. Fix: colocate, denormalize, or index the join column !
  • Batch/prepare to amortise round-trips; single-shard scans beat scatter-gather.
  • Coordinator = any node. The TServer the client lands on runs the plan and fans out; no dedicated router tier, so route clients cluster-wide (LB) — no single choke point.
  • Single-tablet query = one RPC to one leader (fast). Scatter-gather = an RPC per tablet, gathered — cost grows with tablet count and shrinks with a selective pushdown/index.
EXPLAIN (ANALYZE, DIST, VERBOSE) SELECT ...;
-- read the DIST section: # RPCs, rows scanned,
-- rows removed by pushdown. High RPC count = scatter.

Performance Tuning & Scaling

Diagnose in order: balance → round-trips → connections.

  • Scale-out is linear only for balanced load. Add TServers → tablets/leaders rebalance → ~2× nodes ≈ 2× throughput. A hotspot pins throughput to one node regardless of cluster size !
  • Hotspot = #1 killer: monotonic PK on a range shard funnels all writes to the last tablet. Fix: hash-shard / random UUID / salt+bucket / key reversal.
  • Round-trips: write = Raft quorum hop; distributed txn = 2PC coordination; cross-region = WAN hop. Cut with batching, prepared statements, single-shard txns, index-only scans.
  • Connections: YSQL = a PG backend process per connection → thousands exhaust memory/CPU. Use the YSQL Connection Manager (server-side pooling) or PgBouncer !
  • Follower reads to offload leaders; weakest correct isolation for throughput.
# add capacity: start a tserver at the masters, then
yb-admin -master_addresses $M get_load_move_completion

High Availability & Failure

  • No SPOF. Node/zone/region loss → automatic Raft leader election (seconds) for affected tablets; unaffected tablets untouched.
  • Self-heal: master detects under-replication (missed heartbeats) → re-replicates lost tablet peers onto surviving nodes to restore RF.
  • TServer fails: its leaders re-elect elsewhere; brief per-tablet blip, cluster stays up.
  • Master fails: if it was the master leader, the other 2 elect a new one; data path unaffected (masters aren't in it).
  • Rolling upgrades = zero downtime — one node at a time, leaders move off first, then the node restarts and rejoins its Raft groups.
  • Blacklist to drain a node before decommission — the load balancer moves its tablets/leaders off first, so removal is clean with no under-replication scare.
  • Backups: distributed snapshots + PITR (point-in-time restore). xCluster for cross-region DR.

Read Path & MVCC Merge

  • A read carries a read point (a hybrid time). DocDB returns each column's latest version ≤ read point — so readers never block writers and see a consistent snapshot.
  • Per tablet, the read merges the memtable (recent writes) with the on-disk SSTables, newest-version-wins, skipping tombstoned/superseded values.
  • Bloom filters skip SSTables that can't hold the key; the block cache serves hot blocks from RAM; compression shrinks IO. That's how an LSM keeps reads sane despite append-only writes !
  • Intents pass: if a provisional (uncommitted) record for the key exists, the reader looks up the owning txn's status record — COMMITTED & commit-time ≤ read point → visible; PENDING → conflict/ignore; ABORTED → skip.
  • Read amplification is the LSM tradeoff — a key's current value can be spread across memtable + several SSTables until compaction merges them. Compaction reclaims tombstone/old-version space.
  • Follower/leader: a linearizable read hits the leader under its lease; a follower read serves a local replica at bounded staleness (older read point).

Follower & Replica Reads

Three ways to read, trading freshness for latency:

ModeServesFreshness
leader read (default)tablet leaderlinearizable
follower readlocal follower (voting)bounded staleness
read replicaasync non-voting copybounded staleness
  • Follower reads offload leaders and cut latency by reading a nearby replica — you pick a staleness window; typically small, never unbounded !
  • Read replicas = extra async, non-voting copies in another region with their own RF; don't count toward write quorum → pure read-offload / local-read / light DR.
  • Enable per-session for read-mostly, latency-sensitive queries where slight staleness is fine (dashboards, catalogs). Correctness-critical reads stay on the leader.
SET yb_read_from_followers = true;
SET default_transaction_read_only = true;   -- required
-- bounded by yb_follower_read_staleness_ms (e.g. 30000)

Colocation & Tablespaces

  • Colocated tables = many small tables share one tablet instead of each getting its own Raft group. Two wins: local joins/lookups (same tablet, no network hop) and far less per-tablet Raft/heartbeat overhead !
  • Use for: reference/lookup tables, config, small dimension tables — the "lots of little tables" schema. Don't colocate large high-throughput tables — they need their own tablets to spread load, or you recreate a hotspot.
CREATE DATABASE app WITH COLOCATION = true;
-- small tables colocated by default; opt the big ones out:
CREATE TABLE big_events (...) WITH (COLOCATION = false);
  • Tablespaces are repurposed from Postgres's "which disk" into placement policy — which regions/zones a table's or partition's tablets live in, and at what RF.
  • Pattern: colocate the small stuff for locality, shard the big stuff for scale; use tablespaces to pin where data physically lives (foundation of geo-partitioning).
CREATE TABLESPACE eu_ts WITH (replica_placement=
 '{"num_replicas":3,"placement_blocks":[
   {"cloud":"aws","region":"eu-west","zone":"a",
    "min_num_replicas":3}]}');

CQL YCQL Data Model

Same two-part key as Cassandra: PRIMARY KEY ((partition), clustering...).

  • Partition key (double-parens) → hashes to a tablet; all rows with that key co-locate on one tablet.
  • Clustering columns → sort rows within the partition on disk (clustering order).
CREATE TABLE iot.readings (
  device_id uuid, bucket date,      -- bound partition size
  reading_at timestamp, metric text, value double,
  PRIMARY KEY ((device_id, bucket), reading_at, metric))
  WITH CLUSTERING ORDER BY (reading_at DESC);
  • "Latest N for a device today" = single-partition, pre-sorted scan — the classic time-series pattern.
  • Bucket the partition key (e.g. a day) so no partition grows unbounded — same anti-hotspot discipline as YSQL hash sharding !
  • Give up vs YSQL: no arbitrary JOINs, no FKs/triggers/extensions, thinner SQL — query-first denormalized modeling. Gain: simple high-throughput key access.
  • Shell ycqlsh <host> 9042 (familiar Cassandra client port + drivers).

  • PITR (point-in-time restore) — roll a database/table back to any moment in a retention window; recovers from bad deploys / accidental DROP/DELETE, not just node loss.

Design Playbook — worked DDL

Multi-tenant SaaS

-- hash the tenant → spread; cluster by id → per-tenant scans
PRIMARY KEY ((tenant_id) HASH, order_id)

Hashing tenant_id distributes tenants evenly and naturally discourages cross-tenant scans (tenant isolation). Colocate the small per-tenant config tables.

Global app, EU/US residency

CREATE TABLE users (id uuid, region text, ...,
  PRIMARY KEY ((id) HASH, region)) PARTITION BY LIST (region);
CREATE TABLE users_eu PARTITION OF users
  FOR VALUES IN ('eu') TABLESPACE eu_ts;   -- +us_ts

Row-level geo-partitioning: each region's rows (all 3 replicas + leaders) live in-region → GDPR residency + local write latency, no ocean hop.

Time-series / events

PRIMARY KEY ((device_id) HASH, ts DESC)  -- fan writes, ordered scans
-- must range globally? bucket it:
PRIMARY KEY ((bucket) HASH, ts)          -- bucket = hash(id)%16

Never make a bare SERIAL/timestamp the leading un-hashed range key — that's the monotonic-key hotspot ! Pre-split big tables: ... SPLIT INTO 24 TABLETS;

Transaction Retry Pattern

Conflicts abort with 40001 — the app owns the retry. Wrap every txn in bounded retries with backoff; never let a 40001 surface as a user error.

for attempt in range(MAX):        # e.g. 5
  try:
    with conn.transaction():      # BEGIN..COMMIT
      row = tx("SELECT bal FROM acct WHERE id=%s
                FOR UPDATE", src)          # lock intent
      tx("UPDATE acct SET bal=bal-%s WHERE id=%s", amt, src)
      tx("UPDATE acct SET bal=bal+%s WHERE id=%s", amt, dst)
    break                          # committed
  except SerializationFailure:    # SQLSTATE 40001
    sleep(backoff * 2**attempt + jitter)   # then retry
  • Keep txns single-shard & short — fewer tablets touched = fewer conflicts + no 2PC coordination cost.
  • Read restart errors are a different beast: clock-skew ambiguity, retried internally where possible; if surfaced, tighten NTP, don't just retry harder !
  • Use the weakest correct isolation — Read Committed retries per-statement (fewer client retries) vs Serializable's more aborts. Reserve Serializable for real write-skew invariants.

☐ Schema / Design Review Checklist

  • ☐ Do you actually need distributed SQL (vs Postgres/Aurora)? Justify the write-scale / multi-region / HA driver.
  • ☐ PK chosen to distribute load & avoid hotspots — no bare monotonic SERIAL/timestamp on a range shard.
  • ☐ Right sharding: HASH for spread, RANGE only where ordered scans are truly needed.
  • ☐ Composite PK groups related rows ((tenant) HASH, ts DESC) and orders within.
  • ☐ RF odd (3/5) & replica placement gives the required node/zone/region fault tolerance.
  • ☐ Transactions kept single-shard & short; app retries 40001 serialization failures.
  • ☐ Isolation is the weakest that's correct (Serializable only where write skew matters).
  • ☐ Indexes match access patterns; covering/INCLUDE where hot; not over-indexed (write cost).
  • ☐ Multi-region topology fits residency/latency/RPO; leaders in the preferred region.
  • ☐ Connection pooling on (YSQL Connection Mgr / PgBouncer); NTP/chrony tight; TLS + RBAC on.
