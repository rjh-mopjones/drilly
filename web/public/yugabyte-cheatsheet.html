Distributed SQL: YSQL (Postgres) + YCQL (Cassandra) APIs over DocDB. YB-Master = control plane (not in the data path); YB-TServer = data + query layer. Spanner-inspired, shared-nothing, strongly consistent.

Distributed SQL / NewSQL

  • NewSQL = SQL + ACID + horizontal scale + HA (RDBMS guarantees at NoSQL scale).
  • CP in CAP (strongly consistent, never split-brain). Spanner lineage.
  • Scale by adding nodes; no single point of failure; multi-region capable.
  • Peers: CockroachDB (closest), Spanner, TiDB, Citus/Vitess (middleware), Aurora (shared-storage, not shared-nothing).

  • Rows → tablets (shards) by the PK. Tablets auto-split as they grow; presplit with SPLIT INTO.
  • Colocation: pack small reference tables into one tablet (local joins, less overhead).

Replication & Raft

flowchart LR L["tablet leader"] -->|replicate log| F1["follower"] L -->|replicate log| F2["follower"] L -. commit on majority .- F1
  • Each tablet = a Raft group (RF=3: leader + 2 followers). A write commits once a majority/quorum acks → strong consistency + durability.
  • RF=N survives ⌊N/2⌋ failures (RF3→1, RF5→2). Leader dies → automatic election (seconds), no SPOF.
  • Spread replicas across nodes → zones → regions for zone/region fault tolerance.

Consistency & Transactions

  • Isolation: Snapshot Isolation (YSQL default) · Serializable (no write-skew, more retries) · Read Committed.
  • Single-shard ops = fast (one Raft write, linearizable). Multi-shard distributed txns = 2PC-style: provisional records/write intents + a transaction status tablet flips COMMITTED atomically.
  • Conflicts → serialization failures (40001) → app must retry ! Keep txns single-shard & short.
  • MVCC readers don't block writers.

Time: HLC (not TrueTime)

  • Orders events with Hybrid Logical Clocks = physical time (NTP) + a logical counter — no atomic clocks (unlike Spanner's TrueTime + commit-wait).
  • Assumes bounded skew: max_clock_skew_usec — keep NTP/chrony tight !
  • Clock skew → occasional read restarts; excessive skew can break guarantees.

YSQL — Postgres Compat

-- reuses the REAL Postgres query layer over DocDB
CREATE TABLE users (
  id   uuid,
  email text,
  PRIMARY KEY ((id) HASH)          -- distribute by id
);
CREATE TABLE orders (
  user_id uuid, order_ts timestamptz, amt numeric,
  PRIMARY KEY ((user_id) HASH, order_ts DESC)  -- hash + range
);
  • Joins, secondary indexes, FKs, triggers, PL/pgSQL, extensions, PG drivers/ORMs — mostly just work (ysqlsh).
  • Differences: tracks a PG version, sequence/SERIAL contention at scale, distributed-execution nuances !

PK / Sharding Data Modeling

  • The PK IS the sharding key — drives distribution & performance, not just uniqueness.
  • ((col) HASH) = even spread (point lookups). col ASC/DESC = ordered (range scans).
  • Monotonic PK (SERIAL/timestamp) on range shard = write hotspot → hash-shard, use UUIDv4, or add a bucket/salt !
  • Composite: ((tenant_id) HASH, created_at DESC) — distribute tenants, order within one. Colocate small tables.
  • Global sequences contend → prefer UUIDs / cached sequences.

YCQL vs YSQL

  • YSQL = full relational Postgres API (joins, rich SQL) — recommended for new apps.
  • YCQL = Cassandra-CQL API over the same engine, but strongly consistent, global indexes, distributed txns (unlike Cassandra — no tunable consistency / repair / gc_grace zombies) !
  • Use YCQL for Cassandra-style key/wide-row/time-series or migrating off Cassandra. Separate keyspaces (no shared tables).

Indexes & Query Execution

  • Secondary indexes are distributed, global & strongly consistent (not Cassandra's local 2i) — but each write updates the index too (write cost) !
  • Covering indexes (INCLUDE (cols)) → index-only scans (avoid a second RPC).
  • Pushdowns: filter/projection/aggregate/LIMIT pushed to DocDB → less data over the network.
  • Cross-tablet joins shuffle data across nodes → slow; colocate/denormalize/index !
  • Tune with EXPLAIN (ANALYZE, DIST) — see RPCs, rows, pushdowns.

HA & Ops

  • No SPOF: node/zone/region loss → automatic Raft leader election (seconds) + self-heal re-replication. Rolling upgrades = zero downtime.
  • Scale out by adding TServers (auto-rebalance). Pool YSQL connections (heavy per-conn like Postgres) !

☐ Schema / Design Review Checklist

  • ☐ Do you actually need distributed SQL (vs Postgres/Aurora)?
  • ☐ PK chosen to distribute load & avoid hotspots — no bare monotonic SERIAL/timestamp on a range shard.
  • ☐ Right sharding (HASH for spread, range only where ordered scans are needed).
  • ☐ Composite PK groups related rows (tenant/user) + orders within.
  • ☐ RF & replica placement give the needed node/zone/region fault tolerance.
  • ☐ Transactions kept single-shard & short; app retries 40001 serialization errors.
  • ☐ Indexes match access patterns (covering/index-only where hot); not over-indexed.
  • ☐ Multi-region topology fits the residency/latency/RPO need; leaders in the preferred region.
  • ☐ Connection pooling; NTP tight; TLS/RBAC on.

★ Troubleshooting Playbook

One node hot / writes bottlenecked

  • ☐ Monotonic PK on range shard → hash-shard, UUIDv4, or bucket/salt.

Cross-region write latency 100ms+

  • ☐ Sync quorum spans regions → preferred-region leaders / geo-partition, or accept for zero-RPO.

Slow txn / lots of retries

  • ☐ Multi-tablet txn or conflicts → colocate, shorten, single-shard, handle 40001.

Slow join

  • ☐ Cross-tablet shuffle → colocation/denormalize/index/index-only scan; check EXPLAIN DIST.

Read-restart errors

  • ☐ Clock skew → tighten NTP / max_clock_skew.

Remote-region read latency

  • ☐ Leader far → follower reads / read replica / geo-partition.
